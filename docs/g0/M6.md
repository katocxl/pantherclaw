### G0 — M6 Gateway & non-bypassable boundary — 2026-10-09

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M6 pull requests and, at the end of the milestone, in the exit status below. It builds on `main` at a4649e7: M3 complete, M4 part 2 through slice 214 (slices 215 and 216 are open as #103 and #104), and M5 part 1. M5 part 2 (approvals, transaction-bound step-up, the Agent Waitlist) is being briefed in parallel; the M6 work that needs it is stacked on it (decision 1).

**Purpose:** turn the walking-skeleton gateway into the real enforcement point. A gateway proves which organisation it serves with a certificate from PantherClaw's own certificate authority, never with a token. It learns of containment changes within a second and stops dispatching when it cannot be sure it is up to date. It serves reviewed tools to MCP clients and reviewed routes to HTTP clients, both defined by signed tool packages, and sends the target exactly the request that was authorized, with a credential the agent never sees. An organisation can stop everything at once with a kill switch, and needs two people to start again. In product terms this is the Checkpoint component, the custody half of Stash, and the kill switch of Reflex ([PRODUCT.md](../PRODUCT.md) §4). The refund scenario table S01–S13 is the exit.

**Scope (planned):**
- **Gateway enrollment and mTLS** (`internal/gateways`): gateway records, single-use `pcg_` enrollment tokens, an internal certificate authority, 24-hour Ed25519 client certificates bound to one gateway and one org, renewal before expiry, and revocation that takes effect on the next call. The server gets a second listener for gateways (TLS 1.3, client certificate required). The M1.5 development gateway token is removed.
- **Containment stream:** `GatewayService.WatchContainment` sends a full snapshot, then changes and a heartbeat every 500 ms. A gateway loads the snapshot before serving and refuses to dispatch when its last heartbeat is more than 2 seconds old (HR-010).
- **Kill switch** (decision 2): an emergency-stop page. One person with step-up engages it; restoring needs a proposal and a confirmation by a second person with a different security key, each with step-up. Engaging and restoring each increment the containment epoch (HR-002, HR-113). `pclaw killswitch status`.
- **Connections and routes** (`internal/connections`): a connection is one target (an HTTP API or a remote MCP server) served by one gateway through one tool package. Each of its routes runs in `monitor` or `enforce` mode (PN-013). Connections can be quarantined and restored. Enforcement-weakening changes need a person (HR-183).
- **Credential custody** (`internal/credentials`): broker keys (X-Wing) per gateway, registered by the gateway itself; `pclaw seal` encrypts a target credential locally to the broker key of the connection's gateway; the server stores only sealed bytes; the gateway opens a credential in memory for one dispatch (HR-060, HR-061, HR-182).
- **Package format** (additive): per-definition `dispatch` templates (HTTP method, path and body, or an upstream MCP tool call), reviewed MCP tool descriptions and input schemas, and the expected digest of each upstream MCP tool. The mock-payments package gains them.
- **Gateway** (`internal/gateway/...`, ARCHITECTURE §9):
  - `control`: the mTLS client, enrollment, renewal, configuration sync and the containment stream;
  - `dispatch`: the one path every channel uses (Authorize → permit → BeginDispatch → re-serialized request → RecordExecution), monitor mode, the circuit breaker;
  - `egress`: per-connection clients with the host pinned, URL construction from templates (HR-073), response caps and secret-echo redaction (HR-076);
  - `broker`: the broker key file and just-in-time opening;
  - `httpproxy`: `/{connection}/…` routes matched from the package (PN-003.5), replacing the hard-coded refund route;
  - `mcp`: the MCP server face for 2026-07-28 (stateless) and 2025-11-25 (sessions), reviewed tool lists, header and body consistency, HOLD as tasks or pending results, and the upstream client for remote MCP servers with elicitation and sampling blocked and drift detection;
  - `hook`: the decision endpoint for cooperative clients (the Claude Code hook).
- **Action tokens** (PN-002.6): for connections marked target-enforced, the Authority mints a `PAP-Action` token at `BeginDispatch` over the exact outbound body; the payments simulator verifies it as a reference target.
- **`pclaw`**: `gateway create|list|get|revoke|enroll-token`, `connection create|list|get|update|set-mode|quarantine|restore|retire`, `seal`, `credential list|revoke`, `killswitch status`, `mcp proxy` (stdio shim, HR-092) and `hook claude-code`.
- **Claude Code plugin** (`integrations/claude-code`, Apache-2.0): a PreToolUse hook for the Bash and PowerShell tools that asks the gateway, normalizes Windows paths, and fails closed (decision 4).
- **Simulators:** the payments simulator gains a credential check, `GET /v1/refunds/{id}`, the action-token verifier and redirect faults; a small MCP simulator serves the same refunds over MCP for the upstream tests.
- **End to end:** the refund scenarios S01–S13 through the real gateway over mTLS, plus MCP, hook and kill-switch scenarios.

**Out of scope:** the connector runtime for third-party MCP servers that run as local processes (HR-084, HR-085: M9, on the Docker sandbox, decision 3); coverage states and snapshots (M9: M6 records the facts coverage needs, such as access mode and channel, but computes no coverage); effect verification and reconciliation of `UNKNOWN` outcomes (M7); approval requests, the approval page and wait handles (M5 part 2); gateways serving several orgs, and PantherClaw-hosted multi-tenant gateways (design decision 6); revoking credentials at the target's provider; pausing automations (none exist before M11; the kill switch records "nothing to pause"); policy gates that allow upstream elicitation or sampling (design decision 14); `sdk/go` target verifier middleware and the Agent SDK `canUseTool` integration (M8; the simulator's verifier is the reference until then); disclosure obligations on destinations (HR-079's M10 part).

**Security constraints and design decisions:**
1. **Gateway identity (HR-180).**
   - A person holding the human-only `gateway.manage` creates a gateway record and asks for an enrollment token: 256-bit random, single use, valid 15 minutes, stored as SHA-256, bound to that gateway. The response shows the CA certificate's SHA-256 next to it.
   - `pantherclaw-gateway enroll` generates an Ed25519 key on the gateway host and sends the token with a certificate request signed by that key (proof of possession). It accepts the returned CA certificate only if its SHA-256 equals the pin it was given. A man in the middle at enrollment therefore cannot substitute its own CA, and a stolen token used first makes the real enrollment fail visibly.
   - The certificate lives 24 hours. The gateway renews it over mTLS with a new key after 16 hours; the old certificate becomes `SUPERSEDED` and is accepted for 10 more minutes, so calls in flight finish. A gateway that missed its renewal re-enrolls with a new token.
   - Replicas of one gateway enroll separately (one token each) and share its record, its broker key and its configuration.
   - `RevokeGateway` revokes the record and every certificate. Revocation needs no CRL: the server checks each certificate's row on every call (design decision 3).
2. **The gateway listener (HR-181, HR-020).**
   - The server opens `gateway_api.addr` with TLS 1.3 only, X25519MLKEM768 preferred, a client certificate required and verified against the internal CA. Its own certificate comes from the same CA for `gateway_api.hostnames`, valid 7 days and reissued daily in memory.
   - `AuthorityService` and `GatewayService` (except `Enroll`) are served only there. The public API refuses them with `PermissionDenied`, so a bearer credential of any kind can never act as a gateway.
   - The authenticator reads the URI SAN, loads the certificate row (cached at most 1 second), and requires the gateway to be `ACTIVE` and the certificate to be unexpired by the database clock and `ACTIVE` (or superseded by a renewal less than 10 minutes ago). The org comes only from that row. An action whose org differs is `DENY` (`ORG_MISMATCH`, already in M1.5), and a permit, transaction or connection of another gateway is refused.
   - The gateway's client certificate is used only by its control client. Egress transports never carry it (HR-074).
3. **Revocation on every call.** The certificate check is one indexed read per call, cached for at most a second. CRLs and OCSP would be slower to take effect and add a fetch path; with 24-hour certificates and a per-call check, neither is needed.
4. **Containment stream (HR-010).**
   - `WatchContainment` sends a snapshot first: the epoch, the kill switch, the configuration version, and the state of every connection the gateway serves. After that it sends a change as soon as the server sees one, and a heartbeat every 500 ms.
   - The server learns of changes through `LISTEN`/`NOTIFY` (payload: the org id only, HR-056) and also polls each watched org's containment row every 250 ms, so a missed notification costs at most a quarter of a second. It sends a heartbeat only after a poll succeeded within the last second. A server that cannot read the database therefore goes quiet, and its gateways fail closed.
   - The gateway serves nothing until it has a snapshot. It refuses every dispatch (`enforcement_failed: containment_stale`) when its last heartbeat is more than 2 seconds old by its monotonic clock, and reconnects with backoff, reloading the snapshot each time.
   - Locally the gateway refuses any action while the kill switch is on, any action on a quarantined connection, and any permit whose epoch is older than the stream's. `BeginDispatch` stays the authoritative check (HR-001).
   - Streams are capped at 4 per certificate and live at most 15 minutes before the gateway reconnects; heartbeat writes have their own deadline.
5. **Kill switch (HR-113, HR-002; decision 2).**
   - Engaging: a person holding `containment.killswitch`, on the emergency-stop page, with a step-up on that browser session less than 5 minutes old (M5 part 1) and a reason of at most 500 characters (stored and shown as untrusted text). One transaction sets the kill switch, increments the epoch, records who, when and why, writes `security.kill_switch_engaged` to the ledger, notifies org admins (M5 notifications) and sends `NOTIFY`.
   - Effects: every permit issued before fails `BeginDispatch`; `Authorize` denies at step 3; gateways refuse within 1 second (S13). Monitor-mode routes stop too (HR-184). Nothing else is undone: transactions in flight keep their recorded outcome, and grants, runs and credentials are untouched, so restoring brings back exactly what was there.
   - Restoring: a person holding `containment.killswitch` proposes a restore with step-up. A different person holding it confirms within 30 minutes with step-up, using a different WebAuthn credential (HR-035's rule for two-person decisions). The confirmation clears the kill switch and increments the epoch in one transaction. Either person can cancel a pending proposal. Every step is audited and notified.
   - `pclaw killswitch status` shows the state and pending proposals, and prints the page link. There is no CLI or API path that engages or restores.
   - The engage record lists, per connection, what else the kill switch did: "credential revocation at the provider: not supported" in M6, and "automations paused: none exist". The fields are ready for M11 and for connectors that can revoke.
6. **One org per gateway, customer-hosted.** In M6 every gateway is customer-hosted and serves one org; its certificate names that org. Hosted multi-tenant gateways need a different trust model for credentials and connectors (HR-084) and are not built. Private targets are reachable only through a customer-hosted gateway whose operator lists the range in `egress.allowed_prefixes` (HR-077); tenant input never widens that list.
7. **Connections and modes (HR-183, HR-184, PN-013).**
   - A connection names its gateway, its package (the org's pinned version of it), its base URL (`https`, or `http` only for a private address in the gateway operator's list), the hosts a credential may be sent to (default: the base URL's host), its destination class (`public` or `internal`; HR-079, recorded in ActionIR destinations), its access mode (`pantherclaw_held`, `agent_held`, `target_enforced` or `none`, F416), and where the credential goes (a header name and an optional scheme such as `Bearer`).
   - Registration refuses PantherClaw's own hosts (the server's public URL and gateway listener) and cloud metadata addresses, in any spelling (HR-077); the gateway's dial-time checks still apply to whatever the name resolves to.
   - Each package route of the connection has a mode, `monitor` by default for a new connection (PN-013). Monitor mode: the gateway still needs a verified, admitted workload; the Authority runs the whole pipeline and records the result as a hypothetical decision, reserves nothing, and issues a monitor permit unless identity (step 2) or containment (step 3) fails; the permit still goes through `BeginDispatch`. Receipts say `monitor: true`; nothing about a monitor-mode action is ever reported as prevented, and M9 will label it `OBSERVE_ONLY`.
   - Weakening changes need a person holding `connection.manage`, are audited with the old and new values and notified to org admins: switching a route from `enforce` to `monitor`, changing the base URL, allowed hosts, gateway, package or access mode, restoring a quarantined connection, and replacing a credential. Strengthening changes (to `enforce`, quarantine, retire, revoking a credential) take effect at once and increment the epoch in the same transaction.
8. **Credential custody (HR-060, HR-061, HR-182).**
   - The gateway operator runs `pantherclaw-gateway broker-key generate`. It writes the X-Wing private key encrypted with a key-encryption key file (AES-256-GCM, M1 AEAD with the key's fingerprint as AAD). The gateway registers the public key at start, over its mTLS identity, as a new version. A broker key can be registered only this way. Its fingerprint appears in `GetGateway`, `pclaw gateway get` and `pclaw seal`.
   - `pclaw seal --connection C --from-file F` asks `GetSealingKey` for the active broker key of C's gateway and the next credential version, prints the fingerprint, seals locally with `info` binding org, connection, version, allowed hosts, broker key and placement, and uploads the sealed bytes with `PutCredential`. The plaintext never leaves the machine running `pclaw`.
   - The server checks the blob's format, broker key and version, stores it, and supersedes the previous version. No user-facing RPC returns sealed bytes; only `GetConfiguration` sends them to the gateway that owns the broker key.
   - The gateway rebuilds `info` from its own view (org from its certificate, the connection and version from its configuration), opens the credential only inside a dispatch to an allowed host, places it in the outbound request, and drops the plaintext when the request ends (R-09 still applies). A credential that does not open, or a request to a host it is not bound to, fails the dispatch as `enforcement_failed` before any byte is sent.
   - Credentials, sealed or open, never appear in logs, job arguments, receipts or errors (HR-056, HR-061). Responses are scanned for the credential in plain, base64 and percent-encoded form, and every match is replaced (HR-076).
9. **Package format additions (HR-124).**
   - `dispatch.http`: method, path template with `{target.id}` and `{params.x}` placeholders, a JSON body template that maps body fields to canonical ActionIR fields (money splits into value and currency), and the name of the target's idempotency header. The gateway builds the outbound request only from the ActionIR the permit binds (HR-075).
   - `dispatch.mcp`: the upstream tool name and an arguments template for remote MCP connections.
   - On each MCP mapping: `description` and `input_schema` (a JSON Schema subset: objects, strings with patterns, enums, and no `$ref`), which are what MCP clients receive (HR-081); and for upstream tools `upstream_digest`, the SHA-256 of the canonical upstream tool definition the package was reviewed against.
   - A property of `input_schema` may carry `x-mcp-header` (MCP 2026-07-28): the name of the `Mcp-Param-{Name}` header clients mirror the argument into. It is allowed only on a string, integer or boolean property reached from the root through `properties` (never inside `items`), as a header name (a letter, then letters, digits and hyphens, at most 64), unique in the schema ignoring case, and at most 32 per tool.
   - The fields are additive to format 1, decoded strictly, and part of each definition's digest. The mock-payments package gains them, and its golden tests and pinned digest change deliberately.
10. **One dispatch path (HR-001, HR-008, HR-073, HR-075).** Every channel goes through `gateway/dispatch`:
    - The gateway maps the request with `mapping.Mapper` (the reviewed package), adds the connection, and calls `Authorize`.
    - On `ALLOW` it verifies the permit and, when the decision constrained parameters, applies the obligations and checks that the result hashes to the effective action hash.
    - It builds the outbound request from the template. Substituted values are percent-encoded; `..`, `%2f`, `@`, `#`, `?`, CR and LF are refused in substitutions. The final URL is parsed again and must have the connection's scheme, host and port and match the route's path pattern.
    - It calls `BeginDispatch` with that request's method, URL and body hash, then sends it with `Idempotency-Key: pc-<transaction id>` where the template names an idempotency header, through the connection's egress client.
    - It records the outcome. 2xx is `ACCEPTED`. A refused dial, an unopenable credential or a URL check failure is `FAILED`, and nothing was sent. 4xx is `FAILED`. Anything else, including a timeout after sending, is `UNKNOWN`.
11. **Egress responses (HR-076).** At most 1 MiB per response by default (per connection up to 8 MiB). The gateway asks for `identity` encoding and decompresses gzip it did not ask for only up to 20 times the compressed size. Responses over the cap are cut and marked truncated. Only `Content-Type` and the target's request id headers are passed back.
12. **Circuit breaker (HR-078).** Per connection and gateway, over 60 seconds: at least 5 `UNKNOWN` outcomes making up at least half of all outcomes opens the circuit. The gateway stops dispatching to that connection (`enforcement_failed: circuit_open`) and reports it. The server quarantines the connection (epoch +1, audit, notification). Only a person can restore it (HR-183).
13. **MCP face (HR-080, HR-081, HR-083, HR-185, PN-015).** No MCP SDK dependency: JSON-RPC handling is ours, on `encoding/json/v2` with HR-100 limits.
    - **2026-07-28 (stateless):**
      - Per-request `_meta` carries the protocol version and client capabilities. `MCP-Protocol-Version` must equal the `_meta` version, `Mcp-Method` must equal `method`, and `Mcp-Name` (after `=?base64?…?=` decoding) must equal the tool name or task id. A mismatch, or a missing required header, gets HTTP 400 with `-32020` (HR-080).
      - On `tools/call`, the `Mcp-Param-{Name}` headers must be exactly those the tool's reviewed schema declares (`x-mcp-header`) for the arguments the body carries and that are not null, each once and equal to its argument after decoding (integers compared as numbers, within ±(2^53−1)). A missing, repeated, different or undeclared one, a header for an absent argument, or a value with characters outside printable ASCII is the same 400 with `-32020`, before the Authority is asked (HR-080, T-019).
      - Batches (any JSON array) are refused. `GET` and `DELETE` get 405.
      - `server/discover` answers with the gateway's capabilities; `tools/list` gets `cacheScope: private`.
    - **2025-11-25 (sessions):**
      - `initialize` creates a session: a 256-bit random id, bound to org, connection, instance and key thumbprint, idle 30 minutes, at most 8 hours and never beyond the run, and at most 16 per instance.
      - Every later POST must carry the session id and a proof from the same key, and is verified again (HR-083). `DELETE` ends the session. `GET` gets 405, because the gateway has nothing to push.
      - JSON-RPC ids are remapped per session on the upstream side.
    - **Both versions:**
      - Tools are exactly the package's MCP mappings for that connection, with the reviewed descriptions and schemas; upstream text never reaches the client (HR-081).
      - Responses are `Cache-Control: private, no-store`.
      - `tools/call` maps through the package and goes down the one dispatch path. Every MCP request carries PAP/1 credentials; off-the-shelf clients connect through `pclaw mcp proxy` (HR-092).
14. **Upstream MCP servers (HR-082, HR-081, HR-086).**
    - A `kind: mcp` connection points at a remote MCP server over Streamable HTTP. The gateway is its client. It declares no elicitation, sampling or roots capability, answers any such request on a 2025-11-25 stream with a decline or a method-not-found error, and turns a 2026-07-28 `input_required` result into a tool error the agent sees. The upstream call is then recorded `FAILED`, because the server did not complete it.
    - Allowing elicitation through a policy gate is a follow-up; until then HR-082's "blocked by default" is "blocked".
    - The gateway compares the upstream `tools/list` with each mapping's `upstream_digest` when its configuration loads and every 10 minutes. A difference is reported (`ReportDrift`), and the server quarantines the org's pin of that package version (epoch +1), which stops every connection using it (HR-081).
    - A 2026-07-28 `tools/call` carries an `Mcp-Param-{Name}` header for each argument that the upstream tool's pinned definition marks `x-mcp-header`, encoded as the specification says. The declarations come only from the definition the last check found matching `upstream_digest`, and the values from the arguments built from the permitted action, so the agent's headers never reach the server and the body `BeginDispatch` binds also fixes the headers. When no check of the connection's revision has run yet, the call checks first, with the credential only; a server that cannot be listed fails the call before it is sent. A pinned definition whose declarations break the specification's constraints is never called (`enforcement_failed` / `upstream_tool_invalid`, logged as `security.upstream_tool_invalid`). A server that answers `HeaderMismatch` makes the next call check again, which finds a changed definition as drift; drift that a call's check finds is logged and reported at once, as the loop's is. 2025-11-25 servers get no request metadata headers.
    - Routes through remote MCP servers are opaque and labelled `PARTIAL` (HR-086).
15. **Holds in MCP (HR-185; PAP-1 §8).**
    - A `REQUIRE_APPROVAL` or `REQUIRE_STEP_UP` on `tools/call` becomes a task when the client supports one: the 2026-07-28 tasks extension when the request declares it, or a 2025-11-25 task-augmented call. The task id is random and bound to org, connection, run, instance and the action. `tasks/get` (and in 2025-11-25 `tasks/result`) from that binding re-submits the same action with the polling request's fresh credentials. A poll is the workload's resubmission, so the Authority runs the whole pipeline again and nothing else changes on its side. When the action is allowed, the gateway dispatches and completes the task with the tool's result. A poll from any other binding gets "task not found".
    - Without tasks, the call returns `isError: true` with a held message and `_meta` `io.pantherclaw/hold` (transaction id, retry after). An identical call (same tool and canonical arguments) by the same run and instance while the hold is open reuses the held action id, so approvals bind to it. Any changed argument is a new action (F132; S05).
    - Holds and tasks live in gateway memory for at most the approval's lifetime. A gateway restart forgets them, and the agent's next identical call starts a new action.
16. **Cooperative channel: the Claude Code hook (HR-186, HR-187; decision 4).**
    - The plugin's hook configuration matches `Bash|PowerShell` and runs `pclaw hook claude-code` with a 10-second timeout. That command reads the hook input, normalizes the working directory and the shell (`bash` or `powershell`), signs a PAP/1 request with the developer's desktop workload key (L1, HR-092), and posts it to `/hook/{connection}` with the configured run.
    - The gateway maps it through a small reviewed package, `pc.shell` (operation `shell.command.run`: material `shell`, `command` and `cwd`; bidi and control characters refused), and calls `Authorize`. An `ALLOW` goes through `BeginDispatch`, so containment and the kill switch apply, then `RecordExecution` with outcome `delegated`: the developer's machine runs the command, and the receipt says so (access mode `agent_held`, `PARTIAL`, F431).
    - The hook answers `allow` only for `ALLOW` and `ALLOW_WITH_OBLIGATIONS` without unsupported obligations. Every other decision is `deny` with the decisive reason and the transaction id. A hold says where to approve and to retry; it never asks the local user, because the local user is not an eligible approver of their own agent's action (HR-036).
    - Claude Code lets a hook that times out or crashes run the tool. So `pclaw hook claude-code` enforces its own 8-second deadline and turns every error into a `deny` answer with exit code 2 (fail closed).
    - Dogfooding on this repository is opt-in per developer and stays out of the repository's shared configuration, so parallel sessions keep working without a local stack.
    - **Windows paths (HR-187):** `pclaw` resolves the working directory to its long, final form where the file system can (short 8.3 names, junctions). The gateway mapping then normalizes lexically: drive letter upper-case, separators to `\`, `.` and `..` collapsed. It refuses `\\?\` and `\\.\` device paths, alternate data streams (`:` after the drive), and trailing dots or spaces in segments. UNC paths keep their server and share. Normalization never changes the command text itself, which policies see as sent.
17. **Action tokens (HR-188, PN-002.6).** For a `target_enforced` connection, `BeginDispatch` returns a `PAP-Action` JWS. It is signed with the new `action_tokens` key, its audience is the connection id, it expires in at most 60 seconds, and it carries a single-use `jti`, the transaction id, the action hash, the hash of the exact outbound body, the operation and the target. The gateway sends it in the `PAP-Action` header. The payments simulator, started with `--require-action-tokens`, verifies it against the JWKS with its own replay store, and refuses requests without a valid token. Only such routes may later count as `ENFORCED` for cooperative modes (HR-024, M9).
18. **Typed failures (F642).** Every refusal the gateway sends has an `error_class`, one of:
    - `policy_denied` (`DENY`);
    - `cannot_authorize`;
    - `held` (`REQUIRE_*`, with the transaction id);
    - `authentication_failed` (a `PAP-Error`, HTTP 401);
    - `enforcement_failed` (the gateway could not enforce: containment stale, circuit open, permit invalid, credential or URL check failed; nothing was sent);
    - `tool_failed` (the target refused);
    - `uncertain` (`UNKNOWN`: do not retry; reconciliation follows).

    HTTP clients get these as JSON with a status code, MCP clients as tool errors.
19. **Configuration sync.** `GetConfiguration` returns, for the calling gateway only:
    - its connections and route modes;
    - the canonical definitions (with mappings and dispatch templates) of the packages those connections pin;
    - the sealed credentials for those connections;
    - a version.

    The gateway loads it before serving, refetches when the stream reports a new version and every 60 seconds, and keeps the previous configuration if a fetch fails (containment still comes from the stream). It does not re-verify package signatures; the server verified them at import, and the Authority checks the definition digest on every decision (R-01).
20. **Removing the development gateway token.**
    - `dev_gateway`, `DevGatewayAuthenticator` and the gateway's `authority.token_file` go away.
    - `dev seed --gateway-out FILE` creates a gateway record and writes an enrollment file (token, CA pin, URLs).
    - `pantherclaw-gateway serve --enroll-file FILE` enrolls on first start, or when its identity is missing or expired, and keeps the identity in `control.identity_dir`.
    - The development package key (M4 decision 3) is trusted only when the server's API and gateway listeners are both on loopback, replacing the old development-gateway condition.
21. **Authorization and tenancy.** Each use case checks its permission at org scope (gateways, connections, kill switch). Ids from another org return NotFound (T-037). Gateway calls take their org only from the certificate row. Workload calls are unchanged (PAP/1). Every new table gets the cross-tenant tests.
22. **Logging and evidence.** These events are audited (ledger):
    - gateway create, enroll, renew and revoke;
    - broker key registration;
    - connection create and every change (weakening ones flagged);
    - route mode changes;
    - credential put and revoke (metadata only);
    - quarantine and restore;
    - drift;
    - circuit opening;
    - kill-switch engage, proposal, confirmation and cancellation.

    Execution receipts gain the access mode, the channel, the connection and `monitor`. Tokens, certificates' private keys, broker keys, credentials, MCP session ids and hook command text are never logged; logs carry ids, thumbprints and fingerprints.
23. **Failure semantics.** No containment snapshot or a stale heartbeat: the gateway refuses everything. Authority unreachable: `CANNOT_AUTHORIZE`, nothing sent (S09). Any doubt after sending: `UNKNOWN`, the reservation is held, and there is no automatic retry (S07, S08). The hook unreachable or failing: `deny`. Configuration unavailable at start: the gateway does not serve.

**Dependencies to add:** none. X.509 and TLS come from the standard library (Ed25519 certificates work in TLS 1.3), HPKE from Go's `crypto/hpke` (already used by `crypto.Seal`), and MCP JSON-RPC is implemented on `encoding/json/v2`. The Claude Code plugin is configuration plus `pclaw`; it has no code of its own.

6. **How a gateway checks approvals (HR-038, T-030)** (asked 2026-10-10, for slice 23).

   **Answer: "pinned file, fail closed".**
   - **What the permit carries.** The permit of every approved action carries the approval binding's canonical input and the WebAuthn assertion of each counted approver: credential id, authenticator data, client data JSON and signature, as `pc.approval_responses` keeps them. For a batch approval the challenge is the batch hash (PAP-1 §8), so the permit also carries the batch's sorted bindings, from which the gateway recomputes it.
   - **What the gateway pins.** The gateway verifies against a local, customer-pinned file, `approvals.approver_keys_file`: a JSON list of approver credentials (user id, credential id, public key). `pclaw approver-keys export --out FILE` writes it through `GatewayAdminService.ListApproverKeys` (`gateway.read`) and prints fingerprints for review.
   - **The checks:**
     - SHA-256 of the binding input is the binding;
     - the input's action hash and effective hash are the requested action's and the permit's;
     - the WebAuthn challenge is the binding, or a batch hash containing it;
     - the client data type is `webauthn.get`;
     - the RP id hash matches the pinned RP id;
     - the UV flag is set;
     - the signature verifies with a pinned key;
     - there are enough distinct approvers and credentials for the recorded requirement.
   - **Failing closed.** A gateway with no file, or no matching pinned key, refuses an approved action before `BeginDispatch` with `enforcement_failed` / `approval_unverified`. Actions without an approval are unaffected.
   - **Development.** `dev seed --gateway-out` writes the file next to the enrollment file, and the development gateway configuration pins it.

   *Blocks:* slice 23.
7. **When a consumed approval is restored (HR-011)** (asked 2026-10-10, for slice 23).

   **Answer: "server-side proof only".**
   - A consumed approval goes back from `CONSUMED` to `APPROVED` (its consume time and permit cleared) only while its consume-by time is ahead, and only when the server can prove nothing was sent: the permit never reached `DISPATCHING`. Either it expired `ISSUED` and the sweeper released it, or `BeginDispatch` refused it.
   - No outcome after `BeginDispatch` ever restores it. `FAILED` needs a new approval, and `UNKNOWN` goes to reconciliation.
   - Slice 23 also reopens the transaction, so the agent's resubmission of the same run and action can use the restored approval (PAP-1 §7.1). It adds migration `00075`, so that a transaction keeps one current permit and its released one stays as evidence.

   *Blocks:* slice 23.
