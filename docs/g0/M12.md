### G0 — M12 Adversarial range — 2026-10-14

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M12 pull requests and, at the end of the milestone, in an exit status section. It builds on `main` at e28a69e7 (M1–M9 complete; the highest migration is 00095). The founder answered four open decisions (F1–F4) on 2026-10-14 before the brief was written, the recommended option each time; they are recorded at the end as answered. Every other choice is a design decision for the founder's confirmation on this pull request.

**Purpose:** PantherClaw's promise is that the controls hold, and M12 produces the evidence. A scenario engine runs at least 30 attacks against the tenant's real policies, grants and packages, and only against simulators. The coding-agent attacks come first: a merge through the GitHub MCP server without a reviewer, the same merge by raw `curl`, a found PAT or SSH key, a sub-agent that asks for wider authority, an approval reused after a new commit, a secret in an allowed payload, a stolen workload token, a sandbox DNS or IPv6 escape. Each scenario states what must happen, and the server, not the runner, says what did. A signed assurance report (an evidence pack) holds the results, and a regression gate fails when a control that held yesterday does not hold today. The range is safe by construction (HR-120): a run belongs to a range agent, reaches only simulated connections, and says `simulated: true` in every receipt. In product terms this is Trail's adversarial range ([PRODUCT.md](../PRODUCT.md)). The range is not the containment sandbox of M9 (PN-008); it uses the sandbox only as a target for some scenarios.

**Scope (planned):**
- **Range agents and simulated runs** (W1a, W1b; HR-120, HR-220; F2). An agent is marked as a range agent when it is created, and the mark is immutable. Every run of a range agent is simulated, and so are its transactions. Range agents do not count toward the agent limit and are capped at 5 per organization in every edition. A simulated parent may start child runs only of range agents.
- **Simulated connections** (W1a, W2; HR-221). A connection marked simulated points at a loopback or private IP literal, is never a connector container, and passes the simulator handshake before the gateway sends anything to it.
- **Mismatch denial and policy blindness** (W1b; HR-220, T-094). A run and a connection that disagree about `simulated` are denied in both directions. The policy engine's input never contains the mark.
- **Isolation of simulated activity** (W1b; HR-222). Envelope budgets, drift quarantine, coverage, routes and tool observations, notifications, and approval pages treat simulated activity as described in design decision 6.
- **Receipts** (W1b; HR-120; PAP-1 §9). The decision, execution and effect receipts carry `simulated` from the run and the transaction instead of a fixed false.
- **Outbound credential check** (W2, including the server half in phase 3 after W1b; HR-225; F3). The gateway scans the mapped parameters and target id of every action on every face. The dispatching connection's own static credential is refused locally; a known credential format becomes `payload_findings`, which makes the server hold the action for a person with the reason `SECRET_IN_PAYLOAD`.
- **Scenario engine** (W4; HR-223). Strictly parsed YAML scenarios, a closed step catalogue, a runner with verdicts PASS, FAIL, ERROR and SKIPPED over a `Driver` port, and digests for scenarios and sets.
- **RangeService and assurance reports** (W5; HR-224; F4). A range is started, results are recorded, and the server derives the observed decision of every server-observable step from its own records. Finishing a range makes the report; exporting it makes an evidence pack of scope `range` (Team and above).
- **`pclaw redteam`** (W7; PN-009.1). `setup` prepares a range agent, simulated twin connections and a grant shaped like a real one, as a person, plan first. `run` starts a range, runs scenarios through the live driver and records them. `report` exports the pack. `list` shows ranges.
- **The regression gate** (W4, W6; HR-226; PN-009.5; F1). `--baseline <pack>` compares against a verified baseline pack and exits 1 on any failure or regression. `task range` runs every scenario through the harness driver against simulators on the local test stack.
- **The scenario library** (W6; PN-009.1, PN-009.2). 38 scenarios: 23 in the coding-agent suite (community tier) and 15 in the platform suite (business tier), listed in design decision 12.
- **Documents.** `docs/runbooks/range.md`, and the exit status in this brief.

- **The scenario format** (`apiVersion: pantherclaw.range/v1`; files `redteam/scenarios/RT-###-<slug>.yaml`; the file name's id must equal `id`).   title: <≤200 chars>
  ```yaml
  category: boundary              # functional | boundary | recovery | explanation
  suite: coding-agent             # coding-agent | platform
  tier: community                 # community | business
  attacker: A1                    # A1..A12

  rules: [HR-201]                 # ^HR-[0-9]{3}$

  harness_only: false             # true = never run by the live driver (kills or quarantines real state)
  steps:

      do: agent.call
      with: {face: mcp, connection: github, tool: merge_pull_request, args: {}}
      save: {pr: /number}         # optional: name → RFC 6901 pointer into the observed response
      expect: {outcome: HOLD, reason: REQUIRE_APPROVAL, code: "", same_decision_as: "", decisive_control: HR-201}
  ```

  ```go
  type Driver interface {
      Capabilities() map[Capability]bool        // github, payments, mcp, sandbox, person, second_org, harness
      Setup(ctx context.Context, s domain.Scenario) (Fixture, error)   // Fixture: map[string]string

      Teardown(ctx context.Context, s domain.Scenario) error

  type Observation struct { Outcome Outcome; Reason, Code string; DecisionHash string; TransactionID, ProbeReportID string; Response []byte /* JSON, ≤ 64 KiB */; Detail string }
  ```

  Verdicts: PASS (every step matches `expect`); FAIL (any mismatch); ERROR (a driver error, or the 60-second scenario timeout); SKIPPED (a required capability is missing, a harness-only scenario under a non-harness driver, or a person step without an interactive operator). Steps run in order, a FAIL stops the scenario, Teardown always runs, and the runner never retries.
- **The simulator handshake and the gateway's local refusals.**
  - The payments, MCP and GitHub simulators serve `GET /.well-known/pantherclaw-sim?nonce=<32 lowercase hex>` and answer 200 `application/json` `{"simulator":"pantherclaw-sim","kind":"payments|mcp|github","nonce":"<echo>"}` with the header `Simulated: true`.
  - Package `internal/gateway/simcheck`: for a simulated connection, before its first dispatch and whenever the last success is older than 10 minutes, the gateway sends `GET` to the origin root's well-known path with a fresh nonce over the connection's egress client and no credentials, and re-checks that the base URL host is a loopback or private IP literal. A failure is the local refusal `simulator_unverified` (error class `CANNOT_AUTHORIZE`) and nothing reaches the target.
  - Package `internal/gateway/outbound`, run after the simcheck at the dispatch choke point (`Engine.dispatch`, after `refusedUpstream` and before `accountRefusal`):
    - the dispatching connection's own static credential, when at least 8 bytes, in the scanned parameters (raw, base64 standard or URL-safe, or URL-encoded) is the local refusal `secret_in_payload` (`CANNOT_AUTHORIZE`) and the log event `gateway.secret_in_payload` (never the value);
    - known formats (RE2 only): `github_token` (`gh[pousr]_[A-Za-z0-9]{36,}`, `github_pat_[A-Za-z0-9_]{22,}`), `private_key` (`-----BEGIN [A-Z ]*PRIVATE KEY-----`), `aws_access_key` (`(AKIA|ASIA)[A-Z0-9]{16}`), `slack_token` (`xox[abposr]-[A-Za-z0-9-]{10,}`) and `pantherclaw_token` (the repository's real API-key and workload-token prefixes, read from the code) become `AuthorizeRequest.payload_findings`.
    - What is scanned (D31): the mapped ActionIR parameters of the action, recursively, with the one-level base64 decode, and the target id, on every face (HTTP, MCP, SDK, hook). Outbound requests are re-serialized from these parameters (HR-075), so nothing else leaves. Raw bodies, queries and headers are not scanned separately.
    - A finding is `{kind, location}` with a location such as `body:/files/0/content`, `query:q`, `header:X-Foo` or `arg:content`; never the value; deduplicated and sorted, at most 16, one per kind first and then filled by location (D36).
  - **Reason codes.** `SIMULATION_MISMATCH`: a DENY at the scope step when `run.simulated != connection.simulated`. `SECRET_IN_PAYLOAD`: a REQUIRE_APPROVAL reason added by the pipeline's requirements step when findings exist (the pattern of `GRANT_REQUIRES_APPROVAL`), not overridable by policy in M12. The decision receipt gains the optional `payload_findings` (absent when none; PAP-1 §9.1) and the approval page lists the kind and location.

**Security constraints and design decisions:**
1. **Range agents (HR-220).** `range_agent` is set at creation, never changed, and not part of the `pc_app` update grant. `pclaw agent create --range` sets it. Range agents are excluded from the `CheckAgents` count and capped at 5 per organization in every edition (`FailedPrecondition` `RANGE_AGENT_LIMIT`). A real agent never becomes a range agent, nor the reverse.
2. **Simulated runs (HR-220).** `StartRun` sets `runs.simulated = agent.range_agent`. `StartChildRun` sets `child.simulated = parent.simulated OR child agent.range_agent`; a simulated parent may start children only of range agents (otherwise `FailedPrecondition` `SIMULATION_MISMATCH`). A transaction's `simulated` is set at insert from the run and is immutable.
3. **Simulated connections (HR-221).** `pclaw connection create --simulated` sets `CreateConnectionRequest.simulated`. When it is set: for kind `http` or `mcp` the base URL's host must be an IP literal in 127.0.0.0/8, ::1, 10/8, 172.16/12, 192.168/16 or fc00::/7 (otherwise `InvalidArgument` `SIMULATED_TARGET_NOT_LOCAL`); kind `local` is allowed; kind `mcp_container` is refused (`SIMULATED_CONNECTOR_UNSUPPORTED`). The server sets `GatewayConnection.simulated = 23` when it builds the gateway's configuration. Every host a simulated connection may reach (the base URL, `allowed_hosts` and any other per-connection host override) must be such a literal (`SIMULATED_TARGET_NOT_LOCAL`). Custody credentials on simulated connections remain allowed and are sent only to those hosts; deliberate misuse is R-23 (D29).
4. **Pipeline mismatch (HR-220).** Immediately after the pipeline loads the connection, a run and connection that disagree on `simulated` are denied with `SIMULATION_MISMATCH` at the scope step, in both directions. The policy input never contains `simulated` or `range_agent` (tested), so the range exercises real policies exactly as written, and policy cannot behave differently for the range (T-094).
5. **Receipts (HR-120).** The decision receipt's `simulated` field is the run's. The execution receipt and the effect receipt take it from the transaction. The hard-coded false is replaced; existing tests that assert false for real runs stay.
6. **Isolation (HR-222).** For simulated runs and connections:
   1. debit lines owned by an envelope are dropped (grant-owned lines apply); the envelope's bounds and minimum attestation still apply at issue time;
   2. `ReportDrift` on a simulated connection makes no package transition and no epoch change; the audit event is written with `simulated: true`; the gateway still refuses locally (`upstream_drift`);
   3. `CoverageTrafficAfter` excludes simulated runs; sandbox `ReportRoutes` from simulated runs records nothing; snapshots and routes never include simulated connections; `RecordToolObservation` ignores them;
   4. notifications and security events caused by simulated transactions carry `simulated: true` in the payload and the title prefix `[SIMULATED] `;
   5. the approval page and the waitlist show a SIMULATED banner for simulated transactions (F630); approvals stay humans-only;
   6. nothing in the range engages organization containment; scenarios that need it are `harness_only`.
7. **The simulator handshake (HR-221).** The gateway verifies the simulator at the places in "Contracts" and refuses locally otherwise. It runs without credentials, so a proxy to a real target that does not know the nonce handshake is refused; a deliberate proxy by the gateway's operator is residual risk R-23.
8. **The outbound credential check (HR-225, F3).** As in "Contracts". The server treats findings as restrictive only: a finding can add `REQUIRE_APPROVAL` and never remove a hold or allow anything. A fixture key in a test repository can be approved by a person; a policy exception is a follow-up. The scan reads the mapped ActionIR parameters (recursively, plus the one-level base64 decode of design decision 22) and the target id. That is complete because outbound requests are re-serialized from those parameters (HR-075). The held-secret exact match covers only the dispatching connection's own static credential; GitHub App keys are never opened (HR-204) (D31).

19. **Concurrent steps (D22).** `agent.call` gains optional `concurrent: N` (2–50): the driver sends N calls at once and `${n}` (1..N) is available in that step's strings. Expectations add `max_allow: K`: at most K of the N may be ALLOW, and every other observation must match `outcome` (plus reason and code). The observation of such a step is the list, and the runner judges each (RT-026, RT-027). On a concurrent step `outcome` may be empty when `max_allow` is set (D28); then every non-ALLOW observation must be a blocking outcome (DENY, HOLD, CANNOT_AUTHORIZE or REFUSED) and reasons are not asserted (RT-026).
20. **Reasons (D23).** `Observation.Reasons []string` holds all reasons of the decision; `expect.reason` passes when it is one of them. Scenarios assert reason codes only for product-defined controls (pipeline, package, gateway and approval codes); holds that come from a tenant's policy or template assert only the outcome (plus `same_decision_as`), so a tenant's own policy can still pass.
21. **`action_of` and `fault` (D24, D26).** `agent.call` gains optional `action_of: <earlier step id>`: the driver sends the call under that step's action id on faces where the agent chooses it (sdk, PAP direct); RT-025 is the same action id with a changed amount, denied `ACTION_TAMPERED`. It also gains optional `fault: gateway_unreachable`, valid only with face `hook`, observed as REFUSED with code `hook_exit_2`; it is never passed through `args`.
22. **The scanner decodes base64 once (D25).** Besides the formats of "Contracts", the format scan also scans, one level deep, JSON string values that are valid base64 (standard or URL-safe, at least 16 characters) and are scanned as bytes, without requiring valid UTF-8 (decoded size at most 1 MiB). The finding's location gets the suffix `(base64)`. RT-010 keeps the base64 file-content step, the realistic commit path. (D36) The scanner never fails open: when the scan stops at its part cap, or a base64 value decodes to more than 1 MiB, it adds the finding `scan_incomplete` (location: where it stopped), which holds for a person like any other finding.
23. **No literal ids; kill-switch semantics (D27).** Scenarios use no literal object ids: they use `${fixture.<name>}` or a value `save`d from an earlier step (pull request numbers included). `operator.kill_switch` returns only after every gateway has applied the new containment (at most 1 second, otherwise ERROR); RT-034 expects REFUSED with code `kill_switch`.
24. **Accepted expectations (D27).** RT-007 as written (`OUTSIDE_ALLOWED_AUTHORITY` on the delegation, child DENY `NO_GRANT`) is accepted, as are the roles `unlisted` (RT-031) and `real` (RT-022).
25. **Fresh objects per scenario and run (D38).** A transaction backs the steps of only one scenario per range, and only transactions made after the range started count (design decision 11). So every scenario creates the objects it acts on, on every run: a branch, a file and a pull request through allowed `agent.call` steps, with `save`. Names use `${fixture.nonce}`, a 12-hex value that both drivers generate fresh for each range run, plus the scenario id (for example `rt-001-${fixture.nonce}`). Fixtures provide only read-only context (repository, owner, connection roles). Steps inside one scenario may still share a transaction (`same_decision_as`, `action_of`). Payments scenarios use `${fixture.nonce}` in charge ids where the harness feeds facts.
26. **Planted secrets are generated, never real (D39).** Both drivers generate throwaway values per run: `fixture.planted_private_key` (a fresh Ed25519 PKCS#8 PEM) and `fixture.planted_github_token` (`ghp_` plus 36 random characters). RT-010 and RT-011 use them. No scenario or fixture carries a real key or a simulator App key, and there is no `--fixture-file` flag. The generated fixtures are `nonce`, `planted_private_key`, `planted_github_token`, `planted_github_token_file_b64` and `planted_private_key_file_b64`; none of them can be set by the operator. The read-only fixtures the operator passes are `owner`, `repo`, `other_repo`, `main` (the initial head SHA of main) and `file_b64`.
27. **One root run per scenario (D40, D41).** Child runs need a delegated grant, and delegation is capped, so a CI gate would exhaust the range grant within a few runs. Instead the live driver starts each scenario in its own short-lived **root** run (`RunService.StartRun`) for the range instance, bound to the range grant. The runner's principal needs `run.start`, and `run.manage` to end runs early (best effort at teardown; a refusal is ignored and noted in the summary). Pending holds left by a range become moot (`RUN_ENDED`) at the next approvals sweep and leave the approvers' waitlist. The per-run hold cap applies per scenario; the per-grant cap (20 by default) is shared by the range, so run the suites separately if the full library hits `HOLD_LIMIT_REACHED`. `agent.child` steps (only RT-006 and RT-007) delegate from the scenario's run. `pclaw redteam setup` issues the range grant like the real grant, with delegation depth max(real + 1, 2) only so that `agent.child` works. Before it starts a range the CLI checks that the range grant is active, not expiring within the run, and has enough child delegations left for the selected `agent.child` steps; otherwise it exits 2 with a hint to re-issue the grant with `pclaw redteam setup`.
28. **Gateway facts belong to their connection (D43, HR-222).** A fact name had one provider per organization and one stored value per (org, name, subject), so a simulated twin of a GitHub connection could not get `github.*` facts, and if it could, its values would overwrite the real connection's for the same repository and pull request. Now a fact name has one provider per source scope: service-account providers are organization-scoped as before; gateway providers are connection-scoped (one per connection and name, and several connections may each declare `github.*`); a name supplied by an organization-scoped provider cannot also be supplied by a connection-scoped one, or the reverse. Migration 00098 gives `pc.facts` a nullable `connection_id` (NULL for service-account facts, set from the reporting gateway provider's connection) with unique keys on each scope, and makes the declarations' one-provider index per scope. Simulated facts never serve real actions.

**Residual risks** (added to THREAT_MODEL §8 by this brief):
- **R-23:** an operator who controls the gateway host can answer the simulator handshake from a proxy to a real target; the handshake stops mistakes, not a deliberate attacker who already operates the gateway. Range agents could also be used to avoid the agent limit. Compensating controls: the cap of 5 range agents per organization in every edition, loopback and private literals only, the handshake repeated every 10 minutes, `simulated: true` receipts.
- **R-24:** the outbound credential check knows only the dispatching connection's own static credential and the listed credential formats; binary content is scanned, and an incomplete scan holds; only deeper encodings, splitting and paraphrase pass. Compensating controls: exact matches of the dispatching connection's own static credential in raw, base64 and URL-encoded forms (other held secrets and GitHub App keys are not opened for the scan), known formats hold for a person (also inside base64 JSON string values, one level deep, scanned as bytes; a scan that stops at its cap holds as `scan_incomplete`; deeper encodings, splitting and paraphrase pass), findings only add requirements.
