### G0 — M36 — Reach: GenAI spans to each org's own collector, approval fatigue, deputies, digests, Web Push and a read-only VS Code extension — 2026-11-05

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M36 branches and, at the end of the milestone, in an exit status section. M36 is code-only like M30–M35: every stream codes on pushed branches first, and testing (the HR and T rows below) comes later.

**Purpose:** PantherClaw's decisions reach the places people already look ([ADR-0063](../adr/0063-telemetry-and-approval-reach.md); N25, N26). An agent's own trace continues through PantherClaw: each decision, tool dispatch and model call becomes an OpenTelemetry GenAI span in the org's own OTLP collector, carrying metadata only. Approvals reach the right person without wearing them down: fatigue is measured and routes a flagged decider last, a deputy covers an absence, digests and quiet hours delay only that person's notices, and Web Push brings a link to the phone. A VS Code extension shows a developer their agent's coverage, waiting approvals and recent decisions, read through the signed-in `pclaw`.

**Founder decisions (2026-11-05, all recommended):**
- FQ36-1: spans go to each org's own OTLP collector, a destination approved with a security key like SIEM export. Operator telemetry is unchanged (the HR-380 allow-list is kept).
- FQ36-2: spans carry metadata only (operation, decision, timings, model, token counts, ids, links), never prompts, arguments or answers.
- FQ36-3: deputies get the absent person's routing and notifications only. Eligibility is unchanged (HR-173).
- FQ36-4: the VS Code extension reads through the signed-in `pclaw` on the machine. No token lives in VS Code, and it never approves.

**Coordinator decisions:**
- **D1060 Trace context capture.** `dispatch.ReadInbound` parses a W3C `traceparent` strictly (version `00`, a 32-hex trace id that is not all zero, a 16-hex span id, flags) and keeps `tracestate` up to 512 bytes; invalid input is ignored, never an error. MCP also reads `params._meta.traceparent`. The model connection and the HTTP proxy read it before stripping headers and never forward it upstream unless the provider route already allowed it. `AuthorizeRequest.trace_context {trace_id, parent_span_id, flags, tracestate}` is not part of the ActionIR, any digest or any binding. The server stores it on `pc.transactions` (00400). The SDKs forward a caller-supplied `traceparent`; sdk/python injects it when `opentelemetry` is importable, sdk/go and sdk/typescript take an option. No new dependencies.
- **D1061 OTLP destinations per org (FQ36-1; Community, N26).** `pc.otlp_destinations` (00401) with a sealed header secret that is never shown again, created PENDING by `otlp.manage` and made ACTIVE with a WebAuthn step-up like SIEM destinations (HR-259), under the SIEM URL checks and through the egress client. `OTLPDestinationService`: Create, Activate, Disable, List, Get, Test. A River job per org and destination every 30 s exports finalized transactions, executions, model usage and effects from a cursor as OTLP/HTTP protobuf (gzip, 10 s, no redirects) through a per-org client; operator telemetry is untouched. After 24 hours of failures the destination is DISABLED and audited.
- **D1062 Span shapes (FQ36-2).** Spans use the agent's trace id with parent = `parent_span_id`; without a `traceparent` the trace id is SHA-256(run id)[:16] with no parent. Span ids are SHA-256(transaction id + kind)[:8], so a re-export is idempotent. Resource `service.name=pantherclaw`, `pantherclaw.org_id`. Spans: `pantherclaw.decide` (decision, first reason code, transaction, run, agent, operation, channel, coverage, console URL); `execute_tool <operation>` (`gen_ai.operation.name=execute_tool`, `gen_ai.tool.name`, outcome, duration = dispatch time; `mcp.method.name=tools/call` on channel mcp); `chat <model>` (`gen_ai.operation.name=chat`, provider, request model, input and output tokens). Effects are `pantherclaw.effect` span events. Never prompts, arguments, answers, personal target ids (only operation and target type) or approval text.
- **D1063 Fatigue metrics and auto-hold routing (Team).** `ApprovalService.GetApprovalFatigue({window 1 h|24 h|7 d, decider_id?})` per decider: peak approvals per hour, median seconds from first notice to approve, approve share, approvals between 22:00 and 06:00 in the person's time zone (else UTC) and the longest streak without a decline. A River job every 15 minutes flags a decider when, in the last hour, approvals ≥ 30 or the median is under 5 s over ≥ 10 approvals, or in the last 24 hours the approve share is 100% over ≥ 50 approvals; the flag (00405) clears after 4 hours and is audited `approval.fatigue_flagged`. Built-in detection `pc.approvals.fatigue`, alert only, MEDIUM. Org setting `fatigue_routing: route` (default) or `off`: a flagged decider is routed and notified last, only at the final escalation step; eligibility never changes. Invariant: no expiry, escalation, digest, deputy or fatigue path ever approves anything.
- **D1064 Deputies (FQ36-3).** `pc.approval_deputies` (00403): a window of at most 30 days, ACTIVE or CANCELLED, no overlapping live window per person. `SetApprovalDeputy`, `CancelApprovalDeputy`, `ListApprovalDeputies`: a person sets their own (with `approval.respond`), `waitlist.manage` may set one for others; the deputy is an ACTIVE member with `approval.respond` and not the person. A hold routed to a person inside an ACTIVE window also routes to and notifies the deputy, only when `apdomain.Check` makes the deputy eligible for that request; otherwise the deputy is skipped (`approval.deputy_not_eligible`). Audit `approval.deputy_set` and `approval.deputy_cancelled`.
- **D1065 Digests, groups and preferences.** `pc.notification_preferences` (00402): approval delivery IMMEDIATE (default) or DIGEST every 15, 30 or 60 minutes, quiet hours and an IANA time zone; `NotificationService` Get and Set MyNotificationPreferences. Quiet hours and digests delay only that person's direct messages, pushes and emails; routing and escalation to others are unchanged. A digest job every 5 minutes sends one link-only `approval.digest` per due person (HR-313/314), deduplicated per person and window. `ApprovalService.ListApprovalGroups({group_by VARIANT|AGENT|RUN|OPERATION, states})` is read only; approving still goes through the page and the batch flow (HR-175/176).
- **D1066 Web Push (Team, N25).** A deployment-wide VAPID key (purpose `web_push`, ECDSA P-256) served by `NotificationService.GetWebPushKey`. `pc.push_subscriptions` (00404) with an https endpoint whose host ends in an allow-listed push service (fcm.googleapis.com, updates.push.services.mozilla.com, notify.windows.com, web.push.apple.com) and sealed keys. Register, Remove and ListMy push subscriptions for the signed-in person. Delivery kind `web_push`: RFC 8291 aes128gcm, an RFC 8292 VAPID JWT (ES256), TTL 3600, urgency high, stdlib only; a 404 or 410 marks the subscription REMOVED. The payload is link-only: a title and the approval page link, no action details. The PWA is M40.
- **D1067 VS Code extension (FQ36-4).** `integrations/vscode-extension/` (Apache-2.0; plain CommonJS, no dependencies, no build step) runs `pclaw editor status --agent ID --json` and `pclaw editor open approval|transaction ID` through `child_process.execFile` with an argument array, never a shell. Settings `pantherclaw.pclawPath` and `pantherclaw.agent` (or `.pantherclaw/agent`); refresh every 60 s and on demand. A tree view (Coverage, Waiting approvals, Recent decisions), a status bar item "PantherClaw: N waiting", and the commands Refresh and Open in console. No approve, decline or edit action. `pclaw editor status` combines `ListCoverage`, `ListApprovalRequests` (PENDING) and `ListTransactions` (last 24 hours, at most 50) with their console links. **D1067a:** both links use the pclaw session's server URL; JSON is the only format; `pantherclaw.pclawPath` is a machine setting, `pantherclaw.agent` is restricted in untrusted workspaces and `.pantherclaw/agent` is read only in a trusted one; the extension opens only an https link (http on loopback). Marketplace and Open VSX publishing are a Phase C founder step.
- **D1068 Docs and assembly** as in this brief. **D1069 Streams** as in the table above; code-only, all three in parallel.

**Threat map:** T1621 (Multi-Factor Authentication Request Generation) is outside PantherClaw (the identity provider) and the pinned ATLAS catalogue has no approval-fatigue technique, so nothing leaves the "No PantherClaw control yet" list; `pc.approvals.fatigue` is not mapped.

**Out of scope:** operator telemetry changes, OTLP over gRPC, logs or metrics export to org collectors, prompt or answer content in spans, any path that approves, deputies that widen eligibility, the PWA (M40), approving from the editor, other editors, and Marketplace publishing.

**Security constraints.** Fail closed: an OTLP destination exports nothing until a person activated it with a security key, and a trace header never changes a decision, a digest or a binding. Spans and push payloads carry metadata and links only. Deputies, fatigue, digests and quiet hours change who is told and when, never who may decide or whether anything is approved. The editor only reads. Wording follows HR-681's list in code, CLI and docs.
