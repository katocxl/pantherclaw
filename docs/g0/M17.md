### G0 — M17 — Consequence chains, continuous discovery, identity presets and custom scenarios — 2026-10-29

This brief is written before implementation (G0). It lists the planned scope. The M17 pull requests track delivery, and the exit status section records it at the end of the milestone. It builds on `main` at 5225b371 (M1–M14, UI and M13 complete). M15 and M16 land before it, in migration order, and take the migration numbers below 00206. M17 is the third milestone after v1.0. On 2026-10-29 the founder answered four open decisions for M17 (G1–G4), the recommended option each time. Later that day the founder made a fifth decision (G18), against the recommendation: Azure managed identity and Microsoft Entra Agent ID are built in M17. All five are recorded at the end as answered. Every other choice is a coordinator design decision (D100–D129 in the coordinator's tracker), summarised below.

**Purpose:** M17 completes four parts of the product that v1.0 left at their first step.
- *Consequences.* Today a package's consequence rules predict one hop (a merge to `main` triggers a production deploy), and nothing is verified downstream: a predicted consequence that cannot be checked is skipped without a trace, and follow-on work cannot wait for it. M17 verifies consequences as their own transactions, records a parent's downstream state, lets automations and policy wait on it, follows consequence chains to a bounded depth, and lets a customer add rules of their own, but only rules that add requirements.
- *Discovery.* The GitHub organisation scan finds agents once. M17 compares re-scans, on GitHub and from CI, against the inventory: changed and vanished agents are flagged and their owners told, without changing anyone's authority.
- *Identity.* L2 attestation accepts GitHub Actions and Kubernetes tokens. M17 adds GitLab CI, SPIFFE JWT-SVIDs, GCP workload identity, AWS IAM, Azure managed identity and Microsoft Entra Agent ID on the same pinned-claims framework.
- *Range.* The scenario library is PantherClaw's. M17 lets a customer write scenarios for their own tools on the same simulator harness. Those scenarios are labelled customer-authored and never enter an attested pack.

In product terms this is Guardrails, Trail, Badge and Reflex ([PRODUCT.md](../PRODUCT.md)).

**Scope (planned):**
- **17a Downstream verification** (F414; D101–D105). Every predicted consequence is either opened as its own verified transaction or audited as not verifiable. Silent skips end. A parent transaction gets a downstream state, and a `downstream` receipt once its consequences are confirmed. Automations can wait on consequences (`wait_effect` with `consequences: true`), and policy can read a run's pending and unconfirmed consequences. One more verified consequence in `pc-stripe` is in scope only if that package already has a read operation that can find the consequence object from a value captured from the parent. Otherwise there is none, and the S17a pull request says so (D101).
- **17b Customer consequence rules and chains** (F405–F413; D106–D113). Customers can add consequence rules of their own (Team), through a two-person protected change (G1). Those rules only add requirements. Consequences chain: a predicted consequence becomes the next hop. Depth and fan-out are bounded, cycles are stopped, and an unknown link stops the chain. Expired rules yield UNKNOWN. Every consequence carries a derived label and an explanation.
- **17c Continuous discovery** (PN-001.3; D114–D117). Complete scans (the GitHub organisation scan, or a CI scan submitted with a scope) count misses per discovery. After 3 missed complete scans, a vanished discovery notifies its owner once and changes nothing else (G3). A material change of an open or claimed discovery is recorded and its owner told.
- **17d Identity presets** (PN-002.3; D118–D123, D129). The verifier is refactored to one implementation per kind first. Then six presets arrive in this order: GitLab CI, SPIFFE JWT-SVID, GCP workload identity, AWS IAM (G2), Azure managed identity, Microsoft Entra Agent ID (G18). All six are Enterprise. For the last two only, HR-140 (audience) and HR-143 (lifetime) are relaxed under an operator-pinned tenant and app id, with assurance still at most 1 hour from the attestation (HR-469).
- **17e Custom range scenarios** (PN-009.6; D124–D127). Customers write `CX-` scenarios for their own tools, run against a data-only tool simulator. The server labels them customer-authored and never puts them in an assurance pack (G4). The step catalogue stays closed. Library scenarios are accepted only with a matching library digest. Custom scenarios need Business or above.

Editions: package consequence rules, their chains and downstream verification are in every edition where they exist today (F405 in M8). Customer consequence rules are Team (D107). The six identity presets are Enterprise (D121, D129). Custom scenarios are Business and above (D126). Continuous discovery stays Team (PN-001.3).

*Downstream verification* (D102–D104; HR-450..452).
- **Repudiation, and elevation (T-198):** a predicted consequence that cannot be checked is skipped silently, or a parent's acceptance counts as downstream proof, so follow-on work (a merge, a release) proceeds on an unverified deploy. Answered by: the not-verifiable case is audited per consequence (HR-450). Downstream state is CONFIRMED only from the consequences' own evidence, and downstream receipts are appended, never rewritten (HR-451). A wait passes only on CONFIRMED (HR-452).

*Customer consequence rules and chains* (D106–D111; HR-453..457).
- **Tampering and elevation (T-199):** an insider or a malicious admin adds a customer rule meant to loosen authority: it suppresses or replaces a package rule, turns an UNKNOWN into NOT_TRIGGERED, or is waived by an exception. Answered by: every change is a two-person protected change in every protect mode, OFF included (HR-453). Customer rules are evaluated after package rules, and their results are only added (HR-454). An expired rule yields UNKNOWN (HR-456).
- **Denial of service (T-200):** a chain of rules that explodes or cycles, making decisions slow or unbounded, or hiding an unknown link deep in the chain. Answered by: per-rule `max_depth` 1–4, a global cap of 4, at most 16 consequences per action (past it, UNKNOWN `CONSEQUENCE_FANOUT`), a visited set on (operation, target), and a stop at an UNKNOWN link that stays at least a HOLD (HR-455). Every link is a named rule over verified facts (HR-457).

*Continuous discovery* (D114–D116; HR-458..460).
- **Spoofing and tampering (T-201):** a partial, failed or forged scan is used to fake an agent's disappearance or to hide a change. Answered by: only complete scans (a DONE org scan whose `scanned` list includes the kind's source, or a `complete` CI submit with a scope) count misses (HR-459). A vanished discovery only notifies, after 3 misses, and never changes state or authority (HR-458). Material changes are recorded with before and after keys, and the owner is told (HR-460).

*Identity presets* (D118–D121, D129; HR-461..465, HR-469).
- **Spoofing (T-202):** a GitLab CI token from a merge-request pipeline or an unprotected ref, or a token from a rogue self-managed GitLab, attests as an agent. Answered by: protected refs only, no merge-request or external pull request pipelines, numeric project and namespace ids, issuers from operator configuration only (HR-461). GCP keys come from a pinned URL, and the numeric service-account id is the binding (HR-463).
- **Spoofing and tampering (T-203):** SPIFFE trust-domain confusion (an SVID from one trust domain verified with another's bundle), or a smuggled AWS STS request (another action, another host, an unsigned audience, a replayed signature). Answered by: an exact SPIFFE ID, and a `sub` trust domain equal to the bundle's, from operator-configured bundles (HR-462). For AWS, only `GetCallerIdentity` to allow-listed STS hosts, with a signed audience header, at most 15 minutes old, single use (HR-464).
- **Spoofing and elevation (T-205):** an Azure managed identity or Entra Agent ID token, valid for up to 24 hours, is stolen and replayed, or is used to keep assurance until its `exp`; or a token for one organization's app id is accepted for another. Answered by: an operator-pinned `entra_apps` table maps each app id to exactly one organization, and duplicates are refused at start-up. `aud` must equal the pinned app id, and `tid` the pinned tenant. Keys come from the pinned per-tenant URL. Assurance lasts at most 1 hour from the attestation, and the token stays single use until `exp` (HR-469). HR-140 and HR-143 are relaxed for these two kinds only.
- **Elevation:** an attestation of a kind the server does not know falls through to a default verifier. Answered by: an explicit switch that refuses unknown kinds (HR-465).

*Custom scenarios* (D124–D126; HR-466..468).
- **Tampering and repudiation (T-204):** a runner forges a library scenario, or declares a customer scenario as library, to inflate an assurance pack. Answered by: the server derives the origin from the id prefix (HR-466). An RT id is accepted only with a matching library digest from the server build, with its tier from that map (HR-467). Customer ranges export no assurance pack (HR-466).
- **Elevation (T-092):** a customer tool file used to run code or reach a host. Answered by: the simulator's tool file is data only, strictly decoded and size-capped, and every response is marked simulated (HR-468).

**Design decisions:**

*S17a: downstream verification and waiting on consequences*

1. **D101: scope.** Three things:
   - no silent skips;
   - the parent's downstream state and receipt;
   - waiting on consequences: the `wait_effect` option and the run-level counts for policy.

   Plus ONE more verified consequence in `pc-stripe`, only if that package already has a read operation that can find the consequence object from a value captured from the parent. Otherwise there is none, and the pull request says so.
2. **D102: downstream state** (migration 00206; HR-450, HR-451).
   - Column `pc.transactions.downstream_state text NULL CHECK (downstream_state IN ('PENDING','CONFIRMED','UNCONFIRMED','NOT_VERIFIABLE'))`.
   - When a parent becomes CONFIRMED and its consequences are processed (in `Report` and `ResolveReconciliation`, in the same transaction), the state becomes:
     - PENDING if at least one consequence transaction was opened;
     - NOT_VERIFIABLE if PREDICTED consequences existed but none could be opened (NO_DEFINITION, NO_VERIFIER, NO_ENVIRONMENT, NOTHING_CAPTURED, or the new no-capture case);
     - NULL when nothing was predicted.
   - Today's silent return in `pgtransactions/consequences.go` becomes an audit event `transaction.consequence_not_verifiable` (reason NOT_VERIFIABLE) for each PREDICTED consequence that cannot be opened.
   - PENDING → CONFIRMED when every opened consequence transaction is CONFIRMED. At that point a parent effect receipt is appended at level `downstream`, basis `consequence`, listing the consequence transaction ids. 00206 widens the basis CHECK if needed. An earlier receipt is never rewritten.
   - PENDING → UNCONFIRMED when any consequence gets the reconciliation `consequence_unconfirmed` or a negative effect state. If a person later resolves that reconciliation to occurred, the state is computed again.
   - The `Transaction` message in `transactions.proto` exposes `downstream_state`.
3. **D103: waiting and run counts** (HR-452).
   - `wait_effect` gains `consequences: bool` (`with.go`). When it is true, the matched transactions of the step's operation count by `downstream_state`:
     - CONFIRMED counts toward `min`;
     - PENDING, or a parent not yet final whose final evaluation has PREDICTED consequences, is pending and keeps waiting;
     - UNCONFIRMED or NOT_VERIFIABLE → NEEDS_RECONCILIATION, as HR-280 does;
     - a parent without PREDICTED consequences does not count.
   - After the run ends, a `min` that cannot be reached is FAILED, as today.
   - Policy gains `run.consequences_pending` and `run.consequences_unconfirmed` (int) in `policy/app/run.go`. Both are 0 without a run. They count over the transactions of the action's current run, pending and unconfirmed as above; unconfirmed is UNCONFIRMED plus NOT_VERIFIABLE.
   - A new Reader method `RunConsequences(ctx, org ids.OrgID, run ids.UUID) (RunConsequenceCounts, error)` is implemented in every Reader: pgauthority, the recording recorder and reader, replay, the scenario fixture and pipelinetest.
   - The coding-to-production template gains one rule, so only new instantiations get it: HOLD `github.pull.merge` while `run.consequences_unconfirmed > 0`.
4. **D104: chains** (after S17b's `(m17-chain-schema)` commit).
   - `openConsequences` opens only a parent's depth-1 PREDICTED rows.
   - When a consequence transaction becomes CONFIRMED, its children are opened by the same rules: the rows whose `parent_position` is that consequence, at depth + 1.
   - A parent's downstream state covers its whole subtree.
5. **D105: rules and threat.** HR-450, HR-451, HR-452 and T-198 (worded in the tables above). Tests cite `// Covers: F414`.

*S17b: customer consequence rules and chains*

6. **D106: the customer rule store** (migration 00207).
   - Table `pc.customer_consequence_rules` with these columns:
     - `org_id`, `id`;
     - `rule_id` matching `^cx\.[a-z0-9][a-z0-9_.-]{0,63}$`, disjoint from package rule ids;
     - `version int`, `body bytea` (the canonical JSON of the rule, at most 16 KiB), `digest bytea`;
     - `state` (PROPOSED, ACTIVE or RETIRED);
     - `proposed_by`, `approved_by` (CHECK `approved_by` ≠ `proposed_by`), `created_at`, `updated_at`.
   - One ACTIVE version per `rule_id`, and at most 256 ACTIVE rules per organization.
   - RLS and `org_write_guard`, the deleter grant per HR-391 and HR-392, and `pc_audit_ro` without `body`.
   - The body is `defs.ConsequenceRule` plus `max_depth`. The rule's operation and its consequence operation must each name an ACTIVE definition of the organization; they may come from different packages. Recordings pin their definition digests.
7. **D107: the gate** (G1; HR-453).
   - Proposing, changing or retiring a customer rule is ALWAYS a protected two-person change: `protect.Gate.Hold` with a new surface `consequence.rule.put`. This holds whatever the CONSEQUENCE_RULES category mode is; OFF never bypasses it.
   - Approval goes through the existing protect approval flow. There is no approve RPC of its own.
   - A new permission, `consequence_rule.manage`, is granted to Security Admin.
   - Edition: Team (`CustomConsequenceRules()`). Package rules, including their chains, stay in every edition.
8. **D108: only add** (HR-454).
   - Customer rules are evaluated after the package rules, and their results are added to them.
   - A customer rule cannot reference, replace or suppress a package rule, and cannot turn a package UNKNOWN into NOT_TRIGGERED.
   - Exceptions never waive customer consequences.
   - Customer provenance is inherited (D145): a consequence reached through a customer rule counts as customer at every later hop, even when a package rule produces that hop, so an exception never waives it. Its rule id still names the rule that fired.
9. **D109: chains** (F411, F412, F413; HR-455, HR-457).
   - A PREDICTED consequence becomes the next hop's (operation, target), and that hop's facts are read about that target.
   - Every hop is a named rule over verified facts.
   - Depth: a per-rule `max_depth` (1–4, default 1) and a global cap of 4.
   - At most 16 consequences per action in total. Past that cap the result is UNKNOWN, reason `CONSEQUENCE_FANOUT`.
   - A visited set on (operation, target) stops cycles.
   - An UNKNOWN hop is not expanded. It stays UNKNOWN, with a stop marker that gives the rule and depth, so it is at least a HOLD (HR-206). A NOT_TRIGGERED hop ends its branch.
   - Migration 00208: `pc.decision_consequences` gains three columns, with a `pc_audit_ro` grant:
     - `depth smallint NOT NULL DEFAULT 1 CHECK (depth BETWEEN 1 AND 4)`;
     - `parent_position smallint NULL`;
     - `source text NOT NULL DEFAULT 'package' CHECK (source IN ('package','customer'))`.
   - The pipeline and recording version is bumped. v1 and v3 recordings must still replay, and replay pins every rule id in the chain.
10. **D110: validity** (HR-456). An expired rule (`valid_until` in the past) makes its consequence UNKNOWN, reason `CONSEQUENCE_RULE_EXPIRED`. It never becomes NOT_TRIGGERED.
11. **D111: labels and explanation** (F407, F409, F410).
    - Each consequence gets a derived `label`, which is never stored:
      - MAY_CAUSE: PREDICTED;
      - AUTHORIZED: PREDICTED with a permitting decision;
      - UNKNOWN;
      - NOT_TRIGGERED;
      - ACCEPTED: its consequence transaction was opened;
      - CONFIRMED: that transaction's effect is CONFIRMED.
    - ACCEPTED and CONFIRMED are joined from transactions at read time, through the existing link queries.
    - The receipt's consequence gains optional fields: `source`, `depth`, `chain` (rule ids), `description`, and `evidence` (the names of the required facts, never their values). Old receipts must still verify.
    - `explain.go` shows the rule description, the target relationship, the supporting fact names, validity and the unknown links. It keeps the `UNKNOWN_CONSEQUENCE` gap.
12. **D112: API and CLI.**
    - `ConsequenceRuleService` (`consequence_rules.proto`) has Propose, Retire, List and Get. Propose and Retire return the protected change.
    - CLI: `pclaw consequence-rules propose|list|show|retire`.
13. **D113: rules and threats.** HR-453..HR-457, T-199 and T-200 (worded in the tables above). Tests cite `// Covers: F405`–`F413`.

*S17c: continuous discovery*

14. **D114: missed scans** (migration 00209; G3; HR-458, HR-459).
    - `pc.discoveries` gains `missed_scans int NOT NULL DEFAULT 0`, `last_scan_run uuid NULL`, `scan_scope text NULL` (at most 256) and `vanish_notified_at timestamptz NULL`. The source also allows `ci_scan`.
    - When an org scan finishes, only for DONE runs and in the same transaction, a miss is counted for each `github_scan` discovery of that connection that was not seen in the run. A miss counts only when the discovery kind's source is in the run's `scanned` list.
    - A touch resets `missed_scans` to 0. On reappearance it also clears `vanish_notified_at` and writes the agent_change `agent.discovery_reappeared` (no notification).
    - On reaching 3 misses, once, the server writes:
      - the agent_change `agent.discovery_vanished`;
      - a notification;
      - a work-queue item.
    - The discovery's state is unchanged, and so is any agent's authority (G3).
    - Misses count per discovery.
15. **D115: CI mode** (HR-459).
    - `SubmitScanFindings` gains `scope` (at most 256) and `complete bool`; `complete` requires `scope`.
    - CLI: `pclaw scan --submit --scope <repo|host> --complete`, run with a service-account API key.
    - A complete submit uses the source `ci_scan` and counts misses for the `ci_scan` discoveries with the same scope.
    - A non-complete or desktop scan never counts misses. The org scan stays human-started.
16. **D116: changes, the work queue and notices** (HR-460).
    - A material-key change on an OPEN or CLAIMED discovery writes the agent_change `agent.discovery_changed`. It records the before and after values of the material keys only, as untrusted, size-capped text.
    - A new work-queue item kind `DISCOVERY_CHANGE` is raised for vanished discoveries, and for changes on claimed discoveries. It is read with `agent.read`.
    - Notifications go to the claimed agent's owner and backup, or, for an unclaimed discovery, to the organization's admins.
    - New automation triggers: `agent.discovery_changed` and `agent.discovery_vanished`.
    - HR-209 (reopen when DISMISSED) is unchanged.
17. **D117: rules and threat.** HR-458..HR-460 and T-201 (worded in the tables above). Tests cite `// Covers: PN-001.3`.

*S17d: identity presets*

18. **D118: refactor first, no new kind** (HR-465).
    - A `Verifier` interface per kind replaces the GitHub-shaped one in `attest.go`.
    - `issuerkeys` is generalised:
      - algorithms RS256/384/512, PS256/384/512 and ES256/384, from a per-preset list;
      - EC keys;
      - keys with `use` `sig` or `jwt-svid`, where the preset allows it;
      - key-source modes: discovery on the issuer host (the default), a pinned per-preset JWKS URL, or a static JWKS from operator configuration.
    - The kind dispatch in `workloadrpc/workload.go` becomes an explicit switch, and an unknown kind is refused.
19. **D119: GitLab CI (`gitlab_ci`)** (HR-461).
    - Issuers come from the operator configuration `gitlab_issuers` (default `https://gitlab.com`), mirroring `kubernetes_clusters`.
    - Pins: the numeric `project_id` and `namespace_id`, `ci_config_ref_uri` (with an optional `ci_config_sha`), and optionally `environment` and `runner_environment`.
    - Hard rules:
      - `ref_protected` is `"true"`;
      - `pipeline_source` is neither `merge_request_event` nor `external_pull_request_event`;
      - `ref_type` is `branch` or `tag`;
      - the audience is exact.
    - Lifetime: HR-143 is unchanged (at most 1 hour). The docs tell users to keep the job timeout at most 60 minutes.
    - Binding: `project_id`, `namespace_id`, `ci_config_ref_uri`. Execution context: `ci`.
20. **D120: SPIFFE JWT-SVID (`spiffe_jwt`)** (HR-462).
    - Trust domains come from the operator configuration `spiffe_trust_domains`. Each has a bundle endpoint URL (SPIFFE `https_web`) or a static JWKS file. Only the operator can allow private addresses.
    - Pin: the exact SPIFFE ID, with no prefix or wildcard. The `sub`'s trust domain must equal the bundle's.
    - The audience is exact. The replay key is the token hash. Execution context: `service`.
21. **D121: GCP (`gcp_workload`) and AWS (`aws_iam`)** (HR-463, HR-464).
    - GCP:
      - `iss` is `https://accounts.google.com`, with keys from the pinned URL `https://www.googleapis.com/oauth2/v3/certs`;
      - `aud` is `pantherclaw:<org>`;
      - the pin is the numeric service-account `sub`, optionally with `google.compute_engine.project_id` and `instance_id`.
    - AWS is a new verifier kind, `adapters/awssts`. The workload sends a presigned `sts:GetCallerIdentity` request, and the server checks:
      - the method is POST, to an STS host allow-listed in operator configuration (default: the global and regional `sts.*.amazonaws.com`);
      - the body is exactly `Action=GetCallerIdentity&Version=2011-06-15`;
      - `X-Amz-Date` is within 15 minutes;
      - `SignedHeaders` includes `x-pantherclaw-audience`, whose value is `pantherclaw:<org>`.

      It then replays the request through the egress client. The replay key is the hash of the signature. The pins are the account id and the role name, normalised from the assumed-role ARN.
    - Both use the execution context `service`.
    - Migration 00210: the `trusted_issuers.kind` CHECK adds `gitlab_ci`, `spiffe_jwt`, `gcp_workload` and `aws_iam`.
    - Edition: the four new kinds are Enterprise (PN-002.3), through `IdentityPresetsExtended()`, checked in `ProposeIssuer`.
22. **D122: Azure managed identity and Entra Agent ID (superseded by D129).** D122 held both kinds because their audience cannot be `pantherclaw:<org>` (it is an Entra application audience) and their tokens live about 24 hours, both against HR-140 and HR-143. The founder's decision G18 replaces the hold: they are built in M17 under D129.

    1. the refactor;
    2. GitLab;
    3. SPIFFE;
    4. GCP;
    5. AWS;
    6. `azure_mi` (D129);
    7. `entra_agent_id` (D129).
24. **D129: Azure managed identity (`azure_mi`) and Entra Agent ID (`entra_agent_id`)** (founder decision G18; migration 00211; HR-469, and the exception clauses of HR-140 and HR-143).
    - **The organization mapping, pinned by the operator:** the server configuration `entra_apps: [{tenant_id, app_id, org_id}]`.
      - Each `app_id` maps to exactly one organization; duplicates are refused at start-up.
      - For these kinds, `AttestationOrg` finds the organization from the token's unverified `aud` (the `app_id`) through this table, never from a `pantherclaw:` prefix.
      - An organization may propose an issuer of these kinds only for a `tenant_id` and `app_id` pair listed for that organization.
    - **Audience** (HR-140 relaxed for these two kinds only): `aud` must equal the pinned `app_id` exactly, or its `api://<app_id>` URI.
    - **Issuer:** `https://sts.windows.net/<tid>/` (v1) or `https://login.microsoftonline.com/<tid>/v2.0` (v2), with `tid` equal to the pinned tenant.
      - Keys come only from the pinned per-tenant JWKS URL `https://login.microsoftonline.com/<tid>/discovery/v2.0/keys` (the pinned-URL mode of D118; v2 URL only, D137).
    - **Lifetime** (HR-143 relaxed for these two kinds only):
      - the token may live up to 24 hours (`exp` − `iat` ≤ 24 hours, with 60 seconds of leeway);
      - the workload's assurance, and any credential issued from the attestation, lasts at most 1 hour from the attestation, never until the token's `exp`;
      - single use is unchanged: the replay record (the token hash, or `uti` when present) is kept until `exp`.
    - **`azure_mi` pins:** `tid` and the managed identity's `oid` (`xms_mirid` is not used, because it is undocumented; D137). Hard rule: `idtyp` is `app` when the claim is present.
      - Because IMDS caches each managed-identity token for about 24 hours, and each token is single use, a managed identity gets about 1 hour of L2 per day (D137). The founder kept single use (G19): there is no further HR-143 relaxation. The workload-identity runbook documents this.
    - **`entra_agent_id` pins:** `tid` and the agent identity's `oid`, plus the claim that marks the token as an agent identity.
      - That claim and the token format are confirmed from Microsoft's public documentation before coding.
      - If the claim set cannot be confirmed as stable, S17d stops and asks the coordinator instead of guessing.
    - **Kind and context:** execution context `service`. Migration 00211 adds both kinds to the `trusted_issuers.kind` CHECK. Edition: Enterprise, through the same gate as D121.
    - **Rules and threat:** HR-469 and T-205 (worded in the tables above). HR-140 and HR-143 gain an exception clause that names these two kinds and points to HR-469; their meaning for every other kind is unchanged. Tests cite `// Covers: PN-002.3`.

*S17e: custom range scenarios*

25. **D124: ids and origin** (migration 00213; HR-466).
    - Customer scenario ids are `CX-[0-9]{3,5}`, in files named `CX-###-slug.yaml`.
    - The server derives the origin (library or customer) from the id prefix; a runner cannot declare it.
    - Migration 00213:
      - `redteam_results` and `redteam_runs` gain `origin text NOT NULL DEFAULT 'library' CHECK (origin IN ('library','customer'))`;
      - the `scenario_id` CHECK widens to `^(RT-[0-9]{3}|CX-[0-9]{3,5})$`;
      - a CHECK makes origin `customer` exactly when the id starts with `CX-`.
26. **D125: library authenticity** (HR-467).
    - The server build embeds the library's id → digest and tier map. The map is generated from `redteam/scenarios`, and a test checks that the two match.
    - An RT scenario is accepted only when its digest matches. Otherwise it is refused with `RANGE_SCENARIO_NOT_LIBRARY`. Its tier comes from the map, not from the runner.
    - Ad-hoc RT ids in tests and end-to-end fixtures become CX ids or library ids. Coverage stays the same, and no test is weakened.
    - **Upgrade note** (D135): an edited shipped scenario is refused after a server upgrade, because its digest no longer matches the library map of the new build. Use the shipped file, or copy it to a `CX-` scenario.
27. **D126: rules for customer scenarios** (G4; HR-466, HR-468).
    - A range is either all library or all customer.
    - A customer range exports no assurance pack: `ExportAssuranceReport` refuses it with `RANGE_CUSTOMER_NOT_ATTESTED`. It gets only the unsigned summary, labelled "customer-authored".
    - A customer range's baseline is a prior customer range, compared by range id through `GetRange`.
    - `threats` and `rules` are optional for CX scenarios. When present, they must be real `T-###` and `HR-###` ids.
    - CX steps:
      - live-driver kinds only;
      - no `harness_only` and no `sim.mutate`;
      - `requires` only for capabilities the live driver provides;
      - the tier is forced to `business`.
    - The simulator: `pantherclaw-sim mcp --tools FILE` (the kind stays `mcp`), in a new `tools_file.go`:
      - strict decoding;
      - at most 64 tools and 64 KiB;
      - canned results keyed on an exact match of the arguments, with no templating except echoing arguments;
      - every response marked SIMULATED.
    - Scenario content stays local (DIR). The server records the origin and digest of each result.
    - Edition: `RangeCustomScenarios()` = Business and above, in `billing/domain/range.go`. `StartRange` refuses CX declarations below that (`EDITION_REQUIRED`), and the CLI checks early.

**Exit criteria (M17 is done when the local checks and the end-to-end tests show the following):**
- A parent with a predicted, verifiable consequence reaches downstream CONFIRMED only after its consequence transaction is CONFIRMED, with an appended `downstream` receipt. A wait on consequences holds until then. An unverifiable consequence is audited and never passes a wait.
- A customer rule is proposed, held as a two-person protected change, approved by another person and enforced, adding a requirement to a package rule's result. A chain stops at its depth cap, at a cycle and at an unknown link, which holds.
- A complete CI scan that no longer sees a claimed discovery three times notifies its owner once and leaves its state and authority unchanged. A partial scan counts nothing.
- GitLab CI, SPIFFE, GCP, AWS, Azure managed identity and Entra Agent ID attestations reach L2 for a pinned agent, and each preset's refusal cases are refused. An Azure or Entra attestation's assurance ends at most 1 hour after the attestation.
- A customer range runs CX scenarios against `pantherclaw-sim mcp --tools`, is labelled customer-authored, and is refused an assurance pack. A forged RT scenario is refused.
- The HR-450..HR-469 tests and `TestT198_*`..`TestT205_*` are green. `task trace MILESTONE=M17`, `task check`, `task test:integration` and `task range` pass on the exit branch, and the Taskfile's `trace` default moves to `M17`.
