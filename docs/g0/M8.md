### G0 — M8 Coding-agent integrations — 2026-10-11

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M8 pull requests and, at the end of the milestone, in an exit status section. It builds on `feat/m7-exit` at dbf433d (#234, the M7 exit), the top of the post-audit chain #221 → #222 → #225 → #223 → #226 → #228 → #227 → #229 → #231 → #232 → #224 → #230 → #233 → #234, which the founder has not merged yet. Every M8 branch starts from `origin/feat/m7-exit`, merges this brief's branch (`docs/m8-m9-g0-brief`) with a merge commit before its first pull request, and stacks on it ([PARALLEL_WORK](../PARALLEL_WORK.md)). The founder answered every open decision on 2026-10-11 before the brief was written (the recommended option each time); they are recorded at the end as answered.

**Purpose:** ADR-0017 makes coding and DevOps agents the first market. M8 connects them. Agents built on the SDKs get a client for PAP/1 in Go, Python and TypeScript that sends their raw tool calls to a new gateway face, which maps and decides them through the signed package exactly as it does MCP and HTTP calls. Customer services enforce decisions themselves with target verifier middleware. The Claude Agent SDK integration enforces from the SDK's `PreToolUse` hook and fails closed. `pclaw init` wires a developer's machine in minutes without weakening anything already there. The GitHub App connector keeps the App's private key in gateway custody and mints a token for one repository and the minimum permissions per authorized action, so an agent never holds a GitHub credential. Consequence rules stored since M4 (F405) are evaluated in the pipeline, and the §43 scenario (a merge needs an independent reviewer bound to the head commit; a deployment consequence needs a release approver inside a change window) passes end to end on a GitHub simulator. In product terms this is the Checkpoint and Stash components for coding agents ([PRODUCT.md](../PRODUCT.md)).

**Scope (planned):**
- **Conformance vectors** (S1, PN-016.1, PN-002.7). `sdk/conformance/` (Apache-2.0) holds JSON vectors that a Go generator in the main module (`internal/conformance/gen`, licensed like the code it exercises; run by `task sdk:vectors`) produces from the real implementations with fixed test keys:
  - ActionIR JCS bytes and hash, including rejection cases (duplicate keys, numbers in material parameters, invalid UTF-8, bidi controls; HR-100..102);
  - PAP/1 proofs (`htm`, `htu`, `bh`, `ath`, nonce) and their failures;
  - workload token parsing;
  - action-token verification (valid, and each failure of HR-202);
  - the approval binding (PAP-1 §8);
  - the key file (`workloadclient.KeyFile`).

  Every SDK runs every vector; a vector an SDK cannot run is a failure, never a skip.
- **Go SDK** (S2, S3). `sdk/go` stays its own module, standard library only (decision 8). The client:
  - loads a key file;
  - signs proofs, retrying once on a fresh nonce;
  - renews workload tokens;
  - authorizes raw tool calls through `/sdk/{connection}`;
  - waits on a hold through the M5 wait handle (`/v1/wait/{transaction}`, HR-174) and resubmits the identical call.

  `sdk/go/verifier` is `net/http` middleware for customer services (PN-016.2) with a `ReplayStore` interface, an in-memory store (one replica only) and a `database/sql` store (decision 8).
- **TypeScript and Python cores** (S4, S5). They do the same as the Go client (proofs, nonce retry, token renewal, `/sdk` authorize, wait and resubmit, JCS and hash checks), plus an action-token verification function with a `ReplayStore` interface.
  - **TypeScript:** `@pantherclaw/sdk`, zero runtime dependencies, WebCrypto Ed25519, Node ≥ 22.
  - **Python:** the `pantherclaw` package, depending only on `cryptography`, standard-library HTTP, Python ≥ 3.11.

  Framework wrappers wait for M14 (PN-016.3).
- **Claude Agent SDK integration** (S6, PN-014's Agent SDK part, HR-200, decision 2): `integrations/claude-agent-sdk/{typescript,python}`. It returns a `PreToolUse` hook (matcher: every tool) and a `canUseTool` callback that the application passes to the SDK. The hook sorts each call into one of three classes (design decision 8):
  1. a tool of an MCP server served by the gateway's `/mcp` face (already enforced there);
  2. `Bash` and `PowerShell`, decided through the local connection's `/hook` mapping (`pc.shell`). Without a local connection the integration refuses to start, unless the application sets an explicit `shell: "observe"`. Every shell call is then sent to `/sdk` as a built-in tool, answered and recorded `OBSERVE_ONLY`, so the inventory shows an uncontrolled shell route;
  3. any other tool, sent to `/sdk/{connection}`: decided when mapped. An unmapped built-in is recorded `OBSERVE_ONLY` and runs under the application's own permissions; an unmapped tool that is not built in is denied.
- **The `/sdk/{connection}` face** (C1, HR-201, decision 1). The gateway verifies PAP/1 over the exact body and maps the raw tool call itself, through the connection's signed package's `mcp` mapping entries. It then authorizes with channel `sdk` and answers with the decision, the canonical action and its hash. For `target_enforced` connections, an `ALLOW` also carries the exact outbound request and its action token. Every `ALLOW` is recorded as `delegated` (HR-186). Its access mode is `agent_held` and it is labelled `PARTIAL`, except on a `target_enforced` connection, whose target refuses anything without the token (HR-024; design decision 9).
- **Capability-declared connections and their lifecycle** (C2, F346, F351):
  - a package declares, per operation and for the connection, its discovery, observation, enforcement and response support, the permissions it needs with reasons, its limits, its failure behaviour and a harmless `test` read;
  - a connection's sensitive capabilities need a person's approval;
  - `TestConnection` leases that read to the gateway;
  - for a `target_enforced` connection, a `target_verifier` test (amended in C2h, founder decision on N15, 2026-10-11).
    - Under its lease, the server mints test-purpose action tokens for the package's `test: true` read only: one binding the read's empty body and one binding another body. This is HR-188's one exception to minting at `BeginDispatch` (founder decision 2026-10-13): one mint per lease attempt, at most three attempts per test, recorded on the test (`tokens_attempt`) and audited (`connection.test_tokens_minted`, naming both token ids), and only while the connection is ACTIVE and `target_enforced`, the kill switch is off and the leased operation is still the pinned package's test read. The tokens expire no later than that lease. A target's verifier refuses the tokens for any other operation or target.
    - The gateway sends that read four times and expects: without a token, 401; with the token bound to another body, 401; with the fresh token, 2xx; with the same token again, 409.
    - It passes only when the target answers each as stated, the three refusals with its verifier's own problem documents (`urn:pantherclaw:action-token:missing`, `…:body_mismatch`, `…:replayed`). It records the operation it tested.
    - This is the evidence M9 needs to lift the cooperative cap (HR-210), only for that operation. It never extends to other routes the same verifier protects, and write routes stay `PARTIAL` in M9. A test of each write route with a reviewed, target-invalid body is a follow-up. A declared store never counts;
  - `GetConnectionHealth` shows the last successful test, credential state, quarantine, recent `UNKNOWN` and delivery failures, declared versus granted permissions, and the agents whose grants depend on the connection.
- **`pclaw init`** (C3, HR-208). It detects Claude Code settings (user, project, local and managed), `.mcp.json`, Claude Desktop and the other clients `pclaw scan` knows, and Agent SDK projects (`@anthropic-ai/claude-agent-sdk`, `claude-agent-sdk`). It then:
  - enrolls the agent as the signed-in person, with fingerprint confirmation (HR-094);
  - writes the key file with mode 0600;
  - backs up, shows a diff and adds to the configuration: the Claude Code hook, for every command a tool runs in a shell (Bash, PowerShell and Monitor, whose command runs where Bash runs; amended after review, founder decision 2026-10-13, HR-186); for each governed MCP server, a new entry that reaches it through the gateway or `pclaw mcp proxy`; and a `permissions.deny` rule `mcp__<original>__*`, so the original entry stays as it was but cannot be used;
  - prints, never writes, the Agent SDK integration snippet.

  It is idempotent: a second run changes nothing.

  Amended in C3d after review, 2026-10-13: `init` fails, changing nothing, unless each server to govern is configured for Claude Code under exactly that name. The deny rule keeps Claude Code from using the original's tools, but Claude Code still starts the original, with its credentials. For an original from the project's `.mcp.json`, `init` also adds its name to `disabledMcpjsonServers` in the scope's settings (keeping the entries there and removing nothing), so Claude Code does not start it. What still remains, and `init` says so: servers from plugins (`mcp__plugin_…`) and servers configured outside `.mcp.json` keep running and must be removed by the user; MCP resources are denied by the gateway's `/sdk` face, but Claude Code's own `ListMcpResourcesTool` and `ReadMcpResourceTool` are blocked only when the server is disabled.
- **The "coding to production" template** (C4). `templates/coding-to-production/` holds data, applied with `pclaw init --template` or `pclaw template apply` through the existing APIs, as a person, each step audited, with a plan shown first:
  - a guardrail envelope for the chosen repositories;
  - a grant for reads, branch preparation, contents writes to non-default branches and pull requests. Branch creation and contents writes are subject to the same consequence rules as merges, because a push-triggered branch (`release/*`, `staging`) deploys too;
  - a merge requirement (`code_reviewer`, independent, bound to the head SHA) and a one-merge-per-run counter;
  - a deployment consequence requirement (`release_approver` inside a change window);
  - an example weekday change window;
  - a shell rule forbidding merge and push commands (`gh pr merge`, `gh api` merges, `git push`), so the shell is not a quieter route to the same effect. A shell rule is a heuristic over command text; coverage stays `PARTIAL` until M9's sandbox closes the route.

  It binds no people to roles.
- **Consequence rules in the pipeline** (P1, F405's stored rules, HR-206, decision 6). Step 6 (facts) reads the active package's `consequences` for the action's operation.
  - When a rule's `requires_facts` are all current, its `when` (CEL) is evaluated: true makes the consequence `PREDICTED`.
  - When any of those facts is missing, stale or unreadable, the consequence is `UNKNOWN` and the reason is "Consequence unknown" (`CONSEQUENCE_UNKNOWN`).
  - A consequence rule names its consequence's target and environments (amended in P1a; the format is additive): `consequence.target` is a template over the action's target id (`{target.id}` or `{target.id.<group>}`; pc.github's rules use `{target.id.owner}/{target.id.repo}`), and without one the consequence is about the action's own target; `consequence.environments` is a CEL expression over the rule's facts that gives the environments a predicted consequence reaches (pc.github: the fact's `environments`). A fact a rule needs is current for at most 30 seconds, or less when the definition or the policy asks for the same fact; a fact whose object carries an `unknown` member makes the consequence `UNKNOWN` with that reason. The consequence operation is one the rule's own package defines (a virtual write such as `github.deployment.trigger`, or another of its operations); a package whose rule names any other is refused at import (amended in P1a after review, 2026-10-13).
  - **Every ref-moving operation has a rule for the ref it moves:** `github.pull.merge` (the base branch), `github.contents.write` and `github.branch.create` (their branch). Triggers are computed from the workflow files as they will be after the operation: for a merge, the pull request head's files; for a write, the files on the branch with the write applied. Any change to `.github/workflows/` or `.github/actions/` by the operation or the pull request makes the consequence `UNKNOWN`.
  - A predicted or unknown consequence operation (for example `github.deployment.trigger` to environment `production`) is evaluated as part of the action by steps 4, 7 and 8, under the same run, grants and policies. Its denials deny the action, and its requirements are added to the action's (design decision 6). A standalone merge permission never waives a production-change restriction (§43.3).
  - How P1b applies this (amended in P1b): the rules come from the pinned package version the pipeline already decodes for the definition, so replay reloads them by the same pin and the decision recording keeps their ids (pipeline version 3); `00083` needs no query of `consequence_rules`. A consequence is an action of the same run with its operation and target and no params, pinned to its definition in that version: the grant must cover it (step 4), its limits and policy rules apply (step 7), and its grant and policy requirements join the action's (step 8), each labelled with the consequence. An unknown consequence adds the hold item `CONSEQUENCE_UNKNOWN`, which the approvals of those requirements release; when no requirement applies to it, no approval could release it, so the result is `CANNOT_AUTHORIZE` `CONSEQUENCE_UNKNOWN` until its facts can be read. A rule that cannot be evaluated is `CANNOT_AUTHORIZE` `CONSEQUENCE_EVALUATION_ERROR`. The facts a consequence's definition and the policy's rules for its operation need are about the consequence's target, and step 6 reads them with the action's. A policy rule on an operation that is only ever a consequence may therefore read only facts a provider declares about that operation's target type; a policy version whose rule reads another is refused when it is created or published. pc.github's gateway reports `github.*` facts about the action's own target (the pull request or branch), never about the repository a deployment consequence acts on, so a rule on `github.deployment.trigger` cannot read `github.*` facts. A consequence is never dispatched, so nothing is reserved or counted for it: a grant or a guardrail whose budget or counter names an operation that is only ever a consequence is refused (all amended in P1b after review, 2026-10-13).
  - **Monitor mode** (amended in P1e, founder decision 2026-10-13): monitor mode stays observe-only (HR-184). On a monitor-mode route an action whose consequence is `UNKNOWN` still gets its permit, with the same reasons as enforce mode; its answer, its receipt (`would`) and the receipt's ledger entry record "HOLD: consequence unknown" (or the stricter decision the same reasons give), and one `security.consequence_unknown_dispatched` notification goes out per transaction, sent with the decision. On an enforce-mode route the same action is held.
  - Receipts list each consequence with its state and the facts digest; predicted consequences are labelled separately from authorized and confirmed effects.
- **Release controls** (P2, HR-207, decision 4):
  - two new human-only roles, `code_reviewer` and `release_approver`, which hold `approval.respond` so requirements can name them;
  - independence widened, by GitHub user id, to the pull request's author and every pull request commit's author, committer and authenticated pusher, when they are linked to users. When these cannot all be read, the requirement cannot be met (design decision 18);
  - change windows: weekly schedules in a time zone, one-off windows and freezes, per environment and optionally per repository. A requirement can need consumption inside an active window, checked by the database clock in the finalization (HR-171). An environment's name matches whatever its case, as GitHub's environment names do: a window is stored under the name in lowercase (amended in P2a after review, 2026-10-13).
- **Head-SHA binding** (P3, HR-205). The merge operation requires `sha` as a material parameter in every mapping, so the action hash, and with it the approval binding, includes it. At finalization a fresh `github.pull.head` fact must name the same head; otherwise the result is `CANNOT_AUTHORIZE` `HEAD_MOVED` and unconsumed approval requests for that pull request are superseded with a material-change explanation. Dispatch passes `sha`, so GitHub answers 409 if the head moved in between.
  - How P3a applies this (amended in P3a; the format is additive): the definition's constraint is a prerequisite binding, `binds: {member: sha, param: sha, reason: HEAD_MOVED}` on `github.pull.head`, so step 6 refuses a merge whose `sha` is not the fresh fact's with `CANNOT_AUTHORIZE` `HEAD_MOVED`, naming both (pipeline version 4). A hold of a definition with `approval.invalidate_on` records the key `<fact>[<member>]@<target type>:<target id>` of the member its prerequisite binds (for example `github.pull.head[sha]@github.pull_request:acme/payments#7`), without the connection: a moved head has moved for every connection to the repository. A key longer than the column's 300 characters is recorded as `sha256:` and its SHA-256 in hex, so it is superseded too.
  - Option B (founder decision 2026-10-13, amended in P3a; HR-030 and HR-034 amended to match): an approval binds only the fact members a prerequisite declares in `binds`, so for a merge the head SHA. Checks, reviews and `mergeable_state` are not bound: step 6 and the policy check them again when the approval is used, so a failing check still refuses an approved merge. Observation times and providers are never bound, and the display (version 2) lists a fact it binds nothing of without a value. A fact write supersedes requests only when a bound member's value changes; a fact observed again with the same values keeps them. `approval.invalidate_on` must name a prerequisite with `binds`.
  - The supersession runs inside the fact write (amended in P3b): a write that changes a fact's value supersedes every live request whose `invalidation_key` names that fact and subject, as `BINDING_CHANGED`. Each superseded request releases its hold slots and closes its entry, and its audit event names the changed key. Gateway-reported facts (G4b) must be written through the same fact store so they supersede too.
- **Merge review display** (P4, F158). The approval page and its API view show:
  - the repository and pull-request identity, the source (head) commit, the destination branch and a change summary (files, additions, deletions; the title and body as untrusted text);
  - required checks with their status and fact age, and GitHub reviews and rules as facts (decision 4);
  - each predicted or unknown consequence with the workflow and environment behind it;
  - the required reviewers, expiry and single-use scope.

  All of it is rendered from the package's approval template (HR-034).
  How P4 applies this (amended in P4): the merge review is the stored display (HR-034), rendered from pc.github's approval template and the decision's facts. The template's fields show the pull request, the head SHA and the facts `github.pull.head` (base branch, changed files, additions, deletions), `github.pull.checks`, `github.pull.reviews` and `github.branch.rules`, and every fact the decision used is listed with its provider and age. The display gains `consequences`: each predicted or unknown consequence with its environments, the workflows its facts name and, when unknown, why. The decider rules state `independent_of` and `window`. The display travels in `GetApprovalRequest`, so `ApprovalRequest` fields 21–25 stay unused. G4's facts do not carry the pull request's title and body, so they are not shown yet. The page also lists, for each fact an independent requirement names, every GitHub user id the fact lists now, from the read the independence check makes, with how it lists them and the linked user or "not linked". A list that may not name everyone (the fact is unknown, unreadable or `complete: false`, does not name its author and its pushers, or holds something other than positive GitHub user ids) says "the list of people is incomplete" and why; by the same rule as the decision, nobody then counts as independent. Since the founder decision of 2026-10-13, the lists are shown for every requirement that names the fact, independent or not; and when a requirement counts only inside a change window and a consequence is unknown or reaches no known environment, the page says first, before any button, that the action cannot be released until its facts are known.
- **GitHub package** (G1, PN-017.1). `packages/pc-github` (`pc.github` 1.0.0, signed like `pc.mock-payments`) covers:
  - `github.contents.read`, `github.pull.read`, `github.branch.create`, `github.contents.write`, `github.pull.create`, `github.pull.merge` and `github.repo.settings.update`;
  - the virtual consequence operation `github.deployment.trigger` (no mapping, never dispatched).

  Each operation has MCP mappings (the tool names of GitHub's MCP server, with reviewed descriptions and input schemas) and HTTP mappings (`api.github.com` REST routes) sharing one route id (F099). Each also declares its minimum GitHub permissions (`dispatch.credential_scope`), its facts and verifiers (the merge: the pull request reads `merged` and `merge_commit_sha`, and the base branch contains it), and the consequence rules for every ref-moving operation (`merge-triggers-deployment`, `write-triggers-deployment`, `branch-triggers-deployment`). No operation declares GitHub's `workflows` permission. Without it, a token cannot change files under `.github/workflows/`, and `github.contents.write` also refuses paths under `.github/` (`CANNOT_AUTHORIZE`), so an agent cannot rewrite the triggers it is judged by. Golden tests are the HR-124 kind.
- **GitHub simulator** (G2, decision 7). `internal/sim/github` and `pantherclaw-sim github` implement a REST subset, and `mcpsim` gains GitHub tools that call it (an opaque MCP route). The subset:
  - App JWT (RS256) verification, installation tokens honouring `repositories` and `permissions` and refusing permissions beyond the installation's, token revocation, `GET /installation/repositories`, `GET /app/installations/{id}` and org installations;
  - repositories, contents, refs and branches;
  - branch rules and protection;
  - pull requests: create, read, and merge with `sha` (409 when the head moved, 405 when not mergeable);
  - reviews, check runs, Actions workflows, environments, and deployments that move from pending to success after a delay;
  - the repository activity feed (who pushed which ref), and GitHub's rule that a write under `.github/workflows/` needs the `workflows` permission.

  Tokens are random opaque strings of about 520 characters. Every request is checked against its token's repositories and permissions and recorded for assertions. Faults: token endpoint errors and slowness, a grant wider than requested, a lost merge response.
- **App custody and per-action tokens** (G3, HR-203, HR-204, ADR-0021, decision 3). Credentials gain a kind (`static`, the M6 behaviour, or `github_app`). The gateway broker opens a `github_app` credential to sign an App JWT and mints a token per dispatch, verification read, fact read, connection test and scan lease. The token is narrowed to one repository (for a scan, to read-only `metadata` and `contents` of the repositories it lists), checked against what GitHub granted, used once and revoked. Execution receipts carry the access metadata (ADR-0021 item 5).
- **GitHub facts** (G4, decision 5). Before `Authorize`, the gateway reads the `github.*` facts that the operation's prerequisites and consequence rules name, within at most 2 seconds, with a read-only per-lease token, and reports them with `GatewayService.ReportFacts` as the connection's registered provider (HR-160):
  - `github.pull.head`: head SHA, base branch, mergeable state, change counts, whether the pull request changes `.github/workflows/` or `.github/actions/`, draft;
  - `github.pull.people`: GitHub user ids (never logins alone) of the author, of every commit's author and committer, and of every authenticated pusher of the head branch. Pushers come from the repository activity API (`GET /repos/{owner}/{repo}/activity`; G4 checks its availability for Apps). The fact is `complete: false` for a fork, more than 250 commits, or any read that failed;
  - `github.pull.reviews`: the latest review per reviewer on the head;
  - `github.pull.checks`: check runs on the head;
  - `github.branch.rules`: rules and protection on the base branch;
  - `github.repo.deploy_triggers`: the workflows that the operation starts and the environments they deploy to. They are parsed with a bounded parser from every workflow file (`.github/workflows/*.yml` and `*.yaml`) *as it will be after the operation*: the base branch's head for a merge (a pull request that changes a workflow is `unknown`), the target branch for a write. A construct it cannot evaluate, a listing it cannot read whole, or a change to `.github/workflows/` or `.github/actions/` yields `unknown`, never "none". The events evaluated are these:
    - `push`, with its branch filters. A merge pushes to its base branch.
    - `pull_request` and `pull_request_target` by their `types`. A merge starts one only with `closed` and branch filters matching the base branch. A push to a branch may synchronize a pull request from it (`synchronize` is among the default types), and is assumed to start one.
    - `workflow_dispatch`. A workflow the operation starts can raise it with GitHub's own token, so once any workflow starts, every `workflow_dispatch` workflow counts as started.
    - Events no ref move starts (`schedule`, issue and discussion events and the like) are skipped.

    Every other event (`create`, `delete`, the check, status and deployment events chained from a push, `release`, `repository_dispatch`, `workflow_run`) yields `unknown`. A workflow holding another token (a personal access token, an App's) can raise even the skipped events; that chain is not predicted (R-19). `triggered` means a started workflow deploys to a GitHub environment. One that runs without an environment is listed in `workflows` while the state stays `none`, so consequence rules key on both.
- **Organisation scan** (G5, PN-001.2, Team edition, HR-209, decision 5). `pclaw github scan` (a person holding `github.scan.run`) starts an `org_scan` lease on the gateway. The gateway lists:
  - the installation's repositories;
  - the org's App installations, when the App may read them;
  - workflow files, and the agent actions and permissions they use;
  - committed MCP configuration files (`.mcp.json`, `.cursor/mcp.json`, `.vscode/mcp.json`), with server names and commands only;
  - ruleset bypass actors.

  It submits the results through `SubmitScanFindings` with new kinds, under the scan's lease (its secret is checked). The scan run records which sources it scanned and which it could not (F450's honesty; M9 consumes the findings as routes).

  **Sources.** The server keeps the catalog: `repositories`, `workflows`, `mcp_configs`, `org_installations` and `rulesets`. Each is reported scanned, or not scanned with why, never both. A source the report leaves out is recorded as `not reported`. The extra reasons `contents`, `organization` and `findings` (submission failed, or the server dropped findings over its cap) appear under not scanned only. A source is not scanned whenever any part of it was not read: repositories past the deadline, past the first 500 or unreadable; workflow files past 20 per repository, too large, not plain files or refused by the parser; workflows whose agent use the scan cannot check (a reusable workflow, a local or Docker action, an agent CLI run directly: only the known agent actions are recognized); MCP configurations that are not strict JSON. The scan's reads end 20 seconds after its lease was claimed, so the findings and the report fit the 30-second lease (HR-190). An org scan gets three leases at most.

**Security constraints and design decisions:**
1. **The `/sdk` face (HR-201, decision 1).**
   - The gateway reads the body once (≤ 64 KiB), forwards its SHA-256 and the PAP/1 credentials for the Authority to verify (HR-021), and maps the call through the connection's pinned package's `mcp` entries.
   - On a `target_enforced` connection the gateway re-serializes the outbound request (HR-075), reports its body hash at `BeginDispatch`, and returns the request and token as `dispatch` (HR-201).
   - The ActionIR channel is `sdk`. The connection is the one in the path, never one the SDK names.
   - The canonical action and hash in the response let the SDK check what was decided. The SDK never sends an ActionIR or hash, and the face rejects members it does not know.
   - An identical resubmission reuses the action id (HR-005); a changed call under the same id is `ACTION_TAMPERED` (HR-006).
   - Monitor-mode routes answer with the hypothetical decision and `mode: monitor` (HR-184).
2. **The Agent SDK fails closed (HR-200, decision 2).**
   - At start, the integration reads `GET /sdk/{connection}` for each configured connection when it can. While it cannot, every tool it has not seen answered `OBSERVE_ONLY` is treated as mapped, so it fails closed.
   - `Bash` and `PowerShell` are decided through the local connection's `/hook` mapping (`pc.shell`). Without a configured local connection the integration refuses to start, unless the application sets `shell: "observe"`. That opt-out is explicit configuration, and every shell call is then sent to `/sdk` and recorded `OBSERVE_ONLY` (design decision 8).
   - Every other tool is sent to `/sdk/{connection}` and decided before it runs when it is mapped.
   - Any error, malformed answer or timeout means `permissionDecision: "deny"` with the reason. The integration's own deadline is shorter than the hook timeout it registers, and the hook body is wrapped so that a thrown error also denies. `ALLOW` means `allow`. `DENY` and `CANNOT_AUTHORIZE` mean `deny`.
   - A `HOLD` never runs without a later `ALLOW`, in every permission mode and whatever allow rules the application has.
     - The hook answers `ask` only where the SDK documents that `canUseTool` is then called and the pinned S6 tests prove it. The integration's `canUseTool` must be installed, and the permission mode must be on an allowlist: `default` only, until a test proves another mode. No allow rule may name the tool: any rule naming it counts as a match, wildcards included. Each condition is checked at start and per call.
     - Otherwise it answers `deny`, with the wait URL in the reason, and an identical later call resubmits.
     - If a later SDK version ran a tool after `ask` without calling `canUseTool`, the S6 tests would fail. They pin the SDK version range the integration supports.
   - `canUseTool` handles only calls whose hook result was `HOLD` (correlated by `tool_use_id`). It waits on the handle within its own deadline (HR-174's limits), resubmits the identical call, and allows only on `ALLOW` and only with the original input. It denies at its deadline and on any error. Any other call goes to the application's own callback, or the SDK's default when there is none.
   - An unmapped built-in tool (answered `OBSERVE_ONLY`) gets no decision from the hook, so the application's own permission mode applies, and the face has already recorded it `OBSERVE_ONLY`.
   - An unmapped tool that is not built in is denied unless the application sets `observeUnmapped: true` (design decision 8).
   - Subagents' tool calls go through the same hook; S6 tests it.
   - Never "ask the local user" for a PantherClaw hold (HR-186).
3. **Target verifier middleware (HR-202, decision 8).**
   - The middleware reads the body up to its limit (413 beyond it), then checks, in order: the `PAP-Action` header; the JWS (`typ`, `alg`, `kid` from the JWKS, `action_tokens` keys only); `iss`; `aud` equal to the configured connection id; lifetime; `pap.v == 1`; `bh` against the body; and the application's required `Match(request, claims)` for operation and target.
   - Only then does it insert `jti` into the `ReplayStore` (verify before insert, as HR-090). The handler then gets the claims from the context and the body restored.
   - A store keeps each `jti` at least until `exp` plus the 5-second skew. The middleware refuses (503) whenever the store cannot record: unreachable, full, evicting early, or restarted without its entries. The memory store refuses new tokens rather than evict unexpired ones.
   - The JWKS is fetched over TLS from configuration, cached at most 15 minutes, and refetched at most once a minute for an unknown `kid`. An unavailable JWKS or store refuses (503); nothing fails open.
   - Every refusal is 401 (409 for a replay) with a problem document naming a code: `missing`, `bad_signature`, `wrong_issuer`, `wrong_audience`, `expired`, `body_mismatch`, `operation_mismatch`, `replayed`, `store_unavailable`.
   - **Replay stores:** the in-memory store is for one replica and says so (`Shared() == false`). The `database/sql` store keeps `pap_action_tokens_seen (aud, jti, expires_at, primary key (aud, jti))`, inserts with `ON CONFLICT DO NOTHING` (PostgreSQL and SQLite dialects; others implement the interface) and purges expired rows.
   - What a target declares about its store is never evidence (F460). M9 counts a target as verifying only after a passing `target_verifier` connection test (C2) no older than the `ENFORCED` lifetime, and a replay sent to another replica is one of that test's requests when the target declares several (amended in C2i: no package or connection declares a target's replicas yet, so the gateway sends all four requests to the connection's base URL; the replay to a second replica comes with that declaration, a follow-up).
4. **GitHub App custody and tokens (HR-203, HR-204, ADR-0021, decision 3).**
   - The gateway mints a token for every dispatch, verification read, fact read, connection test and scan lease, never shares one between them, and revokes it after use, whatever the outcome.
   - Each token is scoped to its task: a dispatch to exactly the action's repository and the operation's declared permissions; a verification or fact read to that repository, read-only; a connection test to the package's `test` read; a scan to read-only metadata and contents of the repositories it lists.
   - A grant wider than requested is revoked and the dispatch refused (`CREDENTIAL_SCOPE_MISMATCH`).
   - Tokens are opaque: no parsing, egress headers allow at least 4 KiB, and secret-echo redaction covers the exact token bytes.
   - The repository owner must equal the connection's installation account; anything else is `CANNOT_AUTHORIZE` `WRONG_ACCOUNT`.
   - Requests send `X-GitHub-Api-Version: 2022-11-28` (design decision 4).
5. **GitHub facts (decision 5, HR-160).**
   - The gateway is registered as the fact provider of its GitHub connections, for exactly the fact names its package declares and only for targets of that connection. A fact a gateway reports for another connection or name is refused.
   - Reads happen before `Authorize`, bounded by `github.fact_timeout`. A read that fails reports nothing, so the pipeline sees the fact missing: a prerequisite then gives `CANNOT_AUTHORIZE` (HR-160), and a consequence fact gives `HOLD` "Consequence unknown" (HR-206).
   - The workflow parser accepts YAML with the M4 restrictions (no anchors, aliases, merge keys or tags; HR-100), evaluates `on.push.branches` and `branches-ignore` patterns and `jobs.*.environment`, and marks the fact `unknown` with a reason for any expression in those fields, any reusable or remote workflow call, `workflow_run` and `repository_dispatch` triggers, and files beyond the limits.
   - The parser reads the workflow files as they will be after the operation: for a merge, at the pull request's head; for a contents write or a branch creation, at the target branch with the write applied. A pull request or operation that changes anything under `.github/workflows/` or `.github/actions/` makes the fact `unknown`. As a backstop, PantherClaw's tokens never hold GitHub's `workflows` permission, and `github.contents.write` refuses `.github/` paths.
6. **Consequences (HR-206, decision 6).**
   - An `UNKNOWN` consequence is treated as if it were predicted. The result is at least `HOLD`, and its requirements are the union of the requirements of every consequence the rule could produce (for the GitHub rule, a `release_approver` inside a change window), so a `code_reviewer` alone can never release it. An unknown deployment stays fail-closed (founder decision 2026-10-13): a `release_approver` counts only inside a change window for a known environment (P2e), so while the consequence is unknown no approval releases it. It stays held until its facts are known, and the approval page says so before anyone approves. The reason "Consequence unknown" is shown, and a `DENY` from any part still wins. How the union is reached (amended in P1d after review, 2026-10-13): for an `UNKNOWN` consequence, every policy `REQUIRE_APPROVAL` and `REQUIRE_STEP_UP` rule that covers its operation applies, whatever its condition or environment scope, so the hold asks for at least what any outcome would; `FORBID` and the other rules are evaluated as for any action.
   - Policy sees `consequence.unknown` and may forbid instead (§43.3). It can never make the consequence safe. (Amended in P1d: rules read `consequence` with `present`, `rule`, `state`, `unknown` and `environments`; for the action itself `present` is false. A requirement a rule adds only for predicted consequences never releases an unknown one.)
   - A CEL error in a rule's `when` is `CANNOT_AUTHORIZE` (HR-040), never "not triggered".
   - Prerequisite facts keep HR-160's `CANNOT_AUTHORIZE`; only consequence facts hold.
7. **Release controls (HR-207, decision 4).**
   - **Independence** (HR-170 with `independent: true`) also excludes, by GitHub user id when the id is linked to a user, everyone in `github.pull.people`: the pull request's author, every commit's author and committer, and every authenticated pusher of the head branch.
     - Commit author and committer are what the pusher's git configuration claims (GitHub attributes them by email), so the authenticated pusher is the binding part. This stops a reviewer from pushing a commit, early or late, to someone else's pull request and then approving it.
     - When `github.pull.people` is `complete: false` (a fork, more than 250 commits, an unreadable activity feed), the review requirement cannot be met: the merge is `CANNOT_AUTHORIZE` `AUTHORSHIP_UNKNOWN` (retryable) and the page says why (design decision 18).
     - Links live in `github_identities` and are audited. An unlinked person is shown as "not linked".
     - **Verified links (amended in P2f, founder decision 2026-10-13; replaces design decision 14):**
       - A person links their own GitHub account only by proving it: GitHub App user authorization through the device flow (`pclaw github link`). The server asks GitHub which account the sign-in's user access token belongs to, links it to the caller with the time it was proved (`verified_at`), and never stores the token. Nobody creates, changes or removes a link to their own user any other way, and nobody links someone else; a person holding `github.identity.manage` can only unlink other people. Every link change is audited and notified (`security.github_identity_linked` and `_unlinked`). A sign-in that proves an account linked to someone else, or unlinks one not linked to the caller, is refused and audited (`github.identity_link_refused`). Everyone who ever proved a link to a GitHub user id stays excluded as independent of the people the fact lists, after an unlink, a relink to someone else or a manager's unlink (`github_identity_history` in `00083`, insert-only; amended after review, 2026-10-13).
       - An approver of a requirement independent of a GitHub people fact needs such a proved link; without one they are refused (`GITHUB_NOT_LINKED`), because nobody could tell whether they are among the people the fact lists.
       - **Unlinked people (founder decision 2026-10-13, P2f-d):** while anyone the fact lists (the author, commit authors and committers, and pushers) is a person linked to nobody in the org, every approval naming the fact is refused (`GITHUB_PEOPLE_NOT_LINKED`): the approver could be that person under another account. It lasts until they link with `pclaw github link`. An account that is not a person does not count: one the fact lists in its optional `bots` member (GitHub ids whose account type is not `User`), or one an identity manager registered with `pclaw github exemption add` (`github_exemptions` in `00083`, `GitHubService.ExemptAccount`, `RemoveExemption` and `ListExemptions`; each change audited and notified, `security.github_account_exempted` and `security.github_exemption_removed`). An account someone ever linked as their own is a person and cannot be exempted (`GITHUB_ACCOUNT_IS_A_PERSON`), and the identity manager who exempted an account is excluded from approving pull requests that list it (after review, 2026-10-13). The approval page marks each listed account as linked, not linked, a bot or exempted, and says when approvals are refused for it. Until pc.github's reader fills `bots`, a GitHub App bot that authored, committed or pushed must be exempted.
       - Independence uses the links at the request's creation and at approval: the users linked to the listed people when the request was created are kept (`approval_request_linked_people`) and stay excluded, so unlinking, approving and linking again never works. The launcher, represented principal and agent owners stay excluded as before.
       - How P2f-b applies this: the server's `github` configuration (`client_id` and `client_secret_file` of a dedicated sign-in App, with no permissions, installed nowhere, whose device flow is enabled; `web_url` and `api_url`, GitHub's own by default, `https://HOST/api/v3` for GitHub Enterprise Server) turns sign-in on. `GitHubService.GetSignIn` gives pclaw the client id and web origin; `pclaw github link` and `pclaw github unlink` run the device flow, show the code only with a sign-in page on that origin, and send the token to `ProveIdentity`. The server asks GitHub as the sign-in App (`POST /applications/{client_id}/token` with the client secret), which names the account only for a token that App issued, so a personal access token or another App's token proves nothing; it then revokes the token (`DELETE`). A person's account only. The GitHub simulator serves the device flow and those calls (`RegisterSignInApp`, `AuthorizeDevice`, `DenyDevice`, `SignInAs`). (Amended after review, 2026-10-13: the sign-in App was the App that merges, and `GET /user` accepted any token.)
     - How P2d applies this (amended in P2d; the format is additive): the merge's approval template names the fact, `independent_of: github.pull.people`. Every approval of the action and of its consequences, whatever its role and whether or not it is independent, carries `independent_of` in its stored requirement and binding (founder decision 2026-10-13; before, only independent ones did). When a person responds, the approvals side reads that fact about the held action's target as it is then, so a commit pushed after the hold excludes its pusher too, and excludes the users linked to the GitHub ids it lists (`author`, `authors`, `committers`, `pushers`). A fact that is missing or `complete: false` leaves nobody independent (`AUTHORSHIP_UNKNOWN`). After review (2026-10-13): a `code_reviewer` or `release_approver` requirement is independent by its role, whatever its `independent` flag, so no requirement can let the author or a pusher approve; and a fact counts as complete only when it also names its `author` and a `pushers` list, every id a positive integer, so an id that does not decode never drops someone from the exclusion.
   - **Distinct people:** the reviewer and the release approver of one action must be different people (design decision 7). (P2d: already so, because one person counts once per request, HR-035.)
   - **Change windows:** a requirement with `window: true` is satisfied only when the finalization that consumes it runs inside an active window for the consequence's environment, by the database clock. A freeze overrides windows. No configured window means no window, so the hold stays until its deadline.
     - How P2e applies this (amended in P2e): `window: true` may sit on any grant or policy approval requirement and joins its stored requirement and binding; a `release_approver` requirement has it by its role, whatever it says (after review, 2026-10-13). Before the finalization consumes such an approval, it decides every environment of the action's predicted or unknown consequences, with the consequence target as the repository when it names one. Any environment not `OPEN` (`CLOSED`, `FROZEN`, `NO_WINDOW`), or a consequence with no known environment, gives `CANNOT_AUTHORIZE` `CHANGE_WINDOW_CLOSED`, naming each. The approval stays `APPROVED` until its consume-by time, so a resubmission inside the window can use it.
   - GitHub reviews and branch rules are facts. Policy may require them (for example "two approving GitHub reviews on the head"), but a GitHub approval never stands in for the PantherClaw approval.
8. **Head SHA (HR-205).**
   - The material parameter `sha` is required in both mappings. In the MCP mapping it comes from the tool's head-SHA argument (`expectedHeadSha` in GitHub's MCP server's `merge_pull_request`: optional upstream, required by the reviewed package; G1 checks the current schema). In the HTTP mapping it comes from the body's `sha`. A missing value is `CANNOT_AUTHORIZE` (HR-103). The simulator answers 409 when it differs from the head.
   - `github.pull.head` is a prerequisite with a 30-second maximum age, and the definition's constraint requires `params.sha == facts["github.pull.head"].sha`. A mismatch is `CANNOT_AUTHORIZE` `HEAD_MOVED` (retryable).
   - The fact's ingestion supersedes every unconsumed request with the same `invalidation_key` whose bound SHA differs.
   - Dispatch sends `sha`, and GitHub's 409 is a recorded `failed` outcome.
9. **`pclaw init` (HR-208).**
   - Every changed file is first copied to `<file>.pclaw-backup-<UTC timestamp>`. The new content goes to a temporary file in the same directory, then synced and renamed.
   - JSON is parsed strictly and rewritten keeping every existing member and its order. Only entries are added; existing `permissions.deny`, hooks and server entries are never removed or changed.
   - For a governed MCP server, `init` leaves the original entry as it is, adds a governed entry (through the gateway's `/mcp` face or `pclaw mcp proxy`) and adds `permissions.deny: ["mcp__<original>__*"]`, so the original cannot be used. Adding a deny rule only strengthens.
   - A secret found in configuration (an MCP server's environment token, for example) is reported as a route and never copied or written.
   - The unified diff is shown, and nothing is written without confirmation or `--yes`; `--dry-run` writes nothing.
   - Managed settings that disable hooks (for example `disableAllHooks`, or `allowManagedHooksOnly` without PantherClaw's hook) or exclude PantherClaw's MCP server make `init` exit non-zero and explain why. It never edits managed settings.
10. **Org scan (HR-209).**
    - The scan reads repository metadata, the listed workflow and MCP configuration files at their default branch, App installations and ruleset bypass actors. It never calls the Actions secrets API and never reads other file contents. Configuration files often hold literal tokens in environment values, headers or arguments, so the parser keeps only names (servers, environment variables, headers, the command's base name) and drops every value and argument in memory before a finding is built.
    - Findings are untrusted attributes (the existing `ScanFinding` limits: at most 16, each at most 256 bytes; HR-148), become discoveries or M9 route candidates, and never grant authority.
    - Sources it could not read (for example org installations without the needed App permission) are recorded as "not scanned", never as "none found".

**Founder decisions (answered 2026-10-11, the recommended option each time; recorded, not re-asked):**

1. A new gateway face, `/sdk/{connection}`. The SDK sends the raw tool call with a PAP/1 proof and the gateway maps it through the signed package. The SDK canonicaliser is used only to check hashes and to resubmit.
2. The Agent SDK integration enforces through the SDK `PreToolUse` hook, which fires in every permission mode, including bypass.
   - `canUseTool` never fires for auto-approved calls, so it only handles HOLD→wait.
   - Mapped tools fail closed when PantherClaw is unreachable.
   - Unmapped built-in tools are allowed and recorded `OBSERVE_ONLY`.
   - Everything is labelled `PARTIAL`.
3. The GitHub App private key is sealed to the gateway.
   - For each authorized action the gateway mints an installation token scoped to one repository and the operation's minimum declared permissions, then revokes it after dispatch.
   - The agent never sees the token.
   - Tokens are opaque: GitHub's stateless `ghs_` tokens are about 520 characters.
4. The PantherClaw approval is authoritative.
   - A merge is held until an independent person with the new role `code_reviewer` approves, bound to the head SHA; a new commit invalidates the approval.
   - A deployment consequence needs a `release_approver` and a change window.
   - GitHub reviews and rulesets are read as facts, shown (F158), and may be required by policy.
5. The gateway reads branch rules, reviews and workflows through the App. The org scan runs in the gateway and submits through `SubmitScanFindings` with new kinds.
6. Stored F405 consequence rules are evaluated in the pipeline. A fact that cannot be read means `HOLD` "Consequence unknown", never `ALLOW`.
7. A GitHub simulator (a REST subset plus MCP tools) backs all automated tests. Live GitHub tests are a manual opt-in task against a sandbox org that the founder creates.
8. Dependencies:
   - The Go SDK is a separate module that uses only the standard library.
   - Python adds only `cryptography`.
   - TypeScript has zero runtime dependencies, with the Agent SDK as an optional peer.
   - The target verifier has a `ReplayStore` interface with in-memory and `database/sql` implementations. Multi-replica targets must use the shared store.

**Design decisions in this brief, for the founder's confirmation:**
1. **F335 stays in M13 but is measured at the preview.** The 30-minute onboarding target for Claude Code is measured with `pclaw init` and recorded at the v0.1.0 exit; the feature row keeps M13.

6. **An unknown consequence applies the consequence's requirements as if it were predicted**: at least `HOLD`, with the union of the requirements of every consequence the rule could produce, labelled "Consequence unknown", and a `DENY` still wins. Policy can forbid on it but never clear it. Facts that a consequence rule needs hold (HR-206); prerequisite facts keep HR-160's `CANNOT_AUTHORIZE`.
7. **The reviewer and the release approver of one action are different people.** This is stronger than HR-170's "one response counts toward one requirement".
8. **The Agent SDK sorts tools into three classes** (security constraint 2):
   - tools of MCP servers served by the gateway's `/mcp` face pass, because the gateway enforces them;
   - `Bash` and `PowerShell` are decided through `/hook` (`pc.shell`), so a shell command such as `gh pr merge` is decided as `shell.command.run` under the same policies as M6's hook. The C4 template forbids merge and push commands in the shell, and in M9's sandbox that route is closed outright. Without a local connection the integration refuses to start unless `shell: "observe"` is set explicitly;
   - every other tool goes to `/sdk`: decided when mapped; observed under the application's own permission mode when it is an unmapped built-in; denied when it is unmapped and not built in, unless `observeUnmapped: true`.
9. **`/sdk` serves only `agent_held` and `target_enforced` connections.**
   - For `pantherclaw_held` connections, agents use the MCP or HTTP face, where the gateway dispatches with the custody credential (HR-186).
   - On a `target_enforced` connection the gateway re-serializes the outbound request from the ActionIR and the definition's template (HR-075) and reports its body hash at `BeginDispatch`, so the action token binds exactly the bytes the SDK must send.
   - The outcome is still `delegated`, but the execution receipt's access mode is `target_enforced` rather than `agent_held`, because the target refuses anything without the token (HR-024).
   - HR-186's text ("recorded with outcome `delegated`, access mode `agent_held`, and `PARTIAL` assurance") gains the clause "or `target_enforced` when the connection's target verifies action tokens (HR-024)" once the founder confirms this decision. Until then C1 records `agent_held` for both.
10. **The agent supplies the head SHA**, and PantherClaw checks it against a fresh fact at finalization. The gateway does not inject it. This keeps the mapping a pure function of the call, and makes GitHub's 409 the backstop.
11. **Stored consequence rules are evaluated in every edition.** Skipping them would let a Community merge allow a production deployment unseen. The rest of F405–F413 (derivation chains, the consequence graph) stays Team and post-1.0.
12. **GitHub facts are read synchronously by the gateway before `Authorize`**, which adds at most 2 seconds to GitHub actions that need them, instead of webhooks or a polling job. Webhooks are a follow-up.
13. **`task check` stays Go-only.** SDK slices and the M8 exit also run `task sdk:check`, which needs `uv` and `pnpm` (Day-0 item 5). `tools/traceability` counts `test_HR###_` (Python) and `TestHR###_` (TypeScript) test names, so HR-200 can be traced to the integration's own tests.
14. **GitHub identities are linked by a person** holding `github.identity.manage`, not through GitHub OAuth, in M8. *Superseded by the founder on 2026-10-13 (P2f):* a person links only their own account, proved by GitHub sign-in; see Release controls.
15. **The workflow parser is deliberately small.** It understands push triggers and environments only; everything else makes the fact `unknown`, which holds.
16. **Migration order across tracks.** Tracks merge their migration slices in number order (G `00080`–`00081`, then P `00082`–`00083`, then C `00084`), or renumber within their own range before the next one merges, because goose refuses an older version after a newer one.
17. **HR-024 is split across M8 and M9.** Its target-verifier part is tested in M8 (`TestHR024_*` in track S, slice S3) and its `PARTIAL`-labelling part in M9 (track A, slice A3). The MS column stays "M8/M9", so the traceability check expects a `TestHR024_*` test from M8 on.
18. **Unknown authorship fails closed.** When the pull request's authors, committers or authenticated pushers cannot all be read (a fork, more than 250 commits, an unreadable activity feed), the review requirement cannot be met: the merge is `CANNOT_AUTHORIZE` `AUTHORSHIP_UNKNOWN` until they can be read. The alternative was to require a second independent reviewer, which still lets a pusher be one of the two.
19. **The `/sdk` wire contract is the one C1 implements, with the `dispatch` member HR-201 requires** (amended in #244; m8-sdk's proposal v1 with amendment 1 was withdrawn when the brief fixed the contract, and both tracks then agreed on C1's shape, steward note N17).
    - The path is `POST /sdk/{connection}` and the body `{tool, server, input, tool_use_id}` of at most 64 KiB, the MCP tool named `mcp__<server>__<name>`.
    - The answer carries `decision` (`allow`, `hold` or `deny`), the action's id, hash and canonical form, a `wait` shaped like the server's wait info, and `dispatch` on target-enforced connections.
    - Built-in tools are answered `allow`, `OBSERVE_ONLY`; unmapped MCP tools are denied. Waits use the server's existing endpoints.
    - Raw HTTP requests from SDK applications use the gateway's HTTP face, not `/sdk`.
    - `sdk/conformance/sdk_face.json` (S1) fixes it. A change needs m8-sdk, m8-gateway-init and this brief.

**Residual risks** (added to THREAT_MODEL §8 by this brief):

- **R-19:** consequences that GitHub does not show (an external CD system watching a branch, chained or remote triggers) are not predicted unless a rule names them. Constructs the parser sees but cannot evaluate hold.

- **The §43 scenario on the simulator** (`TestE2E_M8_CodingToProduction`). The agent holds only its workload key. The gateway holds the App, mints a token per action and reads GitHub's facts before each decision. The test checks the following:
  - Reading, branching, writing a file and opening a pull request are allowed.
  - The merge is held (`REQUIRE_APPROVAL`) for an independent `code_reviewer` and, because a workflow deploys `main` to `production` on push, for a `release_approver`. The decision and its reasons are the same over MCP (`merge_pull_request` on `/mcp/github`) and over REST (`/github`).
  - Both approve with WebAuthn security keys. Outside a change window the release approval does not count (`CHANGE_WINDOW_CLOSED`).
  - A new commit, pushed by someone else, voids the approval. With the change window already open, the merge at the old head is refused for `HEAD_MOVED`, and the approved request ends `SUPERSEDED` (`BINDING_CHANGED`).
  - An approval refused to a person linked to nobody: while the pusher of the new commit is not linked, the reviewer cannot approve (`GITHUB_PEOPLE_NOT_LINKED`, shown in `pclaw approval get`). Once the pusher is linked, both approve again.
  - Inside a change window the merge runs once, at the approved head. GitHub's acceptance (`PC-Outcome: ACCEPTED`) is reported apart from the effect, which the verifier then confirms (`CONFIRMED`).
  - The verifier confirmed the merge commit, which is now the base branch's head. Confirming it opened the deployment's own consequence transaction, `PROPAGATION_PENDING` until GitHub reported the deployment successful, then `CONFIRMED` (W1c). The merge's token named exactly one repository and the merge's permissions (`contents: write`, `metadata: read`), and that token was revoked after the merge. Every write ran with a token of its own, and every token the gateway minted, for actions and for fact reads, was revoked. The simulator started one production deployment from the merge commit.
