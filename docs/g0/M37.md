### G0 — M37 — Ecosystem: publishers, signed bundles, revocation and a listing-only marketplace — 2026-11-05

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M37 branches and, at the end of the milestone, in an exit status section. M37 is code-only like M30–M36: every stream codes on pushed branches first, and testing (the HR and T rows below) comes later.

**Purpose:** people outside the PantherClaw project can publish content for PantherClaw, and an org can use it without trusting anyone it did not choose ([ADR-0064](../adr/0064-publishers-and-bundles.md)). A publisher signs a bundle of data (tool packages with their OpenAPI specs, detection rules, playbooks, fact provider declarations and channel templates) with its own key. An org admin pins that key and confirms the pin with a security key; only then does a bundle from that publisher install, and it installs as drafts that the org reviews and signs as before. A revoked publisher key or bundle stops being used at once. A static marketplace lists publishers and their bundles and vouches for nobody.

**Founder decisions (2026-11-05, all recommended):**
- FQ37-1: an org admin pins each publisher key with a security-key step-up before any of its bundles install. The marketplace only lists and vouches for nobody.
- FQ37-2: bundles are data only, never code. Nothing in a bundle runs as code on the server or gateway, and each install still goes through the org signing step (FD8).
- FQ37-3: a revoked publisher or bundle stops being used at once. Its packages refuse or hold, its detections and playbooks turn off, and admins get an alert; installing a fixed version resumes.

**Coordinator decisions:**
- **D1080 Names and the bundle format.** A publisher id matches `^[a-z][a-z0-9-]{2,31}$`, and every item in its bundles is named `ext.<publisher>.<rest>`; `pc.` and `org.` names and any other publisher's namespace are refused. A bundle is one `.pcbundle` zip with no directory outside its root: `bundle.json` (spec `pc-bundle/1`, publisher, name `ext.<publisher>.<slug>`, semver version, title, summary, items with kind, name, path, sha256 and size), `bundle.jws` (a compact JWS over the exact `bundle.json` bytes: EdDSA, typ `pc-bundle+jwt`, kid `publisher-<publisher>-<thumb22>`, claims sha256, publisher, name, version, iat and exp at most 400 days later) and the item files under `items/<kind>/<file>`. At most 64 items, 1 MiB per item and 8 MiB in all; strict decoding refuses unknown fields. The item kinds are a closed list of data (FQ37-2): `tool_package` (a `package.yaml`, optionally with an `openapi` simulator over a bundled `openapi_spec`, the only simulator allowed), `openapi_spec`, `detection_rule` (custom rule YAML, id `ext.<publisher>.…`), `playbook` (an automation definition, closed step catalog), `facts_declaration` (a provider declaration with no reader) and `channel_template` (an existing channel kind with non-secret fields only). Never executables, scripts, WASM, binaries, symlinks or paths outside `items/`. `internal/bundles/format` holds `Decode` and `Verify`, used by pclaw and the server alike.
- **D1081 Publisher key pins (FQ37-1).** `pc.publisher_pins` (00410): the raw Ed25519 key, its hex SHA-256 fingerprint, allowed kinds (empty means all), an optional https `revocations_url`, and PENDING, ACTIVE or REVOKED (UNPINNED, COMPROMISED or PUBLISHER_REVOKED) with a guard trigger on the transitions. `PinPublisherKey` creates a PENDING pin; activation happens only on the core page `/integrations/publisher-pins/{id}/confirm` with a WebAuthn step-up, and `ActivatePublisherPin` over RPC always answers STEP_UP_REQUIRED. Permissions: `publisher.manage` (people only; Security Admin and Org Admin), `bundle.install` (Org Admin, Security Admin) and `bundle.read` (those and Auditor). Audit `publisher.pin_created`, `publisher.pin_activated`, `publisher.pin_revoked`. The mechanism is Community; each item kind keeps its own edition gate.
- **D1082 Install (FD8, FQ37-2).** `InstallBundle` (at most 8 MiB, `bundle.install`, a person signed in as themselves) decodes and verifies the bundle against the org's ACTIVE pins for that publisher and their allowed kinds, refuses a lower version than the highest installed (ROLLBACK) and the same version with another digest (EQUIVOCATION), and hands each item to its kind's existing draft path: a tool package becomes a DRAFT package like the M31 OpenAPI importer's, reviewed and org-signed; a detection rule a DRAFT custom rule; a playbook a DRAFT automation; a facts declaration a DRAFT provider declaration, or a TEMPLATE record; a channel template a TEMPLATE record only. Nothing activates. `pc.bundle_installs`, `pc.bundle_items` and `pc.bundle_state` (00411). Audit `bundle.installed` and `bundle.install_failed`.
- **D1083 Revocation (FQ37-3).** An admin revokes a pin as COMPROMISED or revokes an install; a publisher signs a revocation statement (typ `pc-bundle-revocation+jwt`, scope KEY or BUNDLE) with any key of that publisher the org ever pinned, submitted with `SubmitRevocation` or fetched daily from each ACTIVE pin's `revocations_url` through the egress client (https, 64 KiB, no redirects). `pc.bundle_revocations` (00412). In one transaction every affected install and item turns REVOKED, its package versions are quarantined as for a compromised org key, its custom rules are disabled and its automations paused. Audit and notification `bundle.revoked`, and the built-in alert-only detection `pc.bundles.revoked` (HIGH). Installing a higher version that is not revoked resumes.
- **D1084 SDK in pclaw.** `pclaw publisher key create --publisher ID --out FILE [--passphrase-file FILE]` writes an Ed25519 key file (0600) and prints the kid and fingerprint. **D1084a:** it mirrors `pclaw package-key create`: the key is written through `rootkey.Encode` and `rootkey.WriteNew` with the purpose `publisher` (`rootkey.PurposePublisher`), encrypted when a passphrase of at least `rootkey.MinPassphrase` characters is given, plus a `.pub` file holding the public JWK; `pclaw bundle sign` takes `--key FILE [--passphrase-file FILE]` like `pclaw package sign`. `pclaw bundle init|lint|build|sign|verify|inspect` work offline: lint and inspect only decode, build zips, sign writes `bundle.jws`, verify checks against a given public key or fingerprint. `pclaw bundle install FILE` uploads a bundle; `pclaw publisher pin --publisher ID --key-file FILE|--fingerprint HEX` creates a pending pin and prints the confirm link. Guide [publishing.md](../extensions/publishing.md) and the example bundle `examples/bundles/ext.example.starter/`.
- **D1085 Marketplace.** `tools/marketplace` (tools module, nothing from `internal/`) renders `dist/marketplace` with `task marketplace:build` from a Hub build directory and the publisher listings in `marketplace/listings/<publisher>.json`: static HTML and CSS, no JavaScript. Every page says a listing is not an endorsement and that installing requires pinning the publisher's key, and shows digests, key fingerprints and the `pclaw publisher pin` and `pclaw bundle install` commands. No payments, no install button; hosting is Phase C.
- **D1086 Docs and numbers** as in this brief. **D1087 Streams** as in the table above; code-only, both in parallel.

**Threat map:** AML.T0010 (AI Supply Chain Compromise) and T1195 (Supply Chain Compromise) are already mapped through their sub-techniques (AML.T0010.005, T1195.001), so neither is in the "No PantherClaw control yet" list and the map is unchanged.

**Out of scope:** bundle items that run code (simulators other than the data-driven OpenAPI one, fact readers, channel kinds), install buttons, payments or ranking in the marketplace, hosting the marketplace (Phase C), automatic trust of a publisher across orgs, and publisher accounts on PantherClaw's side.

**Security constraints.** Fail closed: no bundle installs until a person confirmed the publisher's pin with a security key, every install is checked against that pin, its allowed kinds, the digests and the namespace, and a lower or equivocating version is refused. A bundle is data: lint, build and install decode it and never execute it, and an install creates drafts only, each reviewed and signed by the org. Revocation stops use at once and alerts. The marketplace lists and vouches for nobody. Wording follows HR-681's list in code, CLI and docs.
