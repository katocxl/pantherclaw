**Purpose:** today a policy version goes from draft straight to published, and the published version decides every agent's actions at once. Nothing checks that a version was tested, nothing shows what it will change, and one person can loosen it. M11.1 makes policy changes staged and reviewable. A version advances draft → validated → tested → published, and the publication gate re-runs validation and the version's own scenario tests (with mutation testing, HR-044) in the publish call. A classifier compares the new version with the published one: a tightening is published by one publisher; anything that is not provably tighter needs confirmations with security keys from two people when the organization has two publishers. Before a version is enforced everywhere, a simulation replays it over recorded decisions, a shadow rollout replays live traffic without enforcing anything, and a pilot enforces it for named cohorts of agents first, with a status per agent. A rollback keeps emergency rules, and temporary exceptions waive one marked rule for one agent, at most for 30 days. Three task templates ship with tests. In product terms this is Guardrails' policy lifecycle ([PRODUCT.md](../PRODUCT.md)).

**Scope (planned):**
- **Draft-first versioning** (S1b; F184, F199). States DRAFT → VALIDATED → TESTED → PUBLISHED → SUPERSEDED, each a conditional update, and a content digest per version.

- **Bundle additions** (S1a, `internal/policy/domain`). `Rule.Exceptable bool` (`json:"exceptable,omitzero"`), `Rule.Emergency bool` (`json:"emergency,omitzero"`; refused on ANNOTATE rules, design decision 4) and `Bundle.Tests []TestCase` (`json:"tests,omitzero"`). `ContentDigest(b)` is the SHA-256 of the RFC 8785 form ([ADR-0011](../adr/0011-strict-json-canonicalization.md)) of `{"id","rules","tests"}` (the version is excluded); `RuleDigest(r)` is the SHA-256 of the rule's canonical form. Validation: at most 200 tests, unique ids matching `^[a-z][a-z0-9-]{0,63}$`.
- **The classifier** (S1a, `internal/policy/domain/diff.go`). `Compare(base, next *Bundle) Diff` (base nil means no policy: every rule is ADDED) returns one `Change{RuleID, Kind ADDED|REMOVED|CHANGED, Field, Before, After, Direction, Sentence}` per change, with a direction TIGHTER, LOOSER, UNKNOWN or NEUTRAL, matched by rule id:
  - adding a rule that is not ANNOTATE is TIGHTER and removing one is LOOSER; ANNOTATE rules, `summary` and `reason` text, tests and labels are NEUTRAL;
  - operations and environments: a superset is TIGHTER, a subset LOOSER, anything else UNKNOWN (empty means all, the widest); any textual change of `when` is UNKNOWN;
  - kind (design decision 23): only a change to FORBID is TIGHTER (FORBID denies every action it matches, so the requirement or constraint fields it drops do not count as changes); FORBID → any other kind is LOOSER; every other kind change (CONSTRAIN ↔ REQUIRE_APPROVAL or REQUIRE_STEP_UP, REQUIRE_APPROVAL ↔ REQUIRE_STEP_UP) is UNKNOWN, because a CONSTRAIN violation is a DENY while a REQUIRE_* match is a hold an approver can release;
  - constraints: a lower `amount_max` or `count_max` (same parameter and currency) is TIGHTER and a higher one LOOSER; a smaller allowed, target or destination set is TIGHTER and a larger one LOOSER; a change of parameter, currency or constraint kind, or any other set change, is UNKNOWN;
  - a higher verify level, more approvals, independence or a change window switched on, a shorter deadline, facts added or a lower `max_age` are TIGHTER, and the reverse LOOSER; a change of approval role or of step-up subject or method is UNKNOWN;
  - `exceptable` false → true is LOOSER and true → false TIGHTER; `emergency` true → false is LOOSER and false → true TIGHTER.

  `Diff.Direction` is TIGHTER when every change is TIGHTER or NEUTRAL and at least one is TIGHTER; NEUTRAL when all are NEUTRAL; otherwise LOOSER when any change is LOOSER, else UNKNOWN. `Loosens()` is true for LOOSER and UNKNOWN. Sentences are plain, for example "Rule hold-large-refunds: approval threshold 50.00 USD → 100.00 USD (looser)".

**Security constraints and design decisions:**
1. **States** (S1b, HR-230, F184). DRAFT → VALIDATED (validation passed with the current digests) → TESTED (tests passed) → PUBLISHED → SUPERSEDED, each a conditional update (HR-004). VALIDATED and TESTED never go back; a stale result makes the publish call re-run them. The store always sets the content digest on insert, so a version from before 00110 can never be published again; an organization's currently published pre-00110 version stays published until a new one supersedes it.
2. **Bundle additions** (S1a). `exceptable` and `emergency` per rule, `tests` per bundle, the content and rule digests, as in "Contracts".
3. **The classifier** (S1a). As in "Contracts", with an exhaustive table test. A change it cannot prove tighter counts as loosening.
4. **Emergency carry-forward** (S1a, S1b; HR-236). A rule with the field `emergency: true` is an emergency rule; validation refuses the field on ANNOTATE rules, and labels stay ANNOTATE-only as today. `CarryEmergency(current, target)` returns the target plus every emergency rule of the current version (replacing a rule of the same id) and the carried ids. A rollback always carries them. Publishing a version that drops or changes an emergency rule of the published version is LOOSER and needs the publisher to hold `incident.respond` as well as the confirmations of decision 11.
5. **Decision categories** (S1a, `internal/authority/replay/classify.go`). Severity ALLOW 0 < ALLOW_WITH_OBLIGATIONS 1 < REQUIRE_STEP_UP 2 < REQUIRE_APPROVAL 3 < DENY 4 = CANNOT_AUTHORIZE 4. `Classify(before, after, beforeReason, afterReason)`: same decision and reason → UNCHANGED; higher severity → NEWLY_DENIED, NEWLY_HELD or NEWLY_CONSTRAINED by the new decision; lower severity → NEWLY_ALLOWED (expanded exposure, F189); same severity with another decision or reason → REASON_CHANGED. Callers mark incomplete replays UNEVALUABLE. Used by shadow and simulation.
6. **The publication gate** (S1b; HR-230, F1). `PublishPolicyVersion` (human, `policy.publish`) loads the version; re-runs validation and tests with the current definitions and catalog in the call and records both rows; refuses with `POLICY_VALIDATION_FAILED` or `POLICY_TESTS_FAILED` (findings and failing cases in the error details), leaving the state unchanged; advances the state as each passes; compares with the published version. A version that does not loosen is published in one transaction with the audit event, by an update that requires state TESTED, the same content digest and a passing test run of that digest. A loosening creates a PUBLISH change request with the published version as its base, returns it, and leaves the version TESTED. Without a validator or test runner the publish is refused (fail closed). The same gate runs on every path that makes a version enforced: pilot and completion (S2), rollback, template apply (S5) and the development seed. `ValidatePolicyVersion` and `TestPolicyVersion` advance the state when they pass; `DiffPolicyVersions` returns the classified changes and the sample outcome diff. A hook `Versions.OnPublished(ctx, tx, org, version, base)` for S2 runs inside the publishing transaction, both on a direct publish and when a PUBLISH change request is applied (nil is a no-op).
7. **Scenario tests** (S1a; HR-044, HR-232, HR-238). The runner evaluates each case with the real `pipeline.EvaluateWith` over an in-memory fixture reader: containment clear; a VERIFIED agent at attestation L2 with an active run; one root grant covering the operation, with the case's constraints; usage from `given.budget`; facts from `given.facts`; the organization's current active definition for the operation, read once and read-only; the version under test compiled with the tenant's CEL budget; a connection in enforce mode; holds from `given.approval`. A case passes when the decision and the decisive reason (and the rule, when given) match. The gate passes only when every case passes, every HR-044 mutant (each comparison in each `when`) is killed by at least one case, and every rule that is not ANNOTATE has a removal mutant that is killed. Bounds: 200 cases and 20 000 evaluations per run, mutants included; beyond them the run fails with `TESTS_TOO_LARGE`. The runner reads only definitions and the catalog, never finalizes and never writes.
8. **Validation and sample outcomes** (S1a, `internal/policy/validate`; F196, F197, HR-238, R-25). Errors (block publication): compile errors, `OPERATION_UNKNOWN`, `CONSTRAINT_UNSUPPORTED` (a constraint a matched definition does not declare), `VERIFY_UNREACHABLE`, `FACT_UNKNOWN`, `CONFLICT` (two CONSTRAIN rules on the same parameter whose allowed, target or destination sets do not intersect, or `amount_max` in different currencies, for an action both match, with the example). Warnings: `SHADOWED`, `APPROVER_NONE`, `FACT_NO_SOURCE`. Info: `REDUNDANT`. Samples per operation come from the definition's parameter schema with boundary values around every numeric or money literal and constraint maximum, each allowed value plus one outside, and equality string literals, with facts present with literal values: at most 256 per operation and 4 096 per run. Every sample-based finding says so. `OutcomeDiff(base, next)` reports the changed outcomes over the same samples, with the categories of decision 5, using the policy engine only.
9. **Rollback** (S1b; F206, F207, HR-236). `RollbackPolicy(to_version_id)` (human, `policy.publish`) creates a draft with the target's rules and tests plus the carried emergency rules, then follows decision 6: a looser result becomes a PUBLISH change request, a tighter one is published. The response lists the carried rule ids. Containment, grants and envelopes are separate records and are never touched; the CLI says so.
10. **Callers of the old publish** (S1b). Every product path (the policies RPC, `pclaw policy publish`, template apply and remove, the development seed in `internal/server/devholds.go`) goes through the gate; the seed's bundle gets baseline tests that pass it. Test setup that needs only "some policy published" uses the test-only helper `internal/policy/policytest.Publish`, which inserts the version and a passing test run for its digest and publishes through the store; the gate's own tests use the real path.
11. **Change requests** (S1b; HR-231, F1, F2). One mechanism for PUBLISH, ROLLOUT and EXCEPTION. Required confirmations: 2 when the organization has at least two active persons holding `policy.publish` at the organization path when the request is made, else 1. Only persons holding `policy.publish` confirm, each with a security-key BINDING ceremony over the request's binding; persons and credentials must be distinct (`SAME_PERSON`, `SAME_KEY`, as for the kill switch). The requester's confirmation counts when they hold `policy.publish`. On the last confirmation, in one transaction: the base still holds (for PUBLISH and ROLLOUT the published version is still the base, else VOIDED `BASE_CHANGED`; the definitions and catalog digests are still those of the recorded test run, else VOIDED `STALE_TESTS`; for EXCEPTION the rule still exists in the published version, is `exceptable` and has the same rule digest, and the agent is not retired, else VOIDED `BASE_CHANGED`, and the requested expiry has not passed, else EXPIRED), the kind's apply callback runs, the request becomes APPROVED and `policy.change_approved` is audited. Any eligible confirmer may decline with a reason. Requests expire 24 hours after creation, checked by the database clock at use. Every RPC that creates a request returns its URL.
12. **Rollouts, cohorts and per-agent selection** (S2; F200–F205, F3, HR-234; shadow, pilots and cohorts are Team). Rollout flows are human and need `policy.publish`. `StartRollout` enters SHADOW (no cohorts means every agent). `StartPilot` runs the gate and the classifier; a looser version becomes a ROLLOUT change request whose apply enters PILOT, otherwise PILOT starts at once. `ExpandPilot` needs no new approval while the base is unchanged. `ExcludeTarget` marks an agent EXCEPTION, which stays on the published version. `CompleteRollout` publishes through the gate (the base must still be published, else `BASE_CHANGED`). `CancelRollout` returns the cohort agents to the published version without approval. In Community every publish creates a COMPLETE rollout whose targets are every agent that is not retired, for status only. Selection happens in pgauthority: an agent in an ENFORCE cohort of the organization's PILOT rollout whose target is not EXCEPTION gets the rollout version, everyone else the published version; when the rollout version cannot be compiled for an evaluation, the published version decides (FALLBACK). Nothing about selection comes from the request. Target states are set by a River sweeper (every minute, per due organization, at most 1 000 evaluations per tick): ACKNOWLEDGED when a decision for the agent was made under the rollout version (from the recording's policy reference or the receipt basis; receipts do not change); FAILED when a cohort agent was decided with FALLBACK (the owner is set and notified, `policy.rollout_target_failed`); VERIFIED when ACKNOWLEDGED and the agent's latest unexpired coverage snapshots for the version's rule operations are all PARTIAL or ENFORCED (the weakest is stored; no snapshot keeps the target ACKNOWLEDGED with reason `COVERAGE_UNKNOWN`). The authority never writes these rows.
13. **Shadow** (S2; F200, F203, HR-232, HR-233, HR-237, R-26). For a SHADOW rollout, or the SHADOW-mode cohorts of a pilot, the sweeper replays each new evaluation of an in-scope agent with the version and once with the recorded policy, classifies the pair with decision 5 (not reproduced or incomplete: UNEVALUABLE with the limitation codes) and writes a shadow result: at most 500 replays per tick and 100 000 rows per rollout, then daily counters only. Nothing changes on the hot path: a test proves the decision, basis digest and checklist are identical with and without an active shadow. `GetShadowSummary` gives counts by category, operation, agent and day, newly held per day (approval burden) and samples with ids, decisions and reasons only, never input values; every response and CLI line says "shadow prediction, not enforcement".
14. **Exceptions** (S3; F208–F210, HR-235, F2). A person holding `policy.exception.request` asks for an exception to a rule that exists and is `exceptable` in the published version, for one agent and 1–16 exact operations inside the rule's scope, with a reason, an owner who is a person and a requested expiry at most 30 days ahead; the request creates an EXCEPTION change request whose apply activates it. `expires_at` is the earlier of the requested expiry and activation plus 30 days, set by the database clock. `policy.publish` may revoke at any time; there is no renewal or extension, only a new request. The pipeline's policy read (after selection) loads the agent's ACTIVE, unexpired exceptions in the snapshot transaction and waives a rule only when it is `exceptable` in the selected version, its rule digest matches and the operation is listed. The engine still requires the rule's facts (missing or stale facts are not evaluated, as today, and never waived). A waived rule whose condition matches is reported WAIVED with `EXCEPTION_APPLIED` and the exception id, has no effect, and its obligations are dropped. Grants, envelopes, containment, identity, budgets, coverage and route mode are untouched, with a test for each. Replay serves the recorded exceptions. Built in two phases: new files from `origin/main` first, then the hook into selection and the engine after S1b and S2 push.
15. **Simulation** (S4; F187–F192, F287, HR-232, HR-237; Team). A simulation covers a window of at most 30 days inside retention and at most 50 000 evaluations (10 000 by default), one QUEUED or RUNNING per organization. The job takes decision receipts in the window, newest first, up to the cap, replays each with the recorded policy and with the version (as in decision 13), and classifies them; results are stored as counts, by workflow (per operation and per agent), the approval burden (newly held per day and by required role) and at most 25 samples per category and operation. Reports keep newly denied, held, constrained and allowed (flagged "expanded exposure"), unevaluable and changed reasons apart, and state the limits (F192): "predicts decisions, not agent replanning or business outcomes". Outputs carry no recorded input values; drill-down goes through the existing `ReplayDecision` with its own permission. Built in two phases: a local copy of decision 5's signature until S1a pushes, then S1a merged and the stand-in deleted.

New `templates/refunds` (pc.mock: refunds above a placeholder threshold held for an approver, denial above the cap, a count limit per run, reads allowed), `templates/release-deployment` (pc.github: `github.deployment.trigger` needs `release_approver` inside a change window; other repositories and environments are denied, as in design decision 18) and `templates/production-diagnostics` (pc.shell: read-only commands only, network and write commands denied, a working directory outside the workspace denied). Each has the coding-to-production file set plus `tests.json`, which passes the gate including every mutant, and a disclosure in `template.json` (`protects`, `excludes`, `requires.packages`, `requires.connections`). Coding-to-production gets `tests.json` after the preview's CEL fix for that template reaches its base. `template apply` creates the merged version (rules and tests) and publishes it through the gate; a loosening prints the change-request URL and exits 0 with "waiting for confirmation"; `template remove` works the same way (it loosens). Placeholders stay as today.

**Residual risks** (added to THREAT_MODEL §8 by this brief):
- **R-25:** conflict, shadowing and redundancy detection and the sample outcome diff are sample-based (ADR-0004): a conflict that no generated sample reaches is not reported. Compensating controls: boundary values around every literal and constraint maximum, every allowed value plus one outside; findings labelled `sample_based`; scenario tests with mutation testing; the classifier treats any change it cannot prove tighter as loosening.
