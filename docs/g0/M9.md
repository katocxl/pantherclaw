This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M9 pull requests and, at the end of the milestone, in an exit status section. It builds on `feat/m7-exit` at dbf433d (#234, the M7 exit), the top of the post-audit chain #221 → … → #234, which the founder has not merged yet, and runs in parallel with M8 ([g0/M8.md](M8.md)). Every M9 branch starts from `origin/feat/m7-exit`, merges this brief's branch (`docs/m8-m9-g0-brief`) with a merge commit before its first pull request, and stacks on it ([PARALLEL_WORK](../PARALLEL_WORK.md)). The founder answered every open decision on 2026-10-11 before the brief was written (the recommended option each time); they are recorded at the end as answered.

**Purpose:** PantherClaw's promise is not "we have a gateway" but "this route is enforced, and here is the evidence". M9 makes coverage a computed, expiring claim. Every route by which an agent can cause an effect is inventoried per agent, connection and operation, and gets a state (`UNKNOWN`, `OBSERVE_ONLY`, `PARTIAL`, `ENFORCED`) derived only from evidence. `ENFORCED` comes from a containment sandbox: `pclaw sandbox run` puts the agent on an internal Docker network whose only route is a trusted edge sidecar that proxies HTTP(S), intercepts TLS with a per-session CA and signs PAP/1 to the gateway, so a raw `curl` to the GitHub API gets the same action and decision as the MCP route (F099). Signed probes and an external canary prove that every other route is closed, with controls, and the promotion expires. The same container machinery runs third-party MCP servers as connectors in customer-hosted gateways. Their egress goes through an edge, and credentials are injected on that path by the gateway, so neither the connector nor its edge ever holds one (design decision 18). In product terms this is Checkpoint's coverage claim and Reflex's containment sandbox ([PRODUCT.md](../PRODUCT.md)).

**Scope (planned):**
- **Coverage scopes and routes** (A1, A4; F433, F443, F450, decision 6). A scope is agent × connection × operation. For each scope, the inventory lists every route that can cause the operation's effect, with its kind, source, control, usability and evidence.
  - **Route kinds:** gateway MCP, gateway HTTP, SDK, hook, target-verified, direct API with an agent-held credential, git over SSH or HTTPS, browser session, CI/CD, child agent, other.
  - **Sources:** connections and their routes, transaction channels seen, M8's `tool_observations`, discoveries and `pclaw scan` findings (an MCP server holding a token is a direct-API route), the GitHub org scan (workflows are CI/CD routes), and sandbox sessions (refused destinations).
  - As implemented (A4d, A9): GitHub org-scan findings (kinds `github_app`, `github_workflow`, `github_mcp_config`) count only from discoveries of source `github_scan`, which only the gateway's org scan writes (N20). A workflow is a route when it writes, deploys or runs a job on the repository's default permissions (`permissions_default`), which may write; an MCP configuration is one finding per file. A finding that names no connection of the org, or shows no route, is never selected. A finding counts only for the connection it names, and only when its `scan_run` is a scan run of that connection; its route is recorded per connection.
  - **Honest limits** (F450): every scope also lists the sources that were not observed. For example, browser sessions have no source, and a developer laptop's SSH keys are not observed unless `pclaw scan` submitted them. They read "not observed", never "absent".
  - As implemented (A4c): transaction channels are inventoried incrementally, after a watermark on transaction ids (UUIDv7). Each refresh rereads the transactions up to 5 minutes behind the watermark by id time, so one that commits up to 5 minutes after its id was generated is still inventoried. A transaction that commits later than that is not, which is accepted for M9: its channel is a gateway route, and a later transaction on the same route records it.
- **The state calculus** (A3; F435, F460, HR-210, HR-024, HR-086, INV10). A pure function computes a scope's state, reasons and expiry from its routes, controls, evidence, exclusions and the time. It is property-tested (design 1).
- **Invalidation and freshness** (A5; F439, F453, HR-211, decision 3).
  - Every change that can reopen a route writes a coverage invalidation in the same transaction and marks the affected evidence invalid at once: a connection, package version, route mode, gateway, sandbox image or configuration, credential or agent instance.
  - A reassess job recomputes snapshots.
  - Expiry is applied when coverage is read, so a stalled job never keeps `ENFORCED` alive.
  - A published freshness contract states these timings.
- **Snapshots and the ledger** (A6; F021, HR-217, decision 7). Each computation appends a snapshot and a `coverage.snapshot` ledger entry (chained and checkpointed by M7).
  - Agent states `PROTECTED` and `PARTIALLY_PROTECTED` are derived from snapshots (F021). Since M3 nothing has set them; `OBSERVED` remains the default.
  - Decision receipts gain the optional coverage claim. `pclaw verify` and packs check it against the snapshot ledger.
- **Access-mode disclosure, findings and exclusions** (A7; §39.2–39.3, F048, HR-212, decisions 6 and 9).
  - Per connection, an access detail: custodian, mode (target-enforced, narrow temporary, PantherClaw-held, constrained runtime, agent-held), scope, audience, expiry, issuance source, affected agents, verification basis, residual routes. Never a secret.
    - As implemented (A7b): `GetAccessDetail` needs `coverage.read` over the agent, and for an agent, coverage on the connection. The credential version, its hosts, the target hosts, the issuer and the gateway are the connection's configuration and need `connection.read` too. The verification basis lists, per read of the scopes shown, the latest passing target-verifier test (founder decision N15). Residual routes read each scope as its record does now, and a route counts as closed only by the closure that confines the agent now.
  - Credential-overreach findings compare three sets: declared (the package's credential scope for the operations the agent's grants allow), used (operations executed in the last 30 days) and actual (for GitHub, the installation's real permissions read in M8).
    - As implemented (A7c, A9): actual is the permissions of the GitHub App installation behind the connection, as last read into `connection_github` (M8 #297). While the gateway has not read them (`read_at` NULL, as after a re-seal), or last read them more than 7 days ago, the reach is not observed, never "no overreach" and never current: no finding is raised or resolved until a scan reads them again (coordinator decision D7). The org scans that read them run when the installation is recorded and daily (M8 #351). The org scan's `github_app` findings are the organization's other Apps, one per App: target-side routes (F449), never this credential's permissions. A dismissed discovery still counts. `metadata:read`, which every App holds, counts as declared, and a held level coverage does not know ranks as admin.
  - Findings go to a `coverage_findings` table that M10 extends.
  - Exclusions are human-only, with a reason and an expiry, and audited.
- **`pclaw coverage` and the coverage card** (A8; F329, F451, F457, F277).
  - `pclaw coverage show|routes|history|exclude|findings|reassess`.
  - A read-only, server-rendered card page under M5's page rules. It shows which routes were tested, the closing control and evidence of each, the tools that remain uncovered, the exclusions, the expiry, and a before-and-after comparison of the last two snapshots.
  - The route graph data (F277) is Team-only, through the API.
- **Docker wrapper** (B1; HR-218, HR-085, HR-122, decision 8). `internal/sandbox/docker` runs the `docker` CLI with fixed argument lists (`exec.Command` with argument slices, never a shell).
  - Names, labels and digests are validated before they reach an argument.
  - It checks the engine (≥ 28) and API version, detects `runsc` and Docker Desktop, and creates internal isolated networks and hardened containers.
  - An isolation self-check inspects every network and container before the agent starts.
  - Cleanup removes only resources carrying the session's label.
- **The edge** (B2; HR-213, HR-214, ADR-0022, decision 1). A new binary, `pantherclaw-edge`, in its own image:
  - an HTTP proxy on the sandbox network;
  - the per-session CA, with name constraints limited to the mapped hosts;
  - TLS interception for mapped hosts only;
  - PAP/1 signing with the run's workload key, and forwarding to the gateway's HTTP face;
  - stripping credentials from agent requests (a stripped credential becomes an observed `credential` route);
  - refusing and recording everything else.

  It also has a connector mode (C3).
- **Probes and the canary** (B3; HR-121, HR-215, decision 2).
  - A new binary, `pantherclaw-probe`, in its own image, runs the catalogue: DNS through 127.0.0.11 and directly over UDP and TCP; IPv6; ICMP; direct TCP 443 and 22 to the canary and to the mapped hosts' real addresses (resolved on the host); cloud metadata (169.254.169.254, `fd00:ec2::254`); the host gateway, `host.docker.internal` and the host's addresses; a planted canary PAT and SSH key used to push; an unmapped `CONNECT` through the edge; and a mapped request through the edge.
  - `pantherclaw-sim canary` runs outside the sandbox (on the host by default) and records every hit carrying the session's marker.
    - *As built (B3a):* the canary listens on TCP for its HTTPS and SSH ports and on UDP and TCP for its DNS port, and records a hit for any connection or query that carries a session marker. It has no ICMP listener and no delegated DNS name, so it cannot see ICMP or DNS leaving through a recursive resolver. Those routes are covered by the probes' own observations (`icmp`, `dns_docker_resolver`, `dns_external`), each with a positive twin in the control run, and never by the canary.
  - Configuration checks (mounts including `docker.sock`, user, capabilities, read-only root, security options, networks, runtime, engine) come from `pclaw`'s own `docker inspect`, outside the sandbox.
  - The probe and canary reports are signed with the per-session key and the server nonce.
- **Sandbox sessions and promotion** (B4; F454, F457, PN-008.2, decision 3).
  - `SandboxService` opens a session (agent, mapped connections, image digests, configuration digest, probe public key) and returns its id, a single-use nonce and the enrollment of a sandbox instance.
  - It verifies the signed reports and evaluates the controls (design decision 15).
  - Passing evidence promotes the session's scopes to `ENFORCED` for the configured lifetime (24 hours by default) and records each closure: what was tested, with which identity and effect, which control blocked it, and what reopens it.
  - Re-probing during a long session refreshes the evidence (Team: scheduled re-probes, F454).
- **`pclaw sandbox run`** (B5; PN-008.1). In order, it:
  1. checks Docker;
  2. resolves images by digest, refusing a tag without one;
  3. opens the session;
  4. enrolls the sandbox instance, holding its key only for the edge;
  5. starts the run;
  6. creates the network and the edge, and waits for its CA;
  7. copies the workspace into a volume, its repository cleaned;
  8. runs the probes and the canary, and submits the reports;
  9. starts the agent with the hardened flags and the proxy and CA variables (*as built (B5b):* after the probes, so the agent never shares the sandbox network with the probe container);
  10. streams the agent's output;
  11. writes the agent's changes as a patch to an output directory at the end (patch only, design decision 10);
  12. removes everything it created, also on interruption.
- **Docker-gated tests** (B6; decision 8). The build tag `sandbox` plus `PC_TEST_SANDBOX=1`, run by `task test:sandbox`. They never run in `task check`. gVisor is detected and skipped on Docker Desktop.
- **Connector runtime** (C1–C4; HR-084, HR-085, HR-086, HR-216, decision 5). A connection of the new kind `mcp_container` describes a third-party stdio MCP server:
  - its image digest, command and arguments;
  - non-secret environment values and credential placeholders;
  - the HTTP connection through which its egress is mediated;
  - its resource limits.

  It is accepted only for a customer-hosted gateway. The gateway's host process starts it in a hardened container on its own internal network with an edge, through the Docker CLI with fixed arguments, and speaks MCP to it over stdio through a new upstream sender. Connector egress goes through the edge to the gateway, which accepts only requests that map to the in-flight call's action (design decision 6) and injects the credential through the M6 dispatch path.
- **End to end:**
  - the exit scenarios;
  - S11 completed: the coverage state of a direct call to the simulator is computed, not only shown;
  - a connector over stdio (`mcpsim --stdio`) with mediated egress.
    - *As built (C4):* `TestE2E_M9_ConnectorOverStdio` and `TestT088_AConnectorCannotBreakOutOrTakeACredential` (Docker-gated, `task test:sandbox`) run the gateway with real connector and edge containers. The connector is `pantherclaw-sim mcp --stdio --upstream https://payments.test --misbehave`; the Authority and the target are the gateway tests' fakes. The authorized refund goes out once, with the credential the gateway places; the target echoes `Authorization`, and the connector gets it back redacted. The simulator then misbehaves by the refund's charge, and the gateway refuses each attempt:
      - an inflated amount (`outside_the_call`);
      - the same refund twice (`repeated_write`);
      - a refund of another charge (`outside_the_call`);
      - the refund again after answering (no call in flight);
      - a request to the listener without the binding.
      
      The kill switch engaged mid-call stops the connector's request (`contained`). The containers are inspected: no socket, host namespace, writable mount, host environment or credential, and only the placeholder and the edge's CA. Connector routes stay capped at `PARTIAL` until connector probe evidence exists (a follow-up).
      - An agent's MCP call to the connector goes over stdio. The connector posts the refund through its edge, and the gateway takes that request only during the call. It sends it once to the payments target, rebuilt from the definition, with the credential and the call's idempotency key. The connector's answer never carries the credential.
      - The server side (specs, hosting, run reports) is covered by the C1–C2 integration tests, so this test does not need a full server.
      - The edge maps host names only, so a connector reaches its egress connection by one of that connection's agent hosts when the base URL is an IP literal.

**Contracts:**
- **Migrations.** M9 owns `00085`–`00095`: A `00085`–`00089`, B `00090`–`00092`, C `00093`–`00095`. Tracks merge their migration slices in number order or renumber within their range. Every tenant table has `org_id`, composite keys and forced RLS.
  - **`00085_coverage.sql`** (A1, as built in #236; this brief follows it). Scopes are not a table: a scope is the triple (agent, connection, operation) that routes, closures, snapshots and exclusions name.
    - `coverage_routes`: agent (null for every agent of the connection), connection, operation (null for every operation); kind `channel | direct_api | host | git_ssh | credential | browser | delegated | intermediary | target_side`, plus the channel for `channel` routes; an untrusted locator; observation `observed | declared | proposed`; source `gateway | connection | discovery | scan | probe | person` and its reference; the last observed route mode; attributes; seen count; first and last seen.
    - `coverage_closures`: insert-only sandbox closure evidence for (agent, connection). It holds the session, the result `PASSED | FAILED`, the probe results (JSON, the closure contract's vocabulary below) and the three control flags. It also holds the signing-key thumbprint, the server nonce, the SHA-256 of the signed results, the engine, API version and runtime, the image digests and the configuration digest. Finally the bindings it was taken under (gateway, connection revision, package version, and the active credential's version, if any), `pclaw`'s configuration checks of the agent container (`config_checks`), and its times: session start, observed, expires (≤ 7 days after observed), recorded. A server nonce is recorded once per agent and connection (HR-215).
    - `coverage_invalidations`: insert-only events of kind `connection | package_version | route_mode | gateway | credential | sandbox_image | sandbox_config | closure_failed | exclusion | evidence_expired | route | instance`, for a connection and optionally an agent, with the subject and when it was reassessed. `route` is a new material route or source inventoried, and `instance` an agent instance admitted outside a sandbox; #236 adds both in `00085`.
    - `coverage_snapshots`: append-only (agent, connection, operation) with the state, reasons, the closure an `ENFORCED` state rests on, the last valid snapshot a downgrade follows, the invalidation that caused it, the body and its SHA-256, the ledger entry, the computation time and the expiry. Only `ENFORCED` expires. A trigger and a composite key make an `ENFORCED` snapshot rest on a `PASSED` closure of its own agent and connection, expiring no later than that closure.
    - `coverage_exclusions`: agent (or every agent), connection, operation (or every one), route kind (or the whole scope), a reason of 10–1,000 characters, state `ACTIVE | REVOKED`, created by a user, expiry at most 90 days after creation, revoked by and at. A trigger allows only the one change from `ACTIVE` to `REVOKED`.
    - Route sightings rank `observed` over `declared` over `proposed`. A weaker sighting changes nothing, and only observations count towards `seen_count`, each source reference once.
    - `coverage_findings`: kind `credential_overreach` (F048), with the subject, the declared, held, used and excess permissions, the severity, state `OPEN | RESOLVED | DISMISSED`, a fingerprint and dismissal by a person with a reason. M10 extends the kinds.
    - What the brief had planned as separate findings is recorded elsewhere. An edge-refused destination and a found credential become `coverage_routes` (kind `direct_api` or `credential`, source `probe`, observation `observed`). A failed control is a `FAILED` closure with its reason. F450's "not observed" sources are derived when coverage is read (design decision 19).

    - `decision_receipts.coverage_snapshot_id` (A6, for lookups; the claim itself lives in the signed receipt);
    - ledger entry kinds `coverage.snapshot` and `coverage.invalidation` (A6), which need no schema change.

    - `sandbox_sessions`: agent; launcher; the run and the instance; mapped connections; image digests (agent, edge, probe); configuration digest; the probe public key; engine, API version and runtime; state `OPEN | ENDED | EXPIRED`; opened, expires and ended at;

- **The edge protocol** (B2, C3):
  - **Configuration** (`pantherclaw.edge/v1`, a read-only file mount): mode `sandbox | connector`; session id; gateway URL and CA pin; a map from agent host to connection; the run id; the key file path (sandbox mode) or the connector binding token file (connector mode).
    - *As built (B2):* the configuration also names `token_file`, the instance's current workload token. The edge dials only the gateway, so it cannot renew a token itself: `pclaw` renews it outside the sandbox and the edge reads the file for every request. An optional `gateway_addr` is the address dialed for the gateway URL when the gateway listens on the host's loopback (`host.docker.internal:<port>` on Docker Desktop); proofs still name the gateway URL. The CA pin (`sha256:<hex>`) may name any certificate of the chain the gateway presents. Inside a tunnel the edge speaks HTTP/1.1 only (clients fall back); HTTP/2 is a follow-up. The configuration also names `subnet`, the sandbox network's: the edge listens on its own address there and drops any connection that arrives on another local address, so nothing on its uplink can use it. Host certificates live at most an hour and are issued again before they expire, and the session CA serves only server authentication. Credentials in the query string (by parameter name or by a well-known token prefix) are stripped and reported like credential headers.
  - **Sandbox mode** (edge to gateway):
    - The edge sends each intercepted request to the gateway's existing HTTP face, `/{connection}/<path>?<query>`, with `Authorization: PAP <workload token>`, `PAP-Proof` over the exact forwarded body, `PAP-Run-Id`, a fresh `PC-Action-Id` per request, and `PC-Sandbox-Session` (informational; the server binds the session through the instance).
    - It forwards `Content-Type`, `Accept` and the body. It drops hop-by-hop headers, `Authorization`, `Cookie`, `Proxy-*` and `Forwarded`/`X-Forwarded-*`.
    - The gateway's answer is relayed with a header allowlist. A hold or refusal reaches the agent as the face's decision response.
  - **Connector mode:**
    - The edge sends `POST /edge/v1/egress` to a gateway listener bound only to the connector's egress network. It authenticates with a 256-bit binding token that the gateway generated for that container and keeps in memory.
    - The body carries method, host, path, query, the allowed headers and the request body (≤ 1 MiB).
    - The gateway accepts only while a call to that container is in flight, maps the request through the egress connection's package, and requires the in-flight action's operation and target, or an `access: read` operation on the same target. It then injects the credential and dispatches through the M6 egress path.
    - *As built (C3a):* the edge strips and reports credentials as in sandbox mode, and forwards only `Content-Type` and `Accept`. *Review fixes:* over plain `http` it sends the binding token only to a non-routable gateway address (loopback, private or link-local, or `host.docker.internal`); a header or query parameter carrying only the connector's placeholder (`placeholder` in the configuration) is dropped but not reported, as it is no secret.

- **The coverage claim in decision receipts** (A6; PAP-1 §9.1, additive, §13):
  - **Shape:** `pap.coverage: {"v":1,"state":…,"snapshot":"<uuid>","scope":{"agent":…,"connection":…,"operation":…},"snapshot_state":…,"lapsed":false|true,"reason":…,"exclusions":["<uuid>",…],"expires_at":…}`. It sits inside the signed payload and is absent (never null) when no scope exists.
  - **The claim's `state`** is the one effective at decision time:
    - **Current snapshot:** `state == snapshot_state` and `lapsed` is false.
    - **Expired or invalidated snapshot:** `lapsed` is true, `reason` names why (`expired`, or the invalidation kind), and `state` is the state recomputed from current evidence at decision time, capped at `PARTIAL` and possibly lower (HR-211).
    - As implemented (W4c): a snapshot's record lists the pending changes its computation read (`seen`), read before its evidence, so each was committed before the evidence reads and is reflected; one committed later is not listed. A claim lapses on a pending change unless the snapshot read it and it came before the snapshot's computation, the same interval `pclaw verify` checks. So a change found while a closure is recorded (a route the sandbox saw during its session) does not lapse the ENFORCED snapshot computed from it, and a change after the computation always does.
  - **The ledger:** each snapshot appends a `coverage.snapshot` entry (body `{scope, state, snapshot, computed_at, expires_at, exclusions, routes_digest, closure}`), and each invalidation appends a `coverage.invalidation` entry (body `{connection, agent, kind, subject, occurred_at}`).
    - As implemented (A5b): the snapshot row keeps the full record (routes, reasons, last valid snapshot, cause) as its body, and `body_sha256` is the digest of the ledger entry. `routes_digest` is `sha256:` and the hex SHA-256 of the canonical `{"routes": [...]}` of the record, so the row is bound to the entry.
    - Ledger body format (W4c): every id in both bodies (`snapshot`, `scope.agent`, `scope.connection`, `exclusions`, `closure`; `id`, `connection`, `agent`, `subject`) is the canonical lowercase UUID string (`0199e2a4-1111-7000-8000-000000000005`), as receipts' claims and `pclaw verify` name them; times are `2006-01-02T15:04:05.000000Z`. The snapshot row body (the record `GetSnapshot` exports) names its ids the same way (`id`, `agent`, `connection`, `closure`, `exclusions`, `last_valid`, `cause`, and each route's `route` and `closure`), so `routes_digest` is the SHA-256 of the JCS form of `{"routes": [{kind, channel?, locator?, route?, status, closure?}, ...]}` with those strings, and anyone holding the exported routes recomputes it. Earlier builds wrote ids base64-encoded, which no verifier could match; nothing was released, so no entry is migrated. `TestHR217_CoverageLedgerBodiesNameIdsAsUUIDStrings` pins both bodies and the routes encoding and verifies them; `TestIntHR217_TheRoutesDigestIsRecomputedFromTheExportedSnapshot` recomputes the digest from exported snapshots.
    - Coverage reads the target-verifier test through an interface (`app.TargetVerifier`), per connection and operation. The server reads M8's connection tests through `app.ConnectionTests` (wired 2026-10-14): of an operation's `target_verifier` tests in `pc.connection_tests`, only the latest finished one counts, only while it is `DONE` and `PASSED`, and only if it finished after the connection's latest revision, its active credential and its package pin (`TestHR210_ConnectionTestsVouchWhileTheLatestPasses`, `TestHR210_TheServersVerifierLiftsTheTestedRead`, `TestHR211_AChangedConnectionDropsTheVerifierLift`). Without a passing test, cooperative and target-enforced channels stay capped at `PARTIAL`. A test lifts only the operation it tested, and only a read (design decision 1, founder decision N15).
  - **`ExportBundle`** includes, for each claim, the claimed snapshot's entry, the scope's next snapshot entry if any, and every invalidation entry for the scope from the snapshot's computation up to the decision's `iat`.
  - **`pclaw verify` checks** that the claimed entry is present and inclusion-proven, has the same scope and `snapshot_state`, lists the same exclusions, and was computed before `iat`. Then:
    - when `lapsed` is false: the snapshot had not expired at `iat`, no invalidation entry for the scope falls between its computation and `iat`, and no next snapshot was computed before `iat`;
    - when `lapsed` is true: the stated reason holds (an expiry before `iat`, or an invalidation entry in that interval), and `state` is not `ENFORCED`.

    A bundle without the needed entries reports "not available"; anything else fails.
    - Coordinator decision (T-089): a claim naming a snapshot the bundle does not hold fails when the bundle holds the scope's snapshots on both sides of the receipt's ledger entry (the latest before it, which was current at decision time, and the next one) and the claimed id is not the current one; without both it is "not available". `ExportBundle` carries, for every claim, the scope's snapshot current at decision time and the next one, so a bundle it exports can always decide.

**Security constraints and design decisions:**
1. **The state calculus (HR-210, HR-024, HR-086).**
   - The calculus is an ordered function over the scope's routes (`coverage_routes` with observation `observed` or `declared`; `proposed` routes are hypotheses and count only as unclosed), its closures, its invalidations, its exclusions, the `target_verifier` tests and the time. The first matching step wins:
     1. `UNKNOWN`: the scope has no route at all.
     2. `OBSERVE_ONLY`: no route of the scope is a gateway channel in enforce mode, so only monitor-mode or observed routes exist.
     3. `ENFORCED`, only if all three hold:
        - every material route is either a gateway channel in enforce mode on `pantherclaw_held` access, or on `target_enforced` access with a passing `target_verifier` test of the scope's own operation no older than `coverage.enforced_ttl` (HR-024, HR-210; in M9 only for a read, founder decision N15), or closed by a current `PASSED` closure (its route kind is one the closure's passing probes close, the closure's bindings still match, and no invalidation for the scope follows its session start);
        - every source that was not observed (F450) is closed by that closure;
        - every active instance of the agent is a sandbox instance covered by the closure (design decision 2).
     4. `PARTIAL` otherwise. This covers a cooperative `sdk` or `hook` channel without target-verifier evidence (HR-024), an opaque MCP route without `connector_egress_mediated` (HR-086), an unobserved source, a route that is uncontrolled or only proposed, and expired or invalidated evidence.
   - So a source that was not observed (always true for browser sessions) only blocks `ENFORCED`. It never pushes a scope below `PARTIAL` once a gateway route is enforced.
   - Route modes, access modes, declared replay stores and connection settings alone never yield `ENFORCED` (F460).
   - **Properties tested:** adding a route never raises the state; removing, expiring or invalidating evidence never raises it; a scope's state reads only its own routes and evidence (INV10, M9 part).
   - **As implemented in A3b** (`internal/coverage/domain/calculus.go`):
     - `ENFORCED` always rests on a current `PASSED` closure, since browser sessions are never observed and only a closure closes them. It expires with the closure, or earlier with the target-verifier test it uses.
     - A channel counts as in enforce mode only on an `ACTIVE` connection. Access mode `none` (local connections) mediates like `pantherclaw_held`, and `agent_held` never mediates. A cooperative channel needs the verifier test whatever the access mode.
     - A proposed channel route blocks `ENFORCED`. `target_side` routes are exposure (F449, F048) and never block it.
     - Exclusions, of the whole scope or of a route kind, are listed but never change the state (design decision 1, as the founder decided). An excluded route kind the closure did not close stays open, so the scope stays `PARTIAL` at most, with the kind named (`route_not_closed:<kind>`) and the reason `excluded`.
     - A passing target-verifier test lifts the cooperative and target-enforced caps (HR-024, HR-210) only for the operation it tested, which in M9 is the package's `test: true` read (founder decision N15). Write operations stay `PARTIAL` in M9 whatever the test, with the reason `write_not_liftable_m9`. A scope counts as a read when its package defines the operation only with `access: read`.
     - "Adding a route never raises the state" is tested for routes that are not gateway channels in enforce mode, on scopes with a known route. Step 1 to step 2 raises a scope from `UNKNOWN` by definition.
2. **Expiry and invalidation (HR-211, decision 3).**
   - Closures carry `expires_at` (`coverage.enforced_ttl` after observation, at most 7 days) and the bindings they were taken under (gateway, connection revision, package version). They are insert-only and never updated: an invalidation event at or after a closure's session start makes it invalid when coverage is read. Events of kind `route`, `exclusion` and `evidence_expired` are the exception: they make the next read recompute the scope, but leave the closure valid. The closure still closes the route kinds its probes closed, and a session's own refused destinations are recorded as routes after the session started.
   - The invalidation events are written in the changing transaction, through triggers or the closure contract's `RecordInvalidation`:
     - every connection change (`connections/app/changes.go`, `after`): base URL, hosts, agent hosts, gateway, package, access mode, route mode, restore;
     - `PutCredential` and `RevokeCredential`;
     - a change to the GitHub App installation behind a connection (`connection_github`, kind `credential`; migration 00092, A9), but not reading it again unchanged;
     - package drift and activation;
     - a gateway's replacement on a connection, its quarantine or its retirement, but not a certificate renewal (the binding is the gateway, not its certificate);
     - an agent instance admitted outside a sandbox (kind `instance`);
     - connector spec changes;
     - a sandbox session with different image or configuration digests;
     - a new material route or source in the inventory (kind `route`).

     A read in the next transaction already drops to `PARTIAL` or lower.
   - The reassess job (River, per org through the `coverage_reassess` lister purpose) writes the new snapshots within `coverage.reassess_every`.
     - As implemented (A5c): each scope is reassessed in a savepoint, in (agent, connection, operation) order. A scope whose evidence cannot be read or recorded is rolled back alone, logged and skipped, and every invalidation that touched it stays pending. While one does, every scope of its connection reads lapsed: recomputed from current evidence and capped at `PARTIAL`. This fails safe, and lasts until the scope can be reassessed again. A job reads at most 200 pending invalidations; if that many stay pending behind failing scopes, later ones wait, and their scopes read lapsed in the same way.
   - Reads compute expiry themselves. An expired or invalidated scope is recomputed from its current routes and evidence and capped at `PARTIAL`; it reads lower when, for example, a route went to monitor mode or a new route appeared that nothing observes. It is returned with the last valid `ENFORCED` snapshot and the reason it lapsed.
   - Work continues: no decision is blocked by stale coverage in M9 (decision 3).
3. **Exclusions (HR-212, decision 6).**
   - An exclusion records, until it expires, that a person accepts one route (or route kind) of one scope as outside the boundary. It never raises the state: the excluded route still counts as open, so the scope stays `PARTIAL` at most. The claim and the card always list it (design decision 1).
   - Creating one needs a person holding `coverage.manage`, a reason and an expiry of at most 90 days. It is audited with the scope and route, notified to org admins, and invalidates the scope's current snapshot so it is recomputed with the exclusion visible.
   - Revoking takes effect at once.
4. **The edge (HR-213, HR-214, ADR-0022).**
   - The edge listens only on the sandbox network.
   - It intercepts `CONNECT` only to port 443 of an agent host of a mapped connection, and HTTP/1.1 or HTTP/2 inside. Everything else is refused with 403 and recorded as an observed `direct_api` route (source `probe`, host and port as its locator, aggregated by `seen_count`): another host or port, an IP literal, plain HTTP, WebSocket upgrades.
   - The CA key and the workload key exist only in the edge's memory and in its read-only key mount, which the agent container does not have.
   - The edge's only outbound connection is the gateway's listener, over its second network. It never dials a destination itself, so with the gateway down a mapped request fails instead of reaching the target.
   - A request the gateway holds or refuses is answered to the agent as the gateway's decision; the edge never retries on its own.
5. **Probe trust (HR-215, decision 2).**
   - `pclaw` creates the session's probe key outside every container, registers its public key in `StartSession`, and mounts the private key read-only into the probe container and the canary only. The agent never has it, and every report needs a fresh server nonce.
     - *As built (B3c):* two keys, both created by `pclaw` outside every container and both registered at `StartSession`. The probe key is mounted read-only into the sandbox run's probe container alone, signs only the `sandbox` report, and its file is removed as soon as that run is over. The host key never leaves `pclaw`'s process: the control run prints its report unsigned and `pclaw` signs it, and the canary's report, with the host key. The server verifies each kind with its own key, so nothing on the agent's network, the probe container included, can forge the control or the canary.
   - Configuration checks are made by `pclaw`, never by a container. Results from the agent container are never evidence.
   - The probe container runs on the agent's network, as a different uid, with `--cap-drop ALL --cap-add NET_RAW` and the other hardened flags.
     - *As built (B1):* no capability is added. Docker gives a non-root process no ambient capabilities, so `NET_RAW` would never be effective for the probe's uid. Instead the probe container's own group may open unprivileged ICMP sockets (`net.ipv4.ping_group_range` set to its gid; every other container gets `1 0`), so the probe still sends echo requests to show the network drops them. This is less privilege than the planned `--cap-add NET_RAW`.
6. **Connector egress is bound to the call (HR-086, decision 5).**
   - A connector container handles one MCP call at a time. The gateway binds the container's egress to that call alone.
   - *Amended by the founder, 2026-10-11 (exact match, once):* during an authorized call, a connector's write egress is allowed only when it equals the authorized action: the same canonical parameters, the same destinations and the same action hash as the permit's bound action. Each call allows at most one such write. Reviewed `access: read` operations on the call's target stay allowed. Everything else is refused and recorded. A tool that needs several writes is modelled as several actions; a package-declared write plan is a follow-up.
   - Each forwarded request is checked against the mapping, carries the credential the gateway injects, and is recorded with the call's transaction.
   - Requests outside a call, or that map elsewhere, are refused and become findings.
     - *As built (C3b):* `Fly` binds the connector's egress to one call before the call goes over stdio, and `land` unbinds it when the answer comes back or the call's window (the connection's `timeout_ms`, 30 s when unset) closes. A second call to the same connector waits for the first to land, and a connector that stopped or whose last exchange was abandoned takes none, so a request is never judged against, or sent under, another call's action. A request through the edge is mapped with the call's own ids through the egress connection. A write is sent only when its action, with the call's connection, channel, route and definition, has the bound action's hash, and only once per call; a read only when it is an `access: read` operation on the call's target over GET or HEAD, at most 64 per call. It is then rebuilt from the reviewed definition (HR-075), so nothing the connector chose beyond the mapped fields goes out; it carries the call's idempotency key and the credential the gateway places, and goes through the egress connection's hardened client, kill switch, quarantine and circuit breaker included. It is also refused once the containment epoch moved past the call's permit or while the connector connection is contained, and it ends when the call lands. Refusals answer `PC-Refused-By: gateway` with a code (`unknown_binding`, `no_call_in_flight`, `unmapped_request`, `outside_the_call`, `repeated_write`, `too_many_reads`, `contained`, `not_sent`). As `coverage_findings` holds F048's kind only in M9, a refusal is recorded as the gateway log event `gateway.connector_egress_refused` (connection, code and, once the request mapped, the transaction and operation), and a sent request as `gateway.connector_egress`; M10's detections read them.
   - With this binding and current connector probe evidence (the same probes on the connector's network), the route can be `ENFORCED`; without either, it stays capped at `PARTIAL`.
7. **Connector placement (HR-084, HR-216).**
   - A gateway's `hosting` is `customer` unless the server's configuration lists it as PantherClaw-hosted. Neither a tenant nor a gateway can set it.
   - Connector connections are refused at creation and left out of configuration delivery for PantherClaw-hosted gateways.
   - The gateway starts connectors only when `connectors.enabled` is set, it runs as a host process (not inside a container), and the Docker CLI is present.
   - Containers get no Docker socket, no host environment (a fixed environment list only) and no host network. Arguments are fixed lists built from validated spec fields; image references are digests.
8. **Docker hardening (HR-085, HR-122, HR-218, decisions 4 and 8).**
   - Every container: `--read-only`, `--user <uid>:<gid>` (non-root, distinct per role: agent, edge, probe, connector), `--cap-drop ALL`, `--security-opt no-new-privileges`, Docker's default seccomp, `--pids-limit`, `--memory`, `--network <sandbox network>`, tmpfs `/tmp` (`noexec,nosuid`), no `--privileged`, `--pid host`, `--ipc host`, `--network host`, device or socket mounts.
   - The network: `docker network create --internal --ipv6=false -o com.docker.network.bridge.gateway_mode_ipv4=isolated`.
   - The self-check (`docker inspect`) must find exactly these settings, or nothing starts.
     - *Review fixes (B1):* the Docker CLI fills any proxy variable a container leaves unset from the user's `~/.docker/config.json`, proxy credentials included, so every container sets all ten (`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `FTP_PROXY`, `ALL_PROXY`, in both cases), empty unless asked. The self-check requires the environment to be exactly the image's with the requested variables over it. Logs go to the `local` driver, rotated (2 files of 8 MiB), which the self-check also requires; `docker logs` still reads them.
   - `runsc` is used when `docker info` lists it, unless the engine is Docker Desktop, where it is detected and skipped.
9. **Sandbox instances.**
   - `StartSession` creates an enrollment for a new instance of the agent with the sandbox session recorded on it. `pclaw` generates the key and shows the fingerprint, and the launching person, who must hold `sandbox.run` and `agent.admit` for the agent, admits it in the same command (HR-094, design decision 3).
   - The instance's attestation level is L1. It can act only inside the session, and the session ends at its expiry (≤ 24 hours).
   - **The CI path.** A service account holding `sandbox.run` can open sessions only for an agent whose sandbox instances are admitted by an L2 auto-admission policy (M3: a trusted issuer such as GitHub Actions OIDC, with pinned claims; HR-094's exception, HR-140). Without one, a person admits the instance, so CI needs either that policy or a person in the loop. The evidence names the service account and the attestation.
10. **Workspaces.** `pclaw sandbox run` copies the workspace into a session volume and copies it out at the end. The agent never gets a bind mount of the host's files, so credentials elsewhere on the host stay out of reach (design decision 4).
    - **Founder decision (2026-10-11): patch only.** The host's `.git` never goes into or out of the sandbox as it is. Copy-in gives the agent a cleaned repository. `--out` never writes `.git` (or any tree) back: the changes come back as a patch, which the developer applies to their own repository. `pclaw` lists every changed dotfile and editor or task file. The decision answers a review finding that a copied-back `.git/config` (`core.fsmonitor`, `core.hooksPath`, `core.sshCommand`, filter drivers) or a hook would run on the host at the developer's next `git status`.
    - *As built (B5a):*
      - **Copy-in** keeps the top-level repository's objects (without `objects/info/alternates`), refs, `HEAD`, `index`, `packed-refs` and `shallow`, none of them executable. It writes its own `.git/config`: only the repository format, plus `objectformat = sha256` when the host's repository uses it. Hooks, the host's config (remotes, credential helpers, `fsmonitor`, `hooksPath`, `sshCommand`), `info`, `logs`, `modules`, nested repositories and `.git` files stay on the host. Everything else under `--workspace` goes in, `.env` files included, and `pclaw` says so.
      - **Copy-out:** the helper container packs the volume's files without any `.git`, and the host refuses a `.git` entry before writing anything. On a Windows host it also refuses names Windows would misread (`:`, device names, a trailing dot or space).
      - **The patch** is built by `pclaw` in Go from the files' contents into a private directory, never by git and never in the sandbox's directory. It compares them with the copied-in workspace and writes `changes.patch` to `--out` in git's format, which `git apply` takes: unified hunks, and new, deleted and mode lines. Executable bits come from the sandbox's archive, because a Windows host keeps none. `changes.txt` lists every change, with the agent's paths quoted.
      - **Binary files are not in the patch.** git applies a binary patch only with the files' SHA-1 blob ids, and SB-3 keeps SHA-1 out of the code. Their new content goes under `--out/binary/`, never executable, for the developer to copy. Allowing SHA-1 for git object ids (an exception to SB-3) would put them in the patch; that is the founder's call.
      - **What `pclaw` prints:** the changed files, and separately every changed dotfile, dot directory and build or task file (`.envrc`, `.vscode/`, `.idea/`, `.githooks/`, `Makefile`, `package.json`, `Taskfile.yml`, …), for review before anything runs.
11. **Findings and routes never grant anything.** A found credential is recorded as a `credential` route with the credential's kind and a SHA-256 prefix, never the value. Every route locator, attribute and finding detail is untrusted, bounded and shown in the untrusted block.

**Dependencies to add:** none (decision 8). The Docker CLI is an external program, called with fixed arguments. Proxying, TLS, X.509 with name constraints, ECDSA, JWS and DNS probing come from the Go standard library (`net`, `crypto/*`, `net/http`), plus the existing go-jose for JWS. DEPENDENCY_POLICY §3 is unchanged. Images are pinned by digest (DEPENDENCY_POLICY §2).

**Design decisions in this brief, for the founder's confirmation:**
1. **Exclusions never raise a coverage state** (founder decision, 2026-10-11). An excluded material route keeps the scope at `PARTIAL` at most and never counts towards `ENFORCED`. The claim, the card and the receipt's scope always carry the exclusion. The same holds for agent protection: an excluded scope counts as not protected, so the agent is `PARTIALLY_PROTECTED` at most, with the exclusion listed.
   - The brief first proposed the narrowing reading, in which an excluded route no longer prevented `ENFORCED`. The founder rejected it: an exclusion is a person's recorded acceptance of a gap (HR-212: a person, a reason, an expiry of at most 90 days, audit and notification), not evidence that the gap is closed.
   - Founder decision N15: a passing target-verifier connection test lifts the cooperative `PARTIAL` cap (HR-024, HR-210) only for the one operation it tested, which is the package's `test: true` read. Write routes stay `PARTIAL` in M9.
   - As implemented (A3b, A6c, A7a): an excluded route kind reads *excluded* but still counts as open, a whole-scope exclusion never changes the state, and agent protection counts a scope with an exclusion as not protected. Creating one needs `coverage.manage` (Security Admin), is audited and notified (`security.coverage_excluded`, without the reason).
2. **Agent-level coverage counts every active instance.** A scope is `ENFORCED` only when every active instance of the agent is a sandbox instance covered by current evidence. An agent that also runs on a laptop stays `PARTIAL` for the same scope.
3. **Sandbox instances are admitted by the launching person in the same command.** `pclaw` computes the fingerprint itself, so the HR-094 confirmation is the person's, and the instance cannot outlive its session.
4. **Workspaces are copied into a volume and back**, never bind-mounted.
5. **git over HTTPS and SSH is closed in M9.** Agents change repositories through mapped API operations. Mapping git's smart-HTTP protocol is a follow-up, shared with M8's.
6. **Connector egress is bound to the in-flight call, one call at a time per container.** Concurrency needs per-request correlation and is a follow-up.
7. **PantherClaw-hosted gateways are listed in server configuration.** Everything else is customer-hosted. Tenants cannot mark a gateway either way.
8. **Probes target only the canary, the host's own addresses and the mapped hosts' real addresses** (resolved on the host). No other third-party address is contacted.
9. **Expiry is evaluated at read time**, so no job's failure keeps `ENFORCED` alive.
10. **New binaries and images.** The edge (`cmd/pantherclaw-edge`) and the probe (`cmd/pantherclaw-probe`) are new binaries in this repository. Their images are built locally for tests (`task sandbox:images`), published with releases later, and always referenced by digest.
    - *As built (B3c):* "by digest" includes a local image id (`sha256:…`, the digest of the image's configuration), which is how `task sandbox:images` and the Docker tests reference the images they build; every container runs with `--pull never`, so an id pins the image on the engine that holds it. Evidence names the reference as given, so a session that used a local id names the id, not a registry digest. A tag is always refused.
11. **F021 derivation.** An agent is `PROTECTED` when every scope of the operations its grants allow is `ENFORCED`, and `PARTIALLY_PROTECTED` when at least one is; otherwise its state stays `OBSERVED`. The derivation runs after each snapshot, through the existing lifecycle transition. As implemented (A6c): the scopes are each operation an active grant allows on every connection whose pinned package defines it; a scope never assessed counts as not `ENFORCED`, and so does a scope with an exclusion, whatever its state (design decision 1, as the founder decided); and the derivation runs once per agent after every reassessment, after its changes are marked, so a change of grants or exclusions that records no snapshot still reaches the agent. Each job also derives every agent held `PROTECTED` or `PARTIALLY_PROTECTED`, so a grant that starts, ends or changes, which writes no coverage change, lowers the agent within one run; an agent a grant would raise waits for the next reassessment of its scopes.
12. **Editions.** F277's graph data needs Team. The card, the states, the sandbox and connectors are Community. Scheduled re-probes (F454) need Team.
13. **HR-219 keeps a "reserved" row** with no milestone, so the number is not reused and the traceability check skips it.
14. **The decision receipt's claim is an object named `coverage`.** Effect receipts keep their existing `coverage: "PARTIAL"` string label; the two receipt types are distinct.
15. **The controls.**
    - **Positive controls must succeed:** the catalogue run on a deliberately open control network reaches the canary, and a mapped request through the edge gets the gateway's decision. A failed positive control makes the closure `FAILED` with that reason and promotes nothing; so does a report that lacks any control.
    - **Negative controls must fail:** every catalogue route from the sandbox is closed, the canary sees nothing for the session, and an unmapped `CONNECT` is refused. A failed negative control makes the closure `FAILED` (shown as the reason), writes a `closure_failed` invalidation, and so drops any current `ENFORCED` for the session's scopes at once (decision 2).
16. **HR-024 is split across M8 and M9**, as M8's design decision 17 records. M9 tests the labelling part in A3.
17. **The snapshot ledger is the org's existing evidence ledger** (entry kind `coverage.snapshot`), so M7's chain, checkpoints, anchoring and `pclaw verify` apply without a new log.
18. **Connector credentials are injected at the gateway end of the edge path.** Decision 5 says the edge "injects credentials". Doing that inside the edge container would put plaintext credentials outside the gateway, which HR-061 forbids (credentials are opened only in gateway memory at dispatch). So the edge forwards each egress request to the gateway, and the gateway's broker opens and places the credential exactly as for a dispatch. The connector and its edge never hold a credential.
19. **Unobserved sources are derived, not stored.** When coverage is read, F450's "not observed" list comes from which sources exist for the agent: a submitted `pclaw scan`, an org scan run, a sandbox session, gateway traffic. Browser sessions are always listed as not observed (F446 is post-1.0).
20. **Track A's schema is #236's**, adopted after the review of this brief, and B uses the closure contract (`side-session-notes/m9-coverage-closure-contract.md`).
    - The schema has one `00085_coverage.sql` with routes, closures, invalidations, snapshots, exclusions and findings. Closures are insert-only and invalidated by later events. Findings are F048's only. The probe vocabulary is `name`, `role`, `expect`, `observed` with `blocked | reachable`.
    - The brief's earlier separate scopes, sources, evidence and probe-result tables are dropped.
    - Two changes to the contract: its optional `target_requires_token` probe is M8's `target_verifier` connection test, and the invalidation kinds gain `route` and `instance` (both in `00085`).

**Residual risks** (added to THREAT_MODEL §8 by this brief):
- **R-17:** sandbox evidence is produced by `pclaw` on the launcher's host, so it is only as trustworthy as that host and person. Compensating controls: the person is named, the nonce is single-use, evidence expires within 24 hours, and CI runners with L2 attestation are the stronger setting.
- **R-20:** on `runc` (always on Docker Desktop), a kernel vulnerability can break container isolation. Compensating controls: the hardening flags, gVisor where available and recorded, and expiry.
- **R-21:** the edge sees plaintext for mapped hosts and is in the TCB for the routes it mediates, like the gateway (R-01). Compensating controls: a per-session CA whose key never leaves the edge, name constraints, and an image pinned by digest.
