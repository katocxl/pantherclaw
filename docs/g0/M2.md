### G0 — M2 Tenancy & service authentication — 2026-10-08

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M2 pull requests and, at the end of the milestone, in the exit status below.

**Scope (planned):** everything listed for M2 in [BUILD_GUIDE §8](../BUILD_GUIDE.md#m2--tenancy--service-authentication):
- Org → business unit → team → environment hierarchy; users (from OIDC), team memberships, invitations (single-use, expiring), the role and permission catalog, separation-of-duties (SoD) primitives.
- PantherClaw as OIDC relying party for the CLI device flow; `pclaw login`.
- Service accounts with `private_key_jwt`; `pck_` API keys with scopes and expiry; the authentication interceptor; a bootstrap admin token (printed once, single use).
- Keycloak development realm (`deploy/keycloak`) and mock-oauth2-server in CI.
- `pclaw` commands for tenancy, access, service accounts and API keys.

**Out of scope:** browser sessions, WebAuthn step-up and approvals (M5); agents and PAP/1 (M3); gateway mTLS (M6, the M1.5 development gateway token stays until then); SCIM and multi-org fleet administration (Enterprise); API-key IP allowlists (optional in SB-2; need trusted-proxy handling first); a UI.

**Threat slice:** T-003 (tenant escape), T-032 (token replay, alg confusion, substitution), T-037 (IDOR, mass assignment, OIDC mix-up, login CSRF), T-043 (admin abusing platform administration).
**Hardening rules in scope:** HR-095 (algorithms pinned per key), HR-104 (validation at every edge), HR-050..057 (every new table), HR-004 (conditional transitions), HR-056 (no secrets in job args or logs).
**Product requirements:** F036, F573, F581, F583 (part), F585 (part), PN-021.

**Founder decisions (2026-10-08, asked before coding):**
1. **Credentials carry their org id.** API keys are `pck_<env>_<org>_<secret>`; device codes, refresh tokens, invitations and service-account client ids have the same `<prefix>_<org>_…` shape. The server reads the org from the credential, opens a tenant transaction for that org and looks the credential up by SHA-256 under RLS. HR-053 ("one SECURITY DEFINER function") stays unchanged. Org ids are not secret.
2. **`pclaw login` is server-mediated.** The CLI runs an RFC 8628-style device flow against PantherClaw; PantherClaw is the OIDC relying party toward the customer IdP (authorization code + PKCE S256 + `nonce` + RFC 9207 `iss`) and issues its own tokens. One IdP client registration; the IdP does not need to support device flow.
3. **Admins may grant roles to themselves**, audited and flagged (`self_grant: true`). Org Admin never contains approval, policy-publication or restricted-evidence permissions (F583), so becoming an Approver is an explicit, visible step.
4. **CLI tokens are stored in a private file** (`<user config dir>/pantherclaw/credentials.json`, 0600). An OS keychain is a later upgrade.

**Contracts:**
- Migrations `00015_tenancy.sql` (`business_units`, `teams`, `environments`, `users`, `memberships`, `service_accounts`, `role_bindings`, `invitations`) and `00016_authn.sql` (`service_account_keys`, `api_keys`, `device_codes`, `cli_sessions`, `auth_replay`; key purpose `access_tokens`). `cli_sessions` (refresh tokens) and `auth_replay` (client-assertion `jti`s) are additions to BUILD_GUIDE §7. Every table: `org_id`, composite keys, forced RLS (covered by the M1 catalog tests).
- Protos: `tenancy.proto` (`TenancyService`), `access.proto` (`AccessService`), `service_accounts.proto` (`ServiceAccountService`). Every RPC declares `// permission: <name>`; a test checks each name exists in the Go permission catalog and matches the server's procedure → permission table.
- OAuth endpoints (form-encoded, outside Connect): `POST /oauth2/device_authorization`, `POST /oauth2/token` (device code, refresh token, client credentials), `POST /oauth2/revoke`, `GET /.well-known/oauth-authorization-server`; browser pages `GET|POST /device` and `GET /oauth2/callback/<provider>`.
- Access tokens: JWS (EdDSA, `typ: at+jwt`) signed by a new `access_tokens` key (not published in the JWKS), 15 min, claims `iss`, `aud`, `sub`, `pc_org`, `pc_ptyp`, `sid`, `jti`, `iat`, `nbf`, `exp`.

**Security constraints and design decisions:**
1. **Authentication then authorization, twice.** The interceptor authenticates (access token or API key), checks the principal and its org are still active (per request, so disabling a user, session, service account, key or API key takes effect immediately), and refuses procedures whose permission the principal holds nowhere. Each use case then checks the permission at the exact scope of the resource (org, business unit, team, environment; a binding on an ancestor scope applies to descendants).
2. **Org comes only from the credential.** No request carries an org id. Every lookup runs in `InTenantTx(principal.Org)`, so ids from other orgs are NotFound (IDOR).
3. **Human-only permissions** (`approval.respond`, `policy.publish`, `evidence.read_restricted`) are never effective for service accounts or API keys, and roles that contain them cannot be bound to service accounts. API keys are owned by a service account; their effective permissions are the account's permissions ∩ the key's scopes.
4. **SoD primitives:** human-only permissions; Org Admin excludes approval/publication/restricted evidence (F583); the last Org Admin binding cannot be removed and the last active admin cannot be disabled; `sod.Distinct` for later approval checks; self-grants audited.
5. **Service-account assertions (RFC 7523, SB-2):** `kid` required and resolved to an active, unexpired key of that account; the header `alg` must equal the algorithm pinned on the key (EdDSA or ES256; `none`, HMAC and anything else rejected, HR-095); `iss = sub = client_id`; `aud` a single string equal to the issuer or the token endpoint URL; `exp` required and at most 5 minutes ahead; `jti` required and recorded only **after** the signature verifies; replay → `invalid_grant`. Private keys are generated by the client; PantherClaw stores only public JWKs.
6. **OIDC relying party (SB-2):** discovery via go-oidc; ID token signature limited to RS256/ES256/EdDSA; `iss`, `aud`, `azp`, `exp`, `iat`, `nonce` checked; one callback URL per provider and the RFC 9207 `iss` parameter (required when the provider advertises it) defend against mix-up; `state` is single use; the browser that confirmed the code must present the binding cookie at the callback (login CSRF); IdP endpoints must be HTTPS except explicitly configured loopback development issuers.
7. **Device flow:** user codes are 8 characters from a 20-letter alphabet, expire after 10 minutes, and the confirmation page shows the device name, IP and time and warns against codes the user did not start (RFC 8628 §5.4); polling faster than the interval returns `slow_down`. Tokens are bound to a device key: the CLI proves possession of it with a client assertion at code exchange and at every refresh.
8. **Sessions:** access tokens 15 minutes; refresh tokens rotate on every use, expire 8 hours after login, and reuse of a rotated token revokes the session.
9. **Invitations:** single use, default 7 days (max 30), bound to an email that the IdP must assert as verified (or a provider marked `trust_email`). Invitation tokens are high-entropy random secrets (≥ 256 bits) in the `<prefix>_<org>_<secret>` shape of founder decision 1, stored only as SHA-256 and looked up under RLS. This **replaces the "signed" invitations of BUILD_GUIDE §8**: the stored row (state, expiry, single use) is authoritative, so a signature would add no integrity, and revocation takes effect immediately. The bootstrap admin token is an Org Admin invitation created only by the operator command `pantherclaw-server org create` (or `org admin-invite` for recovery), printed once, valid 24 hours, unbound to an email. The Business edition is required for business units; `org create` enforces the licence org limit.
10. **Secrets at rest:** only SHA-256 hashes of API keys, refresh tokens, device codes, invitation tokens, OAuth `state` and the browser binding are stored. The PKCE verifier and nonce live on the device-code row only until the callback completes. The IdP client secret is a file (SB-7).
11. **Abuse limits:** per-IP rate limits on the OAuth endpoints and device pages; failed authentications are logged (not written to the ledger); successful logins, token issuance to service accounts and every tenancy/access change are written to the evidence ledger (F585).
12. **IdP HTTP client:** a dedicated client that never follows redirects or reads proxy variables (HR-070, HR-072) and talks only to the configured issuers and their discovered endpoints.

**Dependencies to add:** `github.com/coreos/go-oidc/v3 v3.21.0` and `golang.org/x/oauth2 v0.37.0` (both already approved in DEPENDENCY_POLICY §3; outside the 7-day cooldown). Container images (digest-pinned, dev/CI only): Keycloak, mock-oauth2-server.

**Tests to write first:**
- `TestHR095_*`: assertions with `alg: none`, HS256 (keyed with the public key), an algorithm other than the key's pinned one, and an unknown `kid` are rejected.
- `TestT032_*`: wrong `aud`/`iss`, expired, not-yet-valid and overlong tokens; a token for another org, a revoked session, a disabled user/service account or a revoked key; a substituted token type (permit or receipt JWS presented as an access token); a replayed client assertion; refresh-token reuse.
- `TestT037_*`: IDOR (another org's ids return NotFound for every get/update/delete), mass assignment (only declared fields change), OIDC mix-up (callback with the other provider's `iss`), wrong `nonce`, `state` reuse, missing browser binding.
- `TestT043_*`: Org Admin holds no approval, publication or restricted-evidence permission; service accounts and API keys can never hold them.
- Permission catalog: every RPC declares a known permission; the interceptor table matches the protos.
- `TestIntTenancy_*` CRUD and end-to-end `pclaw login` → CRUD → service account → API key against the real server.
