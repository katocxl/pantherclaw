### G0 — v0.1.0 preview (coding-agent wedge) — 2026-10-14

This brief is written before implementation (G0). It builds on `main` at 8fc4434a (M1–M9 and M12 complete; the highest migration is 00098). It is the plan for the v0.1.0 preview release: what remains after M12 so that "three routes, three stops" holds, is provable offline and live, can be tried in 30 minutes, and ships as signed binaries and sandbox images ([ADR-0017](../adr/0017-coding-agents-first-and-proven-coverage.md), [BUILD_GUIDE §8](../BUILD_GUIDE.md#v010-preview-exit--coding-agent-wedge-adr-0017)).

**Purpose:** show a customer that a coding agent cannot reach production through any route that PantherClaw does not decide, and give them evidence they can check without trusting us. The same merge is attempted three ways (the GitHub MCP server, a direct `curl` to the GitHub API, a push with a found credential) and each attempt is stopped, mapped to the same action and decision, or held, with a signed record.

## Scope

The five exit bullets of BUILD_GUIDE §8 "v0.1.0 preview exit", plus the release.

1. **Three routes, three stops**, in CI against the simulators and live against a sandbox GitHub repository: a merge through the GitHub MCP server without a reviewer is held; the same merge by direct `curl` to the GitHub API is mapped to the same action and decision (F099); a push with a found PAT or SSH key fails because the sandbox holds no reusable credentials and its egress is closed. Each attempt has a signed receipt that `pclaw verify` checks offline.
2. **The §43 scenario** (coding to production) passes end to end with effect verification on the target branch.
3. **The coverage card** shows the repository routes `ENFORCED` from sandbox probe evidence, with expiry.
4. **The 30-minute onboarding path** for Claude Code (F335) is measured and recorded.
5. **The M12 coding-agent scenarios** are green and gate the change: locally (`task range`) while EX-004 is active, in CI once it ends.
6. **The release:** seven binaries with SBOMs and provenance attestations, and the sandbox edge and probe images on GHCR.

Not in scope: see "Known limits".

## Design decisions

**D1 — CI repair.** The CI workflow is repaired so that every job can pass; the repair is done in the hygiene pull request (D13). The SDK jobs run what `task sdk:check` runs: `node --test` for TypeScript (the SDK has no dependencies, so no pnpm) and `unittest` through uv for Python; the Go integration job runs the same package set as `task test:integration` with a longer timeout; the "Verify modules" loops cover every module in `GO_MODULES`; a `sandbox` job (Docker server ≥ 28, Postgres and the mock OIDC provider as services) runs `task test:sandbox`, `SANDBOX=1 task range` and `task test:preview`, with a path filter over `internal/sandbox`, `cmd/pantherclaw-edge`, `cmd/pantherclaw-probe`, `deploy/sandbox`, `internal/gateway`, `internal/authority`, `internal/coverage`, `internal/evidence`, `packages`, `redteam` and `test/e2e`; `ci-ok` needs it. Actions stay SHA-pinned with default `permissions: {}`. A TypeScript type-check is deferred because it needs a dev-dependency row in DEPENDENCY_POLICY.

**D2 — Release pipeline.** GoReleaser builds seven binaries; `pantherclaw-edge` and `pantherclaw-probe` are linux amd64 and arm64 only, static (`CGO_ENABLED=0`, `-trimpath`, same ldflags). Images `ghcr.io/katocxl/pantherclaw-edge` and `ghcr.io/katocxl/pantherclaw-probe` are built from `deploy/sandbox/{edge,probe}.Dockerfile` (pinned distroless base) for linux/amd64 and linux/arm64, tagged with the version only (no `latest`), and get build-provenance attestations pushed to the registry; the release notes list the two digests. `pclaw` is unchanged: users pin digests in `sandbox.images`, and the sandbox runbook gains "Use the released images" (`docker pull …@sha256:<digest>`, `gh attestation verify`). The release `verify` job also fails unless the tagged commit is on `main` and its `ci-ok` check run succeeded. The runbook documents a signed annotated tag; while the signing item of Day-0 is open, an annotated tag pushed by the founder is acceptable and the exit status records it. No tag is pushed by a build session.

**D3 — Closure evidence offline (HR-227, T-095).** The found-credential push has no decision receipt, only a signed probe report. The coverage use case that records a sandbox closure also appends, in the same transaction, a ledger entry of kind `sandbox.closure`: closure, session, agent, connections, result, the two verifying public keys (probe and host), the reports (`run`, kind `sandbox|control|canary`, SHA-256 of the compact JWS), the probes' outcomes and the record time. `pclaw evidence bundle` gains `--closure <id>`; a bundle for a transaction whose receipt's coverage claim names a closure carries it automatically, with the entry's inclusion proof up to a signed checkpoint and the compact JWSs as the item `probe_reports`. `pclaw verify` checks the entry hash, inclusion and checkpoint signature, verifies each report under the key for its kind (a report that verifies only under the other kind's key fails), matches the SHA-256, session and closure, and prints one line per probe. A missing or mismatching report is `failed`, never `not_available`. Range packs carry the same items, so probe-based range steps are re-derived offline instead of reporting `NotAvailable`. No migration is needed: the ledger kind is pattern-checked only. Tests first: `TestHR227_ClosureEvidenceIsLedgered`, `TestHR227_ProbeReportsVerifyOffline`, `TestT095_ASwappedOrForgedProbeReportFailsVerify` and `TestHR224_RangeProbeStepsReDeriveOffline`.

**D4 — The three-routes test.** `TestE2E_Preview_ThreeRoutesThreeStops` (build tags `integration && sandbox`, task `test:preview`) runs one stack with one real sandboxed agent on the GitHub simulator and a `pc-github` App connection in enforce mode with the "coding to production" template: setup traffic through the edge (read contents, create branch, write file, open pull request: all `ALLOW`); an MCP merge without a reviewer is `HOLD` with reason `MERGES_NEED_AN_INDEPENDENT_REVIEW`; a raw `curl` merge from inside the sandbox yields the same ActionIR hash, dedupe key, decision and reasons (F099); pushes with a planted PAT over HTTPS and a planted SSH key are refused and nothing reaches the simulator's refs; a bundle per attempt verifies offline with `pclaw verify`; `pclaw coverage list` shows every repository operation the flow used (`github.contents.read`, `github.branch.create`, `github.contents.write`, `github.pull.create`, `github.pull.merge`) as `ENFORCED` with an expiry within 24 hours, naming the closure. The closure bundle step for the push lands after D3.

**D5 — Live runs.** `TestLive_GitHub_ThreeRoutes` runs the flow of D4 in its two-session form (D18: the MCP merge is made host-side, the `curl` merge and the pushes run inside a sandbox session) against the founder's sandbox repository (the connection's base URL is the real `api.github.com`; the sandbox edge maps it to the gateway; planted secrets are generated per run and never real; every object is named `pv-<nonce>`; nothing is merged). `TestLive_GitHub_CodingToProduction` runs §43: hold, an independent `code_reviewer` approves with a security-key assertion, the merge executes through the gateway's REST face, the effect is `CONFIRMED` (the branch head equals the merge SHA, read back through the gateway), the deployment consequence is held for a `release_approver` inside an open change window, approved, the repository's deploy workflow reports success, effect `CONFIRMED`. It merges into a throwaway base branch `pv-base-<nonce>`, never into `main`. The runbook gains the deploy workflow, the sandbox prerequisites (Docker ≥ 28, `task sandbox:images`) and "Record the run". A build session cannot run it (it has no App); it must show that the tests compile and skip without `PC_GITHUB_LIVE`.

**D6 — Quickstart and onboarding.** `docs/quickstart.md` follows PRODUCT.md §6 "First 30 minutes" on the simulator: `task demo:up`, `pclaw login`, `pclaw init` (Claude Code and MCP), enrol and confirm the fingerprint, apply the "coding to production" template, `pclaw sandbox run`, `pclaw coverage list` shows `ENFORCED`, then one allowed, one held (approved on the page) and one blocked test. `tools/scripts/demo.sh` (`up`, `down`, `status`) is idempotent, keeps its state under `.demo/`, and works in Git Bash and on Linux and macOS. `docs/perf/onboarding.md` records the founder's timed run (step, command, start, end, minutes, notes); the figure is measured, not guaranteed.

**D7 — G0 approvals and EX-003.** See P5. Docs only.

**D8 — This brief.** BUILD_GUIDE §8 links it; the rows of HR-227 and T-095 are written with D3.

**D9 — Day-0 roots.** After the offline keygen and signing, one pull request commits `internal/billing/licence/roots.json`, `internal/definitions/trust/roots.json` (public keys only) and `packages/targets.jws` (one targets document over the three packages, version 1, 180 days), and ticks BUILD_GUIDE §1 items. Tests that assert empty roots are fixed only where they assert emptiness, never weakened. The Team licence file stays out of the repository.

**D10 — Gates on.** After every stream has merged and before `v0.0.1`: EX-004 is marked ended (GATES_AND_REVIEW §4 and a §7 row); CLAUDE.md, PARALLEL_WORK.md, CONTRIBUTING.md and BUILD_GUIDE §0 return to the CI and G1 flow; the founder enables `required_signatures` on `main`. Then the `v0.0.1` dry-run tag, then `v0.1.0`, by the founder.

**D11 — Taskfile entries.** The streams share `Taskfile.yml`, so each adds only its own entries next to their siblings: the three-routes test adds `test:preview` (tags `integration sandbox`, `-run '^TestE2E_Preview_'`, `PC_TEST_SANDBOX=1`, `-timeout 30m`), the live runs change only `test:github-live`, the quickstart adds `demo:up`, `demo:down` and `demo:status`.

**D12 — Preview code gaps and hygiene.** Two streams outside the preview plan are folded in because they change files the preview depends on. "Preview code gaps": MCP merges on GitHub App connections with per-action tokens (M8 deviation 2), coverage reading the M8 target verifiers, an M9 exit check that every repository operation is `ENFORCED`, and an M8 unreadable-workflow fault with an end-to-end test; its files are in the gateway, coverage, simulators and the M8 end-to-end tests, and preview streams do not edit them. "Hygiene": dependency and lint tasks, the `ci.yml` repair of D1, a dev-seed guard that refuses a configuration that is not local-only, CEL cost configuration, evidence-pack retention and documentation drift for M5–M8 and M12.

**D13 — CI repair deltas.** The hygiene stream's `ci.yml` is the vehicle for D1, with these additions: the sandbox job's first step fails unless the Docker server major version is ≥ 28; a `task test:preview` step after the range step, guarded by `task --list | grep -q 'test:preview'`; the extra path-filter entries listed in D1; and the module loop includes `sdk/go/internal/sqltest`.

**D14 — No migration for D3.** `evidence_ledger.kind` is only pattern-checked (`^[a-z][a-z0-9_]*(\.[a-z0-9_]+)+$`, migration 00011), so `sandbox.closure` fits. Migration 00100 stays reserved and is used only with the coordinator's agreement.

**D15 — Coverage of every operation.** If any of the five operations of D4 is not `ENFORCED` on `main`, the three-routes stream stops and reports; the plan then decides whether it stacks on the preview-code-gaps work. A control is never changed to make a test pass.

**D16 — Test identifiers.** `test/e2e/preview_live_test.go` (tags `integration && github_live && sandbox`) compiles next to `preview_e2e_test.go` (tags `integration && sandbox`). The three-routes stream prefixes every top-level identifier it adds with `preview`, the live stream with `live`; each keeps helpers in its own files and edits no other end-to-end file (the live stream may extend `m8_github_live_test.go`).

**D17 — Closure keys.** A probe run is signed by two keys (the probe key for sandbox reports; the host key for control and canary reports). The `sandbox.closure` body therefore carries `probe_key` and `host_key` (base64url raw Ed25519) instead of one session key, and report rows are `{run, kind: sandbox|control|canary, sha256}`. Verification picks the key by kind. `TestT095` includes a "re-signed with the other kind's key" case.

**D18 — The MCP route is host-side.** The gateway's MCP face is not reachable from inside the sandbox; by design ([M9](M9.md)) the MCP route is the agent's host-side route. The three-routes flow therefore uses two sandbox sessions: the first does the setup (the agent opens the pull request through the edge); the harness makes the MCP merge as the agent's workload (`HOLD`); the second does the `curl` merge of the same pull request and the pushes. The closure of the second session backs the offline and coverage steps. The two merges are separate actions with equal ActionIR hash (apart from channel and per-call ids), dedupe key, decision and reasons. Mediating MCP from inside the sandbox through the edge is a product change and a follow-up.

## Known limits

Kept on purpose; each is recorded in the exit status.

- M8 deviation 2: until the preview-code-gaps work lands, the MCP face on a GitHub App connection fails closed for allowed calls, so MCP merges are decided but not executed.
- Git smart-HTTP and SSH are closed in the sandbox, not mapped to actions.
- Cooperative and SDK write routes stay `PARTIAL` (N15).
- Connector routes are capped at `PARTIAL`.
- The MCP route is host-side, not mediated from inside the sandbox (D18).
- `pclaw up` is M13; the quickstart uses `task demo:up`.
- A TypeScript type-check in CI needs a dev-dependency row in DEPENDENCY_POLICY.
- Python and npm publishing waits for the Day-0 package-name item.
- No image-provenance check inside `pclaw sandbox run` and no image update channel yet.
