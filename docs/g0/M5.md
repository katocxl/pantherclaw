### G0 — M5 Human approvals, step-up & Agent Waitlist, part 1: browser sessions, WebAuthn, notifications — 2026-10-09

This brief is written before implementation (G0). It lists planned scope for **part 1** of M5 only. Part 1 runs in parallel with M3 (agents and runs) and M4 part 2 (grants and the decision pipeline). It therefore covers only the pieces of M5 that depend on neither: how people sign in with a browser, how they register and use security keys, and how PantherClaw sends notifications. Part 2 builds approvals, transaction-bound step-up and the Agent Waitlist on top of them.

**Purpose:** an approval is only as strong as the person behind it. Part 1 gives PantherClaw a browser session it can trust (no fixation, no cross-site requests, short lifetimes), a WebAuthn security key or passkey bound to that person, and a way to reach them (email, Slack, signed webhooks) that can never itself approve anything.

**Scope (planned, part 1):**
- **Browser sign-in** (`internal/authn`): PantherClaw is the OIDC relying party of the M2 providers (authorization code, PKCE S256, `nonce`, RFC 9207 `iss`, one callback per provider), now for browsers. `GET /login?org=<org>` starts a sign-in; the existing callback URL `/oauth2/callback/<provider>` serves both flows, told apart by the state's prefix, so the identity provider needs no new registration.
- **Browser sessions:** the `__Host-pc_session` cookie, stored as a hash; idle 30 minutes and absolute 12 hours (SB-2); rotated at sign-in, at step-up and when the person's roles change; ended by sign-out, by an administrator, or when the user is disabled; at most 10 per user.
- **CSRF defences** for every state-changing browser request: `SameSite=Strict`, Fetch Metadata (`Sec-Fetch-Site`) or `Origin`, and a required custom header (SB-2).
- **The account page** (`GET /account`): who you are, your security keys (add, rename, remove) and your browser sessions (revoke), plus sign-out. It is server-rendered with `html/template`, has one static script for the WebAuthn ceremonies and runs under a strict CSP with Trusted Types. The part-2 approval page reuses its layout, headers and script loader.
- **WebAuthn** registration and assertion through `go-webauthn` (decision 1): credential storage, signature-counter handling (decision 4), user verification required, and a session-bound step-up that lasts 5 minutes. The assertion takes a caller-supplied challenge, so part 2 can pass the approval binding (HR-033).
- **Notifications** (`internal/notifications`): one notification per event, rendered from a fixed template, fanned out as deliveries to `log`, `email` (SMTP), `slack` (incoming webhook, deep link only) and `webhook` (signed per Standard Webhooks) channels, plus personal emails to one user. Deliveries are River jobs with bounded retries, and each channel reports its delivery health.
- **Connect RPCs:** `AccountService` (your own sessions and keys; administrators list and revoke another user's) and `NotificationService` (channels, secrets, tests, deliveries).
- **`pclaw`** commands: `pclaw session list|revoke`, `pclaw key list`, `pclaw user sessions|revoke-sessions|keys|remove-key`, `pclaw channel create|list|get|update|delete|rotate-secret|test`, `pclaw delivery list`.
- Part-1 producers of notifications: security-key added, removed or suspended, sessions revoked by an administrator, a channel paused, and channel tests.

**Out of scope until M3 and M4 part 2 land (part 2):** approval requests and responses, the binding hash (HR-030) and transaction-bound step-up, the server-rendered approval page and its untrusted box (HR-034), eligibility, independence and the two-person rule (HR-035, HR-036), invalidation and expiry at use (HR-031, HR-039), HOLD caps and variant history (HR-037), the Agent Waitlist beyond M3's `ADMISSION` entries (entry types, deadlines, escalation, wait handles, batch review, SLA metrics) and approval routing to eligible deciders.

**Also out of scope:** session cookies on the Connect API (part 1 accepts them only on PantherClaw's own pages; the UI phase decides with its own CSRF review); OIDC back-channel logout and Shared Signals (PN-024, M10); authenticator attestation policies (Enterprise, later); accepting invitations in the browser (M2's `pclaw login --invitation` stays the way in); Slack approval cards and interactivity (PN-017.3, M14); digests and attention levels (F607–F623, M10); OCSF export (PN-018, M10).

**Security constraints and design decisions:**
1. **Browser sessions authenticate pages only (part 1).** They are a new credential beside M2's CLI sessions and API keys. The Connect API keeps bearer credentials, so the RPC authentication interceptor does not change. Only users can have a browser session: service accounts and API keys have no identity at the provider (HR-156).
2. **Sign-in (HR-152).** `GET /login` checks the org and provider, creates a `login_requests` row, sets the `__Host-pc_login` binding cookie (`SameSite=Lax`, because the provider's redirect back is cross-site) and redirects to the provider. The callback consumes the state first (single use), then checks the binding cookie, RFC 9207 `iss`, the code exchange with PKCE, the ID token and its `nonce`, and, when `max_age` was requested, that `auth_time` is present and recent. The person must already be an active member of the org. `next` is a path from a fixed list (`/account` now, `/approvals/…` in part 2), stored on the request row, never taken from the callback URL. The callback answers with a short same-origin "continue" page, because a `SameSite=Strict` cookie is not sent on a redirect chain that started at the provider.
3. **Session cookie (HR-150).** `__Host-pc_session` (`Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`; without `__Host-` and `Secure` only on a loopback `http://localhost` development URL). The value is a 256-bit `pcb_` secret issued only at a successful callback, so no value set before sign-in can become a session (fixation). Only its SHA-256 is stored. Every request checks, in one tenant transaction and by the database clock: org active, user enabled, session active, idle under 30 minutes, age under 12 hours. `last_seen_at` is written at most once a minute. A new session beyond 10 per user ends the oldest.
4. **Rotation.** The secret is replaced at sign-in, at step-up, and on the first request after the user's role bindings change (the session stores a digest of the bindings it last saw). The previous secret stays valid for 60 seconds for requests already in flight; presenting it later ends the session and writes `authn.session_reuse`, a theft signal.
5. **CSRF and page hardening (HR-151).** Every non-`GET`/`HEAD` request authenticated by a session cookie must carry `Sec-Fetch-Site: same-origin` (or, from a browser without Fetch Metadata, an `Origin` equal to the public origin), the header `PC-CSRF: 1`, and `Content-Type: application/json`. Plain HTML forms cannot do that, so the page script makes these requests with `fetch`. `GET` handlers never change state. Pages send `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'; require-trusted-types-for 'script'; trusted-types 'none'`, `Cache-Control: no-store`, `X-Frame-Options: DENY` and `Referrer-Policy: no-referrer`. Templates use `html/template`, there is no inline script or style, and the script writes text with `textContent` only. No CORS headers are ever sent.
6. **WebAuthn parameters (HR-153).** RP ID from configuration; the only accepted origin is exactly the public origin (no subdomains). User verification is `required` and the UV flag is checked. Attestation is `none`: the AAGUID is stored but marked untrusted (an attestation policy is a later Enterprise option). Discoverable credentials are `discouraged`, because PantherClaw always names the allowed credentials. Algorithms: ES256, EdDSA, and RS256 with keys of at least 2,048 bits (Windows Hello). The user handle is the user's id, which carries no personal data. Registration excludes the user's existing credentials, and a credential id may exist only once per org.
7. **Ceremonies.** Each begin call stores a `webauthn_ceremonies` row bound to the browser session and the user, with a 32-byte random challenge, valid 5 minutes. The finish call consumes it with a conditional update (HR-004), so each challenge works once. A ceremony from another session or user is refused. Part 2 adds the purpose `BINDING`, whose challenge is the approval binding hash, passed to the library as a caller-supplied challenge.
8. **Signature counter (HR-154, decision 4).** Synced passkeys report 0 every time: a counter that is 0 in storage and in the assertion is accepted. Otherwise the new counter must be greater than the stored one, or the assertion is refused and the credential becomes `SUSPENDED` (`CLONE_SUSPECTED`), with an audit event and a notice to the user and to channels subscribed to `security.*`. The backup-eligible flag may not change after registration (the library enforces it).
9. **Step-up (HR-156).** A successful assertion records `step_up_at` and the credential on the browser session and rotates its secret. A use case that requires step-up checks it is at most 5 minutes old. It never carries over to another session, a CLI token or an API key.
10. **Adding and removing keys (HR-155, decision 2).** Adding a key requires either a provider sign-in at most 5 minutes old (requested with `max_age=300`, checked through `auth_time`) or, when the user already has a key, a step-up with it at most 5 minutes old. Removing a key needs the same. Each change writes an audit event and sends the user a personal email. An administrator can remove a user's key (`user.manage`), for example when it is lost, but can never register one for someone else: the ceremony runs in that person's browser.
11. **Notification model.** A producer calls `notifications.Enqueue` inside its own transaction. It renders the notification from the type's template, resolves the matching channels and recipients, and inserts the notification, its deliveries and one River job per delivery with `InsertTx`. A rolled-back change therefore sends nothing, and enqueueing never waits on a channel. Job arguments are `(org_id, delivery_id)` only (HR-056).
12. **Templates (HR-158).** Each notification type has a fixed template, a severity (`INFO`, `WARNING`, `CRITICAL`) and typed parameters: ids, canonical names and counts. There are no free-text parameters, no agent text and no secrets. Link targets are PantherClaw paths with the org (`/account?org=…`). Each channel escapes for its format: Slack `&`, `<` and `>`, so text cannot forge a link; email headers reject CR and LF and are encoded; webhook bodies are JSON from `encoding/json/v2`.
13. **Channels and routing.** A channel subscribes to event types (exact names or `prefix.*`, at most 32) at or above a minimum severity. `log` writes a structured `notification.delivered` event. `email` sends to every enabled user who holds a chosen role at org scope. Personal notices go by email to one user. Email goes only to users' addresses from their identity provider, never to addresses typed into a channel, so PantherClaw cannot be used to mail strangers.
14. **Destinations (HR-157).** Webhook URLs must be `https`, without credentials or a fragment, on port 443 or 1024–65535, and not on PantherClaw's own host. Requests go through `httpx.NewEgressClient`, which checks the connected address at dial time, follows no redirects and ignores proxy variables. Private ranges are reachable only through `notifications.allowed_private_ranges`, set by the operator, never by a tenant. Slack channels accept only `https://hooks.slack.com/services/…` URLs. The Slack URL and the webhook signing secret are encrypted with the org's notification key (AES-256-GCM, AAD bound to org, table, column and row, HR-062), shown once at creation or rotation, and never returned again.
15. **Webhook signing.** HMAC-SHA256 `v1` signatures (Standard Webhooks), because every receiver library supports them. `RotateChannelSecret` keeps the old secret for 24 hours, and both signatures are sent while they overlap. Ed25519 `v1a` signatures are a later option.
16. **SMTP.** Go's `net/smtp`, with TLS required (implicit TLS or STARTTLS, at least TLS 1.2, certificate verified). Plaintext is allowed only to a relay on a loopback address (local development). Messages are `text/plain` UTF-8 with `Auto-Submitted: auto-generated`. When no relay is configured, email deliveries are `SKIPPED` with a reason, and the operator sees this in delivery health.
17. **Retries (HR-159).** At most 8 attempts in all (the first and 7 retries), on a schedule adapted from the Standard Webhooks example (which recommends exponential backoff but does not mandate a schedule; its eighth attempt comes 14 hours after the seventh): at once, then after 5 seconds, 5 minutes, 30 minutes, 2 hours, 5 hours, 10 hours and 10 hours (about 27 hours in all). A 2xx answer is success. A redirect is a failure and is never followed. `429` waits for `Retry-After`, at most 1 hour. A destination that reports itself gone (`410`, or Slack's answers for a revoked webhook) pauses the channel. Attempts stop when the notification expires. Each request times out after 10 seconds, and at most 4 KiB of the response is read, which is never stored.
18. **Bounded queues and health.** A channel holds at most 1,000 pending deliveries; beyond that new deliveries are `DROPPED` and the channel is flagged. Health is `HEALTHY`, `DEGRADED` (recent failures) or `FAILING` (10 or more consecutive failures). A channel that has failed continuously for 72 hours is paused automatically, with an audit event and a `notification.channel_paused` notice to the org's other channels and the log.
19. **Delivery is never approval (HR-159, HR-039 groundwork).** Delivery rows are read only by `internal/notifications`; an architecture test fails if any other module reads them. A delivered, failed or acknowledged message changes nothing except delivery and channel health. Channels have no inbound path in part 1: PantherClaw does not receive Slack interactions or webhook replies.
20. **Authorization and tenancy.** Self-service RPCs and pages act only on the caller's own sessions and keys. Administrative RPCs check `user.read` or `user.manage` at org scope, and notification RPCs check `notification.*`. Ids from another org return NotFound (T-037). Browser sessions take their org from the cookie (ADR-0016 decision 1).
21. **Logging and evidence.** Session secrets, login states, challenges, webhook secrets and Slack URLs are never logged, never put in job arguments and never stored in clear. Logs carry ids and hashes only. These events go to the evidence ledger: browser sign-in and sign-out, session revocation and reuse, key registration, rename, removal and suspension, step-up, and every channel change, secret rotation, pause and resume. Failed sign-ins and ceremonies are logged, but not written to the ledger (as in M2).
22. **Failure semantics.** A provider outage stops sign-in. A failed WebAuthn verification refuses the step-up; it never falls back to a weaker check. An unavailable SMTP relay, Slack or webhook endpoint delays its own deliveries only.

**Founder decisions (answered 2026-10-09 before implementation; the recommended option each time).** Each one says which code it blocked (GATES_AND_REVIEW §5).
1. **WebAuthn library.**
   - **(a) Recommended:** `go-webauthn` v0.18.2, which DEPENDENCY_POLICY already approves. It is maintained, handles every attestation format and many browser and authenticator quirks, and it accepts a caller-supplied challenge, which part 2 needs. The cost is about ten modules in the build (listed above).
   - **(b)** A small verifier written here that accepts only attestation `none`, with one CBOR module. Fewer dependencies, but security-critical parsing written and maintained by us alone.

   **Answer: (a)** `go-webauthn` v0.18.2. *Blocked:* slices 5 and 6.
2. **What proves it is you when you add a security key.** A stolen session cookie must not be enough to add an attacker's key, because the key is what approves.
   - **(a) Recommended:** a provider sign-in at most 5 minutes old (the page sends you back to your identity provider with `max_age=300`), or a step-up with a key you already have; you get an email for every key added or removed.
   - **(b)** A one-time enrollment code from an administrator for the first key (like an invitation). Stronger against a compromised provider account, but every new user needs an administrator.
   - **(c)** Only the session. Simplest, and a stolen cookie could add a key: not recommended.

   **Answer: (a)** a provider sign-in at most 5 minutes old, or a step-up with an existing key, and an email for every key added or removed. *Blocked:* key registration (slices 5 and 6).
3. **Which editions get which channels.** PRODUCT §7 says editions gate scale and integrations, never safety, and reaching deciders is part of safety (PN-004.2 is Community).
   - **(a) Recommended:** all four kinds in Community, at most 3 org channels; unlimited from Team. Slack approval cards (PN-017.3) stay Team, and digests (F620) stay Team in M10.
   - **(b)** Community gets `log` and `email` only; Slack and webhooks from Team.

   **Answer: (a)** all four kinds in Community, at most 3 org channels; unlimited from Team. *Blocked:* the channel limit in `CreateChannel` (slice 7) and an edition-limit field in billing.
4. **A security key whose counter goes backwards** (a sign of a cloned key, or of a faulty one).
   - **(a) Recommended:** refuse the step-up and suspend the key; the person removes it and registers a new one (fail closed).
   - **(b)** Accept, but flag the key and alert. Kinder to faulty keys, but a cloned key keeps working.

   **Answer: (a)** refuse the step-up and suspend the key. *Blocked:* the assertion code path (slice 5).

### G0 — M5 Human approvals, step-up & Agent Waitlist, part 2: approvals, transaction-bound step-up, the approval page and the Agent Waitlist — 2026-10-09

This brief is written before implementation (G0). It plans the rest of M5. It builds on part 1 (browser sessions, WebAuthn and notifications, on `main`), on M3 (agents, runs and `ADMISSION` entries) and on M4 part 2 (grants and the decision pipeline: slices 202–214 are on `main` as c0165a0, 215 is open as #103, and 216 is still to come). Until part 2 lands, nothing can satisfy a `REQUIRE_APPROVAL` or `REQUIRE_STEP_UP` decision: the pipeline lists the requirement, and the agent can only try again.

**Purpose:** a held action must be decided by the right person, about exactly the action that will run, and must lapse when anything material changes. Part 2 turns a hold into an **approval request** whose binding hash covers the action, its decision basis, its facts, the run, the instance and its key, the requirements, the deadline and the exact text shown. The request is approved with a WebAuthn assertion over that hash, by a person who is eligible and independent when they respond and still eligible when the approval is used. The approval is consumed at most once. Every pending human decision (admissions, access requests, holds, tool reviews, restorations and reconciliations) goes into one **Agent Waitlist** with priorities, deadlines, routing and escalation, and held agents wait on a **wait handle** instead of polling with retries. In product terms this completes the approval half of Pass ([PRODUCT.md](../PRODUCT.md) §4.2).

**What exists today** (from a survey of `main` at a4649e7; the brief fits this code):
- **Requirements.** Step 8 turns grant and guardrail requirements (`gdomain.Requirement`) and `REQUIRE_APPROVAL` / `REQUIRE_STEP_UP` policy rules into checklist items and two flat lists on the evaluation: `ApprovalRequirement{role, count, independent}` and `StepUpRequirement{subject, method}`.
  - The lists do not record which grant level or rule asked.
  - `role` is a free-form name (`finance.approver` in tests) that no tenancy role matches, and `independent` is never read.
  - Policies allow a count of 1–2 and grants 1–5. A policy step-up names `launcher` or `principal`; a grant's step-up subject is not checked.
- **Resubmission.** A resubmitted `OPEN` transaction runs the full pipeline again (at most 32 evaluations) and gets `REQUIRE_APPROVAL` again. There is no approval port, no wait field in `AuthorizeResponse` (fields 1–15) and no `Wait` RPC.
- **Decision basis.** The decision-basis digest covers the policy version, every grant and envelope revision, the definition digest and the digest of the facts used. There is no separate material-facts digest.
  - The evaluation knows the instance, agent, run, launcher and principal, but not the workload key thumbprint (`jkt`).
- **Finalization.** It checks containment and the grant chain only when it issues a permit; holds are recorded without that check. Nothing invalidates an `OPEN` transaction when a grant is revoked or narrowed: the next evaluation simply decides again.
- **Approval templates.** Definitions carry one: a `title` with `{operation}`, `{target.id}`, `{target.account}` or `{params.<material>}` placeholders, and up to 64 canonical fields. It is required for write operations. Nothing renders it yet.
- **Waitlist.** `waitlist_entries` (M3) allows only `ADMISSION`, with states `OPEN | APPROVED | REJECTED | EXPIRED | CANCELLED` and one open entry per subject. `WaitlistService` is read-only, and discovery entries never expire.
- **WebAuthn ceremonies.** `webauthn_ceremonies` allows the purposes `REGISTRATION | STEP_UP`, and a challenge is unique per org. Step-up uses a random challenge from the library; nothing passes a challenge of its own yet (go-webauthn's `WithChallenge` option is unused).
- **Notifications.** Templates have one fixed link per type (`/account`), and a test forbids "approve", "reply", "react" and "click here" in any template. `Enqueue` takes any number of personal recipients, but role routing reaches only org-scope bindings.
- **Roles.** `approver` holds `approval.respond` (human only) and can be bound at any scope; custom roles are a later Enterprise feature. Role bindings record `created_at`, and removals are recorded only in the ledger.
- **Agents.** Agents can be suspended (M3 stores the state they were suspended from), but nothing resumes them.

  - Sign-in may return to `/approvals` and `/approvals/<uuid>` (matched exactly by pattern).
  - The route-table test extends to `/approvals`.
- **SSE route:** `GET /v1/wait/{transaction}`, with PAP/1 headers (`htm` `GET`, `bh` of the empty body), answering `text/event-stream`.
- **Wire formats:**
  - **The binding** (design decision 13):
    ```
    SHA-256(JCS({v: 1, action_hash, effective_action_hash, decision_basis_digest, material_facts_digest, grant: {id, revision}, definition_digest, run_id, agent_instance, jkt, approver_requirements, expires_at, display_hash}))
    ```
    - Hashes are base64url, as in PAP-1, and `expires_at` is RFC 3339 UTC in whole seconds.
    - A restoration binds `{v, subject: "agent.restore", agent_id, agent_change_seq, requested_state, requested_by, reason_code, approver_requirements, expires_at, display_hash}`.
    - A batch challenge is `SHA-256(JCS({v: 1, batch: [sorted bindings]}))`.
    - PAP-1 §8 gains these additive fields (§13) in slice 204.
  - **The wait handle** is the transaction id (design decision 15). `Wait` and the SSE `state` events carry a state (`PENDING`, `EVIDENCE_REQUESTED`, `READY`, `DECLINED`, `NARROWER_PROPOSED`, `EXPIRED`, `SUPERSEDED`, `INVALIDATED`), codes, the deadline and, for `READY`, the consume-by time.
- **Notification types** (fixed templates; the link gains one id placeholder, `/approvals/{request}`; no parameter values, amounts or free text):
  - `approval.requested`, `approval.reminder`, `approval.escalated`, `approval.decided`, `approval.expired`, `approval.invalidated`;
  - `approval.unroutable`, `approval.multi_person_completed`;
  - `security.variant_suspected`;
  - `waitlist.entry_created`, `waitlist.entry_escalated` (non-hold kinds).
  - Titles say "approval" or "decision", never "approve": the part-1 template test stays as it is.
- **Configuration:**
  - `approvals.default_deadline` and `approvals.consume_window` (decision 6);
  - `waitlist.max_waits_per_instance` (default 4), `waitlist.max_waits` (default 1,000 per server), `waitlist.long_poll_max` (30 seconds, the maximum).

**Security constraints and design decisions:**
1. **Requirements (HR-170, decisions 2–4).**
   - The pipeline keeps each requirement with its source (grant level and revision, or policy rule) and its reason.
   - **Merging:**
     - Approval requirements that name the same role merge into one: the larger count wins, and `independent` holds if either asks for it.
     - Requirements for different roles stay separate, and each needs its own approvers.
     - One response counts toward one requirement only.
     - Step-up requirements are kept per subject.
   - **Validation from M5:**
     - the approval role follows decision 2;
     - a grant's step-up must name `launcher` or `principal` with the method `webauthn`, as a policy already must;
     - the counts stay as they are (1–2 in policies, 1–5 in grants), and a count of n needs n distinct people with n distinct credentials.
   - A stored requirement that fails these checks gives `CANNOT_AUTHORIZE` (`REQUIREMENT_INVALID`) at decision time, never a hold anyone could satisfy.
2. **The binding (HR-030).**
   - `action_hash` is the requested action and `effective_action_hash` the action after obligations clamp it: the approver sees, and binds, the action that will run (F108).
   - `material_facts_digest` is the digest of the facts the evaluation used.
   - `grant` is the run's grant id and revision; the whole chain is inside the decision-basis digest.
   - `jkt` comes from the identity step, which starts carrying it into the evaluation.
   - `approver_requirements` is the merged list from constraint 1.
   - `display_hash` is the SHA-256 of the canonical JSON of the stored display (constraint 9).
3. **Recording a hold (HR-171, HR-037).** When an evaluation's decision is `REQUIRE_APPROVAL` or `REQUIRE_STEP_UP`, the finalization that records it also:
   - takes the containment row `FOR SHARE` and checks the grant chain, as it does for a permit, which closes today's gap;
   - computes the binding;
   - keeps the transaction's current request if its binding is the same, so resubmitting while waiting creates nothing;
   - otherwise marks that request `SUPERSEDED` and inserts a new one linked to it;
   - takes a hold slot for the grant and the run, or answers `CANNOT_AUTHORIZE` (`HOLD_LIMIT_REACHED`) when they are full (decision 7);
   - opens or updates the `ACTION_HOLD` entry and enqueues the routing job with `InsertTx`.

   A decision that is `DENY` or `CANNOT_AUTHORIZE` creates no request, even when it lists approvals (S03).
4. **Using an approval (HR-031, HR-005).** A resubmission runs the whole pipeline.
   - Step 8 recomputes the binding with the request's stored deadline and accepts the transaction's request with that binding in state `APPROVED`, provided its stored requirements equal the current ones.
   - After the containment and chain checks, the finalization re-reads every approver's current eligibility (HR-170), then runs `UPDATE approval_requests SET state = 'CONSUMED' … WHERE state = 'APPROVED' AND binding = $b AND consume_by > now()`.
   - Zero rows roll everything back and re-evaluate, so one approval yields at most one permit.
   - The permit's receipt records the request id and binding; M6 adds the assertion to the permit (HR-038).
5. **Ending a hold (HR-039, HR-171).**
   - **Ends as `DENY`:** a decline (`APPROVAL_DECLINED`), a narrower proposal (`NARROWER_PROPOSED`), a deadline passed without approval, an approval not used by its consume-by time, and an evidence deadline passed without evidence (`APPROVAL_EXPIRED`). The transaction becomes `FINAL` with `DENY`, which is terminal for that action id (PAP-1 §7.1).
     - All of this is checked at use, by the database clock.
     - A minute janitor only updates states and sends notices; correctness never depends on it.
   - **Does not end the transaction:** a `SUPERSEDED` or `INVALIDATED` request. The next evaluation decides again.
6. **Invalidation (F153, F154, F639, S04).**
   - **Correctness comes from the binding:** any change to the action, the grant revision, a guardrail, the policy, the definition, a fact, the run, the instance or the key gives a different binding, so an old approval cannot match.
   - **Jobs keep the queue honest, for deciders and agents.** These transactions enqueue an invalidation job with `InsertTx` that marks the affected requests `INVALIDATED` with a reason, ends their entries and tells the deciders and the waiting agent:
     - the ones that raise the containment epoch: revising or revoking a grant, changing a guardrail, quarantining a definition, suspending or retiring an agent, and the kill switch;
     - removing a role binding, disabling a user, and removing or suspending a credential. These void that person's unconsumed responses instead, and a request below its count returns to `PENDING`.
7. **Approving and stepping up (HR-032, HR-033, decision 1).** Approval happens only on the approval page, in a `BINDING` ceremony.
   - **`approve-options`** checks:
     - the request is `PENDING`;
     - the caller is eligible for a requirement that still needs approvers;
     - the caller has not responded yet.

     It then stores a ceremony bound to the browser session, the user and the request. Its challenge is exactly the binding, and its allowed credentials are the caller's active ones.
   - **`approve`** verifies the assertion with part 1's checks (origin, RP ID, UV, counter). Then, in one transaction, it:
     - consumes the ceremony;
     - checks eligibility and cooldowns again;
     - inserts the response;
     - when every requirement is met, moves the request to `APPROVED` with its consume-by time (decision 6), by a conditional update.
   - A step-up is the same ceremony, completed by the person the requirement names. Nothing else grants: no RPC, CLI command, channel message or `GET` request can approve.
8. **Eligibility (HR-170, HR-035, HR-036, decisions 2, 3 and 5).**
   - **Who qualifies:** a decider must be an enabled user of the org, holding `approval.respond` through the requirement's role on the agent's scope path (its business unit, team and environment, as for every agent permission). They must also have at least one active WebAuthn credential.
   - **Who never qualifies:**
     - the run's launcher and represented principal;
     - the launcher and principal of every ancestor run;
     - for an `independent` requirement, also the agent's owner and backup owner and the person who issued the run's grant (decision 3).
   - **n-person requirements:** need n distinct users and n distinct credentials, with the cooldowns of decision 5, and the org's admins are told each time one is satisfied.
   - **When it is checked:** when the person responds, and again in the consuming finalization (F149).
9. **What the approver sees (HR-034, F139–F143, F157, F159).** The display is rendered when the hold is recorded, from the pinned definition's approval template, and stored as structured JSON. The page shows only that stored display, so what the approver reads is what the binding covers. It contains:
   - **the consequence first:** the title with canonical values filled in, the operation, the target, the effective value, and reversibility and verifier from the definition;
   - **the canonical fields:** stable ids verbatim, never normalized; amounts as canonical decimal with currency;
   - **the facts used,** each with its provider and age;
   - **the run:** task label, principal, agent, instance and run;
   - **the requirement basis:** the decisive checklist items and their sources;
   - **who can decide and why,** and the deadline;
   - **variant history and context:** the earlier variants of this grant, operation and target, plus at most five approved requests for the same operation and target in the last 30 days, labelled as context rather than precedent;
   - **one untrusted block** for agent-supplied text (the task label, text parameters, evidence notes and reported attributes):
     - bidi and control characters are removed, mixed-script identifiers are flagged, and each item is capped in length;
     - a fixed label says the text was written by the agent or the requester and not checked by PantherClaw.

   Readable names appear only beside the stable id, and only from facts the template names. The template may name them with `facts.<name>`, an additive change to the definition format.
10. **The approval page (HR-151, HR-034).**
    - `/approvals` lists the requests waiting for the caller and says which scope was checked (F626). `/approvals/{id}` shows one request.
    - Both use part 1's layout, CSP with Trusted Types, `no-store`, frame denial and CSRF rules. A new static script, `approvals.js`, writes text with `textContent` only.
    - A request is visible to its eligible deciders, the run's launcher and principal, and holders of `approval.read` on the agent's scope path. Anyone else gets "not found".
    - `GET` never records a decision, and nothing on the page is pre-filled from the URL.
11. **Decider actions that grant nothing (HR-172).** These need a human session (browser or CLI), not a security key. All are available on the page, through the API and through `pclaw`.
    - **Decline:** a reason code from a fixed list (`NOT_NEEDED`, `TOO_RISKY`, `WRONG_TARGET`, `NEEDS_DIFFERENT_APPROACH`, `OTHER`), an optional safer-alternative code, and a note.
      - The note is shown to people only: never returned to the workload, never sent in a notification and never logged (design decision 18).
    - **Request evidence:** a question code and note, and an evidence deadline before the hold's deadline. The request moves to `EVIDENCE_REQUESTED`.
      - Evidence is a note from the workload (`SubmitEvidence`) or from the run's launcher or principal. It is untrusted and does not change the binding; the request returns to `PENDING`.
      - A fact pushed by a registered provider does change the binding: the agent resubmits and gets a new variant.
    - **Propose a narrower action:**
      - The proposal keeps the operation, target, account and destinations, and changes only material parameters: amounts and integers no larger in magnitude, lists as subsets.
      - The pipeline simulates the proposal, and the decider sees its decision.
      - The original transaction ends as `DENY` (`NARROWER_PROPOSED`), and the wait handle returns the proposed canonical parameters.
      - The agent may submit them under a new action id, and that action gets its own decision and approval (F147). The original consent never transfers.
12. **Waitlist entry types (HR-177).** Priority (1–4) comes from the kind, the definition's reversibility and the deadline, never from agent input. Lists sort by priority, then deadline.

    | Kind | Subject | Created by | Decided by | Deadline | When it passes |
    |---|---|---|---|---|---|
    | `ADMISSION` | instance, or discovered agent | M3 (unchanged) | `AdmitInstance`, claim | 7 days (instances) | expired, not admitted |
    | `ACCESS_REQUEST` | the run's grant | `RequestAccess` from a person or the workload (decision 10) | `ReviseGrant` citing the entry, by someone allowed to issue that grant, or `DismissAccessRequest` | 7 days | expired, nothing changes |
    | `ACTION_HOLD` | approval request | the hold finalization | the approval page | the request's deadline (decision 6) | `DENY` |
    | `TOOL_REVIEW` | imported package version | `ImportPackage` | `TransitionPackage` by a `package.activate` holder | 30 days | expired, stays inactive |
    | `RESTORATION` | suspended agent | `RequestAgentRestoration` with a reason | the approval page, by an `agent.restore` holder other than the requester (decision 11) | 24 hours | expired, stays suspended |
    | `RECONCILIATION` | transaction with an `UNKNOWN` outcome | `RecordExecution` (unknown) and the sweeper | M7; in M5 only assignment | 72 hours | stays open and escalates; never resolves by itself (HR-003) |

    - A request parked with `RECONCILIATION_REQUIRED` names its open `RECONCILIATION` entry.
    - Assignment (`AssignWaitlistEntry`) only shows who is working on an entry; it never changes who may decide.
13. **Routing and escalation (HR-173, decision 8).**
    - **The routing job** computes the eligible deciders with a scope-path query (current role bindings, enabled users, minus the people constraint 8 excludes).
      - It sends personal notifications to at most 50 of them, nearest scope first, plus channels subscribed to `approval.*`.
      - It records each recipient in `waitlist_routes`.
    - **Reminders and escalation** follow the chain. Each step recomputes eligibility and adds deciders at a wider scope; no step makes anyone eligible. Every step happens before the deadline.
    - **Routing health:**
      - No eligible decider sets `NO_ELIGIBLE_DECIDER` and sends `approval.unroutable` to the org's admins and Security Admins. The hold stays and resolves to `DENY` at its deadline (F635).
      - Failed deliveries set `DELIVERY_FAILING` and never count as a decision (HR-039).
14. **Wait handles (HR-174).**
    - **`WorkloadService.Wait`** long-polls for at most 30 seconds. **`GET /v1/wait/{transaction}`** streams `state` events with a heartbeat every 15 seconds, and closes after 5 minutes or at a terminal state.
    - **Who may wait:** both need a PAP/1-authenticated workload whose run and instance are the transaction's.
    - **What a wait returns:** states, codes and times only; never approver identities, notes or the display.
    - **How waiters learn of changes:** each server holds one `LISTEN` connection on `pc_wait`, with payloads `org_id:transaction_id` only (HR-056). A waiter re-reads the state from the database, and re-reads every 5 seconds in case a notice was missed.
    - **Limits:** 4 waits per instance and 1,000 per server; beyond them the answer is `ResourceExhausted` with a retry time.
    - Waiting never extends a deadline or dispatches anything; on `READY` the agent resubmits the identical action.
    - The development gateway's reply to a hold carries the handle and the deadline. M6 maps it to MCP pending results.
15. **HOLD caps and variants (HR-037, decision 7).**
    - Pending holds (`PENDING`, `EVIDENCE_REQUESTED`, or `APPROVED` and not yet used) are capped per grant and per run, with counter rows changed by conditional updates, so concurrent holds cannot exceed the cap.
    - A variant is a request for the same grant, operation and target as an earlier one. Approvers see the variant history.
    - The third variant within 24 hours raises `security.variant_suspected` (an audit event and a notice). The detection rule is M10.
16. **Batch review (HR-175, Team, decision 9).**
    - **What may be approved together:** at most 25 `ACTION_HOLD` entries with the same operation and definition digest, a reversible definition, one approver without step-up or `independent`, and a value at or below the org's batch ceiling.
    - **The ceremony:** one `BINDING` assertion whose challenge is the batch hash of exactly those bindings.
    - **Each entry** gets its own response, audit event and later consumption.
    - **Batch decline** is allowed for any set with the same operation.
    - Irreversible, two-person and high-value entries are always reviewed one by one.
17. **Access requests and restorations (HR-176, decisions 10 and 11).**
    - **Access requests:**
      - An access request creates no rights (F051). The deadline is 7 days.
      - It is routed to the person who issued the run's grant and to `grant.issue` holders on the agent's team. *As implemented,* it is routed to the holders of `grant.issue` on the agent's scope path, and the grant's issuer only when they are one of them (part 2 exit status, deviation 8).
      - It is resolved only by a grant revision through `GrantService`, with that revision's issuance checks and audit, or by dismissal.
    - **Restorations:**
      - A restoration is an approval request with subject kind `RESTORATION`, bound as in the wire format above.
      - It is decided on the approval page with a `BINDING` assertion, by someone other than the requester.
      - When approved, it returns the agent to the state it was suspended from, in the same transaction.
    - No approval widens a grant, a guardrail or a policy, and nothing approves "all similar" requests (F148).
18. **SLA metrics (Team, PN-004.4).** `GetWaitlistMetrics` reports, per kind and per decider, over a window of at most 90 days:
    - counts;
    - median and 90th-percentile time to first response and to decision;
    - expiry rate, escalation rate and routing failures.

    It filters by the caller's permissions before aggregating (T-042). Server metrics are OpenTelemetry histograms without org labels.
19. **Editions (PRODUCT §7).** Approvals, step-up, every entry type, routing, escalation and wait handles are Community, because reaching deciders is safety. Batch review and SLA metrics are Team, as FEATURES lists them. Without a Team licence, their routes and RPCs answer `PermissionDenied` with an edition reason.
20. **Logging and evidence.**
    - **Ledger events:**
      - every request created, superseded, invalidated, expired and consumed;
      - every response and void;
      - batch decisions, with one event per entry;
      - escalations, routing failures, assignments;
      - access requests and restorations;
      - escalation-chain and settings changes.
    - **Logs** carry ids, hashes and codes only. Notes, evidence and displays are never logged.
    - **Consent history is kept (F160).** Requests and responses are never deleted by M5; retention is M7.
21. **Failure semantics.**
    - If the approvals store is unavailable, the decision is `CANNOT_AUTHORIZE`, never `ALLOW`.
    - If a notification channel is down, holds wait until their deadline.
    - A lost `LISTEN` connection falls back to polling.
    - A failed WebAuthn verification records no response.

**Dependencies to add:** none. go-webauthn already provides `WithChallenge`; SSE is plain `net/http`.

**Founder decisions (answered 2026-10-10; the recommended option each time).** Each one says which slices it blocked (GATES_AND_REVIEW §5).

1. **Which approvals need a security key.** HR-033 asks for a WebAuthn assertion bound to the action for high-consequence approvals; the question is whether that covers every approval.
   - **(a) Recommended:** every approval, step-up and restoration is a WebAuthn assertion whose challenge is the binding, made on the approval page. Actions that grant nothing (decline, request evidence, propose a narrower action) need only a signed-in person, through the page, the API or `pclaw`.
     - A stolen session cookie or CLI token can then never approve, and M6 can put an assertion into every approved permit.
     - The cost: every approver needs a passkey or security key, and `pclaw approval approve` opens the browser.
   - **(b)** Only high-consequence approvals need a key: irreversible definitions, values above an org threshold, or a rule that asks for it. Others may be approved by a signed-in person through the API or the CLI. This is more convenient, but it creates a second, weaker approval path, and "high consequence" has to be defined now.
   - *Blocked:* slices 207–209 and 216.

   **Answer: (a)** every approval, step-up and restoration is a WebAuthn assertion bound to the action, made on the approval page; decline, evidence requests and narrower proposals need only a signed-in person.
2. **What the `role` in an approval requirement means.** Policies and grants name a role (tests use `finance.approver`), but PantherClaw has only its default roles; custom roles are a later Enterprise feature.
   - **(a) Recommended:** the role must be a default role that contains `approval.respond` (today only `approver`). The scope does the rest: someone is eligible when the role is bound on the agent's scope path. So "release approver" means Approver on the production environment, and "reviewer" means Approver on the team. Policies and grants naming another role are refused from M5 on (stored ones give `REQUIREMENT_INVALID`). Approver groups come later.
   - **(b)** Approver groups now: named sets of users that Org and Security Admins manage, which a requirement names. More expressive, but it adds a new table, API and CLI, and group membership becomes a new way to make yourself eligible.
   - **(c)** Keep the names as labels only: anyone with `approval.respond` in scope qualifies. Simple, but a policy saying `finance.approver` would accept any approver: misleading, so not recommended.
   - *Blocked:* slice 204 (eligibility) and the requirement validation in slice 206.

   **Answer: (a)** the role must be a default role that contains `approval.respond` (today `approver`), bound on the agent's scope path; other role names are refused from M5 on, and approver groups come later.
3. **Is every approval independent?** The `independent` flag exists but nothing reads it.
   - **(a) Recommended:** yes. The run's launcher and represented principal, and those of every ancestor run, never count toward an approval. `independent: true` additionally excludes the agent's owner and backup owner and the person who issued the run's grant.
     - "Confirm it yourself" is what a step-up is for: a solo developer trying PantherClaw uses a step-up rule, and an approval needs a second person.
   - **(b)** Only requirements marked `independent: true` exclude the initiator; otherwise a developer may approve their own agent's action. Easier for solo trials, but it makes self-approval (T-002) a matter of how each rule is written.
   - *Blocked:* slice 204.

   **Answer: (a)** every approval is independent of the run's launcher and represented principal and those of every ancestor run; `independent: true` also excludes the agent's owner and backup owner and the grant's issuer.
4. **A step-up whose subject is not a person.** A rule asks the `launcher` or the `principal` to step up, but a run can be launched or represented by a service account, and a child run is launched by its parent's instance.
   - **(a) Recommended:** the decision is `CANNOT_AUTHORIZE` (`STEP_UP_SUBJECT_NOT_A_PERSON`), so the policy author uses an approval for automation instead. The checklist says why.
   - **(b)** Fall back to the agent's owner (or backup owner). This keeps CI runs moving, but it quietly turns a step-up into an owner approval without independence.
   - **(c)** For a child run, `launcher` means the nearest ancestor run launched by a person; otherwise (a).
   - *Blocked:* slices 204 and 206.

   **Answer: (a)** `CANNOT_AUTHORIZE` (`STEP_UP_SUBJECT_NOT_A_PERSON`).
5. **Approver cooldowns and notices (HR-035).** These guard against a fresh account or a freshly granted role being used to approve, especially by an administrator who grants themselves Approver (allowed and audited since ADR-0016).
   - **(a) Recommended:**
     - For a requirement of two or more people, each approver's account must be at least 7 days old in the org, the role binding that makes them eligible at least 24 hours old, and the credential they use at least 24 hours old.
     - For every approval, a role a person granted themselves counts only after 24 hours.
     - Each satisfied multi-person approval notifies the org's admins and Security Admins.
     - An org may lengthen these periods, never shorten them.
   - **(b)** Cooldowns only for multi-person approvals, with no self-grant rule.
   - **(c)** No cooldowns, only notices.
   - The cost of (a): in a brand-new org, the first approvals need someone whose role was granted by another person, or a day's wait.
   - *Blocked:* slices 204 and 207.

   **Answer: (a)** for two or more approvers, an account at least 7 days old in the org, an eligibility-giving role binding at least 24 hours old and a credential at least 24 hours old; for every approval, a self-granted role counts only after 24 hours; admins and Security Admins are told of each satisfied multi-person approval; orgs may lengthen these periods, never shorten them.
6. **Deadlines.**
   - **(a) Recommended:**
     - A hold's deadline is 1 hour by default. A policy rule or grant requirement may set its own, from 5 minutes to 7 days (an additive `deadline` field), and the shortest wins.
     - Once approved, the agent must resubmit within 15 minutes, and before the deadline.
     - Other kinds: `ACCESS_REQUEST` 7 days, `TOOL_REVIEW` 30 days, `RESTORATION` 24 hours, `RECONCILIATION` 72 hours (then escalation only). `ADMISSION` stays 7 days.
     - Orgs may shorten them in their waitlist settings.
   - **(b)** A short fixed lifetime for every hold (10 minutes, as in the product specification's example). Simpler, but a merge review or a refund approval outside office hours would expire before anyone sees it.
   - *Blocked:* slices 202, 204 and 206 (the deadline is in the binding).

   **Answer: (a)** holds last 1 hour by default (a requirement may set 5 minutes to 7 days; the shortest wins), and an approval must be used within 15 minutes and before the deadline; `ACCESS_REQUEST` 7 days, `TOOL_REVIEW` 30 days, `RESTORATION` 24 hours, `RECONCILIATION` 72 hours (then escalation only), `ADMISSION` 7 days.
7. **HOLD caps and variants (HR-037).**
   - **(a) Recommended:**
     - At most 20 pending holds per grant (an org may lower this; hard maximum 100) and 5 per run. Beyond them the answer is `CANNOT_AUTHORIZE` (`HOLD_LIMIT_REACHED`).
     - The third variant of one grant, operation and target within 24 hours raises `security.variant_suspected`.
     - Approvers always see the variant history.
   - **(b)** At most one pending variant per grant, operation and target: a new variant is refused until the earlier one is decided or expires. Stricter, but an agent that corrects an amount has to wait.
   - *Blocked:* slices 202 and 206.

   **Answer: (a)** at most 20 pending holds per grant (orgs may lower it; hard maximum 100) and 5 per run, then `HOLD_LIMIT_REACHED`; the third variant of one grant, operation and target within 24 hours raises `security.variant_suspected`.
8. **Escalation defaults.**
   - **(a) Recommended**, a chain that orgs and teams may replace (at most 5 steps, `waitlist.manage`):
     - **At the hold:** notify the eligible deciders nearest in scope (environment and team bindings, or the next wider scope if there are none), plus channels subscribed to `approval.*`.
     - **At half the deadline:** remind them and add business-unit deciders.
     - **At three quarters:** add org-scope deciders, and send the agent's owner and backup owner a notice. They get no vote unless they are eligible.
   - **(b)** Notify every eligible decider at once, with no reminders or escalation unless an org configures them. Simpler, but noisier, and nobody is chased before the deadline.
   - *Blocked:* slice 211.

   **Answer: (a)** nearest-scope deciders and `approval.*` channels at the hold, a reminder and business-unit deciders at half the deadline, org-scope deciders and a notice to the agent's owners at three quarters; orgs and teams may replace the chain (at most 5 steps).
9. **Batch review limits (PN-004.5, Team).**
   - **(a) Recommended:** batch approval only for reversible definitions with one approver, no step-up and no `independent`, at most 25 entries, and a value at or below the org's batch ceiling. The ceiling starts unset, so batch approval is off until an Org Admin or Security Admin sets it. Batch decline is allowed for any set with the same operation.
   - **(b)** Only batch decline in M5; batch approval later.
   - **(c)** As (a), with a default ceiling of 100 USD.
   - *Blocked:* slice 214.

   **Answer: (a)** batch approval only for reversible, single-approver entries without step-up or `independent`, at most 25, at or below an org batch ceiling that starts unset (off); batch decline for any set with the same operation.
10. **Who may file access requests (F051).**
    - **(a) Recommended:** the run's launcher or represented principal, and the workload itself when it cites one of its own run's denials whose decisive reason is about scope. Workloads may file at most 3 per run, and their note is untrusted. The request grants nothing; the grantor decides through a grant revision.
    - **(b)** People only. Agents cannot ask, so a person has to notice the denial first.
    - *Blocked:* slice 210.

    **Answer: (a)** the run's launcher or represented principal, and the workload citing one of its own run's scope denials (at most 3 per run, untrusted note).
11. **Who restores a suspended agent (F563).**
    - **(a) Recommended:** a new human-only permission `agent.restore`, held by Security Admin and Responder. The decider must not be the person who asked for the restoration, and they approve on the approval page with a security key. Asking needs `agent.manage` and a reason.
    - **(b)** Also Org Admin. More people can unblock work, but administration would then include a containment decision, against F583's separation.
    - **(c)** The owner may restore an agent they suspended themselves without review; anything else as (a).
    - *Blocked:* slices 203 and 210.

    **Answer: (a)** a new human-only `agent.restore`, held by Security Admin and Responder; the decider is not the requester and approves on the approval page with a security key; asking needs `agent.manage` and a reason.

**Design decisions taken in this brief (confirmed with the approval):**
12. **The WebAuthn challenge is the binding itself** (HR-033, PAP-1 §8).
    - `BINDING` ceremonies are unique per request (or batch) and user while unconsumed, instead of a per-org unique challenge, because several approvers sign the same binding.
    - A captured assertion can only repeat the same person's response to the same binding, which the unique response absorbs.
13. **Binding fields.**
    - The binding adds `v`, `effective_action_hash` and the grant as `{id, revision}` to PAP-1 §8, an additive change.
    - The material-facts digest is the evaluation's facts digest.
    - The identity step carries `jkt` into the evaluation.
14. **Requirement merging** works as in constraint 1. One response counts toward one requirement.
15. **The wait handle is the transaction id.** It is not a secret: PAP/1 authentication as the transaction's run and instance authorizes the wait.
16. **Waiting uses both a long-poll RPC and an SSE route**, as BUILD_GUIDE §8 asks. `LISTEN`/`NOTIFY` carries ids only, with polling as the fallback.
17. **Restorations reuse the approval machinery**, with subject kind `RESTORATION` and their own binding.
18. **Decline and evidence notes are for people.** They are never returned to the workload, never sent in a notification and never logged; the workload gets codes.
19. **Approving is a page action only.** Decline, evidence requests and narrower proposals are also RPCs and `pclaw` commands.
20. **`RECONCILIATION` entries never expire into a resolution.** An `UNKNOWN` outcome stays visible and escalates until M7 resolves it.
21. **Notification links gain one id placeholder.** Channel messages still carry no parameter values, amounts or free text.
22. **Invalidation is decided at use, by the binding.** Invalidation jobs only keep the queue and the waiting agents up to date.

**Founder decision, 2026-10-10 (migration numbers):** part 2's migrations take the next numbers after M6's range: **`00050_approvals.sql`** and **`00051_waitlist.sql`** instead of `00032` and `00033`. **Slice 202 (migrations and schema tests).** Deviations from the contracts above:
1. **`approval_batches` is in `00050`**, not `00051`: approval responses and `BINDING` ceremonies reference it.
2. **A `RESTORATION` entry's subject is its approval request.** The agent is in `agent_id`, and a unique index on `approval_requests` allows one live restoration per agent. With the agent as the subject, a discovered agent's open `ADMISSION` entry would collide with its restoration.
3. **`waitlist_settings` also holds the consume window and the decision-5 cooldowns.** Like the deadlines and caps, each column can only move in the safe direction: deadlines and the consume window shorter, caps lower (the grant cap up to the hard maximum of 100), cooldowns longer. `NULL` means the default.
4. **`pc_wait` is raised by a trigger on `approval_requests`**, as M6's `pc_containment` is, so every use case that creates or changes a request wakes the waiters of its transaction, with `org_id:transaction_id` only.
5. **`waitlist_entries.agent_id` is nullable**, because a `TOOL_REVIEW` entry concerns a package version, not an agent. A CHECK gives each kind its own subject type and required columns.
6. **M3's `CloseOpenAgentEntries` now closes only `ADMISSION` entries**, so claiming or retiring an agent never closes its holds, access requests or `RECONCILIATION` entries (HR-177).
7. **A response, once voided, stays void:** a trigger refuses a second void. A person responds at most once per request (`APPROVE` or `STEP_UP`), including after a void.

**Slice 203 (protos, permissions and roles).** Deviations and additions:
1. **Four RPCs are declared `authenticated`:** `ListApprovalRequests`, `GetApprovalRequest`, `SubmitApprovalEvidence` and `WaitlistService.RequestAccess`. The API's interceptor requires a declared permission somewhere in the caller's roles, but the run's launcher or principal may hold none. These use cases check the relation themselves (`approval.read` on the agent's scope path, eligibility, or being the run's launcher or principal) and answer "not found" otherwise.
2. **`WaitInfo` carries more than the handle, the retry time, the deadline and the state:** the approval request id (for the `/approvals/{id}` link), a code (the end reason or the evidence question, never a note), the evidence deadline and, for `NARROWER_PROPOSED`, the proposed canonical parameters. The state set adds `CONSUMED`, so a waiter can tell that its approval was used.
3. **Code lists the brief left open:** decline's safer alternatives (`NARROWER_ACTION`, `PERSON_PERFORMS`, `RETRY_LATER`, `ASK_OWNER`) and evidence questions (`WHY_NEEDED`, `CONTEXT`, `PARAMETER_BASIS`, `OTHER`). `ProposeNarrowerAction` has `validate_only`, so a decider can see the simulated decision before ending the request.
4. **The workload's access request message is `WorkloadServiceRequestAccessRequest`.** buf's naming rule needs it, because `WaitlistService` also has `RequestAccess`.
5. **Security Admin and Responder become human-only roles.** `agent.restore` is human only (decision 11), so these two roles can no longer be newly bound to a service account. An existing binding keeps its other permissions, because human-only permissions are filtered per permission.

**Slice 204 (approvals domain, `internal/approvals/domain`).** Deviations and choices:
1. **A restoration binds `reason_hash`, not `reason_code`.** The requester's reason is free text (`RequestAgentRestoration`), so the binding covers its SHA-256.
2. **Every hash and digest in a binding is base64url of its 32 bytes**, including the decision basis, facts and definition digests that the API shows as `sha256:<hex>`.
3. **The grant's issuer means every person who issued or revised a grant in the run's chain.** An `independent` requirement excludes all of them, the strict reading of "the person who issued the run's grant", because a delegated grant's direct grantor is an instance.
4. **A response counts toward the first requirement, in order, that is still short and that the person qualifies for.** Approvals come before step-ups.
5. **A requirement's sources (grant level or policy rule) are stored and shown but not bound.** They are already inside the decision-basis digest.

**Slice 205 (rendering).** The display is versioned structured JSON (`v: 1`), and its hash is SHA-256 over its RFC 8785 form. Choices:
1. **"Who can decide" is the rule, not names:** the role, the count, independence and where the role must be bound. Eligibility changes and is checked again at every response and at use, so names would make the hashed display stale.
2. **Variant history and the 30-day context are captured when the hold is recorded.** They are part of the hashed display; `GetApprovalRequest` also returns the live variant history.
3. **An approval template may name `facts.<name>` only for a fact the definition requires**, an additive change to the definition format. Dedupe keys still may not use facts.
4. **A clamped field shows the effective value, with the requested value beside it** (F108).
5. **Agent- and requester-supplied text goes only into the untrusted block:** the task label, text parameters, reported attributes and a restoration's reason. Each item is at most 1,000 characters, a block holds at most 16 items, and bidi and control characters are removed. A word that mixes writing systems is flagged; CJK scripts count as one system.
6. **A fact shows its provider and when it was observed, not its age.** The age changes with time; the page computes it, so a resubmission recomputes the same display and binding.

**Slice 206 is split in two pull requests:** 206a decides (the pipeline) and 206b records (the finalization). Notes for 206a:
1. **The requirement checks of decisions 2, 4 and 6 apply to new policies and new grant requirements only** (`DecodeBundle`, `DecodeRequirements`). Stored ones are read as they are. Step 8 answers `CANNOT_AUTHORIZE` (`REQUIREMENT_INVALID`) for them, as the brief asks, instead of failing to load the policy or the grant.

4. **Step 8 reads the transaction's latest request, its variants and the org's hold deadline in the evaluation's snapshot (#158).** A child run's ancestors are read only for child runs.

**Slice 206b (the finalization records and consumes).** Notes:
1. **A hold takes the permit's containment and chain check** (the containment row `FOR SHARE`, grant and guardrail revisions), so no request is recorded under the kill switch or on changed authority.
2. **The new request is inserted after the transaction row**, in the same transaction, with its hold slots (`HOLD_LIMIT_REACHED` when the grant's or the run's cap is full), its `ACTION_HOLD` entry and an `approval.requested` audit event. A changed binding supersedes the live request (`BINDING_CHANGED`) and closes its entry as `CANCELLED`.
3. **The `ACTION_HOLD` entry's priority comes from a first `internal/waitlist/domain`:** irreversible holds are urgent, and a deadline within 15 minutes raises the priority one step. Slice 210 extends that domain.

If the approval is no longer met, the finalization rolls back. A separate transaction then voids those responses (`ROLE_REMOVED`, `USER_DISABLED`, `CREDENTIAL_REMOVED` or `NOT_ELIGIBLE`), returns the request to `PENDING` with a new open entry, and the action is decided again.

**Slice 207a (responses, `internal/approvals/app`).** Notes:
1. **Migration `00052` keeps the held action's canonical form on its request** (`action_ir`, never shown and not updatable), so a narrower proposal can be checked against it and simulated. The constraint is `NOT VALID`, so requests held before it stay readable.
2. **Declining, asking for evidence and proposing a narrower action need a person with a browser or CLI session** who holds the requirement's role on the agent's scope path and is not excluded. In one transaction it consumes the `BINDING` ceremony (this person, browser session and request, within 5 minutes), checks eligibility and cooldowns again with the credential used, records the response toward the first requirement still short, and moves a met request to `APPROVED` with its consume-by time. **Slice 207b (the approvals janitor).** A per-org River job runs every minute (`approvals.janitor_org`, fanned out through the audited org lister). It:
1. expires overdue requests (deadline, evidence deadline, consume-by);
2. **invalidates live requests made moot**, with the change as the end reason: the kill switch, a suspended or retired agent, an ended run, a revoked grant in the chain, a revised grant, or a definition that is no longer active;
3. **checks the people of every counting response again.** It voids responses of removed roles, disabled users and removed or suspended keys, and returns approved requests no longer met to `PENDING`.

**Deviation:** the brief has each changing use case (grant revision or revocation, guardrails, quarantine, suspension, the kill switch, role binding removal, user disable, credential removal) enqueue an invalidation job with `InsertTx`. Instead, one sweep reads the current state every minute, so none of those use cases (M2, M3, M4, M6) change. Correctness is unchanged: a material change gives a new binding at use, and consumption re-checks eligibility. The queue reflects a change within a minute. **A changed guardrail is caught at use only** (the request is superseded), because a request does not record the guardrail revisions behind its basis digest. The janitor's server wiring comes with slice 215.

1. **`waitlist.Writer.RequestAccess` lets the run's launcher or represented principal file a request for the run's grant**, optionally citing one of the run's transactions. Anyone else gets "run not found". The note is kept as untrusted evidence. The entry records the grant's current revision and the cited denial's reason; its deadline is 7 days.
2. **`RequestWorkloadAccess` lets the run's own instance file one**, citing a denial of its run whose decisive reason a grant revision could change: `OPERATION_NOT_GRANTED`, `TARGET_NOT_GRANTED`, `DESTINATION_NOT_GRANTED`, `GRANT_LIMIT_EXCEEDED` or `OUTSIDE_TIME_WINDOW`. Guardrails, budgets and a missing grant are not the grant's scope. A run's workload may file at most 3.
3. **A grant with an open request returns that one.** There is one open entry per subject, so a second request adds nothing.
4. **`DismissAccessRequest` closes a request as `REJECTED`** with a reason, for a person holding `grant.issue` on the agent's scope path.
5. **`ReviseGrant` with `access_request_id` closes the cited request as `APPROVED`** in the revision's own transaction (HR-176). A revision citing anything other than this grant's open request fails and stores nothing.

Notes for 210c (restorations, decision 11):
1. **`approvals.RequestRestoration` asks for a suspended agent to be restored.** It needs a person holding `agent.manage` where the agent lives, and a reason of 1 to 1,000 characters, shown as untrusted text. It creates a `RESTORATION` approval request whose binding covers the agent's recorded change count and the state it returns to. Its `RESTORATION` waitlist entry shares the request's deadline: 24 hours, or the org's shorter setting. An agent with a live restoration returns that one.
2. **A restoration has one requirement, kind `restore`.** It is met by a person holding a role with `agent.restore` where the agent lives (Security Admin or Responder; a self-granted one only after the self-grant delay), other than the requester, with an active key. Only the server creates it; no grant or policy may name it. `LoadEligibility` loads those roles and the requester for a restoration.
3. **Approving on the page uses the restoration at once.** In the approval's transaction the agent must still be suspended from the bound state with no change since (else `AGENT_CHANGED`). It then returns to that state through `agents.Restore`, which records an `agent.restored` change, and the request becomes `CONSUMED`.
4. **Evidence requests are refused for a restoration**, which has no run to give evidence. The janitor invalidates a live restoration whose agent was retired, left `SUSPENDED` or changed.

**Slice 211 is split in two pull requests:** 211a covers the notice types and first routing, and 211b escalation, reminders, delivery health and decision notices. Notes for 211a:
1. **The approval and waitlist notice types** render only ids, fixed codes, the operation and times (HR-158). An approval notice links to `/approvals/{request}`, the one placeholder a link may hold, and only a canonical id fills it. No title or body asks anyone to approve.
2. **A routing job runs every 15 seconds** (`waitlist.route_org`, fanned out through the audited org lister). It routes each open entry that has not been routed yet, in its own transaction.
3. **Eligible deciders come from a scope-path query, then the eligibility rules.** The query finds enabled people holding a deciding role where the agent lives, ranked by their nearest binding (environment or team, business unit, org). Holds and restorations then apply the approval rules (`MayRespond`), and a step-up's named person is always included. The other kinds need their permission and exclude the requester. Routing never makes anyone eligible (HR-173).
4. **The nearest deciders, at most 50, get a personal notice;** channels subscribed to the type get it too. Each recipient is recorded in `waitlist_routes`, and the next step is set at half the entry's time.
5. **An entry no one may decide is marked `NO_ELIGIBLE_DECIDER`.** For a hold or a restoration, `approval.unroutable` goes to the org's admins and Security Admins. The entry still ends as its kind says (F635). Other kinds get their admin notice with escalation (211b).
6. **`notifications.Enqueued` now names the channels a notice went to**, so routing can record them.

Notes for 211b:
1. **Escalation chains** (decision 8) have 1 to 5 steps. Each step sits at a percentage of the entry's time, starts from 0%, comes later than the one before, stays below 100% and never narrows its scope. A step can remind, notify the agent's owners and notify channels. `Reader.GetEscalationChain` returns the team's chain, else the org's, else the default (revision 0). `Writer.SetEscalationChain` needs `waitlist.manage` at org scope and the current revision, and is audited.
2. **The router takes every step of the chain, the first one included.** `escalation_step` counts the steps taken, so 0 means not routed yet, and a chain whose last step is done has no next step time. Each step recomputes the eligible deciders. It notifies the ones within its scope who were not told before (`approval.escalated`), reminds earlier recipients who are still eligible (`approval.reminder`), and tells the agent's owner and backup owner. Owners get no vote unless they are eligible, and the route records them as `owner`. A step never runs at or after the deadline.
3. **An entry with no eligible decider tells the org's admins and Security Admins once:** `approval.unroutable` for holds and restorations, `waitlist.entry_escalated` for the other kinds.
4. **`DELIVERY_FAILING`**: each run asks the notifications module which routed open entries had a notice fail to deliver, and marks them. Only that module reads delivery state (HR-039). A failed delivery never decides anything.
5. **Notifications gain `PersonalOnly`** (a step that does not notify channels) and `FailedSubjects`.

Notes for 211c (outcome notices):
1. **Each outcome is told once, in the transaction that decides it.** The recipients are the people a request was routed to and the person who asked for it (the run's launcher, or a restoration's requester). Decline and narrower proposals send `approval.decided` with the end reason; an approval or restoration that meets its requirements sends it with `APPROVED`. The janitor's expiry sends `approval.expired`, and its invalidation `approval.invalidated` with the reason. Each notice has its own dedupe key and goes out only when the request is in the matching state.
2. **A completed multi-person approval tells the org's admins and Security Admins** (`approval.multi_person_completed`).
3. **The first routing of a hold that is at least the third variant** of one grant, operation and target within 24 hours tells the Security Admins (`security.variant_suspected`, decision 7).
4. **`approvals.Service.Notify` and the janitor's notifier are optional**: without one nothing is sent. Server wiring comes with slice 215. A request expired at use by the finalization (an agent resubmitting after the deadline) is not told; the janitor finds only requests still live.

**Slice 212 (wait handles, HR-174).** Notes:
1. **`approvals.Waits` serves wait handles** for the instance the transaction's run is bound to, and for that run when one is named. Anyone else gets "no wait handle". A handle shows states, codes and times only: the state at the database clock, the end reason or the evidence question, the deadline, the consume-by time when `READY`, the evidence deadline, the request id and a narrower proposal's parameters. It never shows an approver, a note or the display.
2. **`Wait` long-polls for at most 30 seconds.** It answers at once when the state differs from the known one or is final. Otherwise it answers on a change or at the timeout, reading the state again every 5 seconds in case a notice was missed.
3. **`Run` holds one `LISTEN pc_wait` connection per server** and wakes the waiters of the `org_id:transaction_id` in each payload (HR-056). It reconnects with backoff; without it, waiters still read every 5 seconds.
4. **Limits:** 4 concurrent waits per instance and 1,000 per server, configurable. Beyond them the answer is `WAIT_LIMIT_REACHED` (`ResourceExhausted`) with a 5-second retry time.
5. **`GET /v1/wait/{transaction}`** (`workloadrpc.Workload.WaitStream`) checks PAP/1 with method `GET` and the SHA-256 of the empty body, and consumes the proof. It then streams `state` events at once and on every change, with a heartbeat comment every 15 seconds, and closes at a final state or after 5 minutes. Answers: 404 for anyone else, 401 with `PAP-Error` for bad credentials, 429 with `Retry-After` beyond the limits. Waiting never extends a deadline or dispatches anything. The Connect `Wait` handler comes with slice 213, and the server wiring (the listener, the route, the limits from configuration) with 215.
