### G0 — M30 — Gaps from the threat map — 2026-11-04

This brief is written before implementation (G0). The founder approved the coding-phase plan as planned on 2026-11-04 (FD1–FD15) and answered the M30 questions E, S, C and P the same day. A coordinator makes every design decision as D900–D949; this brief condenses them. **Status: coded, then tested in the testing phase.** Every stream coded on a pushed branch with no tests and no pull requests, and `code/m30` assembled the streams on M29's exit branch. The testing phase (2026-11-05) added the tests, RT-200..RT-203 and the exit e2e on `land/m30`, which lands as one pull request (FD1).

**Purpose:** the M28 threat map listed agent-reachable techniques with no PantherClaw control. M30 adds controls where PantherClaw already sees the act, and maps them on the threat map ([ADR-0057](../adr/0057-firewall-gaps-from-the-threat-map.md)). They fall in two groups (founder, 2026-11-05):
- **Agent identity protection** (Badge): MCP tokens bound to a client's key with DPoP.
- **Runtime firewall:** read limits and share checks (with enumeration and scheduled-send alerts), agent configuration and memory, decoding before content signals, and a vector-store connector.

**Scope (decisions condensed):**
- **Process (D900–D902).** Phase 1 from `origin/main` (fb03e638) covers what M29 does not touch; phase 2 starts when `feat/m29-exit` exists and each stream merges it. Each stream's last commit ends `(m30 final)`; s30e then assembles `code/m30` from `feat/m29-exit` plus docs, dpop, reads, config and vector, in that order.
- **Bound MCP tokens (D910–D915, FD4; every edition).** Migration 00340 adds `dpop_bound` to MCP clients and `dpop_jkt` to codes and refresh tokens. A client's metadata document opts in; the token endpoint and the ID-JAG exchange bind a token to a valid DPoP proof (`cnf.jkt`, `token_type` DPoP); the gateway relay forwards the proof; the server checks key, method, URL, `ath`, `iat`, nonce and single use. Metadata advertises the algorithms; the client read shows `dpop_bound`; issuance records the binding.
- **Decoding (D920, D921; every edition).** Five decode layers to depth 3 within the body bound, `decode_bound` past it; findings name their layers in `encoding`.
- **Vector store (D922–D927; `pc-postgres`'s edition).** Kind `vectorstore` (13), package `pc.vectorstore` with `vector_query`, `vector_upsert`, `vector_delete`; a fixed table layout the admin creates from `pclaw connections vectorstore ddl`; provenance columns from the permit; writers outside `writer_agent_ids` held (`VECTOR_WRITE_NOT_WRITER`); migration 00341 in phase 2; a `float_array` param type; a connection takes 1..12288 dimensions, as many as an embedding carries (D1213a). `content` is capped at 8 KiB (D922a). Provenance comes only from the verified permit, whose `pap` claims gain `agent` and `run` (D923a; PAP-1 §7.2); a write without them fails closed. The connection row also holds host, port, database, user, sslmode, CA and internal, validated like `PostgresConfig`, and the endpoint is immutable after create (`VECTORSTORE_ENDPOINT_IMMUTABLE`, D925a, in 00341). A new param type `string_map` (D922b) for `filter` and `metadata`: gateway-bound and hidden from policy, keys `^[A-Za-z_][A-Za-z0-9_.-]{0,63}$`, values ≤ 1 KiB, `max_keys` 16 (filter) or 32 (metadata), ≤ 8 KiB in all; content signals scan the values.
- **Reads (D930–D932; budgets' edition).** `access` on count rules (`BUDGET_ACCESS_NEEDS_COUNT`), template `read-limits` (a 500-reads-a-day grant and a `count_max` clamp of 500 on `postgres.rows.read`, D1213), off by default (FD6); rules `pc.reads.enumeration` and `pc.exfil.scheduled_sends`, INFERRED.
- **Shares (D933–D935, answer S).** Migration 00342 `pc.owned_accounts`, `OwnedAccountService`, `pclaw org accounts`; adding is a protected change. Share extractors on new AWS and GitHub operations; `shares()` holds `SHARE_PUBLIC` and `SHARE_ACCOUNT_NOT_OWNED`; an empty list holds every cross-account share.
- **Agent configuration (D940–D946, FD5, answer C).** `internal/agentconfig` classifies settings, MCP, hooks, memory and skills paths; scans report digests (`agent_config`), credential formats by source, and a changed digest writes `agent.config_changed` with an OBSERVED alert only; the hook asks the gateway for listed paths (`agent_config.write`, PARTIAL); `pclaw init` adds the write tools to the matcher, user-scope files under home are routed too, credentials in config files go in as `env_secret` with `source=config_file` and their format, and `call` is the dedupe key (D943a); the sandbox binds them read-only and copy-out lists their changes (`--include-protected`).
- **M29 follow-ups (D945, answer P).** Resume an approved hold through the edge by exact request fingerprint; opt-in prompt capture per model connection (migration 00344, Business, protected change). Campaigns through a model connection (D945c) are **deferred** (D945d): `StartCampaign` needs a simulated model relay, so the change needs a proto field, a migration column and new server checks.
- **Threat map (D947, D948).** Prevent controls `prevent.mcp_token_binding`, `prevent.read_limits`, `prevent.share_accounts`, `prevent.agent_config`, `prevent.vector_writers`, `prevent.query_scope` (connector refusals `table_not_allowed` and `column_not_allowed` as `OutcomeCodes`), and `prevent.token_caps` after M29; `prevent.content_hold` gains LLM prompt obfuscation; the new rules carry ATLAS and ATT&CK tags; an automation whose trigger tests more than the rule reads PARTIAL `NARROWED_TRIGGER` (F-M28-1); connector refusals count in Seen (F-M28-2): `RecordExecutionRequest.outcome_code` and `pc.execution_attempts.outcome_code` (migration 00345, D947a) carry the code; a refusal before dispatch is not recorded.
- **Small fix (D949).** Exposure recompute also moves on `audit.agents.*`.

**Out of scope:** read-volume limits applied by default; storing configuration contents or values; DDL run by the gateway; a vector store other than pgvector (FD7); OCSF prefixes (already fixed on `main`).

Fixes from the tests: a finding's `encoding` admits digits (`base64`); a `float_array` is taken as JSON numbers only where a declared `float_array` param is extracted and held in the action as one canonical string, base64 of little-endian float32, which dispatch decodes for pgvector (D1211; HR-101 unchanged, since the param is not material), at most 12288 items so the string fits the 64 KiB string bound (D1213); a bucket policy with `NotPrincipal` counts as a public share; `prevent.mcp_token_binding` names no reason codes, because `invalid_dpop_proof` and `use_dpop_nonce` are OAuth authentication errors, not decisions (D1208). The packages decode under the M34 back-ports (D1002, D1002a): dedupe keys on the GitHub share operations and the S3 puts, the S3 policy left out of the approval fields (HR-034), and the number-array and string-map input schema forms for `pc.vectorstore`.
