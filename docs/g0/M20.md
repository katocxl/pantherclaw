### G0 — M20 — Integrations breadth: signed webhooks, export destinations, target-confirmed rotation, connectors and ticket sync — 2026-10-29

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M20 pull requests and, at the end of the milestone, in the exit status section. The design was written on `main` at cefc6254. M20 lands after M19 in migration-number order (M15 → M16 → M17 → M18 → M19 → M20 → M21), so its migrations start at 00236. The founder answered four open decisions for M20 (G12–G15) on 2026-10-29, the recommended option each time; they are recorded at the end as answered. Every other choice is a design decision made by the coordinator (D250–D290 in the coordinator's tracker), summarised below.

**Purpose:** PantherClaw already governs agents' GitHub, Stripe, Slack and Postgres work, signs its outbound webhooks with HMAC, exports security events to SIEMs, and lets people download evidence packs and organization exports. Customers who run on GitLab, Jira, Microsoft Teams or AWS have no connector; receivers who want to verify a webhook without sharing a secret cannot; evidence can only be pulled by hand, never pushed to the customer's own storage; rotating a GitHub App key is a manual runbook with nothing that checks the new key works or that the old one is gone; and incidents and cases live only inside PantherClaw, so teams that work in tickets copy them by hand. M20 adds:
- Ed25519 webhook signatures, opt-in per destination, next to HMAC;
- export destinations that push packs, proof bundles and organization exports to HTTPS or S3-compatible storage with delivery receipts;
- a target-confirmed rotation of the GitHub App key, run through the gateway so the server never holds the key;
- GitLab, Jira, Microsoft Teams and AWS (deploy and IAM read) connectors;
- ticket sync with Jira in which a ticket can never restore authority;
- approval notices as Slack direct messages and Microsoft Teams cards, link only.

In product terms this is Stash, Trail and the connectors ([PRODUCT.md](../PRODUCT.md)).

*Webhooks* (TB8; D251).
- **Spoofing (T-222):** a webhook signed with one organization's key accepted as another's, or a JWKS that lists another organization's keys. Answered by: a per-org key signs only that org's deliveries and the JWKS lists only that org's keys (HR-511).
- **Tampering:** a receiver that moves to Ed25519 loses HMAC on the way. Answered by: Ed25519 is opt-in and HMAC is always sent too (HR-510); a rotated key stays verifiable for 24 hours, then is gone (HR-512).

*Export destinations* (TB2, TB8; D252).
- **Information disclosure (T-223):** a destination pointed at an attacker or an internal host, activated without a person, or receiving data classes it was not configured for. Answered by: activation only after a step-up and only through the egress guards (HR-513); a data-class filter per destination.
- **Repudiation and tampering:** a push that cannot be shown later, or a removal that claims the remote copy is gone. Answered by: a delivery receipt for every push (HR-514); a signed removal notice, never a claim of remote deletion (HR-515).
- **Denial of service:** half-finished multipart uploads that accumulate at the destination. Answered by: a failed multipart upload is always aborted (HR-516).

*Rotation* (TB2, TB3; D253).
- **Denial of service and elevation (T-224):** a rotation that locks every agent out by activating a key that does not work, or a rollback used to bring back a compromised key. Answered by: a candidate is never in gateway configuration before activation (HR-517); activation needs a passed target test and a step-up (HR-518); rollback only before confirmation (HR-519).
- **Repudiation:** an old key marked revoked while GitHub still accepts it. Answered by: the old key is REVOKED only when GitHub refuses it (HR-520).

*Connectors* (TB2; D254).
- **Elevation (T-225):** an AWS action that runs with more privilege than the decision allowed. Answered by: short-lived AssumeRole sessions with a narrowed session policy per dispatch (HR-525).
- **Information disclosure (T-226):** an agent posts into a customer-visible Jira project or an external Teams channel. Answered by: both count as external disclosure (HR-522, HR-524).
- **Tampering (T-229):** a GitLab deploy triggered without a verified pipeline. Answered by: the deploy is a consequence under M17's consequence and verification model (HR-521).
- **Tampering:** an agent supplies headers or an encoding that changes what the target does. Answered by: headers and encodings are fixed by the signed package (HR-526); a coverage declaration never widens authority (HR-523).

*Ticket sync and approval channels* (TB8; D255, D256).
- **Elevation (T-227):** a Jira transition to Done, a forged webhook or a replay used to lift containment or restore an agent. Answered by: a ticket status never restores authority (HR-527), the sync actor has no permission on those services, and changes to PantherClaw-owned fields are ignored and recorded (HR-528).
- **Information disclosure (T-228):** an approval DM sent to someone who is not an eligible decider, or carrying request details. Answered by: DMs and cards go only to eligible deciders, carry a link only and never take a decision (HR-529).

**Design decisions:**

*S20a — Ed25519 webhooks (D251; founder decision G13)*

1. **Keys.** One ACTIVE `webhooks` key per organization. Migration 00236 redefines the key purpose check to add `webhooks`, and adds a `signature_scheme` column, `hmac` (the default) or `hmac+ed25519`, to the notification channel, SIEM destination and automation endpoint destination tables. The keystore gains the per-org path for this purpose (today's signing keys are platform-wide).
2. **Publication.** A per-org JWKS at `/.well-known/pantherclaw/orgs/{org}/webhook-jwks.json` lists that organization's ACTIVE and RETIRING `webhooks` keys, and no one else's (HR-511). The route is public, so it sits behind `httpx.Limiter` per IP and a per-org in-process cache of 60 seconds, invalidated on rotation in the same replica; an unknown organization is cached as an empty set (D271).
3. **Rotation.** The key moves to RETIRING with a 24-hour overlap, audited; after the overlap it is gone from the JWKS (HR-512): a sweep moves an expired RETIRING key to REVOKED with the `overlap_ended` audit (D271).
4. **Signatures.** A destination with `hmac+ed25519` receives both `v1a,` (Ed25519, Standard Webhooks) and `v1,` (HMAC) in `webhook-signature`. HMAC stays the default and is always sent (HR-510). Inbound automation events stay HMAC.
5. **WebhookKeyService** (D261).
   - `ListWebhookKeys` needs `webhook_key.read`. `RotateWebhookKey` needs `webhook_key.manage` and a fresh security-key step-up.
   - Rotation is refused while a RETIRING key exists, so an organization has at most one ACTIVE and one RETIRING key. Every rotation is audited (HR-512).
   - Opt-in: each destination service gets one audited RPC, under that service's existing manage permission, without a step-up.
   - Permissions are defined in S20a's `permissions_m20_webhooks.go`.
   - Order: S20a builds the signers, the JWKS wiring and 00236 first, and merges M18's keystore work (marker `(m18-keys)`) before it edits `internal/keystore` or `internal/platform/keys` (D258).

*S20b — export destinations (D252)*

6. **Model.** Copied from SIEM destinations: HTTPS PUT and S3-compatible destinations, states PENDING, ACTIVE, PAUSED and DISABLED, activation by a person with a fresh security-key step-up, the egress guards, health, Business edition (HR-513). The edition gate reuses `SIEMExport()` (D276).
7. **Artefacts.** Evidence packs, proof bundles and organization data exports, each with a data-class filter per destination.
   - The filter has a fourth data class, `payload_captures`, and a proof-bundle push takes a ledger range (D276).
   - An artifact past `expires_at` is refused on the database clock at push and at send (D278).
8. **Large pushes.** Above 2 GiB a push streams parts straight into an S3 multipart upload or chunked PUTs, and the multipart abort always runs on failure (HR-516). Downloads keep the 2 GiB cap.
   - A streamed export above 2 GiB starts from a push request, with an uploader goroutine keeping the build transaction alive. It stores 0 parts, the receipt holds the real size, and a download of it says unavailable (D276).
   - The receipt stores the highest part begun. An abort deletes parts 1..n and treats each 404 as already gone, so a target that fails mid-abort leaves no chunks behind a receipt that says aborted (D278).
   - An hourly dispatcher enqueues one unique per-org job on `napp.Queue` with a fitted timeout, so a hanging destination never stops another organization's sweep (D278).
   - A destination timeout ends the current step of an organization's sweep, not the whole sweep, so a hanging abort cannot block every notice. A load error is logged and notices still run (D282).
   - The receipt's `abort_tried_at` orders the aborts, NULLS FIRST then oldest (D282).
   - The manifest is written before the upload completes, so a failed manifest leaves nothing whole behind a FAILED receipt (D278).
   - A failed Complete also removes the manifest, best effort. With an upload id set, it is removed only after `SetExportAborted` returns one row (D282, D288).
9. **SigV4.** In-house in `internal/platform/sigv4`, tested against AWS's published SigV4 test suite; S20e reuses it. From D267:
   - `sigv4.Credentials` never leaks its secret: SecretAccessKey and SessionToken are redacted through JSON, `%#v` and slog, with a test per path.
   - The AWS suite also runs through `Sign`, with an `http.Request` built from each `.req` that Go can represent, and S3 has known answers for keys with special characters.
   - S3 mode refuses `.` and `..` path segments.
   - Whitespace trimming collapses only ASCII space and tab, plus folded CRLF.
10. **Receipts and removal.** Migration 00238 holds delivery receipts, one for every push (HR-514); a claimed streamed receipt can't stay QUEUED (D278). An active legal hold never blocks a push. A retention removal after a push pushes a signed removal-notice object and is shown as "removed here; a copy exists at <destination>"; PantherClaw never claims the remote copy is gone (HR-515).

*S20c — GitHub App rotation (D253; founder decision G14)*

GitHub offers no API that creates or deletes an App private key, so a person creates the new key in the App's settings and deletes the old one there; PantherClaw tests the new key at GitHub and confirms the old one is dead, always through the gateway, so the key is opened only in gateway memory (HR-060, HR-061).

11. **States.**

```
REQUESTED            connection.manage; preview digest of who shares the credential (HR-252)
 → CANDIDATE_SEALED  a person seals the new key (`pclaw seal`) → a pc.credentials row in state CANDIDATE, not in gateway configuration
 → TESTING           lease credential_rotation_test: the gateway opens the candidate, signs a JWT and calls GET /app and the installation read; no token is minted
     definite refusal (401, 403, 404, or 200 for another App) → FAILED   the candidate is REVOKED; the old key is untouched
     0, 429 or 5xx   stays TESTING for the next lease
 → ACTIVATING        protect surface credential.rotate (Custody) and a step-up: the candidate becomes ACTIVE, the old key SUPERSEDED within the rotation; epoch and configuration bump (HR-211)
     failure → ROLLED_BACK   the old key ACTIVE again, the candidate REVOKED; only from here
 → AWAITING_OLD_REMOVAL  the person deletes the old key on GitHub; a posture finding while the rotation is open
 → CONFIRMING        lease credential_rotation_confirm: GET /app with the new key and the old key at the same moment; the new key must get 200 for the same App and the old key 401
     anything else → AWAITING_OLD_REMOVAL
 → CONFIRMED         the old key is REVOKED; audited
```

12. **Migration 00239.**
    - a `pc.credential_rotations` table;
    - a `CANDIDATE` state on `pc.credentials`, with SUPERSEDED → ACTIVE allowed only while the credential's rotation is ACTIVATING;
    - the verification purposes `credential_rotation_test` and `credential_rotation_confirm`;
    - the posture finding kind `unconfirmed_rotation`, added to the posture_findings kind CHECK as a named NOT VALID constraint followed by VALIDATE.
13. **Lease plumbing** (D259). These edits sit outside S20c's own files and are append-style; S20f adds `ticket_sync` to the same plumbing, so on a conflict keep every side.
    - `queries/verifications.sql`: the two purposes, with capped attempts.
    - `internal/transactions/domain/effect.go`: two Purpose constants.
    - `pgtransactions/store.go`: the rotation request on Claim, and a `LeasedRotation` branch on Report that goes through a credentials hook.
    - A new `internal/gateway/dispatch/rotation.go`, with routing in `internal/gateway/verify.go`.
    - One server wiring file.
14. **Sealed bytes in the lease** (HR-061, HR-517).
    - At claim time, the claim attaches the sealed candidate (for a TEST lease) or the old credential (for a CONFIRM lease) to the lease request.
    - It is the same sealed form gateway configuration uses: sealed to the broker key of the gateway the credential is bound to, never decryptable by the server, and sent only to that gateway.
    - `pc.verifications.request` stores ids only. No proto change.
15. **Gates.** A candidate is never in gateway configuration until activation; the gateway sees it only inside its test lease (HR-517). Activation goes through the protect surface `SurfaceCredentialRotate = "credential.rotate"` (category CUSTODY), under the permission of the existing credential create/replace RPC, and needs a passed target test and a step-up (HR-518).
16. **Rollback** is possible until CONFIRMING starts, or for 24 hours, whichever comes first (HR-519). It is gated like activation: `credential.seal`, a fresh step-up and the `credential.rotate` protect surface (Custody), recorded as a rollback, then audited and notified (D274).
17. **Confirmation.** The old credential is never REVOKED on trust, only when GitHub refuses it (HR-520).
    - Confirmation is a controlled comparison (D274). The confirm lease probes GET /app with both the active new key and the old key at the same moment, and confirms only when the new key gets 200 and AppMatches and the old key gets 401. Anything else returns to AWAITING_OLD_REMOVAL, so a skewed clock can't pass for a dead key.
    - A rotation that has been in AWAITING_OLD_REMOVAL or CONFIRMING for more than 24 hours raises an `unconfirmed_rotation` posture finding; leaving those states remediates it.

20. **Coverage declaration** (F756). Packages gain an optional `coverage:` block: environment source, record scope, recipient fact and channels. Definitions validate it, and it never widens authority (HR-523).
21. **Mapping headers and encodings** (D262).
    - Outbound dispatch gains optional fixed `headers` and `encoding: aws-query | aws-json`. `aws-query` is outbound only.
    - The inbound http mapping gains `aws-json` and fixed `headers` only. Nothing routes on body content, and IAM read reaches agents through mcp mappings.
    - Headers and encodings come only from the signed package, never from agent input (HR-526).
    - S20e owns this part of `internal/definitions/domain/dispatch.go`.
    - Old packages and the golden files stay valid.
22. **Nested JSON bodies** (D260, D263).
    - JSON bodies accept the form bracket-key grammar, and the gateway builds the keys into nested objects. The grammar allows a depth of at most 3, no digit-only segments (so no arrays), and no key that is both a value and a parent.
    - JSON booleans use a new namespace, `bool.true` and `bool.false`, which is package data only. `literal.true` stays the string "true", so no signed package changes meaning (D272, amending D263).
    - It is additive: flat keys are unchanged, and old packages and golden files stay valid. An older gateway refuses bracket keys in JSON, so it fails closed.
    - An agent argument can never add a key, in a request or in MCP arguments (HR-526).
    - S20d owns the JSON body builder and the grammar in `dispatch.go`, and pushes nesting, booleans, Jira create and transition together in a commit whose subject contains `(m20-json-nest)` (D268). S20e merges it from `origin/feat/m20-gitlab-jira` before it builds the Teams post, and S20f before it wires Jira create, transition and sync. On a conflict with S20e's headers and encodings, keep both.
    - `(m20-jira)` marks Jira read and comment only (D268).
23. **GitLab** binds hosts per connection, and its deploys reuse M17's consequence and verification model, so a deploy is a consequence that needs a verified pipeline (HR-521, T-229).
    - Every environment is predicted, stopped ones included: there is no `states=available` filter (D287).
    - With an empty environment list the prediction reads `.gitlab-ci.yml` at the head. Absent means no environment. A mention of `environment` or `include`, or a failed read, is Unread, so `CONSEQUENCE_UNKNOWN` holds. This is a text check, not parsing.
    - In that path a project with a non-empty `ci_config_path` or `auto_devops_enabled: true` is also Unread, so the merge holds. Compliance pipelines cannot be read; the package limits and the runbook say so. The 404 rule for `.gitlab-ci.yml` stands (D289).
    - Limit: a new environment name in a project that already has others is not predicted. The package limits and the runbook say so.
    - The verifier has no `disagreement`. A null `merge_commit_sha` reads as `NOT_VERIFIABLE`, with one sentence in the limits.
