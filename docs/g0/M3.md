### G0 — M3 Agents & PAP/1 identity — 2026-10-09

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M3 pull requests and, at the end of the milestone, in the exit status below. It builds on PR #53 (ADR-0017, ADR-0018, the revised PAP-1 §3.3 and §5, BUILD_GUIDE §8 M3, FEATURES PN-002.2, PN-002.3, PN-002.8 and HR-093), merged to `main` as b0dc16b.

**Purpose:** every agent gets an accountable record, and every request from an agent workload proves which admitted instance sent it, in which server-minted run, and for whom. M3 is most of the Badge component ([PRODUCT.md](../PRODUCT.md) §4.1). Nothing in M3 grants authority: grants arrive in M4 part 2, and until then the M1.5 hard-coded development grant is the only one.

**Scope (planned):**
- **Agents** (`internal/agents`): inventory with accountable owner and backup owner, owning team, environment, purpose and execution context (`desktop`, `ci`, `kubernetes`, `service`); the lifecycle state machine; append-only change history; the agent summary (F017) with explicit empty states (F624); the Community agent limit.
- **Enrollment and admission** (`internal/identity`, `internal/waitlist`): `pce_` enrollment tokens; workload keys registered as agent instances; `ADMISSION` waitlist entries (this entry type only), resolved by the owner confirming the key fingerprint, or automatically by an L2 issuer entry that allows it.
- **Workload tokens** (`pap-wt+jwt`), request proofs, server nonces and the partitioned replay store. The Authority verifies them itself on `Authorize` and on every workload call.
- **L2 attestation** through trusted-issuer entries with the **GitHub Actions** and **Kubernetes** presets (ADR-0018). Adding or widening an entry is a protected change.
- **Runs** (`internal/runs`): `StartRun` by an authenticated launcher; the represented principal is the launcher itself or a user proven by an RFC 8693 subject token (PN-002.8); child runs started by a parent workload; the run binding is checked on every `Authorize` (HR-022).
- **Discovery**: unknown workload keys seen by the gateway become `DISCOVERED` agents with an `ADMISSION` entry; owners claim, merge or dismiss them.
- **Gateway**: PAP/1 headers replace the development `PC-Dev-Workload` and `PC-Run-Id` headers. The gateway hashes the raw body, forwards token, proof and hashes to the Authority, serves `PAP-Nonce`, and reports unknown keys. `pantherclaw-server dev seed` and `pantherclaw-sim load` move to PAP/1.
- **`pclaw`**: commands for agents, enrollment tokens, admissions, issuer entries, runs and discoveries; `pclaw workload enroll|token` for the workload side (key file, L1 enrollment, GitHub and Kubernetes attestation for CI jobs and pods).
- **`pclaw scan`** (PN-001.1), if open decision 4 keeps it in M3.

**Out of scope:** grants on runs and the decision pipeline (M4 part 2; a run's grant stays empty until then); resuming a suspended agent, the other waitlist entry types, deadlines with escalation, and notifications (M5); gateway mTLS and the stdio-only `pclaw mcp proxy` (M6; the development gateway token stays until then); detections built on the alerts M3 raises (M10); public SDKs and the GitHub organisation scan (M8); further issuer presets and L3 (PN-002.3); per-org OIDC provider records (providers stay server configuration, as in M2); GitHub Enterprise Server issuers; signed image evidence for the Kubernetes preset (follow-ups below).

**Threat slice:** T-001 (run binding part), T-004 (rogue instance under a real agent's name), T-032 (token and proof replay, substitution), T-033 (desktop key theft, L1 cap part), T-035 (GitHub OIDC mis-binding), and the new rows **T-044..T-050** added to [THREAT_MODEL](../security/THREAT_MODEL.md) by this brief. Also T-003 for every new table, T-037 for every new RPC, T-023 for discovery flooding and key fetching, and T-041 for tokens in logs.

**Hardening rules in scope:** HR-022, HR-090..094, and the new rules **HR-140..HR-148** added to [HARDENING_RULES](../security/HARDENING_RULES.md) by this brief. Also HR-095 (algorithms pinned), HR-004 (conditional transitions), HR-050..057 (new tables), HR-104 (validation), HR-023 (task text stays untrusted), and early parts of HR-002 (suspending or retiring an agent and revoking an instance bump the containment epoch) and HR-021 (the Authority re-verifies forwarded identity; gateway mTLS stays M6).

**Product requirements:** F003, F015, F016, F017, F019, F020, F022, F023, F024, F026, F027, F028, F031, F033, F035, F574, F624, PN-001.1 (decision 4), PN-002.1, PN-002.2, PN-002.4, PN-002.5 (runs bound to instance, launcher and principal; the grant binding is M4), PN-002.8, PN-004.1 (`ADMISSION` entries only), F224 (the run record; the inspector timeline is M7).

**Contracts:**
- **Migrations.** M2 ended at `00016` and M4 part 2 starts at `00020`, so M3 uses exactly three numbers. Every table has `org_id`, composite keys and forced RLS (covered by the M1 catalog tests).
  - `00017_agents.sql`: `agents` (owner and backup owner as columns, F574), `agent_changes` (append-only: UPDATE and DELETE revoked from `pc_app`), `discoveries`, `waitlist_entries` (kind `ADMISSION` only; M5 widens the CHECK).
  - `00018_identity.sql`: `agent_instances`, `enrollment_tokens`, `trusted_issuers` (immutable revisions), `attestations` (accepted attestations; a unique replay key makes each attestation token single use), `dpop_nonces`, `dpop_jti` (LIST-partitioned into time slots, every partition with forced RLS).
  - `00019_runs.sql`: `runs`.
  - BUILD_GUIDE §7 is updated: `agent_owners` becomes the two owner columns (history is in `agent_changes`), `trusted_issuers` is added, and subject-token `jti`s use the M2 `auth_replay` table.

  - `runs.proto` `RunService`: `StartRun` (no grant field in M3; constraint 17), `GetRun`, `ListRuns`, `EndRun`.
  - `workload.proto` `WorkloadService` (called by workloads, authenticated by PAP/1, not by user or service credentials): `Enroll`, `IssueToken` (also refresh and re-attestation), `StartChildRun`.
  - `authority.proto` (additive): `AuthorizeRequest` gains `workload_token`, `proof`, `body_sha256`, `htm`, `htu` and `client_address`; new `GetNonce` and `ReportUnknownWorkload`.

- **Tokens and formats:** enrollment token `pce_<org>_<secret>` (ADR-0016 shape); workload token per PAP-1 §3.4, signed by the existing `workload_tokens` key and published in the JWKS; instance identifier `pc:org/<org>/agent/<agent>/inst/<instance>`.
- **Configuration:** `public_url` on the server and gateway (the `htu` comparison); `auth.oidc_providers[].subject_token_audience` (a provider accepts subject tokens only when this is set); `identity.kubernetes_clusters` (decision 3).
- **Access PantherClaw needs in each trusted cluster** (PAP-1 §3.3): a service account bound to `system:auth-delegator`, for TokenReview, and `get` on `pods` in the namespaces that issuer entries pin, for the pod uid and `status.containerStatuses[].imageID`. Nothing else: no list, watch or write. The runbook ships the minimal ClusterRole and RoleBinding. An entry whose namespace the credential cannot read fails closed when it attests, not when it is saved.
- **PAP-1 clarifications in this PR:** §3.2 (an L2 attestation that matches an auto-admitting entry enrolls without an enrollment token), §3.3 (L2 lasts until the attestation token expires; `refs/pull/` refs; the Kubernetes service-account UID), §4 (nonces per org; `htu` from the configured public URL), §5 (who may be the represented principal; child runs).

**Security constraints and design decisions:**
1. **Identity is ids, never names (F034).** Agents, instances and runs are UUIDv7 records. A display name binds nothing: two agents may share one, a retired agent's name may be reused, and neither case inherits runs, instances or (M4) grants (HR-147). Discovered workloads are never merged with an agent by name, only by an authorized user (F035).
2. **Enrollment tokens** are 256-bit random `pce_` secrets, single use, valid at most 15 minutes, stored as SHA-256, and bound to one agent and environment. Only the agent's owner or backup owner, holding `agent.enroll` in the agent's scope, can create one. A reused token is refused and audited (PN-002.1).
3. **Enrollment** (PAP-1 §3.2): the workload generates its Ed25519 key, then calls `Enroll` with a request proof signed by that key over a server nonce, which proves possession. The Authority creates an instance in `PENDING_ADMISSION` and an `ADMISSION` entry showing the fingerprint (the RFC 7638 thumbprint). Instance states: `PENDING_ADMISSION → ADMITTED → REVOKED | EXPIRED`, and `PENDING_ADMISSION → REJECTED | EXPIRED`; each transition is a conditional update (HR-004).
4. **Admission (HR-094).** `AdmitInstance` must carry the full fingerprint that the workload printed, and it must equal the instance's thumbprint. The decider must be the agent's owner or backup owner, holding the human-only `agent.admit` in the agent's scope. Without a decision, an `ADMISSION` entry expires after 7 days and the instance becomes `EXPIRED`, enforced at use time. The only other path is automatic admission by an active L2 entry (decision 7).
5. **Workload tokens** follow PAP-1 §3.4: valid 10 minutes, `cnf.jkt` set to the instance key, `aud` `pantherclaw-gateway`, `pap.att_lvl` at the instance's current level. They are issued only to `ADMITTED` instances of agents that are neither `SUSPENDED` nor `RETIRED`, and only against a fresh proof. A token never outlives the attestation behind its level (HR-143).
6. **Request proofs (HR-090, HR-091).** Proofs use EdDSA only (HR-095). The verification order is fixed by PAP-1 §4 and the `(jkt, jti)` row is inserted only after every check has passed. The verifier compares `htu` with its configured `public_url`, never with the request's Host header. The raw body is hashed before anything parses it: in the gateway, and on the server by an HTTP middleware in front of `WorkloadService`. `Enroll`, `IssueToken` and unknown-workload reports use the key-only proof profile of PAP-1 §4: no workload token and no `ath`, but the same signature, `htm`, `htu`, `bh`, nonce and replay checks, in that order. A key-only proof shows possession of a key, never an identity; without an enrollment or attestation token, or a match with an admitted instance's key, it is an unknown workload (constraint 15).
7. **Nonces.** The Authority keeps one nonce per org per minute in `dpop_nonces`; each is valid for 5 minutes by the database clock. Workloads get them from `PAP-Nonce` headers (a `use_nonce` error carries a fresh one). The gateway caches its org's nonce from `GetNonce` and `Authorize` responses. A nonce from another org, or one older than 5 minutes, is refused.
8. **Replay store (HR-090).** `dpop_jti` is unique on `(org_id, slot, jkt, jti)`. The slot comes from the issue minute of the nonce the proof carries, so a replayed proof always lands in the same slot. The table is LIST-partitioned into ten one-minute slots. The janitor deletes a slot's rows with `DELETE` (pc_app keeps no TRUNCATE, HR-055) once their nonce has been expired for more than 60 seconds (PAP-1 §4): a nonce from minute m expires by minute m+6, its rows go at minute m+7, and the slot is reused at minute m+10. On `Authorize` the replay insert commits before the decision transaction starts.
9. **Trusted-issuer entries (HR-140, HR-141).** An entry has a preset kind, the issuer, the key source, the audience `pantherclaw:<org>`, the allowed algorithms, the binding claims for exactly one agent, an `auto_admit` flag and a state (`PROPOSED`, `ACTIVE`, `SUPERSEDED`, `DISABLED`). Only preset kinds exist; there is no generic issuer in M3. Proposing a new entry, or a revision that widens one (more refs, workflows, namespaces or images, or turning on `auto_admit`), creates a `PROPOSED` revision; the active revision keeps working until a human with `identity.issuer.activate` activates the new one. The response shows exactly what widens, and both steps are audited. Narrowing and disabling take effect at once. Disabling an entry stops auto-admission through it, and its instances lose L2 at their next token refresh.
10. **GitHub Actions preset (HR-093, PAP-1 §3.3).** The issuer is the constant `https://token.actions.githubusercontent.com`, with RS256 only and `aud` exactly `pantherclaw:<org>`.
    - The entry pins `repository_id` and `repository_owner_id`, and declares which job type it accepts. An ordinary job binds on `workflow_ref`. A job that calls a reusable workflow binds on `job_workflow_ref`, the called workflow's path and ref.
    - Each pinned ref must be `refs/heads/…` or `refs/tags/…`. The entry may also pin `workflow_sha` or `job_workflow_sha` to one exact revision, and `environment` and `runner_environment`.
    - The token cannot show whether a reusable workflow's ref is protected in its own repository. So the activator confirms it as part of the protected change (HR-141), and the CLI recommends pinning `job_workflow_sha`. M8's GitHub App can check it automatically.
    - These rules run in code and no configuration turns them off:
      - the token must report `ref_protected` true;
      - `event_name` must not be `pull_request` or `pull_request_target`;
      - the `ref` must not be under `refs/pull/` (this also covers `pull_request_review` events, which run the pull request's code).
11. **Kubernetes preset (HR-144).**
    - PantherClaw calls TokenReview with the audience `pantherclaw:<org>`. The token must authenticate as the pinned cluster, namespace, service-account name and service-account uid. Pinning the uid stops a deleted and recreated account with the same name.
    - TokenReview must return the bound pod's name and uid. PantherClaw then reads that pod from the API server; its uid must match and it must be running.
    - The image digest comes from trusted cluster state for that pod uid: `status.containerStatuses[].imageID`. That is the only source in M3; signed evidence bound to the pod, such as a verified image signature or admission attestation, is a later option under PAP-1 §3.3. The entry may pin allowed image repositories or digests, and the digest is recorded as the `attested` release (F028). A digest the workload reports itself is only `declared`.
    - The cluster connection (API server, CA, credential, allowed private range) comes from operator configuration (decision 3).
12. **Key fetching (HR-142).** GitHub keys come from the issuer's discovery document and JWKS through `httpx.NewEgressClient`: TLS only, a 64 KiB size cap, at most 20 keys, only keys whose type matches the pinned algorithm, a cache of at most 15 minutes, and at most one refetch per minute per issuer for an unknown `kid`. The Kubernetes calls use the same egress client, with the cluster's CA pinned and private addresses allowed only by the operator's range for that cluster. If the issuer is unreachable, the attestation is refused (fail closed).
13. **Attestation tokens (HR-143).** Each is single use: its key in `attestations` is the `jti`, or the token's SHA-256 when there is none, and the key is recorded only after the token verified. The token must carry exactly `aud = pantherclaw:<org>`, and `exp` must be at most 1 hour after `iat`. It confers L2 until its `exp`; to stay at L2, the workload sends a fresh token with `IssueToken`. Kubernetes projected tokens must therefore request at most 3,600 seconds.
14. **No authority moves between instances (HR-147).** An instance's issuer entry and binding claims are fixed when it enrolls. A re-attestation whose binding claims differ is refused; the workload must enroll as a new instance, which starts with no runs. Any value a workload reports about itself (code hash, image digest, configuration) is recorded as `declared`, whatever its attestation level; only values PantherClaw reads from the issuer or the cluster are `attested` (PAP-1 §3.3). A changed release digest is recorded as drift (F033): an `agent_changes` event, and the instance is flagged for review in its verification metadata (F031). Ownership transfers are recorded and move no runs or instances (F574).
15. **Discovery (HR-148).**
    - The gateway calls `ReportUnknownWorkload` when a request carries a valid proof but no workload token, or a key that is not an admitted instance. The Authority verifies it as a key-only proof (PAP-1 §4: signature, `htm`, `htu`, `bh`, nonce, then replay). A proof that fails any check creates no discovery.
    - On first sight of a key thumbprint it creates a `DISCOVERED` agent, a discovery row and an `ADMISSION` entry; later sightings only update counters. Observed attributes (gateway, route, client address, user agent, truncated to 256 bytes) are stored and shown as untrusted.
    - Limits: at most 60 new discoveries per gateway per minute, and at most 200 open discoveries per org. Past either limit the sighting is only counted and a `security.discovery_flood` audit event is written.
    - The request itself is refused with `instance_not_admitted` (`CANNOT_AUTHORIZE`) and nothing is dispatched.
    - Claiming creates the agent's owner, team and environment. Admitting the observed key then needs the same fingerprint confirmation as an enrollment (HR-094).
16. **Desktop workloads (HR-092, M3 part).** An agent's execution context is set by a human when it is created and cannot change later; a different context needs a new agent. Instances of a `desktop` agent are capped at L1 whatever they present. Each instance remembers the network (/24 for IPv4, /56 for IPv6) it was last seen from, as reported by the gateway or the server. A change writes a `security.instance_network_changed` audit event, which is the alert until detections arrive in M10. The stdio-only proxy rule is M6.
17. **Runs (HR-022).**
    - `StartRun` mints the run id. The run is bound to the agent, optionally one instance, the launcher and the represented principal.
    - **No grants in M3.** `StartRun` has no grant or task-template field; the proto reserves its number for M4. A run's grant column stays empty. The Authority keeps using the M1.5 hard-coded development grant, which exists only behind the loopback-only development gateway. In M3 it applies only after the identity and run-binding checks pass. M4 part 2 adds grant selection to `StartRun` and makes `Authorize` require the run's own grant (PAP-1 §5).
    - Without an instance, the run binds to the first admitted instance of the agent that uses it, by a conditional update; after that, any other instance gets `DENY` (`run_mismatch`).
    - On `Authorize`, an unknown run, a run of another agent or instance, or an ended or expired run gives `DENY` with `run_mismatch`. An instance that is not admitted gives `CANNOT_AUTHORIZE` (`instance_not_admitted`). A suspended or retired agent gives `DENY`.
    - Runs last 8 hours by default (at most 24). `task_ref` is an untrusted label of at most 256 characters (HR-023).
    - Run states: `ACTIVE → ENDED | CANCELLED | EXPIRED | REVOKED`.
    - **Child runs:** a workload in an `ACTIVE` run calls `StartChildRun`. The child inherits the represented principal, records the parent instance as its launcher, and cannot outlive its parent. Nesting is at most 8 levels deep, and ending or revoking a parent revokes its children in the same transaction.
18. **Represented principal (HR-146).** A run's principal can be only one of three things: the launcher itself (a user or a service account); a user proven by a subject token; or, for a child run, the parent's principal. A launcher can never simply name a principal. Presenting a subject token needs `run.represent`, so only designated launchers can start runs for other people. The run records the launcher, the principal, the provider identity `(iss, sub)` and the actor chain (F027).
19. **Subject tokens (HR-145, PAP-1 §5).**
    - `subject_token_type` is `urn:ietf:params:oauth:token-type:id_token` or `…:access_token`. An access token must carry the JWS header `typ: at+jwt` (RFC 9068), so the two types cannot be swapped. Opaque tokens are refused.
    - The issuer must be a configured OIDC provider with `subject_token_audience` set; the provider's own client fetches its keys (operator-configured, as in ADR-0016). Algorithms are RS256, ES256 or EdDSA, and `aud` must contain the configured audience.
    - `exp` must be in the future, and `iat` at most 5 minutes old (60 seconds of clock skew allowed).
    - Each token is accepted once: `auth_replay` stores the issuer's hash and the hash of the `jti` (or of the token), until `exp`.
    - `(iss, sub)` must belong to an `ACTIVE` user of the launcher's org; subject tokens never create users.
    - The token grants nothing: the run's authority comes only from its grant (M4), and the principal's roles never flow into the run.
20. **Agent lifecycle (F020).**
    - Transitions:
      - an agent created through the API starts `CLAIMED`;
      - a discovered one goes `DISCOVERED → CLAIMED`, or to `RETIRED` when dismissed;
      - `CLAIMED → VERIFIED` when its first instance is admitted;
      - `VERIFIED → OBSERVED` on its first verified `Authorize`;
      - any state except `RETIRED` can become `SUSPENDED`, which remembers the state it came from;
      - any state can become `RETIRED`.
    - `PARTIALLY_PROTECTED` and `PROTECTED` come from coverage (M9).
    - Suspending, retiring, or revoking an instance increments the org's containment epoch in the same transaction, so outstanding permits fail `BeginDispatch` (HR-002, early).
    - Retiring an agent also revokes its instances and enrollment tokens, and ends its runs (F023).
    - **There is no resume before M5.** Restoring an agent needs a `RESTORATION` entry with independent review (F563), so in M3 a suspended agent can only be retired.
    - Every change writes an `agent_changes` row and an audit event with actor and reason (F024).
21. **Authorization and tenancy.**
    - Each use case checks its permission at the agent's team scope, as in M2.
    - Ids from another org return NotFound (T-037).
    - Workload calls take their org from the credential: the enrollment token, the instance identifier, or the attestation audience (ADR-0016 decision 1).
    - The Community limit counts agents that are neither `DISCOVERED` nor `RETIRED`, checked at create and at claim. Instances do not count until the M13 instance allowance (PRODUCT §7 item 4).
22. **Logging and evidence.** Tokens, proofs, enrollment secrets and attestation or subject tokens are never logged, never stored in clear, and never put in job arguments (HR-056); logs carry thumbprints and ids only. These events are written to the evidence ledger: enrollment token creation and reuse, enrollment, admission and rejection, auto-admission, issuer proposals, activations and disables, run start and end with principal source, lifecycle changes, discovery floods, and network changes.
23. **Failure semantics.** Missing or unverifiable identity gives `CANNOT_AUTHORIZE` or a 401 `PAP-Error`. A known mismatch or tamper gives `DENY`. If an issuer, TokenReview or OIDC provider is unavailable, attestation or the run start is refused; the server never degrades to a lower check.

**Dependencies to add:** none. `go-jose/v4` (JWS, thumbprints), `go-oidc/v3` (provider keys) and `x/oauth2` are already approved. Kubernetes TokenReview and pod reads are two JSON calls made with `encoding/json/v2` (no `client-go`).

**Tests to write first:**
- `TestHR090_*`: a replayed proof is refused; `jti` is recorded only after token, `cnf` and proof checks pass (a bad signature leaves no row); the replay table is partitioned and a proof's slot follows its nonce; key-only proofs (`Enroll`, `IssueToken`, unknown-workload reports) run the same checks in the PAP-1 §4 order, and one that fails leaves no replay row and no discovery.
- `TestHR091_*`: stale, foreign and unknown nonces are refused; a body changed after hashing fails `bh`; the hash covers the raw bytes, not a re-encoding.
- `TestHR092_*`: a `desktop` agent's instance stays L1 with a valid attestation; the same key from a new network writes the alert event.
- `TestHR093_*`:

- `TestHR140_*`: an entry without binding claims, with only a repository name, with a wildcard, or of an unknown kind is refused; preset rules cannot be switched off by configuration.
- `TestHR141_*`: a widening revision stays `PROPOSED` until activated and the old revision keeps working; activation by an API key or service account is refused; narrowing applies at once.
- `TestHR142_*`: an issuer or cluster on a private address is refused unless the operator allows it; redirects are not followed; the JWKS size, the key count and the `kid`-miss refetch rate are capped; cached keys expire.

- `TestHR144_*`: a recreated service account (same name, new uid), another namespace, a TokenReview without the pod name and uid, a deleted pod and an unlisted image are refused; the digest comes from the pod status, and a digest the workload reports stays `declared` even at L2.
- `TestHR145_*`: a subject token from an unconfigured provider, for another audience, older than 5 minutes, expired, replayed, opaque, of the wrong type, or for an unknown or disabled user is refused.

**Founder decisions (answered 2026-10-09 before implementation; the recommended option each time).** Each one says which code it blocked (GATES_AND_REVIEW §5).
1. **Agents that must run on pull requests (for example review bots).** The GitHub preset refuses every `pull_request` and `pull_request_target` run, because such a run executes code that nobody has reviewed into a protected branch.
   - **(a) Recommended:** run the bot from a workflow on the protected branch that reads the pull request as data. It can be triggered by a maintainer comment (`issue_comment`, for example `/review`), by a label, or by `workflow_run`. The bot's own code is reviewed, so it attests normally. The pull request's content stays untrusted input, limited by the bot's grants (M4). The preset does not change; M3 documents the pattern in a runbook.
   - **(b)** A separate "unreviewed code" class: it accepts `pull_request` tokens (never `pull_request_target`) at a capped level, bound to one pull request, and usable only with read-and-comment grants. It needs M4 grant caps, so it would be a later preset option.
   - **(c)** An owner admits each pull-request run by hand, with one `ADMISSION` entry per run: safe, but slow.

   **Answer: (a).** Pull-request bots run from a protected-branch workflow triggered by a maintainer comment or label and read the pull request as data; the GitHub preset is unchanged and slice 16 adds the runbook. *Blocked:* nothing in M3.
2. **Who can switch on a new or widened trusted issuer before M11.** ADR-0018 makes it a protected change (F582). The "distinct publisher" workflow of F582 arrives in M11.
   - **Recommended:** activation needs a separate human-only permission, `identity.issuer.activate`, in a new "Identity Publisher" role that Org Admin does not contain (as with policy publication, F583). Activation is its own step after the proposal. A solo administrator may grant the role to themselves; that is audited and flagged (M2 decision 3). M11 adds "a different person must activate" as an org setting.
   - **Alternative:** always require a second person, which blocks one-admin orgs.

   **Answer: the recommended role.** `identity.issuer.activate` is human only and sits in a new "Identity Publisher" role that Org Admin does not contain; a solo admin may self-grant it (audited and flagged). *Blocked:* issuer activation (slice 9).
3. **Where Kubernetes clusters are configured.** TokenReview means PantherClaw calls the cluster's API server with a credential, and API servers often sit on private addresses.
   - **Recommended:** the operator lists clusters in the server configuration: API server URL, CA file, credential file, the private address range allowed for that cluster, and the orgs that may use it. Org admins then create issuer entries that name a cluster and pin the namespace, service account and uid.
   - **Alternative:** org admins register clusters through the API with an encrypted credential. That needs tenant secrets at rest, and lets tenants choose private addresses, an SSRF risk in hosted deployments.

   **Answer: operator configuration.** Clusters are listed in the server configuration (`identity.kubernetes_clusters`); org admins pin namespace and service account in issuer entries. *Blocked:* the Kubernetes preset (slices 9–10).
4. **Is `pclaw scan` part of M3?** FEATURES places the local shadow-agent scan (PN-001.1) in M3 and demo 3 uses it, while the BUILD_GUIDE M3 text names only gateway discovery.
   - **Recommended:** keep it in M3 as slice 15. It reads local MCP and agent config files, reports redacted findings, and sends them as discoveries only with `--submit`.
   - **Alternative:** move it to M8, with the GitHub organisation scan.

   **Answer: keep in M3** as slice 15. *Blocked:* only slice 15.

**Design decisions taken in this brief (confirmed by the founder with the approval):**
5. Resuming a suspended agent waits for M5 restoration entries (constraint 20).
6. Only preset issuer kinds; no generic OIDC issuer in M3 (constraint 9).
7. An L2 attestation that matches an active entry with `auto_admit` enrolls the workload without an enrollment token. CI jobs and pods are short-lived, and asking an owner for a 15-minute token per job would not work. The token's audience names the org and the entry names the agent (PAP-1 §3.2 clarified in this PR).
8. Nonces are one per org per minute rather than per workload. RFC 9449 allows shared nonces, and a shared nonce costs one write per org per minute instead of one per request.
