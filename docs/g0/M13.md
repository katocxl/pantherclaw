### G0 — M13 — Commercial and production hardening → v1.0 — 2026-10-21

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M13 pull requests and, at the end of the milestone, in an exit status section. It builds on `main` at acf62ce3 (M1–M12, the v0.1.0 preview, M11.1, M10, M11 part 2, M14 and the UI phase complete, with the UI follow-ups; the highest migration is 00164; 00165–00168 stay unused, and 00169, the last UI spare, becomes M13's platform migration (D40)). The founder made ten decisions (F0–F9) on 2026-10-21 before the brief was written and an eleventh (F10) during wave 1; they are recorded at the end. Every other choice is a design decision made by the coordinator (D1–D41 in the coordinator's tracker: D1–D29, D37 and D40 for wave 1, with the D5 and D6 amendments and the review amendments D14, D19–D29, D37 and D40, and D30–D36, D38, D39 and D41 for wave 2), summarised below. Parts that live only in the commercial distribution (the hosted image, the staging host's scripts and the deploy workflow) are described here only as far as the core and the operating procedures depend on them.

**Purpose:** PantherClaw has a complete backend, a web console, hosted accounts and per-organization plans, but nothing runs outside a developer's machine. There is no hosted environment, no backup that has ever been restored, no rate limit on the authenticated API, no usage meter beyond agent counts, no exported telemetry, no customer-approved support access, no tenant export or verified deletion, and no measured service levels. M13 hardens the product for production: a hosted staging deployment (test layer L3) on free infrastructure (F0, F1), scripted so that a paid host is configuration later; readiness that reflects the schema and the workers; certificates that reload without a restart; signing-key rotation; backups with a measured restore drill; rate limits that hold across replicas; daily usage meters; and, in later waves, the telemetry exporter (F5), support access (F3), export, deletion and retention after a lapse (F2), the FIPS and post-quantum builds, installers, API testing, measured performance (F7), the docs site and the threat-model refresh (G4). Production (L4) and paid sign-up open at v1.0. In product terms this is Root: the platform customers trust to run ([PRODUCT.md](../PRODUCT.md)).

*Support access* (TB4; D32, D33). The first path where people outside the customer read a customer's organization.
- **Spoofing:** someone posing as support staff. Answered by: staff are hosted accounts listed in `support.staff_accounts` and request with a step-up on their own security key; the session is a separate principal kind bound to one grant.
- **Tampering:** a support session that writes. Answered by: the `support_readonly` role has only `.read` permissions (HR-387).
- **Repudiation:** every call is audited in the customer's ledger with the support account and the grant (HR-388).
- **Information disclosure:** credentials, sealed material, payload captures, exports and restricted payloads are never readable; restricted evidence only with a scope the customer approved (HR-387).
- **Elevation:** self-approval or standing access. Answered by: approval by an org admin with a step-up, never the requester (HR-386); only an approved, unexpired, unrevoked grant authenticates (HR-385); break-glass is pre-designated, at most 60 minutes, notified and separately audited (HR-389).

*Deletion* (TB4, TB5; D34). The first path that removes an organization's data.
- **Tampering and elevation:** a deletion by a non-admin, during a legal hold or before day 90 of a lapse. Answered by: an org admin with a step-up and a 7-day window any admin can cancel; organization legal holds block it; a lapse deletes only on day 90 (HR-391, HR-393).
- **Repudiation:** a signed deletion record with per-table counts and the verification result (HR-390).
- **Denial of service:** a deleted organization's gateways failing open. Answered by: the organization is marked DELETED first and fails closed on every path (HR-392).

*The hosted staging host* (TB4, TB5, TB6; D2, D13–D17). The first environment PantherClaw runs outside a developer's machine.
- **Spoofing:** a forged deploy. Answered by: the deploy runs only from a manually started workflow on a self-hosted runner on the VM, with no inbound SSH from GitHub (D23); the image is pulled by digest and recorded in the G3 record.
- **Tampering:** a modified backup or a restored copy with stale state. Answered by: dumps are encrypted with `age` to the founder's recipient before they leave the host; after any restore the server runs with the maintenance hold, so no decision is made from any path, until revocations and containment changes made after the dump are re-applied; then every organization's epoch is raised before gateways reconnect (D20, D26, HR-379, HR-373). Backups sit under B2 Object Lock, so a compromised VM cannot delete them (D25).
- **Repudiation:** every deploy writes a G3 record (artifact digest, configuration hash, previous digest, operator, time, result).
- **Information disclosure:** a leaked backup, backup credential or KEK (T-172). Answered by: the backup role can only read and its credential lives only with the backup job (HR-378), dumps are encrypted, the bucket's application key is scoped to the bucket, the KEK is never in the bucket and its escrow is offline (D2, D16, D21).
- **Denial of service:** management API floods (T-170). Answered by: HR-375, HR-376.
- **Elevation:** development sign-in reaching the internet. Answered by: `deployment: staging`; until the hosted provider's staging account exists the console and API listen on loopback and are reached only through an SSH tunnel under the public name (D14 amended); development OIDC providers are never exposed publicly (HR-346).

**Contracts** (M1 and M2 push their contracts first; the hosting stream codes against them):
1. **D3: readiness (HR-370; amended by D19).** `/readyz` answers 503 unless (a) `SELECT 1` works, (b) the schema version recorded in `pc.schema_info` (D19) equals the latest migration embedded in the binary and (c) for the roles `worker` and `all`, the River client is started and has a heartbeat within the last 30 s. The body is a fixed JSON `{"ready": bool, "checks": {"db": …, "schema": …, "workers": …}}` with no versions and no errors. `serve` refuses to start when the schema is newer than the binary (`SCHEMA_NEWER`) and when it is older (`SCHEMA_PENDING`), except in `deployment: development`, where a pending schema is a warning. `/livez` is unchanged.
   - **D19: the schema version.** `pc_app` keeps no access to goose's version table. Migration `00169` creates `pc.schema_info (id smallint PRIMARY KEY CHECK (id = 1), version bigint NOT NULL, applied_at timestamptz NOT NULL)`, owned by the migrator, with SELECT granted to `pc_app` only; `migrate up` (and only `migrate up`) upserts it to goose's applied version at the end of a successful run. `/readyz` and `serve` read it: a missing row or a mismatch means not ready, `SCHEMA_PENDING` or `SCHEMA_NEWER` as above. No SECURITY DEFINER function and no migrator credentials in the server.
   - **D24: review fixes.** A database without `pc.schema_info` (before `00169`) counts as "nothing recorded": `SCHEMA_PENDING` (a warning in development) and not ready, never a raw error. Readiness of the workers means the River client is running. The `worker` role has no `/readyz` listener; the wave 2 installers add a health listener for it (Helm probes). In a rolling deploy on Helm or a paid host, replicas still on the old binary answer 503 once `migrate up` has run, until they are replaced. `migrate status` prints goose's version only.
2. **D4: certificate reload (HR-371).** The public listener reads `http.tls_cert_file` and `http.tls_key_file` through a reloader: `GetCertificate` serves the cached pair; a watcher polls both files' modification times every 60 s (no file-notification dependency) and swaps only when the new pair parses and its leaf is currently valid; a failed reload keeps the last good pair and logs `tls.reload_failed` without key material. Any listener with file certificates can use the same reloader.
3. **D5: signing-key rotation (HR-372; confirmed).** `pantherclaw-server keys rotate-receipts --confirm` rotates the `receipts` key (decision, execution and effect receipts); `keys rotate-evidence --confirm` rotates the `checkpoints` and `evidence_packs` keys, and `checkpoints_pq` when an active one exists. The `anchors` key is excluded: the anchored global root has its own ceremony (HR-195). Each rotation moves the active key to retiring (it keeps verifying and stays published in the well-known documents; the time of the change is its `not_after`) and creates a new active key. Each rotation is audited with the actor `cli:<user>@<host>`; nothing changes without `--confirm`. Keys are held in memory by each server instance, so the command tells the operator to restart every server instance, as `rotate-gateway-ca` does.
4. **D6: the post-restore epoch bump (HR-373; amended).** `pantherclaw-server keys bump-epochs --all --confirm` runs one tenant transaction per organization (HR-051, HR-054), never one cross-organization transaction, over every organization of any status (suspended and closed included, since their gateways may still hold caches), listed through the audited lister (a purpose `orgs_all` in migration `00169` if the existing purpose lists active organizations only). Per organization the new epoch is `max(epoch + 1, the current Unix time in milliseconds)`, so it is above any value gateways cached after the backup; an organization without a containment row gets one at that value; `containment.epoch_bumped_after_restore` is audited in the same transaction. Any failure stops with a non-zero exit; running it again is safe (it raises again). Gateways refetch containment on a higher epoch, and never act on caches from before the restore.
5. **D7: images (HR-374).** `deploy/docker/server.Dockerfile` and `deploy/docker/gateway.Dockerfile`: multi-stage, `CGO_ENABLED=0`, `-trimpath`, distroless static non-root, linux/amd64 and linux/arm64, no shell, the version as a build argument. The orchestrator checks `/readyz` (distroless has no curl). Publishing these images from the release workflow is wave 2 (a `.github` change, merged by the founder).
6. **D8: API rate limits (HR-375).** In `rpcauth`, after authentication and the permission check and before the plan gate: fixed-window limits per organization (`limits.api.per_org_per_minute`, default 6000) and per credential (`limits.api.per_credential_per_minute`, default 1200; a browser session counts as one credential). The excess answers `RESOURCE_EXHAUSTED` with the code `RATE_LIMITED` and `Retry-After`. Gateway, workload, gateway-enrollment and public procedures (the early returns in `rpcauth`) are never limited by this layer, so enforcement is never throttled. The counters are in memory per replica, documented as per-replica limits; values are validated (greater than 0, at most 1,000,000).
   - **D27: safety actions are never blocked by an organization-wide flood.** Procedures classed `safety` or `allow` in the plan-class table skip the per-organization bucket and are still counted per credential. Containment, the kill switch, revocations and approval decisions therefore keep working while other credentials flood the organization. Sign-up keeps its existing Postgres sliding-hour count (equivalent, and it fails closed). `instances_peak` is the highest hourly sample of admitted instances, and yesterday's recorded peak is kept. RT-065 floods the API through a new range step kind `api.flood`.
   - **D28: review fixes.** Per-credential buckets are keyed by the credential id alone, so a service-account key used directly or through its access token shares one bucket. `Retry-After` comes from the database window.
7. **D9: the shared limiter (HR-376).** `internal/platform/ratelimit` with a Postgres store: the UNLOGGED table `pc.rate_counters (scope, key, window_start, count, PRIMARY KEY (scope, key, window_start))`, an atomic `INSERT … ON CONFLICT DO UPDATE SET count = count + 1 RETURNING count` under the global transaction purpose `rate_limit` (no RLS; keys carry the organization id), and a janitor that deletes windows older than 2 h. Used for automation inbound events per source (R-34), AuthZEN per enforcement point and sign-up per address and account (the existing sign-up counts are replaced only where equivalent). A store error refuses inbound and AuthZEN requests with `RATE_LIMITED` and is logged.
   - **D28: review fixes.** Every caller takes its shared-limit count in its own short global transaction, never while holding another pooled connection. The automation receiver does this between signature verification and the tenant transaction, so the pool cannot be exhausted. `pc.rate_counters` has forced RLS with a policy that admits rows only under the `rate_limit` purpose. The in-memory limiter evicts the oldest keys when full instead of clearing every window.
8. **D10: usage meters (HR-377, F6).** `pc.usage_daily (org_id, day, agents, instances_peak, runs, stored_bytes, computed_at, PRIMARY KEY (org_id, day))` with RLS like other tenant tables. The River periodic job `usage.meter_daily` runs hourly and recomputes today and yesterday per organization from records: active agents, peak concurrently admitted instances, runs started, and stored bytes from row counts times documented average sizes per table, or from the sums of payload and evidence byte columns where they exist (never from per-relation sizes, which cannot be split per organization); the method is documented. Never reported by clients. `limits.usage.enforce` exists and refuses `true` in M13.
9. **D11: `UsageService`** (`usage.proto`). `ListUsage(days 1..90)` returns `DailyUsage {day, agents, instances_peak, runs, stored_bytes}`; permission `entitlements.read`; plan class `read`; registered in the procedure and plan-class tables. The console shows it under Settings › Plan & billing (wave 2).
10. **D21: the backup role (HR-378, T-172).** `db bootstrap` gains an optional `--backup-password-file` and creates `pc_backup LOGIN NOINHERIT BYPASSRLS` with USAGE on schema `pc`, SELECT on every table and sequence, and default privileges so that tables the migrator creates later are readable too; nothing else (no writes, no ownership, no functions beyond the defaults). Migration `00169` re-grants SELECT on existing tables to `pc_backup` when the role exists. Its credential lives only with the backup job.
11. **D26: the maintenance hold (HR-379).** Configuration `maintenance.hold: true` (environment `PC_MAINTENANCE_HOLD`) makes every decision and data-plane procedure refuse with `UNAVAILABLE` and the code `MAINTENANCE_HOLD`: the gateway control and stream procedures (gateways fail closed), workload procedures, `Authorize`, hooks, the `/sdk` face, the MCP faces and AuthZEN. The management API for people and services and the operator command line keep working, so state can be inspected and revocations re-applied. A start with the hold is audited (`platform.maintenance_hold_on`), and so is the first start without it (`platform.maintenance_hold_off`). `/readyz` reports not ready while the hold is on. Production allows it, since it only ever refuses. It replaces "engage the kill switch for every organization" in the restore procedure: an operator cannot engage organizations' kill switches (HR-113 needs the organization's responder and a step-up), and closing the gateway port alone misses hook, SDK and AuthZEN decisions on the API port.

12. **D2: no PROXY protocol, KMS or infrastructure-as-code tool now.** On the staging VM the server is reached directly, so client addresses are real and the PROXY protocol waits for a paid host. KEK custody at $0: the file provider stays; the KEK file is mode 0400, owned by the service user, on the VM's encrypted boot volume; an offline escrow copy is encrypted with `age` (passphrase) per [backup-restore.md](../runbooks/backup-restore.md). The compose stack: `postgres:17` with its data on the block volume, the hosted server (role `all`, `deployment: staging`, public TLS on 443 with the D4 reload, gateway mTLS on 8443), a one-shot `migrate` as `pc_migrator` (the migrator password is mounted only into this service; the server's configuration has none) and a `backup` job. Certificates by ACME HTTP-01 (D25): `certbot --standalone` listens on port 80 only during issuance and renewal; a daily systemd timer runs `certbot renew` into `/srv/pantherclaw/certs`, and the D4 reload picks the new pair up; there is no Cloudflare token on the VM (the DNS script runs on the founder's machine). The console and API host is `staging.app.pantherclaw.dev`; the gateway endpoint is the same host on 8443. Secrets (database passwords, the KEK from `keys gen-kek --out FILE`) are generated at bootstrap into a root-only environment file, never in a repository.
15. **D14: staging sign-in (amended).** Public sign-in only through the hosted OIDC provider's staging environment once the founder's account exists; until then the console and API listener binds to 127.0.0.1 and the founder reaches it through an SSH tunnel: the founder maps `staging.app.pantherclaw.dev` to 127.0.0.1 in the hosts file and forwards local port 443 to the VM's 127.0.0.1:443, so the origin, the WebAuthn relying-party id and the OIDC redirects match the public name and the real certificate validates. Never sign in through `localhost` ([deploy.md](../runbooks/deploy.md)). Development OIDC providers are never exposed publicly. Billing on staging is `fake` until the payment provider's sandbox account exists.
16. **D15: deploy and G3.** A manually started workflow builds or pulls the image digest. Under D23 it runs on a GitHub self-hosted runner installed on the VM, not over SSH:
   - the runner connects outbound to GitHub only and has the label `pantherclaw-staging`;
   - it runs as an unprivileged user whose sudo is limited to the installed deploy script;
   - the workflow is `workflow_dispatch` only, and the image is pulled with the job's token;
   - GitHub has no inbound SSH, and SSH stays limited to the founder's addresses;
   - manual setup over SSH is the fallback; the restore drill runs on the same runner.

   **D29 (amends D23).** Build agents push branches with the founder's credentials, and any pushed workflow can target the runner's label. The runner must therefore be safe even when a hostile workflow runs on it:
   - **Signed images only.** The deploy script verifies the image's Sigstore keyless signature, made by the private repository's `.github/workflows/image.yml` at `refs/heads/main` (F10), and refuses any other image.
   - **No secrets in the job.** The drill reads its `age` identity and the staging KEK from root-only files on the VM; the job pipes no secrets, and the drill's repository secrets are deleted.
   - **Root-owned runner.** The runner installation is root-owned except its work and diagnostics directories, and is started with `--disableupdate`. Upgrades bump the pinned version and SHA-256 in the repository and re-run bootstrap.
   - **Workflow check.** A GitHub-hosted check fails any change that adds `self-hosted` to a workflow other than the deploy and drill workflows. Those two run only when the ref is `main`, and the drill keeps its monthly schedule.
   - **What remains.** A pushed branch can still run code as the unprivileged runner user, with no docker group, no secrets and no sudo beyond the verified deploy (R-62).

   **D37 (amends D29).** The foothold is an accepted residual for $0 staging, which holds no customer data, with these mitigations:
   - **Cleanup around every job.** Runner job hooks (root-owned scripts) call a root-owned cleanup script through a sudoers entry that takes no arguments, before and after every job. It kills every runner-user process outside the runner service's cgroup, clears the runner user's cron and `at` jobs, and resets its home and work directories, except the current checkout at job start. The systemd unit uses `KillMode=control-group`.
   - **G3 records on the VM.** The deploy script writes the authoritative G3 record root-only on the VM (`/srv/pantherclaw/deploy/g3/<ts>.json`); the workflow only prints it back. The staging tag is a convenience: the VM re-verifies the signature on every deploy.
   - **The guard.** It is a merge gate, not a runtime control: a pushed branch's job runs before CI. It is YAML-aware (pinned `yq`):
     - every `runs-on` is a literal `ubuntu-*`, except the two allowed jobs;
     - those two must be exactly `[self-hosted, pantherclaw-staging]` with the exact main-only condition;
     - job-level `uses:` and `${{` in `runs-on` are refused.
   - **The hold value.** The deploy script normalises it with boolean-parsing semantics.
   - **Follow-up.** Just-in-time ephemeral runners after the GitHub organization move (F8).

   The deploy pulls, runs `migrate up`, starts the stack and waits up to 5 minutes for `/readyz` to answer 200; otherwise it rolls back to the previous digest (kept in `/srv/pantherclaw/deploy/previous`). It writes a G3 record (artifact digest, configuration hash, previous digest, operator, time, result) to the job summary and as an artifact; the coordinator copies G3 rows to GATES §7 at landing.
17. **D16: backups.** Nightly at 02:15 UTC: `pg_dump -Fc` as the backup role `pc_backup` (D21), encrypted with `age` to the founder's recipient, copied with `rclone` to a Backblaze B2 bucket whose application key is scoped to that bucket; 14 daily and 8 weekly copies kept by the bucket's lifecycle rules, and B2 Object Lock with a default retention of at least 60 days in compliance mode, so a compromised VM cannot hide or delete backups (D25); a size and age check alerts (logged now, Grafana later). The KEK escrow stays offline, never in the bucket. Targets on staging: RPO ≤ 24 h (point-in-time recovery comes with a paid database), RTO ≤ 4 h.
18. **D17: the restore drill.** A script that runs locally and as a monthly workflow: fetch the latest dump, decrypt it with the drill identity (staging only), restore it into a throwaway Postgres container, check that `migrate up` applies nothing (D24), run an RLS smoke test (a cross-organization read returns nothing), start the server with the escrowed staging KEK and see `/readyz` answer 200 (it unwraps every platform signing key at start and fails closed otherwise), run `keys bump-epochs --all --confirm` against the restored copy, and record the measured RPO and RTO in the summary. Production drills are run by the founder by hand. The script defines the exact restore sequence, which the runbook mirrors once the drill passes.
19. **D20: a restore brings back revocations made after the dump.** After a restore the server starts with the maintenance hold on (D26, HR-379), so no decision is made from any path, and the gateway port stays closed. The operator then re-applies every revocation and containment event logged after the dump's time: signing-key revocations, gateway-certificate revocations, API key, credential and grant revocations, containment and kill-switch changes. They come from the shipped `security_event` log lines (D31, HR-383) and are re-applied with `pantherclaw-server restore reapply --from <ndjson> --confirm` (HR-384). Then `keys bump-epochs --all --confirm` (D6), then a restart without the hold, and the gateway port reopens. Keys created after the dump are lost with it: receipts and evidence they signed stop verifying until their public keys are published again from the logs. Residual risk R-61.
20. **D22: deleted organizations fail closed.** After the day-90 deletion of F2, the organization's gateways and credentials fail closed (denied or unauthenticated), never open (ADR-0035; D34, HR-392).

**Wave 2 decisions** (2026-10-21; the public streams branch from `origin/feat/m13-platform` 7a746ca1):

*Observability (W2-A; F5, [ADR-0033](../adr/0033-observability-exporter.md); [runbook](../runbooks/observability.md))*

22. **D30: the exporter, metrics and the admin listener (HR-380..382).**
    - **SDK.** The official OpenTelemetry SDK (`go.opentelemetry.io/otel/sdk` and `sdk/metric`, no gRPC).
    - **Exporter.** Our own exporter. The OTLP `.proto` message files (opentelemetry-proto, Apache-2.0) are vendored under `proto/third_party/otlp` and generated as messages only, with no gRPC or Connect stubs. It POSTs `application/x-protobuf`, gzip-compressed, to `<endpoint>/v1/traces` and `/v1/metrics` with the headers from `telemetry.otlp.headers_file`, with a 10 s timeout.
    - **Configuration.** `telemetry.otlp.{endpoint, headers_file, sample_ratio (default 0.1; errors always sampled), service_name}`; telemetry is off when the endpoint is empty.
    - **Attributes (HR-380).** One fixed allow-list applied by a single filter, with a test that walks every attribute key used.
    - **Queue (HR-381).** Bounded: spans 2048, batch 512, 5 s; it drops and counts on overflow or export error.
    - **Database tracing.** The pgx tracer opens one span per query, named by the sqlc query name only.
    - **Metrics** (fixed names, `pc_` prefix): RPC duration by procedure and code; decisions by outcome; database pool in use, idle and wait; River jobs by kind and state; rate-limit refusals by scope; a maintenance-hold gauge.
    - **Logs.** Log lines carry `trace_id` and `span_id`.
    - **Admin listener (HR-382).** `admin.addr` serves pprof and `/metrics` as text. It is off by default and refuses any non-loopback address.
    - **Local stack.** A compose `observability` profile with grafana/otel-lgtm.
23. **D31: the security-event log and `restore reapply` (HR-383, HR-384, T-173).**
    - **Event lines (HR-383).** After commit, the evidence chainer emits exactly one `security_event` line per ledger entry whose kind is in the closed security set, with the fields {ts, org, ledger_seq, kind, direction, object{type,id}, actor{type,id}}.
      - Tightening kinds: signing-key, gateway, gateway-certificate, API key, service-account key, credential, sealed-credential, grant, session, invitation and organization package-signing-key revocations; service-account, user and issuer disablements; WebAuthn suspensions and removals; kill switch, containment, quarantine and agent suspension.
      - Their restore counterparts carry `direction: loosen`.
    - **Reapply (HR-384).** `pantherclaw-server restore reapply --from <ndjson> [--since <ts>] --confirm`:
      - re-applies only `direction: tighten` events, idempotently: an object already revoked, disabled or engaged is a no-op;
      - runs one tenant transaction per organization;
      - is audited as `restore.reapplied` (count, first and last sequence) with the operator actor;
      - refuses unless the maintenance hold is on (D26);
      - reports unknown kinds and never guesses.
    - **D41: restores never resurrect deleted organizations or accounts (amends D31 and D34).** The closed set gains the tightening kinds `org.deleted` and `account.deleted`. W2-D writes them in the platform organization's ledger, so the chainer emits their lines, and each line carries the deletion record's digest. W2-A builds `internal/restore` with a handler registry (`restore.Register(kind, Handler)`), so streams plug in re-apply handlers without import cycles. W2-D registers two handlers:
      - `org.deleted` sets the organization DELETED again (failing closed at once), requeues `data.delete_org` and writes a new deletion record that notes "re-applied after restore" with the original record's digest;
      - `account.deleted` pseudonymises the account again and revokes its sessions.

*Support access and break-glass (W2-C; F3, F594, [ADR-0034](../adr/0034-customer-approved-support-access.md); [runbook](../runbooks/support-access.md))*

24. **D32: support access (HR-385..388, T-174, T-175; Enterprise plan, hosted only).**
    - **Staff.** Staff are the hosted accounts listed in `support.staff_accounts` (issuer and subject pairs). An empty list turns the feature off, and it is refused in self-hosted licence mode.
    - **Request.** A staff member, in an account session with a step-up on their own security key, calls `SupportAccessService.RequestAccess{org, task (at most 200 characters, plain text), scope READ_ONLY (default) | READ_ONLY_PLUS_EVIDENCE, duration at most 72 h}`. The request is stored in the organization's scope (`pc.support_access_requests`, `pc.support_access_grants`, forced RLS), audited in its ledger, and the org admins are notified (`support.access_requested`).
    - **Approval.** An org admin approves with a step-up (`ApproveRequest`), never the requesting account even when it is also an org admin, or denies it. Any admin can revoke at any time (`RevokeGrant`). Expiry is enforced at every authentication.
    - **Session.** `OpenSupportSession` gives a browser organization session of the new principal kind `support`, bound to the grant, with the new role `support_readonly`. That role has every `.read` permission except `evidence.read_restricted`, credentials and sealed material, payload captures and exports; `READ_ONLY_PLUS_EVIDENCE` adds `evidence.read_restricted` only.
    - **Audit.** Every call is audited with the actor `support/<account id>` and the grant id, and the console shows a banner.
    - **D38: details (amends D32 and D33).**
      - **Staff identity.** Staff act from their own organization browser session in the operator's staff organization (`support.staff_org`, an organization the operator creates). Staff are its users, with registered security keys. A staff member's identity is that user's linked account, which must also be listed in `support.staff_accounts`. Requesting access and opening a support session need a step-up of at most 5 minutes with the staff user's own active key.
      - **Canonical pages.** Requests (`/support-access/request`), approval and denial (`/support-access/{id}/approve`, `/deny`) and break-glass activation (`/break-glass/activate`) happen on canonical server-rendered confirmation pages with a step-up, so what an admin approves is what they saw. The Connect procedures for these actions refuse with `STEP_UP_REQUIRED`, and the console links to the pages.
      - **Plain Connect calls.** Listing, reading and revoking stay Connect calls. Revoking only removes access, so it needs no step-up.
      - **Support sessions.** They are stored in `pc.support_sessions` (migration `00174`; organization-scoped, forced RLS, bound to the grant id and the account id). They have their own credential prefix and are set as the console's session cookie in that browser. Expiry, revocation and the grant's state are checked at every authentication.
      - **Principal kind.** `support` counts as a person only for checks of permissions reserved to people; it is never treated as a user.
      - **Role binding.** `support_readonly` can never be bound to anyone.
25. **D33: break-glass (HR-389; Business and above).**
    - **Holders.** Org admins pre-designate up to 3 members in Settings as break-glass holders, each with an emergency role (any existing role except org admin).
    - **Activation.** A holder activates with a step-up (`BreakGlassService.Activate{reason}`) for at most 60 minutes, and every other org admin is notified at once.
    - **Audit.** The kinds `breakglass.activated` and `breakglass.ended`, and every call during an activation is audited with its activation id.
    - **Limits.** It never waives two-person rules, approvals or invariants.

*Data requests (W2-D; F2, PN-012.5, [ADR-0035](../adr/0035-export-deletion-and-lapse-retention.md); [runbook](../runbooks/data-requests.md))*

26. **D34: export, deletion, the lapse and account deletion (HR-390..394, T-176, T-177).**
    - **Export.** `DataRequestService.CreateExport` needs an org admin with a step-up; a River job builds a signed export.
      - Content: canonical JSONL per table for a curated allow-list of organization tables, which excludes wrapped keys and DEKs, sealed credentials, token and secret hashes and session secrets; plus the full-range evidence bundle with its proofs.
      - Storage: ZIP parts of at most 64 MiB in `pc.data_request_parts`, which expire after 7 days.
      - Manifest: a JWS signed with the `evidence_packs` key, with an ML-DSA co-signature on Enterprise.
      - Size: at most 2 GiB in total; anything larger is refused with `EXPORT_TOO_LARGE` (object storage is a follow-up).
      - Download: streamed, and audited before the first byte.
    - **Deletion request.** `RequestDeletion` needs an org admin with a step-up and opens a 7-day cancellation window. All admins are notified, and any admin can cancel. A lapse creates the request on day 90 with the reason `lapse_90d` and no window, since the reminders were already sent.
    - **Deletion job.** The worker's `data.delete_org` job runs as the new role `pc_deleter`. That role is created by `db bootstrap --deleter-password-file`, has DELETE on every organization table and an exemption in the immutable case triggers, and is used by nothing else. The job:
      1. sets the organization to DELETED first, so authentication, gateway mTLS and workload authentication fail closed (D22);
      2. deletes in foreign-key order per area, in bounded batches;
      3. destroys the organization's DEKs;
      4. scrubs the organization row to a tombstone (id, state, `deleted_at`);
      5. verifies that zero rows remain in every organization table;
      6. writes a deletion record in the platform organization's ledger, signed with the receipts key: organization, reason, requester, window, start and completion, per-table counts, the verification result and the backup expiry date from the configured backup retention (`backups.retention_days`, default 60, under Object Lock).
    - **Deletion record and holds.** The requesting account fetches the record with `GetDeletionRecord`. Organization-scoped legal holds block deletion (`DELETION_HELD`) until they are released.
    - **After a restore** (D41). Organization and account deletions are `security_event` kinds, so `restore reapply` performs them again: the organization fails closed at once and is deleted again with a new record.
    - **Lapse.** `org_entitlements.lapsed_at` is set on entering a lapsed, paused or past-end cancelled state and cleared on recovery. A daily job sends the fixed template `billing.lapse_reminder` to org admins on days 0, 30, 60 and 83, deduplicated by organization, `lapsed_at` and day. On day 90 or later it creates the lapse deletion request.
    - **Account deletion.** `AccountService.DeleteAccount` needs an account session and a recent sign-in. It is refused while the account is the last org admin of any active organization (`LAST_ADMIN`). Otherwise it disables and pseudonymises the account's per-organization users (email and display name become "deleted user <short id>"), scrubs the account's personal data and revokes its sessions; evidence keeps opaque ids.

*FIPS and post-quantum (W2-E; PN-019.1, PN-019.2)*

27. **D35: the FIPS build and post-quantum links (HR-395, HR-396, T-178).**
    - **Build.** A `GOFIPS140=v1.0.0` build variant (`*-fips` binaries, a second build set in the release configuration) and a CI job that runs the crypto, authentication, key, sealing and evidence tests with `GODEBUG=fips140=only`. The CI job is a `.github` change, so the founder merges the top.
    - **FIPS mode** (`fips140.Enabled()`):
      - sealing uses HPKE MLKEM768-P256, with the suite id recorded per blob;
      - X-Wing blobs refuse to open (`SEAL_SUITE_NOT_FIPS`), so FIPS installs start fresh;
      - ML-DSA co-signing is off (logged once) until the validated module includes ML-DSA;
      - RSA keys under 2048 bits from identity providers are refused.
    - **TLS.**
      - Server listeners use TLS 1.3 with `CurvePreferences` nil (Go's post-quantum-first defaults; never an explicit list).
      - Links between components (gateway to server control, edge to gateway) are limited on both ends to X25519MLKEM768, SecP256r1MLKEM768 and SecP384r1MLKEM1024, and the negotiated group is logged.
      - Third-party outbound connections (egress, OIDC, SMTP, the Postgres connector) keep a TLS 1.2 minimum with nil curves, so post-quantum is offered by default.

*Installers (W2-F; PN-010.1, PN-012.6; [runbook](../runbooks/installation.md))*

28. **D36: images, `pclaw up`, `install.sh` and Helm (HR-397, HR-398, T-179).**

    - **`pclaw up`.** A local single-node install. It generates a Docker Compose stack in `~/.pantherclaw/node` (Postgres 17, the server image at the digest embedded in that `pclaw` release, and a gateway), generates a KEK, runs `db bootstrap`, `migrate`, `org create` and the admin invitation, and prints the URL. It refuses without Docker. `pclaw down` and `pclaw status` complete it.
    - **D39: `pclaw up` details (amends D36).**
      - **Sign-in.** It defaults to `deployment: production` (Community production, PN-010.1) and needs the operator's own sign-in: `--oidc-issuer`, `--oidc-client-id`, `--oidc-client-secret-file` (and optionally `--oidc-name`), and/or `--github-client-id`, `--github-client-secret-file`. Without one, the node still starts and prints how to add one.
      - **`--dev`.** `pclaw up --dev` sets `deployment: development` and takes the same flags. It bundles no identity provider: the docs point to `go run ./test/devoidc` with a host-run server.
      - **Listeners.** The server listens on 0.0.0.0:8080 inside its container with `plaintext_behind_proxy: true`, published on 127.0.0.1:8080 only. The gateway's agent-facing listener gets the same kind of flag, also published on loopback only. The server's gateway mTLS listener stays TLS with the internal CA (D35 is unchanged).
      - **Enrolling the gateway.** There is no new operator enrollment command. The first `pclaw up` starts Postgres and the server and prints the login line. Running `pclaw up` again after `pclaw login` creates the gateway "local" with that session, writes its enrollment into `~/.pantherclaw/node` and starts it.
      - **Containers.** They run as the host uid:gid on Unix. Bootstrap, migrate and `org create` run through `docker compose run --rm server …`.
      - **Releases.** The `release` job builds, pushes by digest and attests the server and gateway images under the one release approval. GoReleaser embeds the digests, and the final job writes them into the release notes.
    - **`install.sh`.** It downloads the archive and `checksums.txt`, verifies the SHA-256, and verifies the GitHub attestation with `gh attestation verify` when `gh` is installed (otherwise it prints the manual command).
    - **Helm chart** (`deploy/helm/pantherclaw`):
      - API and worker Deployments; the worker gets a health listener `health.addr` that serves only `/livez` and `/readyz` (HR-397);
      - a pre-install and pre-upgrade migrate Job;
      - a gateway Service with mTLS passthrough;
      - existing-Secret references for passwords, the KEK and TLS;
      - non-root, a read-only root file system and all capabilities dropped (HR-398);
      - a NetworkPolicy, a PodDisruptionBudget, and a `maintenanceHold` value applied to every replica.
    - **Chart CI.** `helm lint` and `helm template | kubeconform` with pinned tools.

**Residual risks** (added to THREAT_MODEL §8 by this brief; later waves add theirs):
- **R-56:** staging runs on one VM with Postgres in a container: losing the VM is a fail-closed outage until a rebuild, and without point-in-time recovery up to 24 hours of staging data can be lost. Compensating controls: nightly encrypted off-site dumps, a measured monthly restore drill, RTO ≤ 4 h; production gets a managed database with point-in-time recovery (D16).
- **R-57:** the KEK is a file on the staging VM, not in a KMS. Compensating controls: mode 0400 for the service user, an encrypted boot volume, an offline `age` escrow kept apart from the backups; a KMS follows with a paid host (D2).
- **R-58:** the API rate limits of D8 are per replica, so with several replicas the effective limit multiplies. Compensating controls: the limits that must hold across replicas use the shared limiter (HR-376); staging runs one replica.
- **R-59:** usage meters are approximate for stored bytes and are not enforced. Compensating controls: the method is documented; counts come only from records (HR-377); enforcement waits for prices (F6).
- **R-60:** staging sign-in through an SSH tunnel until the hosted provider's staging account exists. Compensating controls: the listener binds to loopback; SSH only from the founder's addresses (D13, D14).
- **R-61:** after a restore, revocations and containment changes made after the dump must be re-applied from the shipped logs before gateways reconnect; anything missing from the logs comes back active, and keys created after the dump are lost. Compensating controls: the server runs with the maintenance hold (no decision from any path, HR-379) and the gateway port closed until the re-application is done, then the epoch bump (D20, D26, HR-373); staging RPO ≤ 24 h, and point-in-time recovery on a paid database cuts the window to ≤ 5 min.
- **R-62:** a pushed branch can run code on the staging VM as the unprivileged runner user, because any workflow pushed to the private repository can target the runner's label. Compensating controls: the runner user has no docker group, no secrets and no sudo beyond the deploy script; the deploy verifies the image's Sigstore signature from the image workflow on `main` (F10); the drill's secrets are root-only files; the runner is root-owned and does not update itself; a GitHub-hosted check limits `self-hosted` to the deploy and drill workflows, which run only on `main` (D29); runner job hooks clean up the runner user's processes, scheduled jobs and files before and after every job, and G3 records are written root-only on the VM (D37). The guard is a merge gate, not a runtime control: a pushed branch's job runs before CI. Accepted for $0 staging, which holds no customer data; just-in-time ephemeral runners follow the organization move.
- **R-34** (the per-source inbound limit per instance) is addressed by HR-376; **R-43** (Stripe live mode) stays open after M13.
