### G0 — M13 — Commercial and production hardening → v1.0 — 2026-10-21

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M13 pull requests and, at the end of the milestone, in an exit status section. It builds on `main` at acf62ce3 (M1–M12, the v0.1.0 preview, M11.1, M10, M11 part 2, M14 and the UI phase complete, with the UI follow-ups; the highest migration is 00164, and 00165–00169 stay unused). The founder made ten decisions (F0–F9) on 2026-10-21 before the brief was written; they are recorded at the end. Every other choice is a design decision made by the coordinator (D1–D18 for wave 1 in the coordinator's tracker), summarised below. Parts that live only in the commercial distribution (the hosted image, the staging host's scripts and the deploy workflow) are described here only as far as the core and the operating procedures depend on them.

**Purpose:** PantherClaw has a complete backend, a web console, hosted accounts and per-organization plans, but nothing runs outside a developer's machine. There is no hosted environment, no backup that has ever been restored, no rate limit on the authenticated API, no usage meter beyond agent counts, no exported telemetry, no customer-approved support access, no tenant export or verified deletion, and no measured service levels. M13 hardens the product for production: a hosted staging deployment (test layer L3) on free infrastructure (F0, F1), scripted so that a paid host is configuration later; readiness that reflects the schema and the workers; certificates that reload without a restart; signing-key rotation; backups with a measured restore drill; rate limits that hold across replicas; daily usage meters; and, in later waves, the telemetry exporter (F5), support access (F3), export, deletion and retention after a lapse (F2), the FIPS and post-quantum builds, installers, API testing, measured performance (F7), the docs site and the threat-model refresh (G4). Production (L4) and paid sign-up open at v1.0. In product terms this is Root: the platform customers trust to run ([PRODUCT.md](../PRODUCT.md)).

*The hosted staging host* (TB4, TB5, TB6; D2, D13–D17). The first environment PantherClaw runs outside a developer's machine.
- **Spoofing:** a forged deploy. Answered by: the deploy runs only from a manually started workflow with a deploy key held in the repository's secrets; the image is pulled by digest and recorded in the G3 record.
- **Tampering:** a modified backup or a restored copy with stale state. Answered by: dumps are encrypted with `age` to the founder's recipient before they leave the host; after any restore every organization's epoch is raised before gateways reconnect (HR-373).
- **Repudiation:** every deploy writes a G3 record (artifact digest, configuration hash, previous digest, operator, time, result).
- **Information disclosure:** a leaked backup or KEK. Answered by: dumps are encrypted, the bucket's application key is scoped to the bucket, the KEK is never in the bucket and its escrow is offline (D2, D16).
- **Denial of service:** management API floods (T-170). Answered by: HR-375, HR-376.
- **Elevation:** development sign-in reaching the internet. Answered by: `deployment: staging`; until the hosted provider's staging account exists the console and API listen on loopback and are reached only through an SSH tunnel (D14); development OIDC providers are never exposed publicly (HR-346).

**Contracts** (M1 and M2 push their contracts first; the hosting stream codes against them):
1. **D3: readiness (HR-370).** `/readyz` answers 503 unless (a) `SELECT 1` works, (b) the schema version (goose) equals the latest migration embedded in the binary and (c) for the roles `worker` and `all`, the River client is started and has a heartbeat within the last 30 s. The body is a fixed JSON `{"ready": bool, "checks": {"db": …, "schema": …, "workers": …}}` with no versions and no errors. `serve` refuses to start when the schema is newer than the binary (`SCHEMA_NEWER`) and when it is older (`SCHEMA_PENDING`), except in `deployment: development`, where a pending schema is a warning. `/livez` is unchanged.
2. **D4: certificate reload (HR-371).** The public listener reads `http.tls_cert_file` and `http.tls_key_file` through a reloader: `GetCertificate` serves the cached pair; a watcher polls both files' modification times every 60 s (no file-notification dependency) and swaps only when the new pair parses and its leaf is currently valid; a failed reload keeps the last good pair and logs `tls.reload_failed` without key material. Any listener with file certificates can use the same reloader.
3. **D5: signing-key rotation (HR-372).** `pantherclaw-server keys rotate-receipts --confirm` and `keys rotate-evidence --confirm` cover the key sets that exist today for decision, execution and effect receipts and for the evidence keys (checkpoints, anchors, evidence packs and the optional ML-DSA co-signature). Each creates a new active key and retires the previous one (`not_after` = now); the retired public key stays published in the well-known documents and accepted for verification. Each rotation is audited with the actor `cli:<user>@<host>`; nothing changes without `--confirm`.
4. **D6: the post-restore epoch bump (HR-373).** `pantherclaw-server keys bump-epochs --all --confirm` raises every organization's containment epoch (the epoch the kill switch and containment use) by one in one transaction and audits `containment.epoch_bumped_after_restore` per organization, so gateways refetch containment and never act on caches from before the restore.
5. **D7: images (HR-374).** `deploy/docker/server.Dockerfile` and `deploy/docker/gateway.Dockerfile`: multi-stage, `CGO_ENABLED=0`, `-trimpath`, distroless static non-root, linux/amd64 and linux/arm64, no shell, the version as a build argument. The orchestrator checks `/readyz` (distroless has no curl). Publishing these images from the release workflow is wave 2 (a `.github` change, merged by the founder).
6. **D8: API rate limits (HR-375).** In `rpcauth`, after authentication and the permission check and before the plan gate: fixed-window limits per organization (`limits.api.per_org_per_minute`, default 6000) and per credential (`limits.api.per_credential_per_minute`, default 1200; a browser session counts as one credential). The excess answers `RESOURCE_EXHAUSTED` with the code `RATE_LIMITED` and `Retry-After`. Gateway, workload, gateway-enrollment and public procedures (the early returns in `rpcauth`) are never limited by this layer, so enforcement is never throttled. The counters are in memory per replica, documented as per-replica limits; values are validated (greater than 0, at most 1,000,000).
7. **D9: the shared limiter (HR-376).** `internal/platform/ratelimit` with a Postgres store: the UNLOGGED table `pc.rate_counters (scope, key, window_start, count, PRIMARY KEY (scope, key, window_start))`, an atomic `INSERT … ON CONFLICT DO UPDATE SET count = count + 1 RETURNING count` under the global transaction purpose `rate_limit` (no RLS; keys carry the organization id), and a janitor that deletes windows older than 2 h. Used for automation inbound events per source (R-34), AuthZEN per enforcement point and sign-up per address and account (the existing sign-up counts are replaced only where equivalent). A store error refuses inbound and AuthZEN requests with `RATE_LIMITED` and is logged.
8. **D10: usage meters (HR-377, F6).** `pc.usage_daily (org_id, day, agents, instances_peak, runs, stored_bytes, computed_at, PRIMARY KEY (org_id, day))` with RLS like other tenant tables. The River periodic job `usage.meter_daily` runs hourly and recomputes today and yesterday per organization from records: active agents, peak concurrently admitted instances, runs started, and stored bytes from row counts times documented average sizes per table, or from the sums of payload and evidence byte columns where they exist (never from per-relation sizes, which cannot be split per organization); the method is documented. Never reported by clients. `limits.usage.enforce` exists and refuses `true` in M13.
9. **D11: `UsageService`** (`usage.proto`). `ListUsage(days 1..90)` returns `DailyUsage {day, agents, instances_peak, runs, stored_bytes}`; permission `entitlements.read`; plan class `read`; registered in the procedure and plan-class tables. The console shows it under Settings › Plan & billing (wave 2).

**Migrations.** `00170` `pc.rate_counters` (UNLOGGED, global, no RLS; only the limiter's purpose reads and writes it; keys carry the organization id) · `00171` `pc.usage_daily` (tenant table: `org_id`, composite key, forced RLS, `pc_app` SELECT and INSERT, UPDATE only on the recomputed columns named in the header comment, `pc_audit_ro` SELECT) · `00172` spare for the limits stream. squawk-clean; every down migration restores the previous state.

**Security constraints and design decisions:**

*Hosting and operations (the commercial distribution; ADR-0032)*
10. **D2: no PROXY protocol, KMS or infrastructure-as-code tool now.** On the staging VM the server is reached directly, so client addresses are real and the PROXY protocol waits for a paid host. KEK custody at $0: the file provider stays; the KEK file is mode 0400, owned by the service user, on the VM's encrypted boot volume; an offline escrow copy is encrypted with `age` (passphrase) per [backup-restore.md](../runbooks/backup-restore.md). Provisioning is cloud-init plus idempotent scripts; DNS records through a small script with the founder's Cloudflare API token.
11. **D12: the hosted image.** The commercial binary with the embedded console, distroless static non-root, linux/arm64 and linux/amd64, published to a private registry on manual dispatch, its digest recorded.
12. **D13: the staging layout.** An Ubuntu 24.04 Arm VM bootstrapped by cloud-init and an idempotent script: Docker with the compose plugin, nftables (SSH only from the founder's addresses, 443, 8443), unattended upgrades, a `pantherclaw` service user and `/srv/pantherclaw/{config,secrets,certs,pgdata,backups}`. The compose stack: `postgres:17` with its data on the block volume, the hosted server (role `all`, `deployment: staging`, public TLS on 443 with the D4 reload, gateway mTLS on 8443), a one-shot `migrate` as `pc_migrator`, a `backup` job and `certbot` (DNS-01 through the Cloudflare token, renewing into `/srv/pantherclaw/certs`). The console and API host is `staging.app.pantherclaw.dev`; the gateway endpoint is the same host on 8443. Secrets (database passwords, the KEK from `keys gen-kek`) are generated at bootstrap into a root-only environment file, never in a repository.
13. **D14: staging sign-in.** Public sign-in only through the hosted OIDC provider's staging environment once the founder's account exists; until then the console and API listener binds to 127.0.0.1 and the founder reaches it through an SSH tunnel ([deploy.md](../runbooks/deploy.md)). Development OIDC providers are never exposed publicly. Billing on staging is `fake` until the payment provider's sandbox account exists.
14. **D15: deploy and G3.** A manually started workflow builds or pulls the image digest, connects over SSH with a deploy key from the repository's secrets, pulls, runs `migrate up`, starts the stack and waits up to 5 minutes for `/readyz` to answer 200; otherwise it rolls back to the previous digest (kept in `/srv/pantherclaw/deploy/previous`). It writes a G3 record (artifact digest, configuration hash, previous digest, operator, time, result) to the job summary and as an artifact; the coordinator copies G3 rows to GATES §7 at landing.
15. **D16: backups.** Nightly at 02:15 UTC: `pg_dump -Fc` as a read-only backup role, encrypted with `age` to the founder's recipient, copied with `rclone` to a Backblaze B2 bucket whose application key is scoped to that bucket; 14 daily and 8 weekly copies kept by the bucket's lifecycle rules; a size and age check alerts (logged now, Grafana later). The KEK escrow stays offline, never in the bucket. Targets on staging: RPO ≤ 24 h (point-in-time recovery comes with a paid database), RTO ≤ 4 h.
16. **D17: the restore drill.** A script that runs locally and as a monthly workflow: fetch the latest dump, decrypt it with the drill identity (staging only), restore it into a throwaway Postgres container, check that `migrate status` equals the binary's, run an RLS smoke test (a cross-organization read returns nothing), decrypt one sealed staging row with the escrowed staging KEK, run `keys bump-epochs --all --confirm` against the restored copy, and record the measured RPO and RTO in the summary. Production drills are run by the founder by hand.

**Residual risks** (numbered and added to THREAT_MODEL §8 at the G4 refresh in wave 3):
- Staging runs on one VM with Postgres in a container: losing the VM is a fail-closed outage until a rebuild, and without point-in-time recovery up to 24 hours of staging data can be lost. Compensating controls: nightly encrypted off-site dumps, a measured monthly restore drill, RTO ≤ 4 h; production gets a managed database with point-in-time recovery (D16).
- The KEK is a file on the staging VM, not in a KMS. Compensating controls: mode 0400 for the service user, an encrypted boot volume, an offline `age` escrow kept apart from the backups; a KMS follows with a paid host (D2).
- The API rate limits of D8 are per replica, so with several replicas the effective limit multiplies. Compensating controls: the limits that must hold across replicas use the shared limiter (HR-376); staging runs one replica.
- Usage meters are approximate for stored bytes and are not enforced. Compensating controls: the method is documented; counts come only from records (HR-377); enforcement waits for prices (F6).
- Staging sign-in through an SSH tunnel until the hosted provider's staging account exists. Compensating controls: the listener binds to loopback; SSH only from the founder's addresses (D13, D14).
- **R-34** (the per-source inbound limit per instance) is addressed by HR-376; **R-43** (Stripe live mode) stays open after M13.
