### G0 — M14 — Framework SDKs and business connectors — 2026-10-17

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M14 pull requests and, at the end of the milestone, in an exit status section. It builds on `main` at 2f9d777c (M1–M12, the v0.1.0 preview, M11.1, M10 and M11 part 2 complete; the highest migration is 00147, and 00148–00149 are M11's spares, left untouched). The founder answered eight open decisions (F1–F8) on 2026-10-17 before the brief was written, the recommended option each time, and approved the plan with "go" the same day; a ninth (F9, CrewAI's test dependencies) came during the build. They are recorded at the end as answered. Every other choice is a design decision made by the coordinator (D0–D132 in the coordinator's tracker), summarised below.

**Purpose:** PantherClaw governs coding agents today: Claude Code, the Agent SDK, MCP servers, GitHub and shell routes. Customers building agents with LangChain, the OpenAI Agents SDK, CrewAI or the Vercel AI SDK must wire the core SDK into every tool by hand, and the business systems those agents touch first (payments, a customer database, the team chat) have no reviewed tool packages. M14 adds framework wrappers on the core clients, three business connectors (Stripe in test mode, a read-only structured Postgres query connector and Slack, both as an approval channel and as an agent target), data scoping for reads (field classes, task-linked records and response redaction), the AuthZEN decision endpoint for enforcement points customers already run, and mediated peer agent-to-agent calls over A2A, where the requester's limits carry over to the peer. Templates and reference packs that waited for these connectors (customer support, internal analysis, treasury payments, aggregate reporting, research and disclosure) ship with them. The refund scenario becomes the second-market demo on real Stripe test mode. In product terms this is Checkpoint's connectors and frameworks, Pass's Slack approvals and Guardrails' data scoping and packs ([PRODUCT.md](../PRODUCT.md)).

*The AuthZEN endpoints* (`/.well-known/authzen-configuration`, `POST /access/v1/evaluation`, `POST /access/v1/evaluations`; TB4 and TB8; D26–D29). The first public endpoint that answers authorization questions for traffic PantherClaw does not dispatch.
- **Who can reach it:** anyone on the network; only a service account holding `authzen.evaluate` that is the subject of an ACTIVE enforcement point gets past authentication (HR-317).
- **Spoofing:** a point naming an agent it does not hold a proof for, or naming the agent only by id. Answered by: the agent's PAP/1 token and proof are forwarded and verified exactly as at the gateway; name-only subjects are refused (HR-318).
- **Tampering and replay:** a proof for another URL, body or method; an evaluation sent twice to spend a budget twice. Answered by: the proof binds method, URL and body digest; nonces and `jti` replay checks; one committed reservation per action (HR-318, HR-319).
- **Repudiation:** transactions and receipts record `decided_via = authzen` and the enforcement point.
- **Information disclosure:** a denial is `{"decision": false}` with a plain reason and a code; nothing about other agents or connections.
- **Denial of service:** body caps, at most 10 evaluations per batch, a per-point rate limit (HR-321).
- **Elevation:** a point can only ask about connections bound to it, and only `agent_held` or `target_enforced` connections can be bound (HR-317, HR-318); routes stay `PARTIAL` (HR-320, R-40).

*Peer agents* (`/a2a/{connection}`; TB1 and TB2; D30–D33). The first route where the target is another agent that may itself be governed.
- **Spoofing:** a swapped agent card or interface URL. Answered by: the card is pinned by digest at creation with a step-up, signed cards are verified against pinned keys, and drift quarantines the connection (HR-322).
- **Tampering:** the agent smuggling files, structured data, push-notification URLs or another run's task id. Answered by: outbound requests rebuilt from ActionIR with text parts only; task and context ids only for tasks this run created (HR-323).
- **Elevation (confused deputy):** a requester asking a peer to do what it may not. Answered by: for an enrolled peer, a child run with a delegated grant that is the intersection of the requester's grant and the route's peer scope, revoked with the requester (HR-324..326); for an external peer, only the outbound message is governed (R-41).
- **Information disclosure:** remote content is untrusted data, capped in size and time (HR-327).

6. **D8: request and response formats (A2, HR-300, HR-301).**
   - `HTTPMapping.Encoding` and `HTTPDispatch.Encoding`: `json` (default) or `form`. One strict form parser: `application/x-www-form-urlencoded` only, Stripe bracket syntax (`a[b]=`, `a[b][c]=`, `a[]=`), depth at most 3, at most 256 keys and 64 KiB; duplicate scalar keys and a key used as both scalar and array are refused. Outbound form bodies are rebuilt from ActionIR references only, keys sorted, RFC 3986 escaping. Ambiguity is refused, never guessed.
   - Money in minor units: dispatch reference `{params.<money>.minor}` (an integer string by currency exponent; a non-integral amount is refused) and CEL `minor_money(int, string)`. Exponents: usd eur gbp cad aud nzd chf sek nok dkk sgd hkd = 2; jpy krw = 0; any other currency is `CURRENCY_UNSUPPORTED`.
   - `HTTPDispatch.Headers`: literal static headers (not reserved names, at most 128 printable ASCII characters, no references), used for `Stripe-Version`.
   - `HTTPDispatch.Success {field, equals}`: a top-level JSON boolean that must equal `equals` on a 2xx answer, else the outcome is FAILED with the answer's sanitised `error` string (at most 64 characters) as the code; used for Slack's `ok`.
   - `Dispatch.CredentialPattern`: an anchored RE2 of at most 128 characters, checked by the gateway on the opened static credential before any byte is sent; a mismatch is a pre-send refusal `CREDENTIAL_PATTERN`.
7. **D9: new definition parts (A2).**
   - `Dispatch.SQL {operation: rows | aggregate | tables}` (W3) and `Dispatch.A2A {method}` (W8); A2 validates them, and their runtime stubs fail closed until the owners land.
   - Mapping channel `a2a`, keyed by A2A method name like MCP tools.
   - Parameter type `query_filter`: a canonical JSON list of at most 20 predicates `{column, op, value | values}`; ops `eq ne lt le gt ge in is_null not_null prefix`; columns are identifiers; scalar values at most 256 characters; `in` at most 100 values; never material by default. `columns`, `group_by`, `order_by` (`col:asc|desc`) and `measures` (`(count|sum|avg|min|max):(col|*)`) use the existing `identifier_list`.
   - `Definition.Response {format: json | rows, fields: [{path, class}]}` with classes `public | internal | pii | secret` (a dotted path into a JSON answer; `*` for array items). `Definition.Scoping` ⊆ {`records`, `classes`}: what the definition can enforce; only on `access: read` definitions.
   - **Build amendments (D48–D50, D52).** `Prerequisite.Binds` gains `op: eq | le` (default `eq`); `le` compares money of the same currency (else CANNOT_AUTHORIZE `CURRENCY_MISMATCH`) or integers. A `target.id.<group>` body reference whose named group is optional and unmatched leaves that body field out (body only; path and query still need a match); if every target-group field of a body is left out the build fails and nothing is sent. The dispatch reference `transaction.key` resolves to `pc-<transaction>` and is allowed only as a body value. A body value may be `literal.<value>` (at most 64 printable ASCII characters, no references) in form and JSON bodies, and form body keys may use the bracket syntax the parser accepts.
8. **D10: core A2 tests.** Form parser strictness and round trip (HR-300), a pattern mismatch that sends nothing (HR-301), a differential between the agent-facing parse and the outbound rebuild (T-140).
9. **D11: data scope on the decision side (B; F101; HR-302, T-144).**
   - Grant `Bounds.Scope map[operation]ScopeBound{Records {key, values (exact ids, at most 100)}, Classes (a match over public | internal | pii)}`; `secret` can never be allowed. Narrowing only: delegation intersects, envelopes cap, and revisions may only narrow without a new issuance.
   - Policy CONSTRAIN kinds `record_scope` and `data_classes` tighten only.
   - The pipeline attaches obligations `record_scope{key, values}` and `data_classes{values}`, the intersection of grant, envelope and rules. If an obligation applies but the definition does not declare the matching scoping, the route is not gateway-held (`pantherclaw_held` HTTP or Postgres), or the channel is sdk, hook or authzen: `CANNOT_AUTHORIZE` `SCOPE_UNSUPPORTED`. With no bound and no rule there is no obligation, except that the gateway always withholds `secret`.
   - Requested columns are checked by the existing `identifier_list` values bound: an extra column is a DENY, never silently dropped (F105).

*Postgres and data scoping (W3; F3)*

13. **D15: the `postgres` connection.** `PostgresConfig{host, port, database, user, sslmode (verify-full; require only with internal and a pinned CA), ca_pem, internal (private addresses, set only with a step-up), tables [{schema, name, scope_key, scope_column, max_rows, columns [{name, type, class}]}], max_rows (default 200, at most 1000), statement_timeout_ms (default 5000, at most 30000), max_result_bytes (default 1 MiB, at most 4 MiB), min_group_size (default 5, at least 2)}`. Identifiers `^[a-z_][a-z0-9_]{0,62}$` only; column types `text int bigint numeric bool date timestamptz uuid`; classes `public internal pii secret`; the password is a sealed static credential. Manifest changes are audited; a widening change (a new table or column, a lowered class, raised limits) needs a step-up (HR-309). The same dial-time egress checks as HTTP connections (HR-330, D55: HR-071 and HR-077; TLS `verify-full`, or `require` only with `internal` and a pinned CA; private addresses only with `internal`, which only a step-up sets).
14. **D16: dispatch** (`internal/gateway/pgdispatch`; HR-307, HR-308). SQL is built only from ActionIR: identifiers looked up in the manifest by exact match and emitted sanitised, values as typed `$n` parameters, `prefix` as an escaped `LIKE`. Every query runs in `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY` with local statement, lock (1 s) and idle timeouts, and always ends in `ROLLBACK`. Row limit = the smallest of the count clamp, the request, the table and the connection, plus one row to report `truncated`; reading stops at `max_result_bytes`. A pool of at most 4 per connection with `default_transaction_read_only=on`, held in `internal/gateway/pgtarget` (D58; [ADR-0002](../adr/0002-control-plane-and-gateway-split.md) note: a customer database is a target, not PantherClaw's own database). Filter, sort and group columns must be columns the agent may read, else `COLUMN_NOT_ALLOWED`. Answer: `{"columns", "rows", "truncated", "redacted"}`.
15. **D17: `pc.postgres` 1.0.0.** `postgres.rows.read`, `postgres.rows.aggregate` (groups smaller than `min_group_size` suppressed, never their row values; HR-312) and `postgres.tables.read` (target type `pg_database`, id = the connection's database name; D59); all `access: read`, scoping `records` and `classes`, response format `rows`. Served natively on the MCP face (tools `query_rows`, `aggregate_rows`, `describe_tables`) and on the HTTP face (`/{conn}/v1/query`, `/v1/aggregate`, `/v1/tables`); the SDK and hook faces refuse Postgres connections (`use_gateway_face`).
16. **D18: the connection test** (HR-309). Refuses a superuser, a member of `pg_write_all_data`, a role with INSERT, UPDATE, DELETE or TRUNCATE on any manifest table, or a missing or retyped manifest column; server version 13 or later.
17. **D19: the test target.** The test cluster with a fixture schema (`shop.customers`, `shop.orders`, `support.tickets`), a read-only role and a write-capable role for the negative test.
18. **D20: the gateway scope engine** (`dispatch/scope.go`; F101–F103; HR-310, HR-311). On gateway-held `access: read` dispatches: `record_scope` adds the mandatory predicate `AND <scope_column> = ANY($k)` for the table whose `scope_key` matches (no such table → `SCOPE_UNSUPPORTED` before any query); `data_classes` replaces values of disallowed classes with `"[redacted:<class>]"`; `secret` is always withheld. A non-JSON or oversized HTTP answer under an obligation is withheld from the agent (`SCOPE_UNENFORCEABLE`). Receipts record counts only.
19. **D21: dev, e2e and range.** `dev seed --postgres <dsn-file>`; `TestE2E_M14_DataScoping`; RT-042 injection through filters and identifiers, RT-043 record-scope escape, RT-044 write attempts through the read connector.

*AuthZEN (W7; F2; ADR-0019)*

24. **D26: endpoints** (HR-317, HR-321). `GET /.well-known/authzen-configuration` (unauthenticated; the evaluation endpoints, no search endpoints, capability `urn:pantherclaw:authzen:pap1-subject`), `POST /access/v1/evaluation` and `POST /access/v1/evaluations` (AuthZEN Authorization API 1.0). Denials are `200 {"decision": false}`.
25. **D27: request mapping** (HR-318). The subject carries the agent's PAP/1 token, proof and run id (and an optional action id); the resource names the connection and carries protocol, method, URL and the base64 body; the action is the HTTP method or `tools/call`. The server rebuilds the workload credentials (body digest, method, URL) and verifies them exactly as the gateway does (nonce, `jti` replay, binding); the URL must sit under the connection's base URL. 26. **D28: decisions** (HR-319, HR-320). `internal/authority/external.go` runs the pipeline, finalization, `BeginDispatch` and `RecordExecution` (outcome DELEGATED) in one request: reservations commit and are never released early. ALLOW and observe are true; HOLD, DENY and CANNOT_AUTHORIZE are false; after a HOLD the agent waits with its own SDK and resubmits with the same action id. Transactions and receipts record `decided_via = authzen` and the point.
27. **D29: enforcement points and the reference PEP.** `EnforcementPointService` (Create with a step-up, naming a service account and connections; List; Get; UpdateConnections, a widening needing a step-up; Disable), `enforcement_point.manage`, audited, Community; `pclaw authzen point …`. RT-047 a point impersonating another agent, RT-048 replaying an evaluation to double-spend.

*Framework wrappers (W4, W5)*

32. **D34: the wrapper contract** (HR-328, HR-329; T-150). Every tool call is authorized on the gateway `/sdk` face; an identical retry (same tool, server and canonical arguments within one wrapper instance) reuses the action id; changed arguments are a new decision. allow → run (a `send` answer for a tool without an `on_dispatch` handler is refused); observe → run (monitor routes only); hold → wait (default 300 s) through `client.resume` and run only on allow; deny, cannot-decide, timeout and wrapper errors → the tool returns a refusal (`PantherClaw refused this call: <code> (transaction <id>)`) without running, unless `raise_on_refusal`. Unmapped tools are refused unless `observe_unmapped`. The original callable is not reachable through the wrapper. A framework tool `t` on connection `c` is sent to `/sdk` as tool `mcp__c__t`, server `c`.
    - **Refusal codes (D47)**, shared through the conformance group: a deny carries the answer's `code` verbatim (for example `GRANT_AMOUNT_EXCEEDED`, `unknown_tool`, `use_gateway_face`), else `denied`; a resumed hold that ends in deny (declined or expired) is `hold_declined`; one that ends in cannot-decide (the wait ran out or failed) is `hold_timeout`; any other cannot-decide is `cannot_decide`; an allow carrying `send` without a handler is `dispatch_required`; an exception inside the wrapper is `wrapper_error`. The transaction part of the message is omitted when the answer has none.

Create and update call the adapter in the same transaction (the card fetch-and-pin and the manifest checks run there).

The receipt is unchanged (the channel is in the action hash).
45. **D66: `slack_app` activation** (W6; HR-315; like SIEM destinations, HR-259). `CreateChannel` stores the channel and sealed token as PENDING_ACTIVATION: no deliveries, routing skips it, and `UpdateChannel` cannot unpause it. The page `/notifications/channels/{id}/confirm` (Org Admin with `notification.manage`, a fresh security-key step-up, CSRF) runs `auth.test` and `conversations.info`, shows the workspace, bot and channel it found, and activates on confirmation. A new token goes through `UpdateChannel` and returns the channel to PENDING_ACTIVATION until confirmed again; tokens are never typed into a web form. Cards are posted only for requests created after activation.
46. **D67: enforcement point activation** (W7; HR-317). `CreateEnforcementPoint` (a person only) stores the point PENDING with its proposed connections and returns a `confirm_url`; a web page with a step-up and CSRF activates it. `UpdateConnections` narrows at once; a widening is stored as proposed and applied by the same page, while the point keeps serving its current set. `Disable` (a person only) applies at once without a step-up. Only an ACTIVE point evaluates; `pclaw authzen point …` prints the confirm URL.
47. **D68: action-id reuse in wrappers** (W4, W5; HR-329). A second Authorize for a final (run, action) returns the stored decision with no permit, and the gateway answers `duplicate_action` (HR-005), so one approval never runs a tool twice. **Residual risks** (added to THREAT_MODEL §8 by this brief):
- **R-40:** AuthZEN routes are cooperative: the enforcement point, not PantherClaw, sends the request, so a compromised or misconfigured point can forward something other than what was decided. Compensating controls: the agent's own proof binds method, URL and body; only bound `agent_held` or `target_enforced` connections; routes labelled `PARTIAL` unless a target verifier checks the action token; reservations commit (HR-317..320).
- **R-41:** an external A2A peer (no `peer_agent_id`) acts under its own authority once it has the message. Compensating controls: the outbound message is decided, held and receipted, with text parts only, disclosure limits and allowed skills; the route is labelled `PARTIAL` (HR-323).
- **R-42:** data scoping applies only to gateway-held reads; on SDK, hook and AuthZEN routes, and on agent-held connections, the answer reaches the agent unfiltered. Compensating controls: where an obligation applies on such a route the decision is CANNOT_AUTHORIZE `SCOPE_UNSUPPORTED`, never a silent pass (HR-302); the policy publish gate tests scope rules on gateway-held routes, so a policy that passes it can still be CANNOT_AUTHORIZE live for sdk, hook and AuthZEN callers (fail closed, D115).
- **R-43:** Stripe live mode is unsupported in M14, so real money cannot move through `pc.stripe`. Compensating controls: every write is refused before sending unless the opened credential is a test key (HR-301, HR-303); the refundable fact refuses a refund on a live-mode payment; any answer or verifier read reporting live mode records `security.stripe_livemode`, notifies the admins and opens the connection's circuit until an admin closes it (D54); live mode follows M13 hardening.
- **R-44:** Postgres structured queries cannot express joins, views or JSON columns, so some questions need several calls or are not answerable. Compensating controls: each call is decided and scoped on its own; aggregates cover reporting; joins and views are a follow-up.
- **R-45:** framework wrappers are cooperative: an agent that calls the original tool, or a framework that bypasses the wrapper, is not stopped, and these routes are `PARTIAL`. Compensating controls: wrappers fail closed, the original callable is not reachable through the wrapper (HR-328, HR-329), and the gateway MCP face and credential custody give enforced routes where they matter.
- **R-46:** members of the Slack channel see an approval card's metadata (request kind, consequence level, expiry, and with SUMMARY the operation id, agent and environment). Compensating controls: no parameters, amounts, principals or approver identities ever; MINIMAL is the default; externally shared channels are refused (HR-314, HR-315).
