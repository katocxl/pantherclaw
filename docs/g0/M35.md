### G0 — M35 — Federation and attestation: pairwise trust between orgs, federated A2A messages under cross-org grants, L3 infrastructure attestation, TUF, witnesses and ML-DSA on receipts — 2026-11-05

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M35 branches and, at the end of the milestone, in an exit status section. M35 is code-only like M30–M34: every stream codes on pushed branches first, and testing (the HR and T rows below) comes later.

**Purpose:** two organizations that trust each other let their agents message each other's listed agents, each side deciding every call under its own grants and keeping a minimal signed receipt ([ADR-0062](../adr/0062-federation-and-infrastructure-attestation.md); N28). A workload whose infrastructure attests its exact PAP key reaches level 3, "Infrastructure-attested". Evidence verifiers fetch Sigstore trust through TUF, independent witnesses cosign the deployment's global log, and receipts can carry an ML-DSA-65 co-signature.

**Founder decisions (2026-11-05, all recommended):**
- FD10: trust is pairwise, and both orgs' admins confirm it with security keys.
- FQ35-1: a trusted peer org's agent may only send A2A messages to our agents named in a cross-org grant, within its limits. Our policy decides every call, and holds wait for our people. It gets no direct tool or data access.
- FQ35-2: we return a minimal signed receipt to the peer: decision, ids, time and request digest. No checks, reasons or policy.
- FQ35-3: public witnesses see only the deployment-wide root log, never per-org logs.
- FQ35-4: the TUF client is go-tuf v2, used only to fetch and check Sigstore trust files.

**Coordinator decisions:**
- **D1020 Per-org federation key and document.** A per-org Ed25519 federation key (`fed-<thumbprint>`), rotated with a step-up, the old key RETIRING 7 days. `GET /.well-known/pantherclaw/orgs/{org}/federation.json` is JWS `pc-federation+jws` (`pantherclaw.federation/1`), signed by the active key and, during rotation, the retiring one; it lists the org's listed agents and never its trusted peers; it expires within 7 days.
- **D1021 Pairwise trust (FD10).** Propose fetches and self-verifies the peer document over HTTPS and pins its keys; both admins compare a safety code derived from both orgs' key digests and confirm with a security key; a signed peer confirmation makes the trust ACTIVE only when both sides confirmed. A daily refresh pins a new key only when a pinned key also signed it; an expired document makes the trust STALE; revoke takes effect at once. No shortcut between orgs on one deployment.
- **D1022 Listings.** An org lists an agent by name with an a2a connection whose peer is that agent and a subset of its card's skills. A peer's agent is "verified" only when the trust is ACTIVE and the document, the card digest and the card signature all check under the pinned keys.
- **D1023 Outbound.** An a2a connection's federation peer `{trust_id, listing}` takes its URL and card from the peer's verified document. Before sending, the gateway gets a `pap-fed+jwt` from `IssueFederationToken`, bound to the exact request and our allowed action, valid 60 s, and sends it as `Authorization: PAP-Fed`. The peer's `PC-Fed-Receipt` goes to `RecordFederationReceipt`; a peer DENY or HELD fails the outcome (`PEER_DENIED`, `PEER_HELD`) with agent-safe text.
- **D1024 Inbound.** The gateway face `POST /fed/a2a/{listing}` and the public signed card `GET /fed/a2a/{listing}/.well-known/agent-card.json` (signed by our org's federation key through `SignListingCard`, cached 1 h). Origin refused, body ≤ 1 MiB. **D1024b:** the methods are A2A v1 `SendMessage`, `GetTask` and `CancelTask`, mapped to `federation.message.receive`, `federation.task.read` and `federation.task.cancel`; any other gets -32601 `FEDERATION_METHOD_NOT_DECIDED`; after an allow the body is forwarded unchanged. **D1024c:** the gateway first calls `StartFederatedCall` (token, body digest, htu, listing) and gets the call, run, federated agent and instance, env and the listing's connection; it maps the action with them and authorizes with `federation_call_id` instead of workload credentials. Channel `federation`, package `pc.federation`, cross-org grants with a federated principal, a federation run per trust, peer agent and UTC day. Every answer carries our minimal `pap-fed-receipt+jwt`; a deny or a hold answers -32001 with agent-safe text.
- **D1025 FederationService** and the errors `FEDERATION_NOT_TRUSTED`, `FEDERATION_PEER_STALE`, `FEDERATION_TOKEN_INVALID`, `FEDERATION_REPLAY`, `FEDERATION_SAFETY_CODE`, `FEDERATION_KEY_UNVERIFIED`, `FEDERATION_LISTING_UNKNOWN`, `FEDERATION_METHOD_NOT_DECIDED`, `FEDERATION_EDITION`.
- **D1030 L3 "Infrastructure-attested".** An attestation from the workload's infrastructure bound to the enrollment by `pantherclaw-l3:v1:<org>:<nonce>:<jkt>`. Sources: `spiffe_x509` (an X.509-SVID chain and a signature over the binding; **D1030a:** the bundle comes only from the operator-configured trust domain) and `gcp_instance` (a GCE identity token whose audience carries the binding). PAP/1 additive: `att_lvl` 3. Azure, AWS and TPM are not in M35.
- **D1040 TUF via go-tuf v2** (FQ35-4) in `internal/evidence/sigstoretuf` only, for `pclaw verify --sigstore-tuf` and `anchoring.trust: tuf`.
- **D1041 Witnesses, deployment root only** (FQ35-3): the global log `<log_origin>/global`, C2SP tlog-witness `add-checkpoint`, `cosignature/v1`, a public global checkpoint endpoint, and `pclaw verify --witnesses --witness-threshold`.
- **D1042 ML-DSA on receipts:** with `mldsa_cosign`, decision, execution and effect receipts carry an ML-DSA-65 co-signature in PAP-1's `sigs[]`; federated receipts stay Ed25519 only.
- **D1045 Docs and assembly** as in this brief. **D1046 Streams** as in the table above; code-only.

**Out of scope:** federation between deployments without HTTPS, transitive trust, a peer's tool or data access, Azure attested documents, AWS Nitro and TPM attestation, per-org witnessing, and any live run against public witnesses or the Sigstore TUF repository (testing and founder steps).

**Security constraints.** Fail closed everywhere: a federated message is never sent without a signed token, never received without an ACTIVE trust, a pinned-key signature, an exact request match and a fresh jti, and never forwarded without an allow under a cross-org grant. The receipt we give a peer carries nothing of our checks, reasons or policy. Keys stay in the key store; federation, peer confirmation and revocation run over HTTPS through the egress client. Wording follows HR-681's list in code, CLI and docs.
