### G0 — M18 — Platform administration — 2026-10-29

This brief is written before implementation (G0). It lists the planned scope. The M18 pull requests track delivery, and the exit status section records it at the end of the milestone. M18 is a post-1.0 milestone: the founder postponed the v1.0 testing steps on 2026-10-29, and coding continues past v1.0. It lands after M15, M16 and M17, in migration order. Its streams branch from `origin/main` once M16 is there. It builds on M15's gateway status reports (`ReportStatus`, `pc.gateway_replicas`, migration 00186).

The founder answered four open decisions for M18 on 2026-10-29 (G5–G8), the recommended option each time. They are recorded at the end as answered. Every other choice is a design decision by the coordinator (D150–D158 in the coordinator's tracker), summarised below.

**Purpose:** administering PantherClaw is all-or-nothing today, and it stops at one deployment's configuration.
- Binding a role needs `role.bind` at the organization (`internal/tenancy/app/bindings.go`), so a business unit or team can't have an administrator of its own.
- Identity providers are configured per deployment (`auth.oidc_providers`), so an organization on a shared deployment can't bring its own.
- API keys can't be limited to a network.
- Gateways report their status (M15), but nobody is told when one falls silent or runs an old version.
- Cohorts organise agents, but exceptions, simulations and rollouts still work one agent or one org at a time.
- Key-encryption keys are files, and wrapped keys can never be re-wrapped.
- `pclaw` keeps its refresh token in a file.

M18 closes these gaps. In product terms this is Root, the platform ([PRODUCT.md](../PRODUCT.md)).

**Scope (planned):**
- **18a Fleet management** (PN-010.6, fleet part). A per-organization fleet policy (an advisory minimum version, a silence threshold), a fleet view, and alerts for silent gateways and gateways below the minimum version.
- **18b Delegated administration** (F584, G5). A Scope Admin role. Binding and unbinding limited to roles the caller holds, at its scope or below.
- **18c Large-fleet administration** (F602). Exception groups, bulk simulation by cohort, a VERIFIED threshold for rollouts, per-cohort aggregated findings.
- **18d Organization identity providers** (PN-012.7, G6). OIDC providers an organization's own admin configures, as two-person protected changes.
- **18e API-key IP allow lists** (PN-012.8). CIDR ranges per API key.
- **18f The OS keychain for `pclaw`** (PN-012.9).
- **18g Adapter ports and OpenBao** (PN-012.10, G7). An OpenBao Transit key provider with in-place re-wrap, and BlobStore and fan-out ports.
- **18h** This brief and the exit end-to-end tests.

- **Gate rule (D161, after D96a).** An edition gates only creating, activating or changing something. Anything already in force keeps working in every edition, so a downgrade never drops a restriction or locks anyone out:
  - a key's CIDR list is still enforced;
  - a rollout's VERIFIED threshold still holds;
  - ACTIVE organization identity providers still resolve for sign-in;
  - existing role bindings stay.
- Reading, removing, disabling and unbinding work in every edition.
- The fleet silence and version sweep and bulk simulation run only for entitled organizations.

*Delegated administration* (TB4; D152).
- **Elevation (T-206):** a Scope Admin binds a role it doesn't hold, binds at a scope above or beside its own, binds an organization-scope role, or unbinds outside its ceiling. Answered by:
  - `role.bind` is checked on the target scope's path;
  - a caller without organization-level `role.bind` must hold a binding of the same role at the target scope or an ancestor;
  - organization-scope roles need organization-level `role.bind` (HR-472..474).
- **Repudiation:** every binding is audited, self-grants included.

*Organization identity providers* (TB4, TB8; D155).
- **Spoofing (T-207):** an admin, or a stolen admin session, adds or swaps a provider to sign in as other people. Answered by:
  - every create, change, disable and "own providers only" setting is a two-person protected change under CUSTODY, always protected in every protect mode, with no emergency path;
  - every organization admin is notified;
  - the issuer is immutable once ACTIVE (HR-481).
- **Information disclosure:** the client secret is sealed with the organization's DEK and never returned (HR-482).
- **SSRF:** discovery is HTTPS only through the egress guard, with no private or loopback address (HR-483).
- **Denial of service:** a change that would leave no active Org Admin a sign-in path is refused; a change that strands some admins lists them in the request (HR-484).
- **Residual (R-08):** whoever runs the customer's identity provider can mint identities that pass as distinct people.

*API-key IP allow lists* (TB4; D153).
- **Spoofing (T-208):** a forged `X-Forwarded-For` header used to appear inside the allowed range. Answered by: the client address comes only from trusted proxies (HR-476), and a refusal is indistinguishable from a bad key (HR-475).

*Large fleets* (TB4, TB7; D154).
- **Elevation (T-209):** an exception group silently widens to agents that join a cohort later. Answered by: membership is a snapshot at approval (HR-477).
- **Information disclosure (T-213):** aggregates or bulk simulations reveal agents outside the caller's scope. Answered by: they are filtered to readable agents (HR-480), and bulk simulation is read-only under the existing caps (HR-478).

*Key service and keychain* (TB6, TB4; D156, D157).
- **Tampering (T-210):** a re-wrap that writes a key which no longer unwraps, or changes only one column. Answered by: verify before write, and a trigger that allows only both columns changing together (HR-487).
- **Denial of service:** an outage fails closed (HR-486).
- **Spoofing:** OpenBao is reached only at its configured address, with TLS (HR-488).
- **Information disclosure (T-211):** pclaw secrets in a readable file or on a command line. Answered by HR-485.

*Fleet* (TB3; D151).
- **Spoofing (T-212):** a gateway fakes its version or masks a silence. Answered by: the version is self-reported and therefore advisory only (HR-470); alerts fire once per silence and once on recovery (HR-471).

**Design decisions:**

*S18a — fleet (D151)*

1. **Migrations.**
   - `00216` `pc.gateway_fleet_policy`: `org_id` primary key, `minimum_version text NULL`, `silence_after_seconds int NOT NULL DEFAULT 300` (CHECK 120..86400), `updated_by`, `updated_at`.
   - `00217` `pc.gateway_alert_state`: org, gateway, `silent_since`, `silent_notified_at`, `below_minimum_notified_at`, and `last_report_at` (unless `pc.gateways` already has such a column), written by the M15 ReportStatus path and never pruned (D167).
2. **The minimum version is ADVISORY** (HR-470): it is flagged and alerted, never refused, because the version is self-reported.
   - Versions are parsed by a local parser for `vMAJOR.MINOR.PATCH[-pre]`, with no new dependency.
   - An unparseable version shows as "unknown" and is never counted as compliant.
3. **The sweep** (HR-471): a River job every minute, fanned out per organization. It sends one `gateway.silent` per silence episode and one `gateway.recovered`, plus `gateway.below_minimum` once per version change.
   - Silence is measured from the per-gateway last-report time, never from replica rows that get pruned. A gateway that never reported isn't silent (D167).
4. **RPCs** on `GatewayAdminService` (D163), the people-facing service that already has `CreateGateway` and `ListGateways`, not the mTLS gateway-only `GatewayService`:
   - `GetFleetPolicy`;
   - `SetFleetPolicy`, with the permission `CreateGateway` uses;
   - `ListFleet`, with gateway read: versions × replicas × configuration lag.
   Per organization only. Fleet view Team (`FleetView`); setting a minimum or changing the silence threshold Enterprise (`FleetPolicy`). Clearing the policy (an empty minimum, the threshold default or unchanged) works in every edition (D167).
5. S18a also builds the M18 exit end-to-end tests.

*S18b — delegated administration and API-key IP lists (D152, D153; G5)*

6. **Scope Admin.** A new role, bindable only at business unit, team or environment scope, with `role.bind`, `role.read` and `user.read`.
7. **The ceiling** (HR-472..474).
   - `CreateRoleBinding` and `DeleteRoleBinding` require `role.bind` on the target scope's path.
   - A caller without organization-level `role.bind` must also hold a binding of the SAME role at the target scope or an ancestor.
   - An organization-scope role is bindable only with organization-level `role.bind`.
   - Re-delegation is allowed: a Scope Admin may bind Scope Admin at or below its own scope (D164), as HR-472's "at the target scope or above" says.
   - The ceiling's target uses the CURRENT hierarchy: for a bind, the target scope's current path; for an unbind, the binding's stored scope resolved to its current path (D164).
   - Unbinding follows the same ceiling.
   - Invitations with roles and the service-account `noEscalation` shortcut stay organization-level.
   - Paths use the current hierarchy. Separation of duties is unchanged, and a self-grant is still audited.
8. **API-key IP lists** (HR-475, HR-476).
   - `00219`: `pc.api_keys.allowed_cidrs cidr[] NULL` (CHECK cardinality ≤ 32), set at creation and immutable (rotate the key to change it). API keys only.
   - `apiKey()` checks `ClientIPFrom(ctx)`, the trusted-proxy-aware address. A refusal is the same `UNAUTHENTICATED` as a bad key, plus an audit `apikey.ip_refused`.
   - The server warns at startup when `http.trusted_proxies` is empty, because CIDR-restricted keys then see the direct peer address.

*S18c — large fleet (D154)*

9. **Exception groups** (`00220`; HR-477): `pc.policy_exception_groups`, plus `group_id` on exceptions. Membership is a snapshot of the cohort's agents at approval, one exception row per agent. The approval path is the same as for exceptions.
   - The request binds a digest of the cohort's definition (its rule, static members and version). Editing the cohort voids a pending group request (`ErrBaseChanged`); the summary shows the current member count (D174).
10. **Bulk simulation** (`00221`; HR-478): one simulation with `cohort_id` (NULL = org-wide) and per-cohort counts, under the same caps.
11. **Rollout gate** (`00222`; HR-479): an optional `require_verified_percent` (1–100, NULL = off). COMPLETE then needs at least that share of non-EXCEPTION targets VERIFIED. No waves.
12. **Aggregated findings** (HR-480): query-only, per cohort: coverage findings, departures, FAILED targets and active exceptions, filtered to agents the caller can read.

*S18d — organization identity providers (D155; G6)*

13. **Migration `00223` `pc.org_identity_providers`:** org, id, name, `issuer` (immutable once ACTIVE), `client_id`, the client secret sealed with the organization's DEK (purpose `idp_client_secret`, never returned), `trust_email`, `state` (PENDING | ACTIVE | DISABLED), the actors and timestamps.
    - At most 20 providers per organization. Only ACTIVE providers and PENDING ones with an open protected change count. A declined or expired activation moves the provider to DISABLED, and the limit error says Update can reuse a provider that was never activated (D169).
    - The protected change's Closer hook does that move. A Closer failure is logged (ERROR plus an audit `protect.closer_failed`), and the decline or expiry still completes (D175).
14. **Protected changes** (HR-481, D162): every create, change, disable and "own providers only" setting is a two-person protected change (G6).
    - It reuses the CUSTODY category: there's no CHECK change, and `00223` doesn't touch `protected_changes`.
    - The IdP surfaces are `AlwaysProtected()`, like M17's `consequence.rule.put`: held in every protect mode, with no emergency path.
    - Each request names its own surface (for example `identity_provider.put`).
    - Every organization admin is notified.
    - Only a person may make these changes (D161).
15. **Resolution per request:** the deployment providers plus the organization's ACTIVE providers. With "own providers only" set, only the organization's.
    - On a name clash the deployment provider wins, and a start-up warning lists each organization's ACTIVE provider that a deployment provider of the same name shadows (D169).
16. **Discovery** (HR-483): HTTPS only, through the httpx egress guard. No private or loopback address, no `AllowInsecureLoopback`, no `Dev`. Subject tokens are off.
17. **Lock-out guard** (HR-484, D162).
    - Refuse a change only when no active human Org Admin would have a sign-in path left after it.
    - An admin has a path through a provider that's available to the organization and whose issuer equals the admin's identity issuer. The available providers are the deployment's (unless "own providers only" is set) plus the organization's ACTIVE ones.
    - The check covers disabling a provider and turning on "own providers only".
    - The protected-change request and its notification list every active admin who would lose their last path, so the second person approves knowing who is affected.
    - Edition: Enterprise for creating, activating and changing; disabling works in every edition (D161).

*S18e — platform (D156, D157, D171, D172; G7)*

18. **Keychain** (HR-485).
    - Library `github.com/zalando/go-keyring`, at a version at least 7 days old.
    - Only secrets go in the keychain: the refresh token, the device key seed, and the access token if it fits. Metadata stays in the file.
    - `--credential-store=auto|keychain|file` (env `PANTHERCLAW_CREDENTIAL_STORE`). `auto` falls back to the file (0600) with a warning.
    - A plain-file store moves to the keychain on the next login or refresh, and the file's secrets are wiped.
    - If the library passes secrets on argv on macOS, a small darwin adapter feeds `security -i` through stdin. No secret ever goes on a command line.
19. **OpenBao** (HR-486, HR-488).
    - An in-house Transit client over `net/http`: encrypt, decrypt and rewrap, with token-file or AppRole auth. TLS is required except on loopback.
    - Config: `key_service: {kind: file|openbao, openbao: {address, mount, key_name, auth}}`.
    - A `kek_id` prefix (`file:` / `bao:`) routes each unwrap, so mixed providers work during a migration.
    - An outage fails closed. The bounded DEK cache keeps serving the keys it already holds.
20. **Re-wrap in place** (`00224`; HR-487).
    - Only a new LOGIN role `pc_keystore` may re-wrap (D171), following the pc_deleter and pc_retention pattern: NOINHERIT, NOBYPASSRLS, bootstrapped like pc_deleter, with its own `--keystore-password-file`. Never a pc_app grant and never SECURITY DEFINER.
    - `00224` grants only pc_keystore SELECT and `UPDATE (wrapped_key, kek_id)` on `pc.deks` and `UPDATE (wrapped_private_key, kek_id)` on `pc.keys`, with RLS policies scoped to that role, plus a trigger that allows only both columns changing together. pc_app gets nothing new.
    - The re-wrap job runs on its own pool as pc_keystore, which exists only when the password file is configured; otherwise re-wrap reports a clear "not configured" error.
    - The job unwraps the old key, re-wraps it, verifies by unwrapping the new one, then writes and audits.
21. **Ports** (D172):
    - BlobStore: the `blob.Store` port (Put, Get and Delete, keyed by org, kind and sha256) plus an in-memory adapter for tests only. No `pc.blobs` table and no migration; `00225` stays spare. The Postgres or object adapter arrives with the first caller that moves (a follow-up).
    - Fan-out: the port with its Postgres adapter, and no change in behaviour.
    - The search port is deferred.
22. **Tests:** an httptest Transit fake, plus a real-OpenBao test that runs only when `PC_TEST_OPENBAO_ADDR` is set. No CI or `.github` change.
