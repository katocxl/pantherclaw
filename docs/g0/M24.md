### G0 — M24 — Agent Posture: findings, MCP supply chain, private catalogue, agent cards and device scans — 2026-10-31

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M24 pull requests and, at the end of the milestone, in the exit status section. The design was written on `main` at ffb6a4e1. M24 builds in parallel with M22 and M23 (W1) and lands after them in migration order (W2). The founder answered the wave 1 rules on 2026-10-31 (H3).

**Purpose:** a security lead asks where agents are weakest and what to fix first, and no one place answers. Developers install any MCP server they find, a poisoned or swapped server can steer every agent that uses it, nobody records what each agent is for, and a laptop scan goes stale the day after it runs. M24 joins what already exists into a ranked queue where each finding has a fix, checks MCP servers before review, adds a private catalogue that starts as Watching, puts risk and purpose on the existing agent record, and runs metadata scans on a schedule. A reading of the code found: no organization registry or server identity; `inputSchema` is not reported; scan drops package identity and reads no hooks or skills; posture findings are Business-gated; `agent.manage` is too broad for laptop keys; the 200-per-source cap breaks fleets; Agent has no risk tier or data classes; nothing signs A2A cards; revoke across connections does not exist.

**Scope (planned):**
- **24a Posture** (F860–F866; D200–D207). A ranked queue over existing sources, with a fix on each finding, an OWASP ASI mapping and daily trends.
- **24b Supply chain** (F867–F871; D210–D214). Pure checks on tool text and schemas, shown in tool review, and `pclaw mcp inspect`.
- **24c Catalogue** (F872–F879; D220–D226). The organization's approved servers, exact matching, Watching first, opt-in enforcement, and a person revoking a server inside one organization.
- **24d Agents and scans** (F880–F889; D230–D238). Risk and AI Act fields, agent cards, signed A2A cards, hook, skill and package metadata in scans, a Scanner role and scheduled scans.

Editions (H3, D201, D222): `PostureFindings()` is Team and up; `PostureTrends()` and `PostureRemediation()` are Business and up. The catalogue is Team to manage, but revoke is Safety class with no edition check, and `List` and `Get` work on any edition, so a downgraded organization can always find and revoke a server (D268, D276). Supply-chain checks, agent cards and device scans are Team, as the vision has them. `pclaw mcp inspect` runs on the customer's machine and is Community (D279). Hook, skill and package findings extend local `pclaw scan`, which is Community.

**Out of scope:**
- a single number for posture: findings are ranked and carry their reasons (F797);
- reading file contents or prompts (H3);
- an endpoint service: a scheduled scan does this job, and an unsigned service would not get through device management;
- revoking across organizations (H3);
- behavioural checks of untrusted server code outside the containment sandbox, on a server or hosted;
- a new HTTP endpoint for the catalogue (D225);
- a claim that an MCP server, a device or an agent is safe;
- the console's posture, catalogue and agent-card screens, which are D26 in [G0 M22](M22.md).

*Supply chain* (TB2, TB11; D210–D214).
- **Tampering (T-250, T-251, T-252):** a poisoned description, a change after approval, or a shadowing name. Answered by: flags that never approve (HR-582); flagged text stays untrusted (HR-583); inspection with no credentials and denied egress, on the customer's machine only (HR-584).

*Catalogue* (TB4; D220–D226).

- **Spoofing (T-149, existing):** a card signing failure yields a bad signature. Answered by: serve unsigned as today and log it (HR-590).

**Design decisions:**

*S24a — posture*

1. **D200** (F860, HR-580). New `internal/postureview/{domain,ports,app,adapters}`, `proto/pantherclaw/v1/posture_queue.proto`, `PostureQueueService`: `ListRankedFindings`, `GetPostureTrends`. `posture.read`, viewer-scoped before ranking. `permissions_m24.go`, roles and the `Source` port push first as `(m24-perms)` and `(m24-source)`.
2. **D201** (F865). Editions (H3): `Entitlements.PostureFindings()` Team and up, `PostureTrends()` Business and up. `PostureRemediation()` stays Business and up. If posture findings are computed only on Business, computation extends to Team.
3. **D202** (F861). `RankedFinding`: `source`, `source_id`, `kind`, `root_cause`, `agent_id`, `agent_label`, `connection_id`, `team_id`, `title`, `severity`, `severity_basis` (STATED, BY_KIND), `state`, `since`, `fix{kind, target_id, label}`, `owasp[]`, `rank_reasons[]`.
4. **D203** (F862, HR-580). No score field anywhere (F797). Sort tuple: severity; reaches production; unowned; age; stable id. `rank_reasons` states which applied. Sources without severity use a fixed table in `domain/severity.go`.
5. **D204** (F863). `ports.Source`: `Findings(ctx, viewer, filter) ([]Finding, truncated bool, error)`, cap 1,000 per source. Sources: posture, coverage, suggestions, open agent changes, recommendations, NEW inventory; S24b adds supply-chain flags, S24c adds unapproved servers. Truncation is shown, never silent.
6. **D205** (F864). `domain/owasp.go`: a pure kind-to-ASI map, values from `rules.KnownOWASP`.
7. **D206** (F865, HR-581). Migration 00270 `pc.posture_daily(org_id, day, kind, severity, team_id, open_count, closed_count)`, a daily River job. Missing days are `NOT_COLLECTED`, never zero (HR-258).
8. **D207** (F866). A finding clears when its source clears. Dismissal goes to the source. Exit test `TestE2E_M24_PostureAndSupplyChain`: a finding, its fix, and a rescan clearing it; a poisoned tool flagged in review; a person revoking the server across connections; lift by a second person. `task range` runs.
   - **D207a: accepted from S24a.**
     - `catalog.read` for Org Admin, Security Admin and Auditor; `catalog.manage` for Security Admin.
     - `pc.posture_daily_runs`, so a collected day with no findings differs from NOT_COLLECTED; `closed_count` is nullable.
     - "Open agent changes" means discovery changes over 7 days.
     - Recommendations need organization scope. Inventory needs `connection.read` at organization scope, and is otherwise shown as permission-denied.
     - A `postureSourceFactories` hook, and no dismiss call on the queue.
     - The suggestions hook runs only where `PostureRemediation()` holds.

*S24b — supply chain*

9. **D210** (F867, HR-583). `internal/supplychain/domain`, pure checks: `hidden_instruction` (zero-width, tag, bidirectional, HTML comment), `injection_pattern` (`injection` package), `tool_shadowing` (same name as a built-in or an approved tool), `overbroad_schema` (free-form command, SQL or URL strings; unbounded additional properties), `rug_pull` (description or schema changed with no version change after approval), `provenance_unknown`. Each returns severity and offsets; flagged text stays untrusted.
10. **D211** (F868). The gateway reports `input_schema` (capped at 64 KiB) and its digest in `ReportInventory`. Migration 00271 adds the columns and `pc.supplychain_flags(id, org_id, connection_id, inventory_id, digest, check_kind, severity, detail, first_seen, last_seen, state)`.
11. **D212** (F869). Run in `discover` and `see` before `OpenToolReview`, and at package import. Flags appear on the TOOL_REVIEW item. Existing drift quarantine is unchanged. Flags feed `ports.Source`.
12. **D213** (F870, HR-582). Clean means "no known flags", never "safe" (F801), in every string.
13. **D214** (F871, HR-584; last phase). `pclaw mcp inspect <spec>`: runs the server in `internal/sandbox` with no credentials and egress denied, lists tools and resources, records egress attempts, runs D210. `--submit` adds an operator-reported note to the inventory row. Runs on the customer's machine only, never on the server or hosted.

*S24c — catalogue ([ADR-0046](../adr/0046-mcp-server-catalogue.md))*

14. **D220** (F872). `internal/mcpcatalog/{domain,app,adapters}`. Migration 00272 `pc.mcp_servers(id, org_id, name, title, status, transport, package_ref, url_host, url_path_prefix, image_digest, notes, decided_by, decided_at, created_at)`, statuses PROPOSED, APPROVED, DENIED, REVOKED, UNIQUE (org_id, name). `pc.mcp_catalog_settings(org_id, mode)`, modes OFF, WATCH, ENFORCE, default WATCH.
15. **D221** (F873, HR-585). `domain/match.go`: exact match only, on URL host and path prefix, image digest, or package ref. No fuzzy matching. D259 adds scheme and effective port; D266 makes denials wider than approvals.
16. **D222** (F872). `mcp_catalog.proto`, `McpCatalogService`: Propose, Approve, Deny, List, Get, `GetCatalogSettings`, `SetCatalogMode`, `PreviewServerRevoke`, `RevokeServer`. `catalog.read`, `catalog.manage`; mode and revoke are person only with step-up. Team.
17. **D223** (F874, HR-586). Enforcement stays out of the decision path, so no pipeline version change.
    - ENFORCE refuses to activate a connection to an unapproved server (`SERVER_NOT_APPROVED`).
    - Switching to ENFORCE shows a preview, then quarantines non-matching connections in one transaction with an epoch bump.
    - ENFORCE → WATCH or OFF goes through `protect`: new surface `SurfaceCatalogMode = "mcp.catalog.mode"`, category `TOOL_MEANING`, permission `catalog.manage`, added to `AlwaysProtected()`, so it always waits for a second person and has no emergency path, as M17 D107 and M18 D155 do. Without a Gate it fails `ErrUnavailable`.
18. **D224** (F875–F877, HR-587). `PreviewServerRevoke` gives a digest (HR-252). `RevokeServer(server_id, preview_digest, reason)` sets REVOKED and quarantines every matching connection and package-bound version, through the response service with a new subject `mcp_server` expanded at execution. Lift follows `restoration.go`, an independent second person. One organization only. Scan-only local servers come back as `not_stoppable_here` with a deny-list hint.
    - **D224a.**
      - Quarantine here means one DENY_ALL connection-scope control per matching connection, through the response service, not state QUARANTINED. A single `connection.manage` Restore must not bypass the independent lift.
      - The server stays REVOKED after a lift. Lifting restores connections; trusting the server again is its own decision. `Approve` on a REVOKED server is refused with `SERVER_REVOCATION_ACTIVE` while any control of that revocation is live, and after that needs a person with step-up. No restoration hook.
      - Package-bound means versions of the package whose name exactly equals `package_ref`. They move to QUARANTINED and return only through fresh review (F402). A lift does not restore them.
      - A new connection matching a REVOKED server is refused in every mode, including OFF, with `SERVER_REVOKED`, because WATCH → OFF needs no second person. Modes govern unapproved servers, not revoked ones. DENIED stays ENFORCE-only.
      - With more than `MaxPlanControls` matches: several restoration plans, under one preview digest, in one transaction, with REVOKED set in that transaction.
      - `mcp_server` joins the `response_actions` scope_type CHECK in 00272. `scopeOf` returns ErrScope for it, so automations and SOAR cannot use it.
      - `PreviewCatalogMode` is accepted.
19. **D225** (F878). `pclaw mcp catalog list|propose|approve|deny|mode|revoke|export`. `export --format managed-allow` writes the allow file of G0 M23 D113; `--format registry-v0` writes a static file in the official registry's shape. No new HTTP endpoint.
    - **D225a.** `managed-allow` never writes a name-only entry: that would allow more than was approved. An image-only server is left out and listed on stderr. `registry-v0` is checked against the official registry's published schema, not from memory. G0 M23 D138 sets how `command` and URLs are written; D268 narrows both formats.
20. **D226** (F879). Finding `UNAPPROVED_SERVER` through `ports.Source`, only once the catalogue holds at least one APPROVED server.

*Review round 2: S24c*

54. **D264** (F875, HR-587). A revoke writes one `response.contain` per control, each with its `control_id`, all under the same action id, which is M13's contract.
    - Replay in `restore_m13.go` accepts several controls under one action: the action insert is idempotent and every control comes back.
    - `mcp.catalog.server_revoked` becomes a security event in the kinds map, and replay restores the REVOKED state and the quarantined versions.
    - A test runs the chainer over a revoke, then a restore, and shows the chain advances and the controls and REVOKED are back. A range or integration leg is added.
55. **D265** (F875, F876, HR-587). The `connection_health` precondition reads "not applicable, recorded" for a server-revocation control whose connection is not ACTIVE, RETIRED included.
    - That lift only ends a block: the connection stays in its own state, and the server stays REVOKED.
    - Controls stay on every non-RETIRED match.
    - Resuming or activating a connection while the server is REVOKED is refused with `SERVER_REVOKED`, so nothing starts running on a lift.
    - Tests: QUARANTINED, and retired after the revoke, since connection states are ACTIVE, QUARANTINED and RETIRED only. All of them can lift, and one never blocks the other 49.
56. **D266** (F873, F875, HR-585). Denials match wider than approvals. Revoke matching and the new-connection refusal compare host and effective port, whatever the scheme; a bare host covers 443 and 80. Approvals stay exact (D259). `Spec` gains an explicit `http://host:port` form, allowed only where the connection rules already allow cleartext. It matches only `Cleartext`, so a private http server can be approved under ENFORCE.
57. **D267** (F875, HR-587). The revoke also quarantines REVIEWED versions: REVIEWED → QUARANTINED joins the lifecycle, used only by revoke. Activating any version whose name is a REVOKED server's is refused with `SERVER_REVOKED`.
