### G0 — M4 Authority core, part 1: tool packages, action definitions, ActionIR mapping, CEL policy engine — 2026-10-08

This brief is written before implementation (G0). It lists planned scope for **part 1** of M4 only. Part 1 runs in parallel with M2 (tenancy & service authentication). It therefore covers only the pieces of M4 that depend on neither M2 nor M3, at the domain and application layers.

**Purpose:** give the Authority a reviewed, signed meaning for every operation (tool packages and action definitions), a strict way to turn an MCP tool call or HTTP request into ActionIR (mapping), and a fail-closed CEL policy engine. The decision pipeline (part 2) then composes these with grants, budgets and facts.

**Scope (planned, part 1):**
- `internal/definitions/domain`: action definitions and packages, all pure:
  - **operation and target identity:** type, id pattern, account requirement;
  - **typed material parameters with units:** `money` with allowed currencies, `decimal` and `integer` with a unit from a closed list and bounds, `enum`, `identifier`, `boolean`, `string_list`, and non-material untrusted `text`;
  - **effects, side effects, reversibility** and read/write class;
  - **constraints** the tool can enforce (F100), **prerequisites** (named trusted facts with maximum age), **retry semantics** and **verifier**;
  - **approval template**, whose placeholders may name only canonical material fields (HR-034 groundwork);
  - the **semantic dedupe key**: a list of canonical fields, hashed from their canonical values, and the **assurance metadata** (basis, reviewers, `valid_until`);
  - **mappings** from MCP tools and HTTP routes;
  - **consequence rules** (ConsequenceIR, F405 groundwork: predicted consequences only);
  - the definition **lifecycle** state machine (F394) and the per-org **pin rule**: version pins only move forward (HR-123).
- `internal/definitions/manifest`: the YAML package format (`format: 1`).
  - Strict decoding (HR-100): duplicate keys, anchors, aliases, merge keys, explicit tags, floats, nulls, multiple documents, unknown fields, excessive depth or size are all rejected.
  - Decoded YAML is converted to JSON and decoded with `encoding/json/v2` (`RejectUnknownMembers`).
  - The **definition digest** is `sha256:` + SHA-256 of the RFC 8785 canonical JSON of one definition, mappings included. This is the `definition.digest` that ActionIR pins (PAP-1 §6).
- `internal/definitions/trust`: TUF-style signed metadata.
  - The offline package root (`pclaw-admin keygen --purpose packages`, Day-0 item 6) signs a **targets** document: `version`, `expires`, and for each `name@version` the SHA-256 and length of the exact package bytes.
  - The signature is a compact JWS (EdDSA only, `typ: pc-package-targets+jwt`, kid `packages-root-…`) verified against embedded roots (`roots.json`, empty until Day-0 item 6).
  - Anti-rollback: a metadata version lower than the last one seen is refused, and so is an expired document.
  - Tests use generated test keys only.
- `internal/definitions/app`: the `ImportPackage` use case. It verifies the metadata, matches the package bytes, decodes and validates the package, checks the pin advance, and stores the package. The trust state, packages and pins are behind interfaces (`TrustStore`, `PackageStore`, `PinStore`) and have no tables yet.
- `internal/platform/celenv`: one CEL environment family for mappings, policies and (later) detections.
  - Custom **`pc.Decimal` and `pc.Money`** types: exact arithmetic and comparison; money across currencies is an error.
  - Struct types generated from the action definition schema, so each parameter is typed at check time.
  - Validators: ordering operators on `string`, `bytes`, `double` or `dyn` are rejected at type-check, and so are `double` literals (HR-041). Optional fields need a `has()` guard (HR-042).
  - Parser size and recursion limits, comprehension nesting limit, and estimated-cost and runtime cost limits (HR-043).
- `internal/definitions/mapping`: MCP tool call or HTTP request → ActionIR.
  - The input is strict JSON (duplicate keys rejected; only integer JSON numbers, which become CEL `int`).
  - HTTP paths match a reviewed template on a strict character set.
  - CEL extraction expressions, compiled and type-checked when the package is loaded, produce the target, parameters and destinations. The dedupe key is then computed from the canonical result, never from raw input.
  - Parameters are validated against their declared types. Material amounts are always decimal strings (HR-101); bidi and control characters are rejected (HR-102); a missing or ambiguous value is an error, never a default (HR-103).
  - The result goes through `actionir.Encode`, which gives the canonical form and hash.
- `internal/policy/domain` and `internal/policy/app`: structured rules with kinds `FORBID`, `REQUIRE_APPROVAL`, `REQUIRE_STEP_UP`, `CONSTRAIN` and `ANNOTATE`.
  - Each rule has a scope (operations and environments), a CEL condition, a stable reason code, a requirement or constraint, and labels.
  - Rules are type-checked per operation when a bundle is compiled.
  - Evaluation is fail-closed (HR-040): an error in a FORBID rule gives `DENY`; an error in a REQUIRE or CONSTRAIN rule gives `CANNOT_AUTHORIZE`; a per-evaluation cost budget overrun gives `CANNOT_AUTHORIZE` (HR-043).
  - A CONSTRAIN rule whose constraint the definition does not declare gives `CANNOT_AUTHORIZE` (F100).
  - Composition is deterministic: prohibitions win, requirements combine, and the checklist puts the decisive item first.
  - The policy result is a verdict (`PASS`, `CONSTRAIN`, `REQUIRE_APPROVAL`, `REQUIRE_STEP_UP`, `DENY`, `CANNOT_AUTHORIZE`), not an `ALLOW`. Only a grant (part 2) can allow.
  - A comparison-flipping mutation tester is included (HR-044 groundwork).
  - Bundles are stored behind a `BundleStore` interface.
- A reference package `packages/mock-payments/package.yaml` that describes the M1.5 refund route. It is golden-tested: canonical JSON, definition digest, and the ActionIR produced for fixed inputs.

**Out of scope until M2/M3 land (parts 2–3):** grants, envelopes, delegation and the lattice (HR-045..047), budgets and counters (HR-048/049), fact providers, the 10-step decision pipeline, idempotency semantics (HR-005/006), decision receipts beyond M1.5, any Connect RPC surface, any migration (M4 tables are numbered after M2's, from `00020`), gateway wiring of packages and mappings (M6), outbound re-serialization templates (M6), approval rendering (M5).

**Threat slice:** T-018 (CEL fail-open), T-020 (parser differentials), T-023 (CEL cost, oversized input), T-036 (package signing compromise, rollback, malicious mapping), and the scope part of T-001 (agent text never changes scope).

**Hardening rules in scope:** HR-023, HR-040..043, HR-100..103 (for mappings and packages; ActionIR itself already meets them), HR-123, HR-124. Partial: HR-007 (definitions declare and require the dedupe key; parking in `RECONCILIATION` is part 2 and M7) and HR-044 (the mutation tester and tests on reference rules; the publication gate is M11).

**Product requirements:** F361 (format only), F372, F374–F387, F394–F398 (lifecycle states), F100, F104 (the declaration of safe constraints), F179–F180 (the structured rule form), F405 (consequence format only), F069 (policy verdicts map onto the six decisions), F076, F092 (policy part).

**Contracts:** no protos and no migrations in part 1. New file formats: package YAML `format: 1`, targets metadata v1 (`typ: pc-package-targets+jwt`), policy bundle v1.

**Security constraints and design decisions:**
1. **Signatures cover exact bytes.** The targets document lists the SHA-256 and length of the raw package file, so no YAML parser differential can change what was signed. The canonical JSON form is used only for the definition digest.
2. **One offline key, no online roles.** The package root signs the targets document directly; there are no snapshot or timestamp roles, because those need online keys. Freshness comes from `expires` plus the monotonic metadata version. Part 1 checks expiry when a package is imported; whether decisions also check it is open decision 1.
3. **A mapping change is a meaning change.** Mappings sit inside the definition, so they are covered by the definition digest that ActionIR and approvals bind (HR-030).
4. **Untrusted text is not in the policy environment.** `text` parameters are carried in ActionIR but are not visible to policy CEL, so they can never change scope (HR-023). They cannot be material, and they cannot appear in approval templates.
5. **No floats anywhere.** Packages reject YAML floats, mapping input rejects non-integer JSON numbers, and CEL rejects `double` literals and ordering on `double`/`dyn`.
6. **Irreversible definitions declare a semantic dedupe key** as canonical fields, for example `[target.id, params.amount]`. The key is a hash of their canonical values, so it is the same on every channel (F099) and reformatting an amount cannot change it (HR-007).
7. **Policies only restrict.** No rule kind produces `ALLOW`. An `ANNOTATE` error never changes the verdict but is shown in the checklist. If approval and step-up are both required, the verdict is `REQUIRE_APPROVAL` and both requirements are listed (F071 tracks them separately).
8. **Cost defaults (configurable per tenant):** at most 10,000 runtime cost units per expression, a per-evaluation budget of 100,000, comprehension nesting ≤ 2, expressions ≤ 4 KiB. A rule whose estimated maximum cost exceeds the per-expression limit is refused at compile time.

**Dependencies to add (with justification):**

- `cel.dev/cel-go` v0.32.0 becomes a direct dependency. It is already approved in §3.

### G0 — M4 Authority core, part 2: grants, guardrails, budgets, facts and the decision pipeline — 2026-10-09

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the part-2 pull requests and, at the end, in a status section below. Part 1 left the rest of M4 to "parts 2–3"; this brief plans all of it as part 2. It builds on part 1 (on `main` as 919771c, which also holds #50) and on the M3 brief (#54, on `main` as 9434a7b). M3's code is being built at the same time (#55 onwards), so this brief also says which slices wait for which M3 pull requests.

**Purpose:** replace the M1.5 hard-coded development grant with real authority. People issue **grants** to agents for a task, inside **guardrails** (envelopes) the organisation sets. A grant can be **delegated** to a child agent only in narrower form, and revoking it stops every descendant at once. **Budgets** and **counters** hold under concurrency. Decisions use **facts** only from trusted sources, and only while they are fresh. The **10-step decision pipeline** combines all of this with part 1's definitions and policies, explains every decision in a checklist, signs a decision receipt, and treats retries as what they are: not new permission. In product terms this is the Pass and Guardrails components and the core of Checkpoint ([PRODUCT.md](../PRODUCT.md) §4).

**Scope (planned, part 2):**
- `internal/grants/domain`, all pure:
  - **lattice bounds** (HR-045): operations, access class, targets, accounts, destinations, typed parameter ranges and allowlists, identifier prefixes, validity and weekly time windows, requirements, and delegation settings, each with a decidable "narrower or equal" test and an intersection;

**Security constraints and design decisions:**
1. **Agents never issue or widen their own authority (HR-161, F054, T-001).** Root grants are issued through the API by a person holding `grant.issue` for the agent's team (decision 7). A workload can only delegate part of its own run's grant to a child run, and only when that grant allows delegation. Nothing in an ActionIR, task text or agent-reported attribute can select, create or widen a grant: the grant comes from the run (HR-022), and only `StartRun` sets it.
2. **A grant** binds one agent by id (optionally one instance), one represented principal (a user or a service account), one environment, an untrusted task label (HR-023), a validity window and its bounds. It records the grantor and what let the grantor issue it: a permission in a scope, or a parent grant (F039). Every change creates a new immutable revision, and decisions record the revision they used. States are `ACTIVE → REVOKED`. Expiry is checked at use time by the database clock, not stored as a state (F044, F053). Narrowing takes effect at once. Widening goes through the same checks as issuance and is audited. The grant id never changes, so its runs keep it.
3. **Lattice bounds (HR-045).** Bounds are independent dimensions. Each one is a lattice with a decidable "narrower or equal" test and an intersection:
   - operations: exact names, or prefixes such as `payments.*`;
   - access class: `read`, `write` (F074);
   - targets, per target type: allowed ids and byte prefixes (for git refs and paths);
   - accounts and destinations: allowlists;
   - parameters, per operation: ranges for integers and decimals (with their unit), a maximum per currency for money, allowlists for enum and identifier values, prefixes for identifiers;
   - time: the validity window, plus optional weekly windows in UTC (no time zones in M4, so daylight saving cannot open a gap);
   - requirements: approval or step-up for an operation, or above a parameter threshold (F043). These only accumulate: a child keeps every requirement of its ancestors and can only lower a threshold;
   - delegation: allowed or not, remaining depth, fan-out.

   An absent dimension means "no restriction at this level"; the other levels still apply. Parameters named in bounds must be material parameters of the operation's active definition, with the same type, when the grant is issued. At decision time, a bound on a parameter that the pinned definition lacks or types differently gives `CANNOT_AUTHORIZE`.
4. **Envelopes (org guardrails, F047, F054).** An envelope is scoped to the org, a business unit, a team, an environment, or one principal (this is how "principal bounds" are expressed). It holds bounds, budget and count rules, delegation and lifetime caps, a minimum attestation level, and the repeat-protection window (decision 6). The envelopes that apply to an action are the org's, the agent's business unit's and team's, the run's environment's, and the run principal's. An org without an org envelope gets an implicit one with the decision-5 defaults and no other limits. Changing guardrails needs the human-only `guardrails.manage`. A widening shows a diff and is audited. A narrowing applies at once to every existing grant through HR-046; no grant is rewritten.
5. **Issuance checks:** the grantor's permission in the agent's team scope; the agent is neither `DISCOVERED`, `SUSPENDED` nor `RETIRED`; the bounds are inside every applicable envelope; the validity window is inside the lifetime cap (decision 5); typed parameters match active definitions; budget and count limits are inside the envelopes' caps. For a delegated grant also: inside the parent, expiring no later than the parent, with depth and fan-out remaining.
6. **Effective authority at decision time (HR-046, F046, F062, F063).** Every ancestor grant, from the root down, and every applicable envelope are evaluated one by one against the action. The action is allowed only if every level allows it. So a wrong issuance check, a narrowed ancestor or a narrowed guardrail still limits the child. A refusal names the level, its revision, the dimension and the permitted alternative (F079). `GetGrant` returns the lineage and the effective intersection: what the grantor could give, what was given, what guardrails remove, and what the run can use now.
7. **Delegation (HR-047, F045, F055–F061).** Creating a child run (M3 `StartChildRun`) and delegating to it are separate calls. A delegated grant binds the child run's agent and inherits the principal. It is checked against its parent and against the depth, fan-out and lifetime caps of decision 5. Fan-out is counted while the parent's row is locked, so two concurrent delegations cannot both take the last place. A child shares its ancestors' budgets (design decision 9) and may set smaller limits of its own.
8. **Revocation cascades, and one lock puts it in order (HR-047, HR-002 early).** Revoking a grant revokes it and every descendant (through `grant_lineage`) in one transaction. The same transaction increments the org containment epoch, so permits already issued fail `BeginDispatch`. Narrowing a grant or a guardrail, and quarantining or retiring a package version, also increment the epoch.
   - Each of these transactions takes the org containment row first (`FOR UPDATE`).
   - Every transaction that delegates, binds a run to a grant or finalizes a decision takes the same row `FOR SHARE` first, and reads the grant chain only after it.

   This orders every removal of authority against every use of it: no child can be created under a parent that is being revoked, and no permit can be issued against a revision that is being removed. The cost is that a revocation also invalidates the org's other in-flight permits (at most about 5 seconds' worth); their agents retry with a new action id.
9. **Budgets (HR-048, F059, F110, F113–F119).**
   - Budget rules sit on grants and envelopes. Each has a grouping (task, meaning the grant; principal; target account; team; org), the operations it covers, a currency amount and/or a count, and a period (none, day, week or month, in UTC). An account is one `budgets` row per rule, grouping key and period.
   - An action reserves against the account of every grant in its chain that has a covering rule (ancestor debiting), and against every covering envelope account. So split requests, new run ids and child grants all draw on the same limits (F117).
   - Each reservation is a conditional `UPDATE`. All of them run last in the finalization, in a fixed order: envelope accounts first, then grant accounts from the root down, ties by id. A 0-row update rolls back the whole finalization; re-evaluation then gives `DENY` with `BUDGET_EXHAUSTED`, naming the account.
   - Accounts for a new period or grouping key are created in a short transaction before finalization, never inside it. Finalization therefore only updates existing rows, and its lock order cannot deadlock.
   - `reservations` records each account debited. Commit, release and hold-unknown apply to every account of the transaction, and a commit lands in the period of its reservation (ARCHITECTURE §6.3). An `UNKNOWN` outcome keeps every reservation (F115).
   - The value debited is the definition's single money parameter. An operation with several money parameters cannot be budgeted (`CANNOT_AUTHORIZE`) until its package names one. An action in a currency that the chain budgets for other currencies, but not for this one, gives `DENY`.
   - Part 2 keeps "budget last" from M1.5. ADR-0015 stays a separate decision.
10. **Counters (HR-049, F111, F112, F121).**
    - Count rules sit on grants and envelopes. Each names its operations, a key (grant, run, principal, target, target account, or one identifier or enum parameter), a window (none, minute, hour or day, in UTC), a maximum count, and an optional maximum outstanding (for concurrency limits).
    - Rows are keyed by rule, key hash and window; only the SHA-256 of the key value is stored.
    - Counters are updated by conditional `UPDATE` in the finalization, together with the budgets and in the same order. They are never checked in CEL.
    - At most 10,000 rows per rule, window and org. Past the cap the decision is `CANNOT_AUTHORIZE` (`COUNTER_CAPACITY`, T-023).
    - Counters count reservations: a released permit gives its count back, and an `UNKNOWN` keeps it. In M4, counters and budgets are PantherClaw's trusted history; agent memory never is (F124, F126).
11. **Facts (HR-160, F085, F120, F122, F125).**
    - An org registers providers. Each declares the facts it may write: name, value type, subject type and maximum lag. Each fact name has exactly one provider.
    - In M4, providers push facts through the API, authenticated as the service account bound to the provider. Pull providers (system-of-record reads through a connection) come in M6 behind the same interface.
    - A fact is (name, subject type, subject id, typed value, observation time). The observation time may be neither later than the database clock nor earlier than that clock minus the provider's maximum lag. A newer observation replaces an older one, never the reverse.
    - A required fact about the action's target (a definition prerequisite, or one a rule declares) that is missing or older than its maximum age gives `CANNOT_AUTHORIZE` (`FACT_MISSING` or `FACT_STALE`), with the fact's name and age (F125).
    - Values a workload sends are never facts. The decision records a digest of the facts it used.
12. **Facts and time in policy.** A rule may declare the facts it reads, each with a maximum age. Those facts and the definition's prerequisites are the only facts in its CEL environment, typed from the provider's declaration. They are required for every action in the rule's scope, so a rule never sees a missing or stale fact: a rule whose facts are missing is listed as not evaluated rather than run. `now` (the decision time from the database clock, in Unix seconds) supports review windows such as "bank details changed in the last 72 hours" (F120). Untrusted text stays invisible (HR-023).
13. **The ten steps in M4** (ARCHITECTURE §6.1):

    | # | Step | M4 meaning | Failure |
    |---|---|---|---|
    | 1 | Scope & coverage | The action pins a definition the org has pinned, through one of its reviewed routes (monitor mode: M6) | `CANNOT_AUTHORIZE` (`ROUTE_UNKNOWN`, `DEFINITION_NOT_PINNED`) |
    | 2 | Identity | M3's verified instance, run and principal; the attestation level meets the minimum set by the grant chain and the guardrails | `CANNOT_AUTHORIZE` (`ATTESTATION_TOO_LOW`, and M3's own codes) |
    | 3 | Containment | Kill switch; the agent, instance, run, a grant in the chain or the package suspended, revoked or quarantined | `DENY` |
    | 4 | Authority | The run has a grant; every ancestor is active, inside its window, and covers the operation, environment and target; so does every envelope | `DENY` (`NO_GRANT`, `GRANT_EXPIRED`, `OPERATION_NOT_GRANTED`, `TARGET_NOT_GRANTED`, `OUTSIDE_GUARDRAIL`, …) |
    | 5 | Exact meaning | The definition is `ACTIVE` and not stale; parameters decode without ambiguity; bounds type-check | `CANNOT_AUTHORIZE` |
    | 6 | Current facts | Required facts present and fresh | `CANNOT_AUTHORIZE` |
    | 7 | Boundaries | Parameter, destination and time bounds of every level; FORBID rules; counters and budgets (read-only check); repeat protection (pre-check) | `DENY`, or `CANNOT_AUTHORIZE` for a failure outside FORBID |
    | 8 | Requirements | Approvals and step-ups from grants and rules; obligations the definition supports | `REQUIRE_APPROVAL`, `REQUIRE_STEP_UP`, `CANNOT_AUTHORIZE` |
    | 9 | Final binding | One finalization transaction (design decision 15) | roll back and re-evaluate |
    | 10 | Observe | `BeginDispatch`, `RecordExecution` and the sweeper, over every reservation | `UNKNOWN` keeps reservations |
14. **Composition (F092, F096).** Every step that can be evaluated is evaluated. A step that depends on a failed one (for example, parameters when the meaning is unknown) is listed as not evaluated. The strictest result wins, in the order `DENY` > `CANNOT_AUTHORIZE` > `REQUIRE_APPROVAL` > `REQUIRE_STEP_UP` > `ALLOW_WITH_OBLIGATIONS` > `ALLOW`. The decisive reason is the first checklist item, in step order, that produced the winning result. So a known prohibition is reported as `DENY` even when evidence is also missing, and missing evidence alone is never reported as a business-policy denial. `ALLOW` needs steps 1–8 to pass with a grant covering the action (F095). If an obligation clamps a parameter (F104), the decision also records the effective action's hash (F107); the gateway dispatches that effective action in M6.
15. **Finalization (step 9).** One transaction, whose statements follow the lock order:
    1. the containment row `FOR SHARE` (kill switch and epoch);
    2. the grant chain and envelopes again: their revisions and states must equal what steps 3–4 used;
    3. the idempotency row (design decision 16);
    4. the dedupe claim (design decision 18);
    5. counters and budgets, in the fixed order, last.

    Then the permit, the receipt and the ledger entry. A difference, or a 0-row conditional update, rolls everything back. The pipeline then runs again, at most twice; after that the answer is `CANNOT_AUTHORIZE` (`CONCURRENT_CHANGE`). Decisions other than `ALLOW` are recorded the same way, without reservations.
16. **Idempotency (HR-005, HR-006).** `(org, run_id, action_id)` is unique.
    - A transaction is `OPEN` while its latest decision is `REQUIRE_APPROVAL`, `REQUIRE_STEP_UP` or `CANNOT_AUTHORIZE`. It is `FINAL` after `ALLOW`, `ALLOW_WITH_OBLIGATIONS` or `DENY`.
    - Same hash, `FINAL`: the stored decision and receipt come back, never a second permit. An `ALLOW` whose permit expired unused stays final; the agent needs a new action id, and repeat protection still applies to it.
    - Same hash, `OPEN`: the full pipeline runs again (PAP-1 §8). The update is conditional on the evaluation count (HR-004), and each evaluation gets its own receipt. After 32 evaluations the stored decision comes back without a new evaluation (T-023).
    - Different hash: `DENY` with `ACTION_TAMPERED`, and a `security.action_tampered` audit event. An `OPEN` transaction then becomes `FINAL` with that denial, so the original action cannot be resumed.
17. **Decision receipt and basis (PAP-1 §9.1, F078, F080).** Each evaluation gets a signed `pap-decision+jwt` with: the transaction id and evaluation number; the requested and effective action hashes; the decision, reasons and full checklist (all ten steps, decisive item first); obligations with their timing; versions (the policy bundle version, the grant chain as id and revision pairs, envelope revisions, the definition digest); the facts digest; the identity summary (instance, attestation level, launcher, principal; ids only); budget and counter state after the reservation (F113, F119); timestamps; and the `simulated` flag. The **decision-basis digest** is the SHA-256 of the canonical JSON of the policy version, grant chain revisions, envelope revisions, definition digest and facts digest; M5 approvals bind it (HR-030). Agent-supplied text never appears in a receipt or an explanation (HR-023). Rules that do not apply are summarised as a count, so receipts stay under the 64 KiB limit.
18. **Repeat protection for irreversible actions (HR-007, F131, F136).** A definition with a dedupe key (every irreversible one has one) makes finalization claim that key in `dedupe_claims`.
    - A new request is parked while the earlier claim's permit is issued, dispatching or `UNKNOWN`, and for the repeat window (decision 6) after an accepted outcome. Parked means `CANNOT_AUTHORIZE` with `RECONCILIATION_REQUIRED`, naming the earlier transaction; the request may be retried.
    - An earlier attempt that expired unused, or that failed at the target, does not park.
    - Claims change by conditional update, so two concurrent identical actions with different action ids get exactly one permit.
    - M5 adds the `RECONCILIATION` waitlist entry, and M7 the reconciliation that resolves an `UNKNOWN`. Until then an `UNKNOWN` irreversible action blocks its exact repeat, which is the safe way to fail.
19. **Grant binding at `StartRun` (HR-022, PN-002.5).** After M3 slice 11, `StartRun` field 7 is `grant_id`. The grant must be active and valid. Its agent (and instance, if pinned), principal and environment must equal the run's, and the run's expiry is cut to the grant's. A child run gets authority only through delegation. `Authorize` uses the run's grant, so an action in a run without one gets `DENY` with `NO_GRANT` (F095).
20. **Part-1 ports and storage.** Trusted package metadata is tracked per org (the port gains an org argument), so no global table is writable by `pc_app`. Package bytes and definitions are stored per org and looked up by definition digest. Quarantining or retiring a version increments the containment epoch (design decision 8). An org has at most one published policy version. Compiled bundles and definitions are cached per org and version in a bounded cache, which a publication clears.
21. **Failures, logging and performance.** If a store the pipeline needs is unavailable, the decision is `CANNOT_AUTHORIZE`, never `ALLOW` (invariant 8). Logs and audit events carry ids, reason codes and digests only. `Authorize` must stay within ARCHITECTURE §15 (p99 ≤ 25 ms co-located); the exit slice measures it as `docs/perf/M1.5.md` did.

- **Latency.** The SLO is not met on the laptop, and the pipeline costs about 40 transactions per refund (see the exit criteria above and [docs/perf/M4.md](../perf/M4.md)). This is a performance follow-up, not a contract change. *Follow-up done 2026-10-10:* one evaluation reads all its inputs in one `REPEATABLE READ, READ ONLY` snapshot (#158, `pgauthority.Reader.Snapshot`), and the finalization skips `Prepare` when that snapshot found every budget account and counter row (#173). The measurements are in [docs/perf/M4.md](../perf/M4.md); the Linux re-measurement is still open.
- **Decision 1 (the signing command's 180-day default).** Part 2 did not add it: `pclaw-admin packages sign` still required `--expires-days`. The 2026-10-10 post-merge audit found the gap; the default is implemented in the post-audit fixes.
