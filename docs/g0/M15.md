### G0 — M15 — Gateway state, discovery and the reviewed MCP surface — 2026-10-29

This brief is written before implementation (G0). It lists planned scope; delivery status is tracked by the M15 pull requests and, at the end of the milestone, in the exit status section. It builds on `main` at 7005db42 (M1–M14, UI and M13 complete; the highest migration is 00185). M15 is the first milestone after v1.0: the founder postponed the v1.0 testing steps on 2026-10-29 and coding continues past v1.0. The founder answered four open decisions for M15 (F1–F4, with F9 on how M15 and M16 run) on 2026-10-29, the recommended option each time; they are recorded at the end as answered. Every other choice is a design decision made by the coordinator (D1–D42 and D46 in the coordinator's tracker), summarised below.

**Purpose:** the gateway knows very little about its own world today. It reports nothing to the server about itself (only the server sends containment heartbeats), it keeps MCP holds, tasks and sessions in memory, so a restart or a second replica forgets them, and it governs only the tools a reviewed package already names: a tool or resource the upstream MCP server adds is ignored, with no way to bring it under review. M15 closes these gaps. Gateways report their status and replicas; MCP holds, tasks and sessions live on the server, so an approval given on one replica binds on another and survives a restart; tools and resources the upstream server lists are recorded as an untrusted inventory, enter review, and can be turned into a draft package that a person completes, signs and activates; reviewed resources are served as read operations decided by the full pipeline; and an upstream server's request for input (elicitation) can reach the agent, but only in form mode, for fields a reviewed package declares, after an injection scan, and with the answer decided as a new action. In product terms this is Checkpoint ([PRODUCT.md](../PRODUCT.md)): the MCP surface agents see stays reviewed, now including what the upstream server adds later.

**Scope (planned, D1):**
- **15a Gateway status** (PN-010.6, status part). A gateway→server status report: its replicas, version, build, configuration version and per-connection serving state; `Gateway` shows its replicas and whether it is connected.
- **15b Shared MCP state** (F1). MCP holds, tasks and sessions live on the server (Postgres) through gateway control RPCs: a hold approved through one replica binds on another, a task created on one is polled on another, and a restart forgets nothing. Task bodies are sealed to the gateway's broker key; the server never opens them.
- **15c Tool and resource discovery** (F352, F2). The gateway lists every tool, resource and resource template of each MCP connection and reports them; the server keeps an inventory, scans descriptions for injection, opens a connection-scoped TOOL_REVIEW entry for anything not covered by an active reviewed package, and drafts an unsigned package from chosen items. Discovered items stay unusable until a reviewed version is active.
- **15d Resources as reviewed reads** (F3). A new `mcp_resource` mapping channel; the MCP face serves `resources/list`, `resources/templates/list` and `resources/read` for reviewed resources only, each read decided by the full pipeline.
- **15e The elicitation gate** (PN-015.2, F4). On a 2026-07-28 upstream, `input_required` is relayed to the agent only in form mode, for fields the reviewed mapping declares, after an injection scan; the answer is decided as a new action.

Editions: everything is Community, except drafting a package from the inventory, which is Team (D23).

*Shared MCP state* (`PutMCPState`, `GetMCPState`, `DeleteMCPState`; TB3; D12–D14).
- **Who can reach it:** only an enrolled gateway on the mTLS gateway listener holding `gateway.sync`; organization and gateway come from the certificate, never the request (HR-181, HR-411).
- **Tampering (T-182):** a compromised replica or a gateway of another organization rewrites a hold so that an approval binds to another call, or swaps a task's stored result. Answered by: rows are keyed per gateway and bound to (connection, run, instance); sealed bodies are sealed to the gateway's broker key with the organization, gateway, kind, key and binding (connection, run, instance) in the additional data, so a body moved to another key, or a row whose binding columns are rewritten on the server, does not open and counts as not found (HR-411, D41).
- **Elevation (T-183):** reusing a hold, task or session across connections, runs, instances or agents. Answered by: every read checks the binding; a session also checks the agent key (jkt) on every replica; only the SHA-256 of a session id is stored (HR-412, HR-413).
- **Denial of service:** per-instance and per-gateway caps; a full store answers `MCP_STATE_FULL`, and a miss only costs the agent a new action (HR-412). An unreachable server never serves a stale entry.

*Discovery* (`ReportInventory`, `ListConnectionInventory`, `DismissInventoryItem`, `DraftPackageFromInventory`; TB3, TB4, TB9; D20–D23).
- **Spoofing:** a gateway reporting tools for a connection it does not serve. Answered by: reports are accepted only for connections the calling gateway serves (HR-418).
- **Tampering (T-184):** an upstream server writes instructions into a tool or resource description, hoping it reaches an agent or a reviewer's draft. Answered by: discovered text is UNTRUSTED, scanned, shown flagged and never used as a served description; a draft puts it only in a YAML comment (HR-415, HR-416).
- **Elevation:** a newly listed tool used before review. Answered by: discovered items are inert until an active reviewed package version covers them (HR-414); drafts are unsigned and enter only through the signature check and TOOL_REVIEW (HR-416).
- **Repudiation:** every inventory state change is audited; review entries close only by coverage, a person's dismissal with a reason, or disappearance in a complete listing, never by timeout (HR-417, D25).
- **Denial of service (T-187):** an upstream server listing thousands of items or huge descriptions to flood the inventory and the review queue. Answered by: at most 10 pages per listing, 1,000 items per kind and 8 KiB per description per report; one row per (kind, name, digest) (HR-418).

*The reviewed surface* (`resources/*`, `input_required`; TB1, TB2; D30–D35).
- **Tampering (T-185):** an agent puts `..`, `@`, another host or encoded separators into a resource URI to reach another path or host (SSRF, path traversal). Answered by: a URI that matches no reviewed template never reaches the upstream server; values are percent-encoded; scheme and host are fixed by the connection (HR-419).
- **Information disclosure (T-186):** an upstream server asks the agent, through elicitation, for secrets or for data outside the task, or phrases the request to manipulate the agent. Answered by: form mode only, fields a reviewed mapping declares, a clean injection scan; the answer travels only as material parameters of a new action that policy decides (HR-420); the retry carries a single-use handle, never upstream state (HR-075, D39); URL mode, sampling, roots and mid-stream 2025-11-25 elicitation stay declined (HR-421).

**Hardening rules in scope:** the new rules **HR-410..HR-421** added to [HARDENING_RULES](../security/HARDENING_RULES.md) by this brief, plus HR-081 and HR-082 (reviewed descriptions; elicitation policy-gated), HR-244 (TOOL_REVIEW for instruction-like descriptions and drift), HR-181 (gateway identity from the certificate), HR-070..077 (egress), HR-075 (outbound only from ActionIR: the elicitation retry), HR-100..104 (input), HR-123 and HR-124 (packages), HR-185 (tasks belong to their binding, on every replica), HR-400 (agent-safe refusals) and HR-004 and HR-050..057 for the new tables.

**Design decisions:**

*S15a — gateway status and shared MCP state*

1. **D10: `ReportStatus`** (`GatewayService`, `gateways.proto`; `gateway.observe`; HR-410). The request carries a `replica_id` (22 characters of `[A-Za-z0-9_-]`, random per process start), `version` and `build` (at most 64 characters each), `start_time`, the `config_version` it serves, and at most 1,000 `ConnectionStatus{connection_id, state, last_drift_check_time}` with `state` one of `SERVING`, `CIRCUIT_OPEN`, `DRIFT_QUARANTINED`, `NOT_LOADED`. The answer carries `next_report_seconds` (the server answers 30). `Gateway` gains `repeated GatewayReplica replicas` (replica id, version, build, start time, configuration version, last seen) and `bool connected` (some replica seen in the last 90 s). The gateway reports on start, every `next_report_seconds`, and 5 s after a connection's serving state changes; a failure is logged and never stops serving. Connection ids the gateway does not serve are dropped on the server. Gateway side in a new `internal/gateway/status.go`.
2. **D11: migration 00186 `pc.gateway_replicas`.** `org_id, gateway_id, replica_id, version, build, start_time, config_version, connections jsonb (ids, states and times only), last_seen NOT NULL`; primary key `(org_id, gateway_id, replica_id)`; foreign key to `pc.gateways` with `ON DELETE CASCADE`. A River periodic job `gateway_replicas.prune` deletes rows not seen for 24 hours, hourly.
3. **D12: the state RPCs** (`GatewayService`; `gateway.sync`; organization and gateway from the certificate; HR-411, HR-412).
   - An `MCPStateEntry` has a `kind` (`HOLD` = 1, `TASK` = 2, `SESSION` = 3 or `ELICITATION` = 4, D39), a `key` of exactly 32 bytes, `connection_id`, `run_id`, `instance_id`, `jkt` (SESSION only, at most 64), `action_id` (HOLD and TASK), `status` (TASK: `working`, `completed`, `failed` or `cancelled`), `busy` (the TASK claim), `sealed_body` (TASK and ELICITATION only, at most 4 MiB, D13), a server-assigned `version` (+1 per write), `expire_time` and a server-set `update_time`.
   - `PutMCPState{entry, if_version}`: `if_version` 0 means the entry must not exist; otherwise it must equal the stored version. A mismatch is `FailedPrecondition` with the detail code `MCP_STATE_CONFLICT`. `GetMCPState{kind, key}` has no side effects. `DeleteMCPState{kind, key, if_version}` answers `deleted=false` without an error for a missing row.
   - **Bounds**, enforced on the server, with today's in-memory values (ELICITATION entries count toward the HOLD and TASK bounds, D39): 32 HOLD and TASK entries per (gateway, instance); per gateway 2,000 HOLD and TASK entries, 10,000 sessions and 64 MiB of sealed bodies, beyond which `ResourceExhausted` with `MCP_STATE_FULL`; 16 sessions per instance, where the least recently updated session of that instance is deleted to make room.
   - Expired rows are invisible to `Get` and deleted every minute by the River job `gateway_mcp_state.purge`.
   - **Per-kind validity** (D42): an ELICITATION entry has no `action_id`, `status` or `busy`, needs a body and expires within 10 minutes; HOLD and TASK entries expire within 1 hour and 1 minute, SESSION entries within 8 hours and 1 minute; 00187's CHECK constraints match. The binding columns (connection, run, instance) cannot change on an update: a change is `MCP_STATE_CONFLICT`. `PutMCPState` refuses a connection the calling gateway does not serve (`PermissionDenied`), as `ReportStatus` and `ReportInventory` do. A versioned delete matches only unexpired rows.
   - Migration 00187 `pc.gateway_mcp_state`: the entry's columns plus `org_id, gateway_id, created_at`; primary key `(org_id, gateway_id, kind, key)`; index `(org_id, gateway_id, instance_id, kind)`; RLS and grants as 00186.
4. **D13: sealing** (HR-411; amended by D41). A TASK body is sealed with `platform/crypto` to the gateway's active broker public key (its X-Wing suite), with the additional data `"pc.mcp_state.v1|" + org + "|" + gateway + "|" + kind + "|" + hex(key) + "|" + connection_id + "|" + run_id + "|" + instance_id`; the plaintext is JSON `{"action": <canonical action bytes, base64>, "result": <tool result or null>}`. ELICITATION bodies are sealed the same way (D39). Gateway replicas share the broker key, so any replica opens it; the server never does. A body that does not open (after a key rotation, or because a row's binding columns were rewritten on the server) is treated as not found. HOLD and SESSION entries carry no body. A session id is never sent: the key is its SHA-256 (HR-413).
5. **D14: the gateway side** (`internal/gateway/mcp`; HR-412, HR-413). The hold `store` and `sessions` become interfaces with two implementations: `state_memory.go` (today's logic, for unit tests and gateways built without a control client) and `state_server.go` (the D12 RPCs); production wiring always uses the server one.
   - A task claim is a `Put` with `busy=true` and `if_version`; the replica that loses the race only reads.
   - A session's last-use time is written at most once per 60 s per session.
   - One `GetMCPState(HOLD)` per `tools/call` before `Authorize`.
   - **Server unreachable:** a hold or task lookup behaves as "not remembered" (a new action); a session lookup answers HTTP 503 with the JSON-RPC error message `session store unavailable`. A stale entry is never served.
   - **Without a broker key** (D42): a gateway that has no broker key cannot seal, so it keeps TASK and ELICITATION entries in its own memory, as before M15; holds and sessions are shared either way. It logs a warning at start-up when it serves an `mcp` connection without a broker key, and it still starts. Tasks are therefore shared across replicas only when the replicas share a broker key ([runbook](../runbooks/gateway.md) §3).
6. **D16: task keys and deduplication on every replica** (HR-185, HR-411).
   - A TASK `key` is the SHA-256 of the task id, as for sessions.
   - A held call's task id is derived, not random: base64url(HMAC-SHA256(K, `"pc.mcp_task.v1|" + hex(actionKey) + "|" + action_id`)), with K = HKDF-SHA256 (input key material the gateway's broker private key, salt the gateway id, info `"pc.mcp_task_id.v1"`). An identical held call therefore yields the same task id on every replica: its `Put` with `if_version` 0 conflicts, and a `Get` returns the existing working task.
   - Tasks of calls that were not held (completed at once) keep random ids.
   - After a broker-key rotation the ids change: the next identical call gets a new task, as after a restart today.
   - `TestHR185_TasksBelongToTheirBinding` runs against both stores.
7. **D15: exit end-to-end tests** (S15a, `test/e2e/m15_e2e_test.go`): see the exit criteria. S15a also writes the performance note `docs/perf/M15.md`: p50 and p99 of an MCP `tools/call` before and after D14, measured with `pantherclaw-sim` on the same machine, side by side.

*S15b — discovery*

8. **D20: the gateway inventory** (TB9; HR-418). A new `internal/gateway/upstream/list.go` adds `ListResources` and `ListResourceTemplates`, paged by cursor as the MCP specification describes, at most 10 pages; `ListTools` also reads every page, with the same cap. From the existing drift loop (on load and every 10 minutes), the gateway sends `ReportInventory` (`gateway.observe`) for each `mcp` connection:
   - `connection_id` (must be served by the calling gateway) and `complete` (every page of every list was read);
   - at most 1,000 each of `InventoryTool{name, digest, description, description_truncated}` (the tool name follows the drift report's pattern; the digest is `upstream.ToolDigest`), `InventoryResource{uri (at most 2048), name (at most 128), mime_type, description, description_truncated, digest}` and `InventoryResourceTemplate{uri_template, name, mime_type, description, description_truncated, digest}`; descriptions are cut to 8 KiB and flagged when cut; resource digests are SHA-256 of the canonical listing entry;
   - the answer carries the count of new items.
9. **D21: migration 00188 `pc.connection_inventory`.** `org_id, id (uuid v7), connection_id, kind (TOOL, RESOURCE or RESOURCE_TEMPLATE), name (tool name, URI or URI template), display_name, mime_type, digest, description (UNTRUSTED, at most 8 KiB), description_scan (clean, flagged, partial or not_scanned), state (NEW, COVERED, DISMISSED or VANISHED), review_entry_id, dismissed_by, dismiss_reason, first_seen, last_seen, updated_at`; unique `(org_id, connection_id, kind, name, digest)`; foreign key to the connection; RLS and grants. Waitlist rows use `subject_type = 'connection_inventory'` (the migration widens a CHECK only if one blocks it).
10. **D22: server rules** (`internal/connections/app/inventory.go`; HR-414, HR-415, HR-417).
   - A new (kind, name, digest) becomes a `NEW` row; its description is scanned with `detection/injection` exactly as drift descriptions are; a `TOOL_REVIEW` waitlist entry is opened for it (`subject_type 'connection_inventory'`, the row id, trusted fields connection, kind and name only), unless it is covered.
   - **Covered** means an ACTIVE package version pinned by the connection maps it: tools by name and digest (the reviewed check the drift path already uses), resources and templates by the `mcp_resource` mapping (D30; until S15c lands, resources stay NEW). A covered item becomes `COVERED` and its entry closes `APPROVED`.
   - A `complete` report that no longer lists a NEW or COVERED item marks it `VANISHED` and closes its open entry `EXPIRED`. Only a complete report does this.
   - NEW rows are re-checked on every report (D25).
   - A changed digest of a covered tool still goes through today's drift path (quarantine); the inventory only adds the new digest as NEW.
   - Every state change is audited (`connection.inventory_*` events).
11. **D23: the user API** (`ConnectionService`, `connections.proto`; HR-414..417).
    - `ListConnectionInventory{connection_id (required), states, kinds, page_size (at most 200), page_token}` returns every D21 field, the description marked UNTRUSTED in the proto comment; `connection.read`; no side effects; keyset paging with an opaque token.
    - `DismissInventoryItem{id, reason (1–500 characters, UNTRUSTED)}`: `connection.manage`; NEW items only; the entry closes `REJECTED`.
    - `DraftPackageFromInventory{connection_id, item_ids (1–100, NEW only)}` returns `{manifest_yaml, todo}`: `package.import`, Team edition through `billing.Entitlements` (refused like other Team-gated calls). The draft is package `draft.<connection-name-slug>`, version `0.0.0-draft`, one operation per item: tools as `access: write` with `effects: []` and an `mcp` mapping by tool name; resources and templates as `access: read` with an `mcp_resource` mapping by URI (template). The upstream description goes only into a YAML comment `# UNTRUSTED upstream description: …`; the `description` field is left empty. The draft fails manifest validation until a person fills effects, parameters and descriptions (`todo` lists them). The server never signs it (HR-416).
    - CLI (`pclaw`): `pclaw connection inventory list <connection>`, `pclaw connection inventory dismiss <id> --reason <text>`, `pclaw package draft --connection <connection> [--item <id>]… [-o file]`.
12. **D25: re-checking and expiry** (HR-417; replaces a reconcile job). There is no hook in `internal/definitions` and no periodic job: every `ReportInventory` re-checks that connection's NEW rows against the currently active pinned package versions, in its own transaction. A newly activated package's items therefore turn COVERED at the gateway's next report (at most 10 minutes). COVERED is bookkeeping only: whether a tool can be served still depends on the active package, as today. TOOL_REVIEW entries with `subject_type 'connection_inventory'` are excluded from the waitlist's expiry (`ExpireWaitlistEntries`): they stay open, and overdue, until covered, dismissed or vanished.
13. **D24: the discovery end-to-end helper** (`test/e2e/m15_discovery_test.go`): see the exit criteria. The upstream mock is `internal/sim/mcpsim` with a configurable extra tool and resource.

*S15c — reviewed resources and the elicitation gate*

14. **D30: definitions** (`internal/definitions`; HR-419). A new mapping channel `mcp_resource`; `Mapping.Resource` is an RFC 6570 level-1 URI template (`{name}` variables only). Its operation must be `access: read` with no effects; template variables map to parameters through `extract`, like other mappings. `MCPDispatch.Resource` is the upstream URI template. Validation refuses anything else; digests and canonical forms follow the existing mapping code.
15. **D36: the resource-read channel.** A resource read's ActionIR channel is `mcp`: there is no new ActionIR channel, and the SDK fixtures are untouched. The pipeline's mapping scope lets an `mcp` action match a mapping whose channel is `mcp` or `mcp_resource`. Manifest validation requires an operation's mappings to be either all `mcp_resource` or none of them, so one operation never has both a tool and a resource mapping.
16. **D31: the MCP face for resources** (`internal/gateway/mcp/resources.go`, both protocol versions; HR-419).
    - `resources/list` returns the reviewed static resources (templates without variables) and `resources/templates/list` the reviewed templates, with names and descriptions from the package only.
    - `resources/read`: the URI is matched against the reviewed templates → ActionIR (the mapping's operation, parameters from the template variables) → `Authorize` → `BeginDispatch` → upstream `resources/read` (new `internal/gateway/upstream/read.go`) with the URI built from `MCPDispatch.Resource`, each value percent-encoded, scheme and host fixed by the connection → `RecordExecution` → the contents (text or blob, capped at the egress response limit). M14's data-scoping obligations apply as to other reads.
    - No match is JSON-RPC error `-32002` "Resource not found", and nothing is sent upstream. `resources/subscribe` is "method not found". The face advertises `resources: {subscribe: false, listChanged: false}` only when the connection has a reviewed resource.
17. **D32: the elicitation spec** (HR-420). An `mcp` mapping gains an optional `elicitation` block with at most 16 `fields`, each a parameter spec of type string, number, integer, boolean or enum. At manifest load each field becomes a material parameter `elicitation.<field>` of the operation, so CEL policy and receipts see it. Without the block, today's behaviour stays.
18. **D37: field types.** Each field's parameter spec is the package author's. Compatibility with the upstream's requested schema: `string` ↔ identifier or content (or enum when the request lists enum values); `number` ↔ decimal (with a unit, as today); `integer` ↔ integer; `boolean` ↔ boolean; a requested enum's values must be a subset of the declared enum values. Anything else is refused (D33).
19. **D38: derived parameters.** Manifest validation checks the `elicitation` block (field names must match the parameter-name pattern); decoding then adds the `elicitation.<field>` parameters with the declared spec, `required: false` and material. The dot keeps them from colliding with authored parameters, and definition digests stay deterministic.
    - **How policy reads them** (D46): CEL reads them as the nested optional object `action.params.elicitation.<field>`, for example `has(action.params.elicitation) && has(action.params.elicitation.channel) && action.params.elicitation.channel == "sms"`. Text-typed fields are not visible to CEL (HR-023). An authored parameter named `elicitation` is refused. ActionIR, receipts and digests keep the `elicitation.<field>` names.
20. **D33: the relay, 2026-07-28 upstreams only** (HR-420).
    - When the upstream answers a `tools/call` with `input_required`, every elicitation request must be form mode, with a requested schema whose fields are a subset of the declared fields with compatible types (D37), and a message whose `detection/injection` scan is clean. Any failure gives today's tool error plus a local refusal report with the code `elicitation_refused` (D40).
    - When all pass, `input_required` goes to the agent on the 2026-07-28 face with the screened requests and a handle in place of the upstream's `requestState` (D39); the 2025-11-25 face keeps today's tool error. The first transaction keeps today's recorded outcome for `input_required`.
    - The agent's retry carrying `inputResponses` is a new action: answers are validated against the declared fields (anything else is a tool error before `Authorize`), put into the `elicitation.<field>` parameters, decided by the full pipeline and forwarded upstream only on ALLOW.
    - The question text is never stored (D40).
21. **D39: retry state** (HR-075, HR-420). The upstream's `requestState` and request keys never go to the agent and are never taken from it.
    - On an `input_required` that passes screening, the gateway stores an `ELICITATION` state entry (D12): key = SHA-256 of a fresh 32-byte random handle, binding (connection, run, instance), a sealed body (D13, with the kind in the additional data) `{tool, request_state, requests: [{key, field names, schema digest}]}`, a 10-minute lifetime, counted in the HOLD and TASK bounds. The agent receives `input_required` with the screened requests and `requestState` = the handle (base64url).
    - The retry must carry a handle that resolves for the same binding and tool; otherwise it is a tool error before `Authorize` and nothing is sent upstream. The handle is single use: the gateway deletes the entry with `if_version` before forwarding, and a lost race is refused.
    - Field names must be unique across all requests of one `input_required` (otherwise refused). Response keys must be a subset of the stored keys. `accept` answers become `elicitation.<field>` parameters; `decline` and `cancel` add none. On ALLOW the gateway forwards the retry with the stored upstream `requestState` and the arguments and answers built from ActionIR.
22. **D40: recording refusals and relays.**
    - `internal/connections/app/localrefusal.go` (S15c) accepts `elicitation_refused` alongside `secret_in_payload` and audits `connection.elicitation_refused` (reason `ELICITATION_REFUSED`).
    - `ReportLocalRefusalRequest` (`gateways.proto`) gains `optional string elicitation_reason` (one of `url_mode`, `undeclared_field`, `type_mismatch`, `duplicate_field`, `too_many_fields`, `injection_flagged`) and `optional bytes question_sha256` (exactly 32 bytes), set only with the code `elicitation_refused` and copied into the audit details.
    - A relayed (clean) question is logged by the gateway only, as its SHA-256 and scan result, never its text. Neither `authority.proto` nor receipts change in M15; question digests in execution evidence are a follow-up.
23. **D34: still declined** (HR-421). URL-mode elicitation, `sampling/createMessage`, `roots/list`, and `elicitation/create` arriving mid-stream from a 2025-11-25 upstream; the gateway's answers to those stay unchanged.
