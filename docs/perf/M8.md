# M8 latency measurements

**Date:** 2026-10-13. **Measured by:** Claude Code. **Targets:** SIMULATED (`pantherclaw-sim payments` and the GitHub simulator). No real money moved and no real repository was touched.

G0 M8 asks the exit to re-measure `Authorize` with what M8 adds to the decision path: consequence rules evaluated in the pipeline (P1, HR-206) and the gateway's GitHub fact reads before `Authorize` (G4, at most 2 s, design decision 12). The method follows [M6](M6.md) and [M7](M7.md): static Linux binaries in the network namespace of a private PostgreSQL container, M6 and M8 side by side.

## Summary

- **On a payments refund, M8 costs about what M6 did.** At 10 rps, five rounds on fresh stacks running at the same moments:
  - `Authorize` p50 is 22.0 ms on M8 against 21.0 ms on M6 (medians of the rounds). The paired p50 difference has a median of **+1.0 ms (+5 %)**.
  - The p99 differences go both ways (from −55 to +26 ms).
  - In `BenchmarkRefund` with 1 worker, the paired p50 difference has a median of **+0.2 ms (+1 %)**.
  - A refund has no consequence rules, so this is the cost of step 6 looking for them and finding none.
- **One signal to watch:** in `BenchmarkRefund` with 8 workers, `Authorize` p99 was higher on M8 in all five rounds, by 3 to 41 % (median of the paired differences +38 ms, **+16 %**). The p50 differences go both ways. This is below the 20 % the exit watches for, and on a shared laptop a contended tail supports no firmer figure.
- **A refund takes about two more database transactions:** about 18.9 per refund on M8 against 16.7 on M6, after the idle rate is subtracted. M6 measured 17.0. Where the two come from was not investigated (see Next).
- **The GitHub path, timed per call, not under load.** Two hundred merges went through the gateway against the GitHub simulator, each a fresh pull request into a branch that deploys to production. The gateway's GitHub fact reads took **p50 58 ms, p95 119 ms, p99 170 ms**, far inside their 2 s budget. `Authorize` after them took p50 29 ms, the same as a refund's on the same stack (29 ms).
- **The SLOs are still not validated** (ARCHITECTURE §15). At 50 and 100 rps both trees collapsed into the gateway's 2 s timeout on the same rounds, as in M6. The laptop is shared with other Claude Code sessions, so only side-by-side runs compare. The Linux/NVMe run stays open, as in M1.5, M4, M6 and M7.

| Server | Log level `warn`, the development configuration of each tree. The gateway's control-plane timeout is 2 s. |

**Method.**
- **Open loop.** Five rounds. Each round started both stacks fresh and at the same time (a new container, `db bootstrap`, `migrate up`, `dev seed`, then the server, the payments simulator and the gateway). It then ran `pantherclaw-sim load --unique --facts-key-file …` on both at the same moments: 10 rps, then 50, then 100, each 30 s measured after a 5 s warm-up. The database's transactions were counted around each run (`xact_commit + xact_rollback`).
- **Closed loop.** `BenchmarkRefund` with `-benchtime 1000x` (1,000 refunds with 1 worker, then with 8): five rounds, both trees at the same moments, each in its own database container.
- **GitHub, per call.** The §43 test stack (`test/e2e`) run co-located in the M8 tree's database container, with the GitHub App connection sealed and the GitHub simulator. A temporary test in that package, never committed, did the following 210 times:
  1. push a branch to the simulator;
  2. open a pull request through the gateway;
  3. merge it through the gateway's REST face;
  4. send a payments refund through the gateway on the same stack, as the baseline.

  The first ten of each were warm-up. Each call's `Server-Timing` laps (`facts`, `authz`, `begin`, `target`, `record`, `total`) were recorded.

All latencies are in ms. Status 200 = accepted; 503 = the Authority did not answer within the gateway's 2 s timeout (fail closed, nothing dispatched); 403 = refused with a decision.

Each run made about 349 refunds (warm-up included), each with its fact report. The idle rates, sampled for 30 s on both stacks at the same time after the runs, were 33 per second (M6) and 28 per second (M8). They are subtracted over the run's 36 s.

| M6 transactions | 6,912 | 7,005 | 7,005 | 7,087 | 7,087 | **≈ 16.7** |
| M8 transactions | 7,580 | 7,569 | 7,661 | 7,705 | 7,602 | **≈ 18.9** |

- M8 ran 515 to 668 more transactions per run than M6 in every round, about **two more per refund**. Without subtracting idle work the difference is the same (about 1.7 per refund).

### The GitHub path, per call (M8 exit, 200 of each)

| Call | Result | `facts` p50 / p95 / p99 | `authz` p50 / p95 / p99 | Gateway total p50 / p95 / p99 | Client p50 / p95 / p99 |
|---|---|---|---|---|---|
| Merge into a branch that deploys to production | 200 × 403, see below | **58.5 / 118.7 / 170.4** | 28.6 / 68.3 / 84.4 | 92.6 / 151.7 / 240.5 | 166.5 / 246.4 / 387.7 |
| Open a pull request (allowed) | 200 × 201 | none | 22.2 / 46.8 / 61.3 | 47.4 / 88.2 / 109.8 | 52.7 / 92.1 / 114.0 |
| Payments refund, the same stack (baseline) | 200 × 200 | none | 29.3 / 57.8 / 67.1 | 50.2 / 87.9 / 125.7 | 53.9 / 95.3 / 129.7 |

- **Every merge was decided after its facts were read and its consequence rules evaluated.** Each answer carries the merge's own requirements: `MERGES_NEED_AN_INDEPENDENT_REVIEW`, and `DEPLOYMENTS_NEED_A_RELEASE` from the predicted deployment to production.
- **Why the answer is a refusal, not a hold.** A run holds at most 5 calls at once, and the schema allows no more (`max_holds_per_run` ≤ 5). Past that, the finalization refuses the hold with `HOLD_LIMIT_REACHED` (`CANNOT_AUTHORIZE`). So these timings include the whole evaluation, but not the approval request's own writes, which a first hold makes.
- **The fact reads are the merge's largest cost:** p50 58 ms, p99 170 ms. They are well inside the gateway's 2 s budget, and they come on top of an `Authorize` that costs what a refund's does.
- **The client time of a merge is about 74 ms longer than the gateway's total** at p50, which a refund's is not (4 ms). That time is spent before the gateway's timer starts and was not investigated (see Next).
- **This is per call, one at a time, not under load.** `pantherclaw-sim load` drives payments refunds only. A GitHub mode for it is a follow-up for M13's k6-at-SLO work.

## Method notes

- **The stacks** were started with each tree's own `deploy/dev` configuration and the commands of BUILD_GUIDE §4, inside the database container. The M6 tree has no `pc_retention` role, so its `db bootstrap` ran without that flag. Secrets were written inside the container with mode 0600.
- **The closed-loop benchmark** ran from a copy of each tree's `packages/` placed where the test binary expects it, against the tree's database container. Each run creates its own database from the migrations.
- **The GitHub timing harness** was a temporary test file in `test/e2e`, never committed. It reuses the §43 stack (`start(t, options{github: true})`) and records `Server-Timing`.
- **What was not measured.**
  - The GitHub path under load.
  - A first hold's approval-request writes on the GitHub path.
  - Lock waits.
  - The origin of the two extra transactions per refund.
