# M1.5 latency measurements

**Date:** 2026-10-08. **Measured by:** Claude Code (founder session). **Target:** SIMULATED (`pantherclaw-sim payments`). No real money moved.

## Summary

| SLO (ARCHITECTURE §15) | Result on the development laptop |
|---|---|
| Authorize p99 ≤ 25 ms at 1k rps, 2 vCPU, co-located | **Not met.** Unloaded, Authorize is p50 ≈ 8–15 ms. Under sustained load the tail is dominated by stalls of up to 2 s (the gateway's timeout). At 1,000 rps the stack collapses into fail-closed `503`s. |
| Gateway overhead p99 ≤ 35 ms at 1k rps | **Not met at 1k rps.** p99 was 26.8 ms at 100 rps in a short healthy run. Sustained runs show the same tail stalls. |

**These numbers measure a laptop, not the design limit.** The SLOs remain unvalidated until a run on Linux with local NVMe. That run uses `pantherclaw-sim load --unique --facts-key-file …`, as in [M4.md](M4.md): since M3 the gateway accepts only PAP/1-signed requests, which k6 cannot produce, so `test/load/refund.js` only records how this baseline was measured.

The measurements still surfaced three design issues:
1. **Budget lock held across other writes.** The hot budget row was locked across unrelated writes. This is **fixed** in this slice: "budget last" now applies to every writer.
2. **Commit flush behind the row lock.** Every refund serializes **two** WAL flushes behind that row. [ADR-0015](../adr/0015-budget-settlement-off-the-hot-row.md) is **proposed**.
3. **No fast-fail.** Without a fast-fail lock timeout, a short stall cascades into timeouts. ADR-0015 is proposed for this too.

Money invariants held throughout every overload:
- After 27,494 reservations across 6 budgets, every budget row equals its budget ledger exactly.
- No budget is over its limit.
- Undeliverable outcomes ended `UNKNOWN` with the reservation **held** (1,369 permits).

| | |
|---|---|
| Laptop | Intel Core i7-11370H (4 cores, 8 threads), 31.8 GB RAM, Windows 11 Home 10.0.26300 |
| Shared load | The Claude desktop app, browsers and a VPN client were running. CPU was about 58% busy *before* any load. |
| PostgreSQL | 17.11 (Debian) in Docker Desktop 29.8.2 (WSL2 VM: 8 vCPU, 15.5 GiB). Defaults: `shared_buffers` 128 MB, `synchronous_commit` on, `wal_sync_method` fdatasync. |
| WAL flush | `pg_test_fsync` on the data volume: fdatasync **0.93 ms average** (about 1,070/s). Occasional much longer stalls are inferred from the results below. |
| Topology | Server (API + workers), gateway, `pantherclaw-sim payments` and the load driver on one machine. The Authority's pool has 20 connections. Logging is at info level (one line per RPC). |
| Load | `pantherclaw-sim load`: open loop, constant arrival rate, 5 s warm-up excluded, $1.00 refunds against a $10M budget. "authorize" and "gateway_overhead" come from the gateway's `Server-Timing`: overhead = total − target time. |

Two placements were measured:
- **W — Windows-native processes.** Postgres sits behind Docker Desktop port forwarding. A `SELECT 1` round trip takes p50 0.58 ms and p99 1.5 ms, and Authorize makes about 13 sequential round trips.
- **L — Linux binaries co-located.** The processes run in Postgres's network namespace (loopback), as in the SLO's "co-located". Disk and VM are the same.

## Results

All latencies are in ms. Status counts are gateway replies:
- 200 = accepted
- 409 = dispatch refused, usually because the permit expired while the call was stalled
- 502 = outcome not recorded or permit invalid
- 503 = Authority unreachable or timed out (fail closed)

### W — before the fix (budget row locked across the ledger and receipt writes)

| Rate | Duration | Statuses | Authorize p50 / p95 / p99 | Overhead p50 / p95 / p99 |
|---|---|---|---|---|
| 100 | 8 s | 799 × 200 | 8.28 / 11.84 / **14.21** | 16.83 / 24.05 / **26.80** |
| 100 | 30 s | 2,997 × 200, 2 × 503 | 10.97 / 1,084 / 1,292 | 22.54 / 2,797 / 3,049 |
| 1,000 | 30 s (747 achieved, 5,561 dropped) | 202 × 200, 24,164 × 503 | 1,747 / 1,971 / 1,997 | 3,881 / 4,239 / 4,376 |

The 30 s runs at 100 rps were healthy for about 10 s, then stalled. The server log shows Authorize durations reaching the 2 s gateway timeout. The timed-out calls left permits to expire, and the sweeper then held the budget row while releasing them one by one.

### Fix applied in this slice

- Each writer now touches the budget row only in its final statement: reservation in `Authorize`, commit or release in `RecordExecution`.
- A sweep releases each budget once with one aggregated `UPDATE`.

### L — co-located, after the fix

| Commit mode | Rate | Statuses | Authorize p50 / p95 / p99 | Overhead p50 / p95 / p99 |
|---|---|---|---|---|
| durable | 20 | 578 × 200, 14 × 503, 7 × 502 | 14.77 / 907 / 1,654 | 30.77 / 1,885 / 2,366 |
| durable | 50 | 1,480 × 200, 15 × 503, 4 × 502 | 14.43 / 1,395 / 1,856 | 32.13 / 2,699 / 3,231 |
| durable | 100 | 2,470 × 200, 27 × 503, 2 × 502 | 9.26 / 1,543 / 1,863 | 20.55 / 3,124 / 3,848 |
| durable | 300 | 8,994 × 503 | timeouts | timeouts |
| **diagnostic only:** `synchronous_commit=off` | 100 | **2,999 × 200** | 7.62 / 83.8 / **171** | 16.44 / 164.6 / **298.6** |
| **diagnostic only:** `synchronous_commit=off` | 1,000 | 29,480 × 503 | timeouts | timeouts |

The `synchronous_commit=off` runs were a **diagnostic only**:
- The setting was applied to `pc_app` on the local development database for those runs, then reset. The `pg_db_role_setting` table confirms the reset.
- It is not an acceptable production setting: a crash could lose a reservation whose permit was already dispatched (ADR-0015, "Alternatives").

The other L runs (durable commits) behave as follows:
- At 20 rps the Authority is under 5% utilized, yet the tail still reaches seconds. Isolated WAL flush stalls on the virtual disk, taken while the budget row is held, explain this.
- With flushes made asynchronous, 100 rps runs cleanly (p99 171 ms, still above the SLO).

So durable commits behind one hot row are the primary limiter here. Pool size, CPU sharing and about 25 SQL statements per refund are the next ones: even without flushes, 1,000 rps collapses on this laptop.

### Unloaded reference (W, after the fix, 10 rps, busy laptop)

Authorize 20.25 / 30.83 / 41.75 and gateway overhead 41.02 / 59.30 / 72.41 (p50 / p95 / p99). This is about 13 Authorize round trips at the Docker Desktop round-trip time above.

## What this means

- **The design is correct under overload.** It fails closed (503 or CANNOT_AUTHORIZE, never a dispatch without a commit), money invariants hold, and the T-011 (1,000 concurrent reservations) and T-024 tests pass in CI.
- **The performance model needs ADR-0015.** One durable flush per hot-row update and two hot-row updates per refund cap one budget at about `1 / (2 × flush)`, and a flush stall stops every request on that budget. ADR-0015 proposes:
  - Settle off the hot row, which halves the hot-row flushes.
  - A `SET LOCAL lock_timeout` of about 100 ms that turns contention into fast `CANNOT_AUTHORIZE`.
  - Escrow slots later, if one budget must exceed the single-row rate.
- **Round trips matter.** Authorize currently makes about 13 sequential statements. Pipelining them with pgx batches is a follow-up that helps on every network.
