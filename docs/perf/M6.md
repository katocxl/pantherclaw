# M6 latency measurements

**Date:** 2026-10-10. **Measured by:** Claude Code. **Target:** SIMULATED (`pantherclaw-sim payments`). No real money moved.

This is the measurement that G0 M6's exit criteria ask for, and the follow-up open since M3: `Authorize` and the gateway's overhead with the M6 path in place. The gateway now reaches the Authority only over mutual TLS (HR-181). Every request is PAP/1-signed and verified by the Authority (HR-021). The refund goes through a connection, its reviewed package and `BeginDispatch` with the outbound request. The layout follows [M4](M4.md).

## Summary

| SLO (ARCHITECTURE §15) | Result on the development laptop |
|---|---|
| Authorize p99 ≤ 25 ms at 1k rps, 2 vCPU, co-located | **Not met.** At 10 rps co-located, the median of five runs is p50 33 ms and p99 109 ms. The best run was p50 23 ms and p99 59 ms. At 50 rps two runs of five accepted every refund (p50 83 ms, p99 0.7–1.0 s), and the others collapsed into the gateway's 2 s timeout. At 100 rps every run collapsed. |
| Gateway overhead p99 ≤ 35 ms at 1k rps | **Not met.** At 10 rps the median of five runs is p50 56 ms and p99 192 ms; the best run was p50 38 ms and p99 95 ms. |

**What this measurement can and cannot show:**
- **It cannot validate the SLOs.** The laptop was shared with other Claude Code sessions, which were building and running their own integration and end-to-end suites throughout. At 10 rps the same binaries gave p50 from 23 to 87 ms from one fresh stack to the next. So only medians are reported, and nothing here compares M6 with [M4](M4.md)'s numbers. The co-located Linux/NVMe run on an idle machine is still needed, as in M1.5 and M4.
- **The database work per refund is stable, and that is the reliable result.** It took about **17 transactions per accepted refund**, the same as after ADR-0015 in M4 (17.3). mTLS and the M6 dispatch path added no database work per refund. The gateway's certificate check is one cached read per second (G0 M6 design decision 3), not one per call.
- **The money invariants held in every run, through every overload** (see below).

**Method.** Five runs, each on a fresh stack: a new container, `db bootstrap`, `migrate up` and `dev seed`, then the server, the simulator and the gateway. Each run made 10 rps (the first after start-up), then 50 and 100 rps on the same stack. The idle rate of database transactions was measured for 10 s just before the 10 rps run.

## Results

All latencies are in ms. Status 200 = accepted; 503 = the Authority did not answer within the gateway's 2 s timeout (fail closed, nothing dispatched); 403 = refused with a decision. The load driver does not record which decision; most likely `CANNOT_AUTHORIZE` `BUDGET_BUSY`, the 100 ms fail-fast on the budget row.

### Database transactions per refund

At 10 rps, about 350 refunds per run (warm-up included). The idle rate (31–42 transactions per second) is subtracted over the run's duration (about 36 s with the fact reports). These are approximations: the duration is the driver's, not measured on the database.

| Run | 1 | 2 | 3 | 4 | 5 | Median |
|---|---|---|---|---|---|---|
| Transactions per accepted refund | 17.2 | 17.0 | 17.0 | 17.1 | 16.1 | **17.0** |

- **This matches M4 after ADR-0015** (median 17.3), so the M6 path adds no database work per refund. A refund's work:
  - identity and run binding;
  - the evaluation's snapshot, which now also checks the connection;
  - the finalization;
  - `BeginDispatch` (which records the outbound request) and `RecordExecution`.

  The gateway's mTLS authentication reads the certificate's row at most once a second (design decision 3).
- **The idle rate is higher than M4's** (26–27 per second). The idle server now runs M7's verification, checkpoint and settlement jobs. The gateway's background calls add more: the containment stream, configuration sync, and claiming verification tasks every 10 seconds.

### Money invariants after the overloads

After every run, checked directly in the database:
- the task-budget account's `spent` equals the sum of its `COMMITTED` reservations, to the cent (for example 18,895.22 USD in run 3);
- nothing is reserved, and no reservation is `HELD` or still pending settlement;
- every permit ended `DISPATCHED` (470–2,397 per run) or `RELEASED` (122–491 per run), and none is left `ISSUED`, `DISPATCHING` or `UNKNOWN`.

The released permits are decisions the Authority finished after the gateway had given up (its 2 s timeout). They expired unused, and the sweeper released them: nothing was dispatched without a commit. None of them used an approval, so HR-011 restored nothing.

## Method notes

- **Starting a stack.** The secrets (database passwords, the KEK, the gateway's identity directory) are created inside the container with mode 0600, because bind-mounted Windows files fail the 0600 check. The commands are those of BUILD_GUIDE §4, run inside the database container:
  - `pantherclaw-server db bootstrap`, `migrate up` and `dev seed --gateway-out … --target-url … --workload-out … --facts-key-out …`;
  - `serve`, then `pantherclaw-sim payments`, then `pantherclaw-gateway serve --enroll-file …`.
- **What the load includes.** The gateway enrolls over the public API and then talks to the server's gateway listener over TLS 1.3 with its client certificate. The load driver gets a workload token from the server and signs every request.
- **Counting transactions.** Transactions are `xact_commit + xact_rollback` from `pg_stat_database` before and after each run.
- **What was not measured.** `BenchmarkRefund` measures the Authority in process, without mTLS or PAP/1, so it was not repeated here; [M4](M4.md) has its latest results. Lock waits were not sampled.
