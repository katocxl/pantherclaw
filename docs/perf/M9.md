# M9 latency measurements

**Date:** 2026-10-13. **Measured by:** Claude Code. **Target:** SIMULATED (`pantherclaw-sim payments`). No real money moved.

G0 M9 asks the exit to re-measure `Authorize` with the coverage claim (A6, HR-217): a decision receipt carries `pap.coverage`, the coverage snapshot current at decision time. The method follows [M8](M8.md): static Linux binaries in the network namespace of a private PostgreSQL container, the M8 exit and M9 side by side.

**Trees.** The M8 exit is #345 at `cb52913d`. M9 is the A9 top, #346 at `f60a3477` (the A stack and the receipt coverage claim). #346 has since moved to `b0aca12d`, with D7 and a narrower verify failure, which are not expected to change latency; it was not re-measured.

## Summary

- **With the claim present, a refund costs about what it did on M8.** At 10 rps, five rounds on fresh stacks, every M9 receipt in the measured runs carried a coverage claim.
  - The paired `Authorize` p50 difference (M9 − M8) has a median of **+3.5 ms (+5 %)**: +11.1, +5.2, +3.5, +0.8 and −2.8 ms.
  - The p99 differences go both ways (median −0.2 ms).
  - The gateway's overhead moved by +3.7 ms at p50 (median of the paired differences).
- **Without inventory** (no coverage scope, so no claim), M9 is also level with M8:
  - `Authorize` p50 has a median of +2.4 ms (+3 %);
  - `BenchmarkRefund` with 1 worker +0.03 ms;
  - with 8 workers, p50 −0.8 ms and p99 +14 ms (+4 %), both directions across rounds.
- **A refund takes about 1.8 more database transactions on M9** (≈ 20.4 against ≈ 18.6), with and without the claim. M9's decision path reads the coverage snapshot for the action's scope, and the coverage jobs (inventory, reassessment every minute, invalidations) run in the background.
- **No regression over 20 %.** One claim-present round (round 1) was 37 % slower at p50 (40.9 against 29.8 ms); the other four were within −5 % to +6 %.
- **The SLOs are still not validated** (ARCHITECTURE §15). At 50 and 100 rps both trees collapsed into the gateway's 2 s timeout on most rounds. The laptop is shared, and the Linux/NVMe run stays open, as in every milestone since M1.5.

## Machine and setup

As in [M8](M8.md):
- the same laptop (Intel Core i7-11370H, 4 cores, 8 threads, Windows 11), shared with other Claude Code sessions throughout;
- PostgreSQL 17 (`postgres:17-bookworm`, pinned digest), one private container per tree per round (`pc-w3-m8`, `pc-w3-m9`, removed afterwards);
- static Linux builds of each tree (server, gateway, simulator and load driver, and the `pgauthority` integration test binary), run inside the tree's database container;
- each tree's `dev seed` org and `deploy/dev` configuration, log level `warn`.

**How the claim is present.** `dev seed` creates no coverage inventory. A route enters it from gateway traffic: the inventory job reads the org's transactions a minute behind the clock, and the reassessment (every minute, `coverage.reassess_every`) then computes the scope's snapshot. So each claim-present round did the following, with no code or configuration change:
1. start both stacks fresh;
2. send 10 s of refunds at 2 rps to each;
3. wait until M9 had computed the snapshot of the refund's scope (85 to 105 s);
4. load both at the same moments.

The snapshot covers agent, connection and `payments.refund.create`, with state `PARTIAL`. M8 got the same priming and wait.

The newest decision receipt on one claim-present stack carried this claim (`pap.coverage` of its signed payload):

```json
{"v":1,"state":"PARTIAL","snapshot":"01a135ff-0f3e-774e-a478-3fc3286ed938",
 "scope":{"agent":"01a135fd-30d5-74fc-9bc1-e87c19f0bd3c","connection":"01a135fd-31b5-73ec-95e0-439b4d0c0790","operation":"payments.refund.create"},
 "snapshot_state":"PARTIAL","lapsed":false,"exclusions":[]}
```

In every round, `pc.decision_receipts` held 20 receipts before the 10 rps run (the priming, before the snapshot) and 370 after it. **All 350 new receipts referenced the snapshot** (`coverage_snapshot_id` set).

**Method.**
- **With the claim:** five rounds, each starting both stacks fresh and priming them as above, then `pantherclaw-sim load --unique --facts-key-file …` at 10, 50 and 100 rps on both at the same moments (30 s measured after a 5 s warm-up), counting the database's transactions around each run.
- **Without inventory:** five earlier rounds, the same but without the priming and the wait, so no scope existed and no receipt carried a claim. Then `BenchmarkRefund` (`-benchtime 1000x`, 1 and 8 workers), five rounds side by side; it creates its own database, so it has no coverage scope either.

## Method notes

- **Starting a stack, the benchmark and counting transactions** work as in [M8](M8.md).
- **The claim's presence** was checked in the database after each run:
  - `pc.decision_receipts.coverage_snapshot_id`;
  - one receipt's JWS payload, decoded (above).
- **What was not measured:**
  - a lapsed claim (an expired or invalidated snapshot), whose state is recomputed at decision time;
  - claims with exclusions;
  - more than one scope per org;
  - the coverage jobs' own cost, apart from the transaction counts.
