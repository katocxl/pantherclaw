# M13 performance measurements (local)

**Date:** 2026-10-27. **Measured by:** Claude Code with `task perf:m13` (`tools/scripts/perf-m13.sh`). **Target:** SIMULATED (`pantherclaw-sim payments`). No real money moved. **Tree:** `feat/m13-wave3-rest` on `main` at `f793d9c9` (M13 waves 1 and 2).

G0 M13 F7 asks for a fixed effort on performance, then published numbers with their conditions; v1.0 is not blocked on the PN-011 targets. These are **local numbers from the founder's shared laptop**. The staging numbers are pending: the same command runs on the staging VM once hosted staging exists (G0 M13 exit status, R-65).

## Summary

- **Authorize** (the decision transaction and the permit), measured by the load driver at the gateway, has a **p50 of 33–42 ms** at 10, 50 and 100 rps. Its p99 is 48–71 ms at 10 and 50 rps, and 282–315 ms at 100 rps. One round at 100 rps collapsed (p50 552 ms, every refund still accepted).
- On PostgreSQL alone (`BenchmarkRefund`, closed loop, no gateway or HTTP), Authorize's **p50 is 15–17 ms with 1 worker and 19–32 ms with 8 workers**. Throughput is 31–34 refunds/s with 1 worker and 113–211 refunds/s with 8.
- The **gateway's overhead** (everything the gateway adds before and after the target's own time) has a p50 of 53–65 ms. It includes the Authorize round trip over the mTLS control link.
- **Gateway memory:** RSS 40–46 MB after each run, high-water mark 52 MB. In the collapsed round it was 64 MB, high-water mark 69 MB.
- **No errors.** Every request was answered 200 (accepted), with no transport errors and no dropped requests. The server and gateway logs had no `ERROR` line.
- **M13 has no measurable cost on the decision path.** Side by side with the tree before M13 (`acf62ce3`), Authorize's p50 was 37.4 against 34.1 ms at 10 rps and 32.8 against 33.2 ms at 50 rps. `BenchmarkRefund` p50 was 19.6 against 16.9 ms (1 worker) and 26.6 against 20.5 ms (8 workers), in one concurrent round (below).

## Conditions

- **Machine:**
  - Intel Core i7-11370H (4 cores, 8 threads), 16 GB;
  - Windows 11 with Docker Desktop 29.8.2 on WSL2 (kernel 6.6.87.2), so the containers see 8 CPUs and 15.5 GiB;
  - shared with other Claude Code sessions throughout, as in every earlier milestone.
- **Database:** PostgreSQL 17 (`postgres:17-bookworm`, the digest pinned in `deploy/compose/compose.yaml`) in a private container (`pc-perf-m13`) with `max_connections=200`, `shared_buffers=256MB` and `--shm-size 256m`. The container is removed afterwards.
- **Binaries:** static Linux builds of this tree (`CGO_ENABLED=0 GOOS=linux go build -trimpath`) of the server, gateway and simulator, and the `pgauthority` integration test binary.
- **Network:** everything runs in the database container's network namespace, so PostgreSQL is on loopback (co-located) and Docker Desktop's port forwarding is not measured ([M8](M8.md)).
- **Server:** role `all`, log level `warn`, 4 job workers. API limits raised out of the way: the load driver's fact reports would otherwise count against them, and the gateway path is never limited.
  - The server, the gateway and the payments simulator all run on the same 8 threads.
  - The gateway enrolls with its one-time token and reaches the Authority over mTLS with a hybrid post-quantum key exchange (HR-395).
- **Data:** the `dev seed` org, its payments connection (`access none`), and a grant of up to 100.00 USD per refund with a 100,000,000.00 USD task budget.
- **Load shape:**
  - `pantherclaw-sim load --unique --facts-key-file …`: open loop, a distinct charge and amount per refund, each charge's refundable fact reported first;
  - 30 s measured after a 5 s warm-up, at 10, 50 and 100 rps, three rounds on one stack, with 5 s between runs;
  - `BenchmarkRefund`: `-benchtime 1000x`, 1 and 8 workers, three rounds, each on a fresh database.
- **Profiles:** `PROFILE=1` took a 15 s server CPU profile through the loopback admin listener (`admin.addr`, HR-382) during the first round at each rate.

Run it again with `go tool -modfile=tools/pins/task/go.mod task perf:m13`. `RATES`, `DURATION`, `BENCHTIME`, `ROUNDS`, `PROFILE` and `NAME` override the defaults. Results land in `bin/perf/out/` (git-ignored).

**How to read it:**
- The stack's latency is level, within the drift of this machine.
- The 8-worker benchmark is 30 % slower in this single concurrent round.
- That round ran while both stacks loaded the laptop. In the three dedicated rounds above, this tree's 8-worker p50 was 19.3 and 19.8 ms (and 31.8 ms in round 3), which matches the earlier tree's 20.5 ms. So it is not counted as a regression. Re-measuring it on the staging VM is the open item.

## Fixed-effort analysis

The CPU profile at 50 rps (round 1, 15 s) shows the server using about 1.2 cores:
- **Authority RPCs.** About 64 % of the samples are under the gateway's mTLS Authority handler, and about 38 % in `authority.(*Service).authorize`.
- **Database round trips.** About 34 % of the samples are inside tenant transactions (`db.(*Pool).InTenantTx`). The largest single parts of Authorize are the decision snapshot (`pgauthority.(*Reader).Snapshot`, 15 %) and binding the decision (`finalize.(*Authority).bind`, 15 %).
- **Waiting, not computing.** 47 % of the samples are the kernel and the scheduler waiting: `Syscall6` 31 % and `futex` 16 %.
- **No single CPU hot spot.** pgx query building and encoding together take about 7 %. The M13 additions (the rate limiter, the telemetry attribute filter, the security-event outbox) do not appear above 1 %.

**The time goes to sequential database round trips and to the shared machine's scheduling, not to computation in the server.**
- Authorize on PostgreSQL alone has a p50 of about 15 ms. Through the stack it is about 35 ms.
- The difference is the gateway's own work: verifying the workload token, the mTLS control round trip, and the facts and permit handling. It was the same before M13.

No code was changed for performance in M13. The fixed effort found no M13 regression and no safe local optimisation worth its risk before staging. The obvious next step is fewer round trips per Authorize (ADR-0015's direction). It should be measured on the staging VM first, because this laptop's drift (up to 5× between sequential runs, [M8](M8.md)) is larger than the effects in question.
