# M7 latency measurements

**Date:** 2026-10-11. **Measured by:** Claude Code. **Target:** none: the closed-loop benchmarks run the Authority against PostgreSQL in process; nothing is dispatched.

G0 M7 design decision 22 asks the exit to re-measure `Authorize` with what M7 adds to the decision path: one sealed insert per evaluation (the replay inputs, decision 11) and one insert per execution (the execution receipt's body). Everything else M7 does (verification, checkpoints, anchors, retention, packs) runs in the worker. The method follows [M6](M6.md) and [M4](M4.md): static Linux test binaries in the network namespace of a private PostgreSQL container, side by side.

## Summary

- **Keeping replay inputs adds about half a millisecond to `Authorize`.** In five rounds of `BenchmarkAuthorizeReplayInputs`, where every other refund goes through an Authority that records, seals and stores its inputs, the paired p50 difference has a median of **+0.54 ms (+6 %) with 1 worker and +0.78 ms (+5 %) with 8 workers**. The p99 differences are within the run-to-run noise.
- **The M6 numbers already include both writes.** [M6](M6.md) measured `82a710c` (M6 slice 23), whose server wires the replay inputs (`authority.Inputs`, #197) and keeps the execution receipt's body (#185): its open-loop result (`Authorize` p50 33 ms, p99 109 ms at 10 rps, the median of five fresh stacks) is the cost with M7's decision-path writes, on a busier day.
- **The rest of M7 since then changed nothing measurable on the decision path.** `BenchmarkRefund` at `82a710c` and at the M7 exit, side by side over seven rounds: with 1 worker, `Authorize` p50 8.68 and 8.63 ms; with 8 workers, the tip was slower in 4 of the 5 rounds where it ran second, and level in the 2 rounds where it ran first. The difference follows the order and the machine, not the code.
- **The SLOs are still not validated** (ARCHITECTURE §15): the laptop is shared with other Claude Code sessions, and only side-by-side runs compare. The Linux/NVMe run stays open, as in M1.5, M4 and M6.

## Machine and setup

| | |
|---|---|
| Laptop | Intel Core i7-11370H (4 cores, 8 threads), Windows 11 Home 10.0.26300, the same machine as M1.5, M4 and M6 |
| Shared load | Other Claude Code sessions were building and testing on the same laptop, with their own PostgreSQL containers running. The machine was visibly quieter during rounds 6 and 7. |
| PostgreSQL | 17 (Debian, the compose image `postgres:17-bookworm`, pinned digest), a **private** container (`pc-m7x-perf`, removed afterwards) in Docker Desktop. Defaults (`synchronous_commit` on, `shared_buffers` 128 MB), `max_connections` 200. |
| Binaries | `go test -c -tags integration` of `internal/authority/adapters/pgauthority`, `GOOS=linux CGO_ENABLED=0`, for two trees: `82a710c` (the code [M6](M6.md) measured) and the M7 exit branch. Each runs in `docker run --network container:pc-m7x-perf`, so the database is on loopback, and creates its own database from the migrations. |
| Benchmarks | `BenchmarkRefund`: `Authorize`, `BeginDispatch` and `RecordExecution` against one task budget, settled once a second as the sweep job does; 1,000 refunds with 1 worker, then with 8. Its Authority keeps no replay inputs in either tree. `BenchmarkAuthorizeReplayInputs` (M7 exit tree only): the same refunds, every other one through an Authority that records, seals (AES-256-GCM under the org's `evaluation_inputs` key) and stores its inputs, so drift of the machine affects both halves alike; 1,000 refunds per worker setting. |

**Method.** Rounds 1–5 ran `BenchmarkRefund` at `82a710c`, then at the M7 exit, then `BenchmarkAuthorizeReplayInputs`. Rounds 6 and 7 ran `BenchmarkRefund` in the reverse order (the M7 exit first), to see the effect of running second. About eleven minutes of measuring in all. Medians are of the rounds; `Authorize` p50 / p99 in ms.

## Results

### Replay inputs: `BenchmarkAuthorizeReplayInputs` (M7 exit)

| Round | 1 worker, without inputs | 1 worker, with inputs | 8 workers, without | 8 workers, with |
|---|---|---|---|---|
| 1 | 9.25 / 48.00 | 9.82 / 55.40 | 15.59 / 58.30 | 16.55 / 61.00 |
| 2 | 9.03 / 39.23 | 9.57 / 32.62 | 16.49 / 95.83 | 17.29 / 96.60 |
| 3 | 8.97 / 32.72 | 9.52 / 30.53 | 13.29 / 49.07 | 13.67 / 69.30 |
| 4 | 9.21 / 21.00 | 9.64 / 22.70 | 16.04 / 73.41 | 16.82 / 87.09 |
| 5 | 8.22 / 14.21 | 8.69 / 17.38 | 12.97 / 30.24 | 13.68 / 31.15 |
| **Median** | **9.03 / 32.72** | **9.57 / 30.53** | **15.59 / 58.30** | **16.55 / 69.30** |

- **p50 is higher with inputs in every round**: by 0.43–0.58 ms with 1 worker (median of the paired differences +0.54 ms, +6 %) and by 0.38–0.96 ms with 8 workers (median +0.78 ms, +5 %). That is the recording reader, the sealing, and one more insert in the finalization's transaction.
- **p99 moves both ways** with 1 worker (from −6.6 to +7.4 ms) and is 0.8–20 ms higher with 8 workers (median +2.7 ms); a tail this noisy on a shared laptop supports no figure.
- **No extra transaction**: the row is written in the finalization's own transaction, with its receipt.

- **With 1 worker the two trees are the same**: p50 within 0.35 ms in every round, and the same refunds per second.
- **With 8 workers the build that ran second did worse** in rounds 1, 3, 4 and 5 (the M7 exit ran second there), and the two were level, within 4 %, in rounds 6 and 7, where the M7 exit ran first. So the medians' gap (222 against 271 refunds per second) is the order and the machine, not shown to be the code.
- **What changed on the path since `82a710c`:** step 8's check that the connection serves the verifier's read and the `verify(level)` obligation (#226), the triggers that guard evidence rows' bodies (#229; on insert they only check that a new row is not marked removed), the gateway's captures in `RecordExecution` (#231; none here) and, in the exit PR, the `UNVERIFIABLE` effect receipt for writes nothing can verify (none here: the refund has a verifier).

## What was not measured

- **Open-loop through the gateway.** [M6](M6.md)'s open-loop runs (`pantherclaw-sim load`, full stack, mTLS and PAP/1) already had M7's decision-path writes, and on this laptop separate runs differ up to four times; a new single stack would compare with nothing. The closed-loop A/B above isolates the change.
- **The execution receipt's body on its own.** It is one insert in `RecordExecution` (not in `Authorize`), present in both trees since #185, so `BenchmarkRefund`'s refunds per second include it on both sides.
- **The worker's evidence jobs** (verification, checkpoints, anchors, retention, packs): they run outside the decision path, and decision 20 keeps authorization from ever waiting for them.
- **Row sizes of the sealed inputs** (the brief estimated 1–4 KiB per decision).
