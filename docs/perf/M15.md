# M15 MCP tools/call latency: before and after server-backed state

**Date:** 2026-10-29. **Measured by:** Claude Code. **Target:** SIMULATED (`pantherclaw-sim payments`). No real money moved.

G0 M15 D15 asks for the p50 and p99 of an MCP `tools/call` before and after D14. Before D14, the gateway kept its MCP holds, tasks and sessions in its own memory. After D14, it keeps them on the server through `GatewayService` (D12). A `tools/call` that carries no action id now makes one `GetMCPState(HOLD)` call before the Authority is asked. A held call also makes a `PutMCPState`. None of the calls measured here is held, so the "after" path adds exactly one gateway-listener RPC and one database transaction per call.

## Summary

| 5 rps, 60 s, 3 rounds side by side | Before D14 (`2d410697`) | After D14 (`feat/m15-gateway-state`) |
|---|---|---|
| Accepted | 897 of 897 | 897 of 897 |
| p50, median of 3 rounds | 84.36 ms | 91.21 ms |
| p99, median of 3 rounds | 719.10 ms | 757.79 ms |
| Paired p50 difference per round | — | +6.9, +20.6, +8.4 ms |

- **The extra cost is one state lookup per call.** In each round, after was slower than before by 7–21 ms at p50 and 36–153 ms at p99. That matches one more mTLS RPC and one more short database transaction on this machine.
- **Absolute numbers are not SLO evidence.** Both stacks ran in-process at the same time on a laptop that other Claude Code sessions were also loading (see [M6](M6.md) for why such numbers vary). Only the paired difference between "before" and "after" is meaningful here.

| | |
|---|---|

| Before | `origin/main` at `2d410697`, plus only the load driver's `--mcp` mode (`internal/sim/load.go`) and `test/e2e/m15_perf_test.go` copied in. |
| After | This branch at `7ff48b32`: the same test and driver. |
| Load | `TestPerf_M15_MCPToolsCall`, which runs `pantherclaw-sim load --mcp --unique --facts-key-file …`: an open loop, 5 s warm-up, then 60 s measured. Each request is a PAP/1-signed 2026-07-28 `tools/call` of `create_refund`, sent to `/mcp/payments` without an action id. Each refunds a distinct (charge, amount). The MCP face sends no `Server-Timing`, so only the client's total is measured. |

**Method.** The before and after runs started at the same moment, one per round, for three rounds. To reproduce a round, run both of these at the same time:

```bash
PC_PERF_M15_OUT=/tmp/after PC_PERF_M15_RATES=5 PC_PERF_M15_DURATION=60s go test -tags integration -count=1 -run TestPerf_M15_MCPToolsCall -v ./test/e2e/
```

The second command is the same, run from a checkout of the "before" commit with the two files copied in.

### 10 and 25 rps: overloaded, not comparable

A first set of rounds ran at 10 and then 25 rps, again with two stacks at once. At 10 rps every call was accepted, but p50 ranged from 236 ms to 3.1 s from one round to the next in both variants. At 25 rps both variants collapsed: up to 97% of calls came back as tool errors, most likely because the Authority did not answer within the gateway's timeout and the gateway failed closed. These rounds measure the machine, not D14, so they are left out of the summary. The raw logs were kept with the measurement notes.

## Not measured here

- **Held calls and task polls.** These add a `PutMCPState`, plus a compare-and-set per poll. They are rare next to plain calls, and each one waits for a person anyway.
- **Sessions (2025-11-25).** Each request makes one `GetMCPState(SESSION)`. Its last use is written at most once a minute.
- **A co-located Linux run on an idle machine.** As with M6, this is still needed before these latencies can be compared with the SLOs.
