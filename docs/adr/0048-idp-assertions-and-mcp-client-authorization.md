# ADR-0048 — IdP assertions and MCP client authorization

**Status:** Accepted (2026-11-01; G0 M26 design decisions D400–D409, the rulings D527, D528, D534, D535, D540, D542, D544, D559 and D560, founder decisions H4, H7 and H8; the [G0 M26](../g0/M26.md) brief records them). Amends [ADR-0039](0039-delegated-administration-org-identity-providers-and-key-service.md) point 2.

**Context.** Enterprises want agent access granted in their identity provider and enforced per task by PantherClaw. Okta Cross App Access uses ID-JAG assertions, and ID-JAG is still an IETF draft. Standard MCP clients expect the MCP 2026-07-28 authorization flow, and they hold bearer tokens, not PAP/1 proofs. Two rules stand in the way of the easy answer. HR-146 says a token proving who is represented never creates or widens a grant. ADR-0039 point 2 covers organization identity providers for sign-in only, and an assertion issuer is a new way for an organization to bring trust in from outside.

**Decision.**
1. **An assertion uses or narrows an existing grant, and never creates one** (D400, D408, H8, HR-620, HR-621). The port is `AssertionVerifier`, and the adapter `adapters/idjag` names the draft revision (draft-06). It enters through jwt-bearer at the shared token endpoint. `iss+sub` maps to a user, and `client_id` maps to an enrolled agent by a pinned binding (HR-140). The run's principal source is `id_jag`. The scope is intersected with an existing active root grant and held on the run; no grant row is written. With no matching grant it is refused `NO_GRANT`, and several matching grants are refused unless the scope names one.
2. **Assertion issuers, client bindings and MCP clients need two people** (D401, D408, H8, HR-622..624). Each is a two-person protected change under CUSTODY in every protect mode, made by a person, with every org admin told; disabling or removing is immediate. Discovery is HTTPS through the egress guard, the audience is pinned, and an issuer's URL, audience and tenant are fixed once ACTIVE. jwt-bearer needs `private_key_jwt` from an admitted instance of the bound agent. **This amends ADR-0039 point 2:** that point dealt with identity providers people sign in through, and it now also covers organization entries that vouch for agent access. They are separate records with the same protection. Sign-in providers are otherwise unchanged.
3. **Standard MCP clients get an opt-in route with a weaker proof** (D402, D408, H8, HR-625..628). `internal/gateway/mcpauth` is off by default per organization, with RFC 9728 metadata, the issuer check, RFC 8707 audience and Client ID Metadata Documents. An allow-listed client acts through its own `mcp_client` instance, whose key no one holds, at level 0. The token is `pap-mcp+jwt`, valid for 5 minutes, for one gateway server, re-verified by the Authority on every call (HR-021), and bearer mode comes from the token type alone. Policy sees `workload.proof == "bearer"`, which never satisfies an attestation requirement. The code flow needs PKCE S256 and a person's consent; refresh tokens rotate and end with the run, and a reused code or refresh token ends the run. An allow-list entry keeps the confirmed client document: a changed one is refused `CLIENT_DOCUMENT_CHANGED` until a second person takes it (D542, D560). PAP/1 routes are unchanged.
4. **Provisioning code stays private, its data does not** (D405, D406, D409, D527, D528, H7, HR-629..634). Tables and ports are in public core; the code is in a private package with `pantherclaw-server-ee`, under the extension prefixes (HR-341). A SCIM token is a hash, bound to one issuer, and inert until a second person activates it. A group never carries a role that binds roles or Emergency Responder (R-08), and mapping changes are two-person changes. Deprovisioning works in every edition, ends sessions, and keeps API keys active as owned findings. A SAML connection is an organization identity provider; sign-in is SP-initiated with a signed assertion.
5. **SaaS agents are listed, not controlled** (D407, D534, D535, HR-635..639). Metadata only, never conversations. A run that could not read something says not scanned, never none found. Found agents land DISCOVERED and observe-only, with an `external` mark and no key path, and naming an owner sets the owner only.

**This is not ADR-0018's token-exchange service.** ADR-0018 rejected a full token-exchange service that issues downstream tokens, because connectors already mint narrow provider-native tokens. M26 keeps that rejection:
- an assertion comes in from the customer's IdP and proves who is asking; it grants nothing, as with a subject token (HR-146);
- PantherClaw issues no token for any downstream provider, and connectors still mint those per action;
- `pap-mcp+jwt` is good only at one PantherClaw gateway server, for 5 minutes, and the Authority still decides each call.

**Consequences.**
- The IdP can only reach what a PantherClaw grant already allows, so an IdP-side grant with no matching PantherClaw grant fails with `NO_GRANT`. Customers must set up both.
- ID-JAG can change without touching the rest of the code, since the draft stays behind one adapter.
- Bearer tokens are weaker than PAP/1 proofs: a stolen token works from anywhere for up to 5 minutes at one server. Audience, lifetime, the policy check on each call, revocation when the run ends and the attribute policy can refuse are what limit it (R-69).
- R-08 stays accepted: a customer's IdP admin can still act as the people they control, create identities that look like distinct people, and change groups with no second person. An assertion or a group gives such an admin nothing a grant or a non-admin role does not already allow.
- A deprovisioned person's API keys stay active until someone rotates or revokes them; the posture queue shows each one.
- The `00291` Down migration refuses, deleting nothing, while evidence still refers to its runs or instances.
- All of this is tested on a simulated IdP and synthetic fixtures. The real tenant checks stay pending (F801).

**Alternatives.** Assertions that create grants (breaks HR-146, and hands authority to the IdP); a token-exchange service that issues downstream tokens (ADR-0018); treating a bearer client as attested (F801); trusting keys in a client metadata document (D408); organization issuers under the organization's protect category (the same reason ADR-0039 gave for sign-in providers); a new enterprise repository (H7); group mappings to admin roles (R-08 would get worse); revoking a deprovisioned person's API keys automatically (D409).
