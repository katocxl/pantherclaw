# ADR-0061 — Cloud agent runtimes

**Status:** Proposed (2026-11-05, with the [G0 M34](../g0/M34.md) brief, which records the founder decisions FQ34-1..5 and the coordinator decisions D990–D1002a). The body was completed on 2026-11-06 with M34's tests (Phase B). Runbooks: [agentcore.md](../runbooks/agentcore.md), [runtime-discovery.md](../runbooks/runtime-discovery.md), [aws-ssm.md](../runbooks/aws-ssm.md).

**Context.** Agents now run inside cloud runtimes: Amazon Bedrock AgentCore, Google Vertex AI Agent Engine and Azure AI Foundry. The runtime runs the tools itself, so no call passes a PantherClaw route by itself. AgentCore offers a request interceptor, a Lambda invoked synchronously before each target, whose answer either passes the request on or answers it. Vertex has no gateway hook, only ADK's in-agent `before_tool_callback`. Foundry hands MCP approvals (`mcp_approval_request`) to the client app. Agents can also be deployed into these runtimes without anyone in the org seeing it, and agents can reach cloud machines through SSM or Azure Run Command.

Two questions need answers (D1205). Agent identity protection: is this really that runtime's gateway, and for whom does it act? Runtime firewall: may this agent run this tool, here, now?

**Decision.**

*Agent identity protection.*
1. **One agent per AgentCore gateway, proven by its AWS role** (HR-761, HR-765, HR-766; founder decision FQ34-2; D992, D994a, D995). The interceptor Lambda (`cmd/pc-agentcore-interceptor`, standard library only) makes an Ed25519 workload key in memory at cold start and never writes it. It enrols with `aws_iam` attestation, a GetCallerIdentity request signed with the Lambda role's own credentials, through an auto-admitting issuer entry bound to the gateway's agent. It renews its token and starts its run with `RuntimeService.StartRuntimeRun` (`workload.run`), which admits only an L2 instance enrolled by `aws_iam`, `gcp_workload`, `azure_mi` or `entra_agent_id` attestation whose issuer entry has a run grant (`RUNTIME_NO_RUN_GRANT`, `RUNTIME_RUN_GRANT_PRINCIPAL`), and reuses the workload run path of `StartPodRun`. The run is named `agentcore:<function>:<log stream>`, with characters outside `[A-Za-z0-9._:/-]` replaced by `-` (D995a), and is audited as `runtime.run_started`.
2. **The account match** (HR-765; D994a). Before the pipeline, the Authority refuses an action on channel `runtime` unless its connection has a runtime target, its run was launched by an `aws_iam` issuer entry, and that entry's bound account is the 12-digit account in the target's gateway ARN (`RUNTIME_ACCOUNT_MISMATCH`, with an agent-safe sentence). The check reserves nothing and starts no transaction, and records no new pipeline step.

*Runtime firewall.*
3. **A `runtime` channel** (HR-760; D990). "A cloud agent runtime's gateway asked before it ran the tool itself." It is cooperative: coverage is PARTIAL, and finalize reports DELEGATED, as for `authzen`. In dispatch a runtime action always goes to `delegate` (BeginDispatch, RecordExecution DELEGATED) and is never forwarded upstream; an allow carrying obligations is refused, since the runtime runs the call as asked. Content signals scan it, because the gateway holds the exact arguments. `Mapper.Runtime` maps a call through the package's `channel: mcp` mappings with the channel stamped `runtime` before canonicalization.
4. **AgentCore through the customer's own gateway** (HR-762, HR-764, HR-765; founder decision FQ34-1; D991, D994). The interceptor posts each event with PAP/1 to the customer's gateway at `POST /runtime/agentcore` (routed before the HTTP proxy, any `Origin` refused, at most 1 MiB, header `PC-Runtime-Gateway` an AgentCore gateway ARN), never to the server, so raw tool arguments stay in the customer's network. `tools/call` splits its name on the first `___` into target and tool and is decided through the one connection this gateway serves whose `runtime_target` is `agentcore:<ARN>/<target>` (`RUNTIME_TARGET_UNKNOWN` otherwise, also when two match). A runtime target is set only on a kind `mcp` connection with custody `agent_held`, unique per org, by `connections.manage`, audited. `initialize`, `ping`, `tools/list` and `notifications/*` pass undecided; any other method gets JSON-RPC -32601 (`RUNTIME_METHOD_NOT_DECIDED`); an HTTP target's event is refused (`RUNTIME_HTTP_NOT_SUPPORTED`). Only an action recorded as delegated passes, as `transformedGatewayRequest` with the original body; a deny or hold is a `transformedGatewayResponse` tool error, a hold saying "held for a person's approval in PantherClaw; ask again after". Refusals before an answer are plain JSON with a non-200 status, and `PC-Run-Ended: 1` makes the interceptor start a new run (D994b).
5. **The interceptor fails closed** (HR-766; D995). Any error — no enrolment, token or run yet, the gateway unreachable, a non-200 or unreadable answer, the deadline of min(Lambda deadline − 500 ms, 8 s), an event over 1 MiB — answers "PantherClaw cannot decide this tool call, so it does not run". It never logs tool arguments. `--local ADDR` serves `POST /invoke` for the simulator and tests.
6. **ADK and Foundry helpers** (HR-767; D996). `pantherclaw_adk.before_tool_callback` (`integrations/google-adk`, Apache-2.0) asks `/sdk` before each ADK tool, Vertex AI Agent Engine included, and returns a refusal dict on anything but an allow. `pantherclaw.foundry.FoundryApprovals` answers `mcp_approval_request` items and the classic `submit_tool_approval` shape with approve true only on an allow; an unknown `server_label`, unreadable arguments, a hold or any error answer approve false.
7. **Deploy and admin-command operations** (HR-525, HR-763; founder decision FQ34-4; D993, D993a, D1002, D1002a). `pc.vertex-agent-engine` (`vertex.reasoning_engine.create`, `.patch`) and `pc.azure-foundry` (`foundry.agent.create`, `.update`) deploy through `agent.deploy` operations; `pc.aws-ssm` (`aws.ssm.send_command` with the literal AWS-RunShellScript, `aws.ssm.send_powershell_command` with AWS-RunPowerShellScript, one EC2 instance) and `pc.azure-compute` (`azure.vm.run_command`, a closed command id) run commands through `code.execute` operations. Each is irreversible, reviewed and named by no template grant; commands or a script are at most 8192 bytes. An AWS package may name up to 3 more exact ARNs in `aws_extra_resources` beside `aws_resource`, under the same reference rules: the session is one action on exactly those ARNs, never a wildcard. `pc.aws-agentcore` is reads only (runtimes, gateways, targets) through a closed aws-rest route table: create and update need `Resource "*"` or `iam:PassRole` on a role taken from a parameter, which HR-525 does not allow.
8. **Daily discovery** (HR-768, HR-769; founder decisions FQ34-3, FQ34-5; D997, D997a). AgentCore runtimes, Vertex reasoning engines and Foundry agents are read through the gateway with the D993 packages' read-only collector credentials, each scan's tenant checked against the connection (the sealed role's account, the regional host's location, the base URL's project). A person sets a daily schedule (`SetSaaSScanSchedule`, audited); an hourly job starts each schedule at most once per 20 hours with origin `schedule`, as the schedule's person, and skips it (`pc_saas_schedule_skipped_total`) when that person is no longer an active member holding `agent.manage`. `pclaw discover scan` schedules the runtime sources daily by default. The `pc.runtime.agent_deployed` detection (LOW, atlas AML.T0103) alerts only on a newly found runtime agent; AgentCore deploys are seen this way rather than decided in M34.

*Both.* The threat map gains `prevent.agent_deploy` (AML.T0103) and `prevent.cloud_admin_command` (T1651), surface GATEWAY, ALWAYS; AML.T0103 is also detected through `pc.runtime.agent_deployed`. The runtime face adds no control row: the per-operation controls apply to channel `runtime` as PARTIAL.

**Consequences.**
- The interceptor is cooperative (PARTIAL): a customer can remove it from the AgentCore gateway, and calls through a gateway without it are not decided (R-82). Discovery lists runtimes, not whether a gateway has the interceptor configured; gateway discovery is a follow-up.
- Callers of one AgentCore gateway are not told apart: grants are per connection and target (R-83). Per-caller identity comes later.
- ADK and Foundry decisions happen in customer code; code that drops the helper is not decided (R-84).
- The Foundry and AgentCore API shapes, and the SSM and Run Command shapes, are checked only against simulators until live checks (R-85).
- AgentCore deploys are seen after the fact by the daily scan, not held before; deciding them needs wider AWS sessions than HR-525 allows.
- A schedule runs with the connection's credential after its person stops watching it (T-349): it stops when the person leaves, and skips are counted.
- AML.T0103 and T1651 leave Unaddressed on the threat map.

**Alternatives.**
- The interceptor calling the PantherClaw server directly (FQ34-1 chose the customer's gateway, so arguments stay in the customer's network).
- Per-caller identity in AgentCore (FQ34-2 left it for later; the interceptor event has no caller identity to prove).
- The account match in the gateway or in the pipeline (D994a put it in the Authority's handler, before the pipeline, so it needs no recording or pipeline Version change).
- Discovery only when a person starts a scan (FQ34-3 chose daily).
- A wildcard or several actions per AWS session for SSM (FQ34-4 chose one action on up to 3 more exact ARNs).
- Deciding AgentCore deploys in M34 (FQ34-5 left them to the daily scan and alert).
