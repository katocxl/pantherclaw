# ADR-0030 — Web console, hosted split and extension point

**Status:** Accepted (2026-10-20; G0 UI founder decisions F1, F2 and F10, with the plan confirmed as written (F13); the [G0 UI brief](../g0/UI.md) records them). Amends [ADR-0007](0007-licensing-bsl-apache-split.md) on where the extension interfaces live, and supersedes the BUILD_GUIDE plan of a Next.js console.

**Context.** Until now PantherClaw had no web console: people worked through the API and `pclaw`, and the only HTML was a set of server-rendered pages (sign-in, account, approval and confirmation pages) under a strict content security policy. The founder decided (F1) that PantherClaw hosts the control plane and the console while customers run the gateway and `pclaw` (the hybrid deployment, PN-010.3), and (F2) that the website, the console, billing and cloud operations are built in a separate private repository: the commercial distribution built from the core plus the extension point. Three questions followed: how a private build adds a console and extra routes to the public server without the public repository naming private code; how a browser console calls the Connect API, which accepts only bearer credentials and serves no CORS; and which web stack can meet the core's content security policy.

**Decision.**
1. **An extension point in the core** (`internal/extension`; HR-341). A `Set` carries an optional built console (a file system with `index.html` at its root), a `Mount` function returning extra routes, and a `Validate` function run at start-up whose error stops the server (`DEPLOYMENT_CONFIG`). Every extra route declares its authentication (none, session, or session with the CSRF checks) and must sit under `/v1/ext/` or `/app/ext/` (the console mount reserves `/app/ext/` for extensions); any other pattern, one that would shadow a core route, or a session-only route that serves anything but GET or HEAD (state-changing routes must use the CSRF checks) is a start-up error. Routes without authentication get a default body cap and a per-address rate limit. With an extension present, the `deployment` setting must be explicit. Extensions receive narrow dependencies (logger, clock, public URL, deployment, a plan writer, an account reader, billing links, an authorizer whose `Require(ctx, permission)` runs the core's own permission check for the request's session principal, and an audit recorder whose `Record` writes `billing.*` events to the core's audit ledger in the organization's tenant transaction; billing actions require the new permission `billing.manage`, held by Org Admin by default) and a `PrincipalFrom(ctx)` helper; ids are strings so the interface stays stable. The package lives at `internal/extension`, not `internal/platform/extension` as ADR-0007 and IP_PROTECTION first said, because it names core domain types (plans, accounts). The server command line moves to `internal/servercli.Main(args, ext)`; `cmd/pantherclaw-server` passes an empty set, so self-hosted behaviour is unchanged, and the commercial binary passes its own.
2. **The console is mounted by the server** (HR-340, HR-345). With a console in the set, `/app/` and `/app/*` serve the bundle with a fallback to `index.html` (no-store), hashed assets are cached as immutable, and every response carries the console policy: `default-src 'none'`; scripts, styles, images, fonts, connections and the manifest from `'self'`; `form-action 'self'`; `frame-ancestors 'none'`; `base-uri 'none'`; `require-trusted-types-for 'script'`; `trusted-types 'none'`. `/` redirects to `/app/`, and `/app` return paths are accepted only as same-origin paths. No Node.js runs in production and there is no cross-origin traffic.
3. **Browser sessions on the Connect API** (HR-342..347; the CSRF review G0 M5 deferred). The existing session cookie (`__Host-`, SameSite=Strict, HttpOnly) is accepted on Connect calls only with same-origin Fetch Metadata (or, when the header is absent, an `Origin` equal to the public origin), the header `PC-CSRF: 1`, method POST and a Connect content type. Cookie-authenticated GET calls are refused, no CORS is served, and a request carrying both a bearer credential and a cookie is refused (`AMBIGUOUS_CREDENTIAL`). The operations stream accepts the cookie under the same checks, never a credential in the URL. Idle refresh, the step-up rule (HR-156) and auditing (`credential_type=browser_session`) apply as for server pages. `WhoAmI` reports the deployment, the session kind and the account id.
4. **The console is a Vite single-page application** in the commercial distribution, using generated Connect clients over Connect JSON; the build has no inline script or style, no `eval`, and inlines no assets. A Next.js static export cannot meet `script-src 'self'` (it emits inline scripts, and nonces need dynamic rendering); the static website, which serves no session, keeps a static-site framework with hashed inline scripts.
5. **Libraries** (F10): free component and animation libraries and original designs only; nothing from a paid component library, and no component recreated from paid previews. Their licences are listed as named exceptions in the commercial distribution's dependency policy (R-47).

**Consequences.**
- The public repository stays generic: it never imports or names private code; tests use a fake console file system and fake extension routes.
- OWASP ASVS V3 moves to L2 for the console and the approval page; the new attack surfaces are cookie-authenticated Connect calls, the console origin and the extension routes (T-160, T-161, T-168).
- The server confirmation pages stay canonical in this phase; the console links to them on the same origin. Re-implementing them in the console is a follow-up.
- The commercial build pins the core at an exact commit and is rebuilt on purpose when the core changes.

**Alternatives.** A separately hosted console calling the API cross-origin with CORS and bearer tokens in the browser (token theft through XSS, a CORS policy to get right); a Next.js console (cannot meet the strict policy statically); plug-ins loaded at run time (a larger attack surface than a compiled-in set); keeping the extension interfaces under `internal/platform` (they need domain types the platform layer may not import).
