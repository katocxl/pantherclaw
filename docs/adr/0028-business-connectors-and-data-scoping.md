# ADR-0028 — Business connectors and data scoping: Stripe test mode, structured Postgres, scope obligations, Slack bot cards

**Status:** Accepted (2026-10-17; G0 M14 founder decisions F3–F6, answered with the recommended option; the [G0 M14 brief](../g0/M14.md) was approved with the founder's go-ahead the same day)

**Context.** Until M14 PantherClaw's reviewed packages cover coding work (GitHub, shell) and a payments simulator. The first business systems agents touch are payments, a customer database and the team chat. Each raises a question the existing model does not answer. Stripe speaks form-encoded requests with integer minor units, and a test key and a live key look alike to a generic HTTP connection. A database connector that accepts SQL text cannot be reviewed: any string the agent writes becomes the action. Reads raise a problem that writes do not: the decision says *whether* an agent may read, but the risk lives in *which* records and fields come back (F101–F103). And approvals by chat are only safe if nothing in the chat can decide (F164–F167), while agents posting to chat can leak data to people outside the organization.

**Decision.**
1. **Request formats are rebuilt, never passed through** (HR-300, HR-301). HTTP mappings and dispatch gain a `form` encoding with one strict parser (Stripe bracket syntax, depth at most 3, duplicate and mixed keys refused) and an outbound rebuild from ActionIR references only. Money can be dispatched in minor units by a fixed currency-exponent table; any other currency is refused. Definitions can pin literal static headers, require a success field in the answer, and declare a credential pattern that the gateway checks on the opened credential before sending anything.
2. **Stripe is test mode only** (F5, HR-303..306). `pc.stripe` covers refunds, payment intents and transfers. Every write is refused before sending unless the opened credential is a test key (by pattern); the refundable fact refuses a refund on a live-mode payment; any answer or verifier read that reports live mode records a security event, notifies the admins and opens the connection's circuit until an admin closes it; idempotency keys are `pc-<transaction>`; effects are verified against Stripe's object states with settlement-aware pending; the refundable amount comes from a fresh gateway read; transfers to a payee whose bank details changed within 7 days, or whose change cannot be read, are a consequence that holds them. A Stripe-shaped simulator backs CI; a live test runs on real Stripe test mode.
3. **Postgres reads are structured, not SQL** (F3, HR-307..309, HR-312). A `postgres` connection carries an admin-written manifest of tables, columns, types and classes. The agent sends structured requests (columns, typed filters, order, limit; or group-by and measures); the gateway builds parameterised SQL from the manifest only and runs it in a read-only, repeatable-read transaction with statement, lock and idle timeouts, row and byte caps, always rolled back, on a pool whose sessions default to read-only. The connection test refuses roles that can write. Aggregates suppress groups smaller than a minimum size and limit measures by column type and class. A manifest is proposed until an Org Admin confirms it on a confirmation page with a step-up, and so is every widening, while the current manifest keeps serving. Only one gateway package (`internal/gateway/pgtarget`) may hold a client for a customer database; the gateway still has no access to PantherClaw's own database ([ADR-0002](0002-control-plane-and-gateway-split.md) note).
4. **Data scope is an obligation the gateway enforces, or the call is refused** (F101–F103, HR-302, HR-310, HR-311). Grants can bound reads by record (a key and exact ids) and by data class (`public`, `internal`, `pii`; `secret` can never be allowed); rules can only tighten. The Authority turns the intersection into obligations on the decision. The gateway enforces them on gateway-held reads: a mandatory record predicate for Postgres, redaction of disallowed classes in rows and declared JSON paths, `secret` always withheld, and an answer it cannot parse withheld from the agent. Where an obligation applies but the route cannot enforce it (SDK, hook and AuthZEN channels, agent-held connections, definitions that do not declare scoping), the decision is CANNOT_AUTHORIZE `SCOPE_UNSUPPORTED`. Scoping is Team edition; existing scope keeps being enforced after a downgrade.
5. **Slack approvals are notifications with a link, never a decision surface** (F4, HR-313..315). A `slack_app` channel uses a bot token, sealed and sent only to four Slack Web API methods; the channel stays pending until an Org Admin confirms it on a confirmation page with a security-key step-up, and again after any token change. Cards carry minimal metadata (never a rendered template title) and a single link button to the authenticated approval page; at most one card is posted per request and channel, and it is updated in place when the request closes. Interactivity stays off and PantherClaw exposes no Slack inbound endpoint, so reactions, replies and crafted interaction posts cannot count. Slack approvals are Team edition.
6. **Agents post to Slack under disclosure rules** (F6, HR-316). `pc.slack` posts to allowed channels with disclosure limits; a gateway fact marks externally shared channels, and posting there is an `external_disclosure` consequence that policies hold or deny.

**Consequences.**
- Business connectors follow the same pattern as GitHub: reviewed packages, gateway-held credentials, facts read by the gateway, verified effects.
- Reads become governable by content, not only by permission; the price is that scope works only on gateway-held routes (R-42), and the gateway now parses and rewrites some answers.
- Stripe live mode (R-43), Postgres joins and views (R-44) and Slack direct messages remain follow-ups; Slack channel members see card metadata (R-46).
- No new server dependency: `pgx` is already used; the form parser and the Slack and Stripe calls are written in-house.

**Alternatives.** Raw SQL with a read-only role only (unreviewable meaning, injection into the decision); passing form bodies through (parser differentials, T-140); Slack interactive approvals (a second decision surface outside WebAuthn, F166); scope enforced by the SDK in the agent (the agent is the adversary, A1); Stripe live mode now (before M13 hardening).
