# ADR-0032 — Hosted deployment, KEK custody, backups and recovery

**Status:** Accepted for staging (2026-10-21; G0 M13 founder decisions F0 and F1, coordinator decisions D2 and D12–D17; the [G0 M13 brief](../g0/M13.md) records them). Production (L4) follows at v1.0 on a paid host under this ADR's paid-host section.

**Context.** The hosted control plane and console were built in milestone UI, but nothing runs outside a developer's machine. M13 needs a hosted staging deployment (test layer L3) with sealed keys, deployment gates (G3), backups and a measured restore. The founder has no budget for hosting yet and has bought the domain (F0), and chose free infrastructure that a paid host can replace by configuration (F1). The gateway's listener needs mutual TLS end to end, so a host that terminates TLS in front of the server cannot carry gateway traffic; most free platforms do exactly that.

**Decision.**
1. **Staging on one free VM** (F1, D13). An Oracle Cloud Always Free Arm VM (Ubuntu 24.04) runs a compose stack: `postgres:17` with its data on the block volume, the hosted server (role `all`, `deployment: staging`; public TLS on 443, gateway mTLS on 8443, both terminated by the server itself), a one-shot `migrate` as `pc_migrator`, a nightly `backup` job and `certbot` with the DNS-01 challenge through Cloudflare. Cloudflare's free plan serves DNS only (no proxying, so client addresses and client certificates reach the server). The host runs nftables (SSH only from the founder's addresses, 443 and 8443), unattended upgrades and a `pantherclaw` service user. Provisioning is cloud-init plus idempotent scripts in the commercial distribution; there is no infrastructure-as-code tool on staging (D2). The deployment procedure is [deploy.md](../runbooks/deploy.md).
2. **Sign-in on staging** (D14). Public sign-in only through the hosted OIDC provider's staging environment; until it exists the console and API listener binds to loopback and is reached through an SSH tunnel. Development OIDC providers are never exposed publicly (HR-346). Billing on staging is faked until the payment provider's sandbox exists.
3. **Deploys and G3** (D12, D15). The hosted image is built once, published to a private registry and deployed by digest from a manually started workflow: pull, `migrate up`, start, wait for `/readyz` (HR-370) for up to 5 minutes, otherwise roll back to the previous digest. Every deploy writes a G3 record (artifact digest, configuration hash, previous digest, operator, time, result).
4. **KEK custody at $0** (D2). The server's file key provider stays. The KEK file is mode 0400, owned by the service user, on the VM's encrypted boot volume; it is generated on the host with `pantherclaw-server keys gen-kek --out FILE` and never enters a repository or a backup. An offline escrow copy is encrypted with `age` under a passphrase and kept on offline media, like the offline roots (HR-063); it is what a restore uses to open sealed rows.
5. **Backups and recovery** (D16, D17, D21). Nightly at 02:15 UTC the backup role `pc_backup` (read-only, bypassing RLS only to dump, its credential held only by the backup job; HR-378, T-172) takes `pg_dump -Fc`, encrypted with `age` to the founder's recipient before it leaves the host, and `rclone` copies it to a Backblaze B2 bucket whose application key is scoped to that bucket; the bucket's lifecycle rules keep 14 daily and 8 weekly copies; a size and age check alerts. Targets on staging: **RPO ≤ 24 h** (no point-in-time recovery on a self-run database) and **RTO ≤ 4 h**. A restore drill runs monthly (and on demand): fetch, decrypt with the staging drill identity, restore into a throwaway Postgres, check the schema version, run an RLS smoke test, open one sealed row with the escrowed KEK, raise every organization's epoch (HR-373) and record the measured RPO and RTO. Production drills are run by the founder by hand. The procedure is [backup-restore.md](../runbooks/backup-restore.md).
6. **After any restore** (D20, T-171) gateways stay disconnected (the gateway port closed at the firewall, the kill switch engaged for every organization) until the operator has re-applied every revocation and containment change logged after the dump's time (signing-key and gateway-certificate revocations, API key, credential and grant revocations, containment and kill-switch changes), from the shipped structured logs. Then every organization's containment epoch is raised (HR-373) and the gateway port reopens, so gateways refetch containment instead of acting on caches. This does not bring back what the dump lacks: signing keys created after the dump are lost with it, and receipts and evidence they signed stop verifying until their public keys are published again from the logs; keys retired before the dump stay published (HR-372). Anything missing from the logs comes back as it was at the dump (R-61).

**Paid host (later; not built in M13).** Researched on 2026-10-21 and kept as the target once there is a budget: an application host that passes raw TCP so the server terminates TLS and mTLS itself (for example Fly.io without HTTP handlers, which then needs the PROXY protocol to see client addresses), a managed Postgres with direct session connections for River (LISTEN and session advisory locks) and point-in-time recovery (RPO ≤ 5 min, RTO ≤ 4 h; ≤ 24 h for a rebuild after losing the provider), never connecting as the database owner role so RLS stays forced; a KMS-wrapped KEK reached through the host's workload identity, with the offline escrow kept; nightly encrypted dumps to a second provider with object lock; OpenTofu with encrypted state for the database, DNS and KMS. Each of these is a follow-up of the M13 brief.

**Consequences.**
- Staging costs nothing and is a single point of failure: losing the VM is a fail-closed outage until a rebuild from the latest dump, and up to 24 hours of staging data can be lost (R-56).
- The KEK is protected by file permissions and disk encryption rather than a KMS; its compromise needs root on the VM (R-57).
- The same image, configuration and runbooks move to a paid host by configuration; only the provisioning scripts differ.

**Alternatives.** Free platforms that terminate TLS in front of the application (no client certificates reach the server, so gateways cannot use mTLS); a self-run OpenBao for the KEK (too heavy for one VM); storing the KEK with the backups (one leak would expose both); no backups until production (the restore procedure would be untested at v1.0).
