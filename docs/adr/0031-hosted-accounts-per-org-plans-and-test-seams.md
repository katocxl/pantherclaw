# ADR-0031 — Hosted accounts, per-organization plans and test seams

**Status:** Accepted (2026-10-20; G0 UI founder decisions F1, F3, F5 and F9, with the plan confirmed as written (F13); the [G0 UI brief](../g0/UI.md) records them). Moves PN-012.2 (entitlements and plan limits) and PN-012.3 (invitations) from M13 to milestone UI.

**Context.** The core signs people in per organization: a sign-in names the organization, users are keyed by (organization, issuer, subject), and a person without a membership is refused. Editions come from one server-wide licence. A hosted control plane needs people to sign in before they belong to any organization, create one themselves, accept invitations in the browser and hold a plan per organization, paid through a merchant-of-record payment provider (F3) and signed in through a hosted OIDC provider (F5). The founder also asked (F9) for a way to use the real app without payments or a real sign-in for testing, placed so that the pieces can be proven before they are joined.

**Decision.**
1. **Global accounts** (HR-348..350, HR-353). A global `pc.accounts` table keyed by (issuer, subject); account tables are reached only through the audited cross-organization lister and restricted functions. A sign-in without an organization resolves the account and lists its memberships through the audited global lister: none gives an account session when self-serve sign-up is on (otherwise `NOT_A_MEMBER`), one gives an organization session, several show a server-rendered organization picker. Account sessions may call only an allow list (account calls, creating and listing their organizations, accepting invitations, `WhoAmI`, allow-listed extension routes); organization sessions stay organization-scoped under row-level security. Accounts are never linked across issuers by email, and switching organization is a fresh sign-in.
2. **Self-serve organizations** (HR-351). `TenancyService.CreateOrg` needs an account session, a verified email and the `signup.self_serve` switch, which is off by default and on only in the hosted configuration. Per-account limits (one organization without a plan, three in total by default, counted from the account's events) and per-account and per-address rate limits apply; the slug is a non-unique display label, never used to look an organization up, so it cannot be used to enumerate organizations (T-164); the creator becomes the organization's admin; the terms and data-processing versions and time are recorded; the session is rotated into the new organization.
3. **Browser invitations** (HR-352). `/invite/{token}` → sign in → `AccessService.AcceptInvitation`: the IdP-verified email must equal the invitation's (`INVITATION_EMAIL_MISMATCH`); single use; expiry. The notification recipient rule (HR-157) is widened for invitation emails only.
4. **Per-organization plans** (HR-354..361). `pc.org_entitlements` (tenant table under RLS) holds each organization's plan, edition, limits, features, status, source, period end and complimentary-plan expiry; `pc.entitlement_events`, keyed (organization, event id), makes plan events idempotent. Self-hosted deployments keep deriving entitlements from the licence as today (no LICENCE rows). The writers are the extension's plan writer (fed by the billing adapter: idempotent by event id, only strictly older events ignored (equal timestamps apply), status changes only from subscription lifecycle events, audited; it may never set the complimentary or development statuses), the operator's complimentary-plan command and development mode; never a browser or API call. Entitlements become per organization, and existing gates and limits read them. With `billing.require_plan` on, organization calls answer `PLAN_REQUIRED` unless the status is trialing, active, past due, complimentary or development or the procedure is allow-listed; a cancelled plan keeps access until its period ends. **A lapse never turns protection off** (PN-012.1): authorization, gateways, the kill switch, containment and open approvals keep working and evidence stays readable; only configuration changes and new agents, instances and connections are blocked. `EntitlementService.GetEntitlements` reports plan, status, limits and usage; the plan catalog stays in the commercial distribution. Because the payment provider's events carry no organization context, **a subscription binds to an organization only through a checkout the server recorded**: a generic `pc.billing_links` table holds checkouts (pending, consumed, expired) and subscriptions (current, ended) with their kind, reference, customer reference, state and expiry; a reference is unique per provider and kind across organizations and never moves to another organization. The extension uses it only through `extension.Deps.BillingLinks` (`RecordCheckout`, `BindSubscription` (the checkout must be pending and unexpired), `SubscriptionOrg`, `EndSubscription`, `CurrentSubscription`; errors `ErrNotFound`, `ErrConflict`), and cross-organization lookups go through the audited cross-organization lister (purpose `billing_link_lookup`). Organization hints inside events are never trusted for the binding, and a link changes no plan by itself (HR-354). An organization has at most one current subscription: a new checkout is refused while one is live or a checkout is pending, and events for a subscription that is not the current one are audited and never applied. A full refund or a chargeback sets the plan LAPSED, the provider subscription is cancelled at once and ended, later events for it are ignored, and an operator is alerted.
5. **Test seams as adapters** (HR-346, HR-358, HR-359). A `deployment` setting (development, staging, production) is required in the hosted configuration and validated at start-up (`DEPLOYMENT_CONFIG`): production refuses OIDC providers marked for development and billing off or faked; development and staging show a permanent banner from `WhoAmI`. `billing.mode` is off (no gate, every organization in development status), faked (a provider-shaped adapter in the commercial distribution that drives the real gate) or the real provider. Complimentary plans are granted and revoked only from the operator command line, with a reason and an expiry of at most one year, audited and shown in the console; this is how the founder and design partners use the real hosted app without paying. Sign-in for testing uses the existing local mock and Keycloak providers marked for development. Every flow is first built and proven on its fake, then the real adapter replaces it behind the same port and the same contract suite. Test layers: L0 in-browser fixtures, L1 the local stack (CI), L2 local with the providers' sandboxes (opt-in), L3 hosted staging (M13), L4 production (v1.0). No bypass code exists in the server.
6. **Onboarding progress from records** (HR-362..364). `OnboardingService.GetProgress` computes the steps from the organization's gateways, agents, decisions, approvals and suspensions, with evidence references; simulated records never complete a step, and a step cannot be marked done by a client.

**Consequences.**
- One core serves both self-hosted (licence, no accounts, no gate) and hosted (accounts, self-serve, per-organization plans) deployments; the hosted behaviour is switched on by configuration and an extension, never by a build flag in the core.
- New tables `pc.accounts`, `pc.org_entitlements`, `pc.entitlement_events`, organization terms and onboarding records, the invitation browser binding and `pc.billing_links` (migrations 00160–00164).
- New threats T-162..T-166 and residual risks R-48, R-49, R-51 and R-52.

**Alternatives.** Linking accounts by email across providers (an account-takeover path); one organization per account (blocks consultants and multi-team customers); deriving plan state from the payment provider on every request (a provider outage would become a PantherClaw outage); switching protection off when a plan lapses (contradicts PN-012.1); test-only bypass code in the server (would exist in production builds).
